## The HRMP blocker is root-caused, and the sixth…

The HRMP blocker is root-caused, and the sixth `target/` bug of the same class turned up next to it

**The drills that would prove Bleavit-as-a-service works are the only ones that have never run, and now we know exactly why.** Genesis-preopened HRMP channels queue DMP notifications at `sent_at = 0`; cumulus's partial-processing cursor, absent a `LastProcessedDownwardMessage`, falls back to `{ sent_at: LastRelayChainBlockNumber, reverse_idx: 0 }`, which on a first candidate is `{0, 0}`; and `drop_processed_messages` scans in reverse, matches the last block-0 message, and drains every one. The runtime then rebuilds an empty MQC head against the relay's non-zero one and traps. **The sentinel conflates "nothing processed yet" with "everything at block 0 already processed"** — opposite states, and it guesses wrong on the only block where the ambiguity exists. Two things make this worth the writeup rather than a one-line note. It is **upstream and unavoidable by configuration**: the faulty fallback is byte-identical in cumulus-pallet-parachain-system 0.22.1, 0.23.0, 0.23.2, 0.26.0 and 0.29.0, so no pin in range escapes it, and the DMP/MQC hash chains agree between relay and cumulus so it is not skew. And it **retires an earlier wrong attribution**: drill 07 was filed against a pinned Paseo Asset Hub quirk, but the identical trap occurs in `bleavit-runtime` with no Asset Hub present — same inherent, same topology feature, different runtime. A diagnosis that names the wrong component is worse than none, because it stops the search. No fix is claimed: the preferred shape (clear the relay's genesis DMP queues in the spec we already post-process) needs a live spawn to verify, and SQ-567 owns it. **Found alongside it:** four more `$repo_root/target/env/` patch paths in `generate-relay-specs.sh`, missed when I converted the load-bearing paths in the same file — the only `mkdir` creates `$bleavit_target/env`, so with `CARGO_TARGET_DIR` set (mandatory here) all four writes fail. ## A weight regeneration is not automatically an…

A weight regeneration is not automatically an improvement, and `sustainability.py` proved it

**CI went red on the reference model, and the right fix was to commit *less*, not to update the spec.** Regenerating `pallet_market`, `pallet_conditional_ledger` and `pallet_question_service` at 50×20 after the client-kit repairs moved `pallet_market::crank_observe`'s base ref_time 141,590,000 → 142,570,000, and `reference-model/sustainability.py` reads that exact term to derive 08 §10's keeper crank fee — so four pinned published figures failed at once, including SQ-527's 2.829× loss-making band. That is the module doing precisely its job: its own docstring says a future regeneration "either changes the result or makes this evidence gate loud." **The tempting fix — update the published economics to the new numbers — would have been wrong**, because `crank_observe`'s code did not change. Diffing the regenerated files by kind settles it: `pallet_market` and `pallet_conditional_ledger` show **zero** storage-dimension changes and only ref_time movement, some terms up and some *down* (453,240,000 → 452,790,000; 29,300,000 → 28,950,000) — the signature of measurement noise on a machine, against a quantity this repo already treats as advisory with a 127 % measured spread. Only `pallet_question_service` carries a real change, and it is a genuine one: the atomic external-pair seed removed a read and a write from `register` (211→210, 91→90). So the two noise-only files were reverted to their previous **generator output** — not hand-edited, so the 15 §4.5 purity gate is untouched, and `--check` still passes because storage dimensions are identical. Reference model **652/652**. **The general rule this establishes:** regenerate whenever pallet code moves, but commit the result only where a fidelity-stable dimension moved; otherwise a routine regeneration launders machine noise into figures the specification publishes as economics.
