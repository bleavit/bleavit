## F5 ✅ — `packages/protocol`, the TS market-math port

**The port reproduces the runtime's integer path rather than out-precisioning it, and that is the whole design decision.** The obvious way to write LMSR math in TypeScript is arbitrary-precision decimals, and it would be *more accurate*; it would also be wrong for the job. 04 §6.1 step 4 refuses a trade when `cost + fee > max_cost`, and three separate roundings decide the last base unit — `fx` floors base units into 64.64, the ×10⁶ rescale truncates inside the 64.64 multiply, and the charge ceils. A quote a base unit under the chain's own figure hands the user a transaction that reverts and pays the fee for it, and no amount of extra precision recovers an integer the runtime reached by a different route. So `bigint` reproduces the guarded-Q96 kernel exactly — 32 guard bits, one final rounding, the same `u128` ceilings *enforced* so an input the chain rejects for overflow is rejected here too. Shipped: `fixed.ts` (`exp2`/`exp2Negative`/`log2`/`ln`, maker-adverse currency rounding, a branded `Fixed` so a base-unit balance cannot be passed where 64.64 is expected — silent and off by 2⁶⁴/10⁶), `lmsr.ts` (log-sum-exp cost, prices, buy/sell, displacement both ways, the `48·b` domain), `quote.ts` (the extrinsic's own pipeline, `MinTrade`/`MaxTrade`, `feeUp`), `twap.ts` (1e9-grid κ-slew with I-13 inward rounding, backward weighting, window staleness). Every tunable is an argument with no default (15 §5.4). **39 tests against the corpus read in place**, never a copy: V1–V6, the 9 high-precision samples, all 1,286 transcendental rows, both TWAP scenarios, all 5 staleness scenarios, and 15 §4.8's three named properties. ## F6 🔨 — the signer firewall

**The connection firewall forbade F6's signer adapters, and the fix was a ruling, not a waiver.** `only-chain-client-opens-a-chain-connection` bans `polkadot-api` outside `chain-client`, but its own comment names the danger precisely: *a second package able to construct a chain or a provider could serve reads that never passed the finalized-only discipline*. `getPolkadotSignerFromPjs(address, signPayload, signRaw)` takes two callbacks and returns a signer — it cannot read anything. Narrowed to the connection surface, with a **second rule** making "signer subpaths only" true rather than assumed, and the boundary asserted across all five import forms. **The narrowed rule shipped broken, and it is V-86 verbatim.** The first pattern matched only the bare specifier — but `import 'polkadot-api'` *resolves*, so it is recorded as a `node_modules/.pnpm/…` path, while every subpath is hidden by the package's `exports` map and recorded bare with `couldNotResolve: true`. The pattern therefore forbade `/smoldot` and `/ws-provider` and let the **root entry point**, the one that can construct both, straight through — written with a comment citing V-86 directly above it. The second attempt *measured* what dependency-cruiser records for all five forms instead of reasoning about it. ## F6 🔨 — the injected signer

**11 §11.3's first signer adapter, with the extension-dependent part isolated to one module.** The logic is written against a structural view of `polkadot-api/pjs-signer` and bound to the real one in `pjs-binding.ts` — the `light-client.ts` pattern, and here it is load-bearing rather than tidy: an extension only exists inside a browser with something installed, so `tsc -b` on that binding is the **only** check in the repository that can notice a stack drift. It declares `external-key-custody` and `decoded-payload` and **refuses `metadata-hash`** (FE-P6 unresolved — declaring it would tell the user their wallet verified the call when nothing has established it can) and `hashed-payload` (an extension falling back to a hash of an oversized payload signs something nobody saw). Accounts are **re-read per signature**: the set changes while the page is open — switch, lock, revoke — and a set captured at connect lets a revoked account look signable right up to the prompt. A mismatch is refused by name before the request goes out, because a signature from the wrong account is *valid* and the transaction dies later on nonce or origin where the user cannot read it. The descriptor became a **function of the extension name**; one `injected` id cannot distinguish two installed extensions, and "Browser extension" asks for a confirmation without saying which wallet will be asked. That broke `assert.equal(INJECTED_DESCRIPTOR.testOnly, false)` — correctly. ## F6 — both signer adapters

**The raw-payload (air-gapped/hardware) signer, and a sixth vacuous control caught by mutation.** The app hands out bytes and takes a signature back; what makes that safe is not the absent key but that **the bytes presented are the bytes signed**, so the transport gets one method, one argument, one return — no path by which a QR renderer or a hex textarea returns a *different* payload for the app to accept. Capabilities come from the flow rather than the transport, because a transport able to declare its own could declare `metadata-hash` — the refusal that is doing the real work, since the device's own decode is what makes air-gapped signing better than blind signing and FE-P6 is unresolved. **The QR framing is deliberately absent, and that is SQ-579.** 11 §11.3 says "QR/hex" and names no standard; UOS and RaptorQ are external, versioned formats, and a plausible chunking invented here would interoperate with nothing and fail in front of someone holding an air-gapped device — R-2 fabrication with a physical failure mode. Hex needs no framing and works today. **Seven mutations, one survivor**: deleting the hex validation changed nothing, because the test's `'NotFoundException'` is caught by the *length* rule (odd character count). The isolating case is a 128-character non-hex string — exactly 64 "bytes", through the length band, refusable only by the hex rule, and the realistic shape of a scanner returning base64.
