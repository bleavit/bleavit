## `packages/ui` is the only package that names React, and…
authorized_by: Me, under R-1's delegated authority; no spec text changed
docs_touched: `app/tsconfig.base.json`; `app/packages/ui/`; `app/tools/check-handoff-emitted-imports.ts`; `.github/workflows/ci.yml`

`packages/ui` is the only package that names React, and `jsxImportSource` points at it.

Two consequences, both deliberate. (i) *"What in this client can render?"* is answered by reading one `package.json`, including `react-dom/client` — `src/application` mounts through `ui.mount()` and imports React nowhere. (ii) The compiler-injected JSX import becomes a **workspace** specifier, so 10 §10.1's *"no package on a handoff path imports anything external"* stays literally true for S21/S22 with no spec amendment and no carve-out in a rule whose own stated reasoning is anti-carve-out. `ui` itself overrides `jsxImportSource` back to `react`, since it cannot be its own source. Recorded here rather than left in a comment because the tempting alternative — exempting React from the handoff rule — is a one-line change anybody could make while believing it harmless, and V-109/V-110 show no gate would object.

## F4 implementation rulings — the foreign feed is its own…
authorized_by: Claude (implementation rulings under R-1; the only `docs/architecture/` change is discharging two verified `[VERIFY]` tags)
docs_touched: `02` §7.7, §8 (tags cleared); `app/.papi/README.md`; `app/fixtures/foreign-chain-feed/README.md`; `tools/release/pin-foreign-runtime.py`; `.github/workflows/ci.yml`

F4 implementation rulings — the foreign feed is its own feed, the AH whitelist is withdrawn, and the presence gate is TypeScript. No spec text changed except clearing two discharged `[VERIFY]` tags.

(1) **A separate `app/fixtures/foreign-chain-feed/` rather than another `chain-feed/` directory.** `check-chain-feed.py` compares metadata against the *runtime source*, the `construct_runtime!` pallet set and `INTEGRATION_CONTRACT_VERSION` — none of which exists for a chain somebody else builds. 02 §13 rule 8 already makes that split normative on the contract side, so mirroring it in the artifact layout keeps one gate honest instead of teaching an existing gate to skip its own checks. (2) **PAPI descriptor extraction from the wasm, not `tools/release/extract-metadata.py`.** That script obtains v15 by booting the runtime in `bleavit-node`, and a foreign runtime has neither the genesis config nor the pallets it expects. PAPI reads metadata straight from the wasm (V-76) and returns **v16**, which `scale_metadata.py` does not implement — so the surface-presence gate is TypeScript over PAPI's own decoder. That is the better home regardless of the version accident: what must be proven present is what the *client* will be able to name. (3) **The genesis hash is read from live operators and the artifact chain is closed around it.** Genesis is chain identity, a property of the chain spec's genesis storage, so no runtime provenance produces it; R-2 prescribes live-source verification and 10 §5.1's "never a live node" rule governs *descriptor generation*, which still comes from the wasm. The pin tool refuses fewer than two distinct sources. (4) **`.papi/README.md`'s Asset Hub whitelist is withdrawn on measurement (V-107)** — PAPI hardcodes the generated package name, so one workspace means one global whitelist, and a per-chain one guts every chain it does not name (`bleavit.ts` 458,662 → 43,258 bytes, `papi generate` silent). ~1.3 MB of committed generated TypeScript is the price of not having that failure mode in the build. (5) **Two `[VERIFY]` tags cleared in 02 §7.7 and §8**, with §8 now recording the *two-chain* scope so the next relay phase re-asks rather than inherits.

## 02 §7.7 + §13 rule 8 — Asset Hub is frozen as contract…
authorized_by: Claude (R-1; the user owns both sides of 02 §13's sign-off and has delegated it, 2026-07-25)
docs_touched: `02` §7.7 (new), §13 rule 8 (new) + history; `PLAN.md` SQ-587, F4, F18

02 §7.7 + §13 rule 8 — Asset Hub is frozen as contract surface, and the contract version deliberately does NOT move (SQ-587).

The gap was real: 11 §11.9.1's deposit leg reads USDC and submits a reserve transfer **on Asset Hub**, and 02 froze nothing about that chain — so 10 §5.2's classifier could not fail on it, and an AH runtime upgrade would have left the banner reading `full` while the deposit leg broke. `check-client-surface-obligations.py` cannot cover it by construction: it keeps only references whose prefix is a Bleavit `construct_runtime!` pallet, and that restriction is what keeps it quiet enough to stay switched on. **Two premises in the question were wrong and are corrected of record.** (i) *Which* Asset Hub was never an open decision — 08 §2.5 and 09 §6.3 already phase it (Paseo at Phase 2, Polkadot at Phase 3), so a release pins the AH of the relay it targets, per release. I had parked this as a user decision; it was under-research, and R-1's warning that a deferred decision is often exactly that. (ii) X-11a does **not** forbid the AH-side `Assets.Account(1337, who)` read — X-11a governs *Bleavit*, where USDC is a `ForeignAssets` entry, and 02 §8's own Location decodes to `PalletInstance(50)`/`GeneralIndex(1337)` **on parachain 1000**. **The load-bearing ruling is the non-bump.** `INTEGRATION_CONTRACT_VERSION` is stamped into Bleavit's runtime, which cannot observe Asset Hub in either direction: no Bleavit upgrade moves the foreign layout, no foreign upgrade moves the constant. Bumping it would publish coverage nothing behind it can attest — the same defect v24 repaired, inverted. So §7.7's surfaces are pinned **where a release can observe them** (AH genesis hash, `spec_version`, metadata hash in the §11 feed) and carry a **separate** §5.2 verdict, never folded into the local one; §13 rule 8 states the exception normatively so that "02 changed and the counter did not" cannot read as a rule-2 violation. Consequence for the artifact feed: **nothing regenerates**, because nothing in Bleavit's metadata moved. The two `[VERIFY]` tags (asset index; exact AH extrinsic + params) stay open with their consumers fail-closed per R-2

## F11 — three implementation rulings, no spec change.
authorized_by: Claude (implementation rulings under R-1; no `docs/architecture/` text changed)
docs_touched: — (PLAN.md only)

(1) **The service worker's cache name is fetched from `release.json` at install, not derived from its own URL.** 12 §5.2 says "cache name = manifest TXID", and the TXID cannot be baked: 12 §1.2's pass 2 only learns it after uploading the tree the worker is part of, so baking it makes the worker's bytes depend on a hash of the worker's bytes. Deriving it from `location` was the other option and was rejected as a **guess**: gateway URL shapes (path-based, sandboxed base32 subdomain, `ar://`) are exactly what prototype gate **FE-P7** has a `[VERIFY]` on, and R-2 forbids resolving one by assumption. Fetching is safe for a reason worth stating precisely — the field **names a cache and does not authorize a byte**: every asset stored under it is still checked against the baked hash map, so a gateway returning a wrong TXID gets a differently-named cache and nothing else. It fails **closed** (absent or malformed ⇒ no install) rather than to a constant name, which two releases would share. (2) **The 10 §5.4 gate's value rule applies only to frozen values of four decimal digits or more.** `MaxPositionsPerAccount = 64` and `GuardianSeats = 7` are chain constants *and* are hash widths, array sizes and the seventh element on every other line — an unrestricted value rule fires constantly on nothing, and a gate that fires on nothing is one somebody switches off, which is a worse outcome than the coverage it buys. Above a thousand the collision rate collapses. The narrowing is written into the tool's own header rather than left implicit: a hardcoded `196` that is never *named* passes both rules, and what covers that case is `CRITICAL_SURFACE` failing the build when a required constant is absent from metadata. (3) **`release.json` carries readiness blockers rather than blocking the build or shipping nulls.** Several INV-FE-11 pins cannot exist pre-genesis. Blocking would leave the pipeline unexercised until a tag — first debugged during a release — and emitting `null` silently would let `verifyChainIdentity` compare against nothing and report `verified`. The third option is the chain-side `tools/release/` pattern already in the repo: name every unresolved pin in the document and refuse `--production` while any stands

## Doc 10 edits (R-1) from the round-3 review; no 02…
authorized_by: Claude Code (R-1: a text correction plus a package the firewall required)
docs_touched: `docs/architecture/10-frontend-architecture.md` §10.1, §13.3

Doc 10 edits (R-1) from the round-3 review; no 02 change, so no contract bump.

(1) **§10.1 gains `app/packages/handoff-envelope`** and the edge rules gain two clauses. The package carries the §13.1 envelope conventions — canonical JSON and the digest pre-image — which all three formats share and which must therefore have exactly one implementation: two copies are two answers to the one question that must have exactly one, *which bytes are hashed*. It is a **separate package rather than a module in `contexts`** for a firewall reason, and that is the part worth recording: `contexts` is the outbound half and depends on `chain-client` for `Finalized<T>`, so a shared module living there would give the **inbound** parser a transitive path to a chain connection — against §13's second load-bearing sentence, that the inbound format carries no chain state. The second clause states plainly that **no package on a handoff path imports anything external**, node built-ins included: the previous rule was a denylist of network libraries, and a denylist only forbids what somebody thought of (`import ky` defeated it while every gate stayed green). (2) **§13.3's `FE-HANDOFF-004` class widens** from "foreign field inside `action`/`limits`" to "a closed core object (`binding`, `action`, `limits`)". This corrects the text to match §13.1's own rule rather than changing a decision: §13.1 tolerates extras "at the top level **only**", which already closes every nested core object, and `binding` is the one object whose entire job is to pin which chain a document is for. The alternative — reporting a foreign field there as a malformed document — was considered and rejected: `-002` reads "this file is damaged" where `-004` reads "contains an instruction Bleavit does not recognise", and the second is both true and actionable. Neither edit touches 02 or an INV-FE text, so §13's joint sign-off does not attach.
