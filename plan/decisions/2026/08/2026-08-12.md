# Decisions — 2026-08-12

## Hosted-service retention is bounded by lawful throughput across the archive horizon
authorized_by: This session under R-1/R-2 (the user owns both sides of the 02 §13 sign-off and explicitly requested remediation)
docs_touched: 00, 02, 04, 13, 14, 15, 16; derived design pack; integration contract v30 → v31

The 64-client roster cannot also bound year-retained hosted questions. Existing candidates were
rejected deliberately: `MaxClients` bounds admitted identities and concurrent live questions;
`MaxLiveExternalMarkets` bounds only live books; and `MaxStoredMarkets` is the independently
reserved primary archive partition. Reusing any of them makes ordinary lawful throughput exhaust
global admission before archive is allowed.

The replacement bounds are derived entirely from existing hard extrema. The fastest lawful
question lifetime is `orc.window_min + 2·mkt.obs_interval_min = 43,210` blocks. Across the
5,256,000-block maximum archive delay, `ceil(5,256,000 / 43,210) + 1 = 123` complete waves can
coexist, including the live wave. At 64 questions per wave this is 7,872 retained question/pair
rows and 15,744 external books; together with the existing 2,240 primary books, the shared
physical `Markets` ceiling is 17,984 rows (3,740,672 bytes at the measured 208-byte maximum book).
The unsafe error direction is downward, which recreates the service-wide denial; upward consumes
state. Every input is already a compiled maximum, so no §13 parameter, amendment bound, max-delta
or cooldown can move the result. A future widening is a CODE change that must re-run this
derivation.

The implementation preserves per-call boundedness: service IDs allocate one aligned consecutive
three-ID family in O(1), pausing records an allocator cutoff rather than scanning retained rows,
and primary/external live and retained counters enforce independent partitions. The integration
surface exposes changed frozen constants, so contract v31 is required. The full market
`try_state` benchmark materializes the complete reachable 17,984-row state and every heavy
dependent-map shape before generated weights are accepted.

## A signing authorization owns its reads and freezes exactly one signing target
authorized_by: This session under R-1 (implementation of 11 §11.3–§11.4 and INV-FE-2; no 02 surface change)
docs_touched: 10, 11 and their verbatim derived copies

`GatePassed` is an authorization, not a caller assertion. Its only public producer now opens a
nominal live chain-head connection, pins one fresh finalized block, performs and brands the
compatibility/precondition reads itself, and refuses evidence from any other pin. A pure predicate
that accepts structural objects is private. The authorization freezes `{scaleHex, account}` from
the preparation; signer adapters derive both values from that frozen target and reject overrides or
mutation. Consequently neither fabricated evidence nor a genuine proof for transaction A can sign
transaction/account B.

## Decision-grade XCM health is protocol-authored and legacy ingress denies all nine program carriers
authorized_by: This session under R-1/R-7 (the prior implementation contradicted 05, 09 and I-24)
docs_touched: 05, 09, 15; RB-XCM; AGENTS runtime/XCM description

Public, inbound and client XCM sends use the bare router and cannot improve the welfare `X` term.
Only the fixed runtime-authored coretime-renewal path uses the health-recording protocol router;
the reserve probe retains its explicit post-commit recorder. The legacy inbound barrier is an exact
closed allowlist: all nine inner-program carriers named by 09 §6.1 are rejected before cap walking
or execution. This removes both the public-success pumping path and the six-instruction
spec/implementation mismatch without pretending nested `Transact` was reachable.

The execution guard's recovery-image release failure also receives its own halt-source bitmap bit.
It remains sticky and retries after migration completion, emits the first-edge diagnostic, charges
the bridge work as Mandatory weight, clears only after successful repair, and cannot clear a
simultaneous independent halt source.

## Release integrity uses independently pinned credentials, exact transport agreement and pinned build inputs
authorized_by: This session under R-1/R-7 (implementation of 12 §1, §2 and §5; no protocol parameter added)
docs_touched: 12, 14, release/monitoring operator docs and runbooks

An unattended verifier cannot discover signatures from the bytes those signatures cover. A strict
`bleavit.release-credentials.v1` index is therefore produced only after final release bytes and
credentials exist, and operators provision its TXID plus SHA-256 through an authenticated channel
independent of ArNS, gateways and the bundle. The monitor requires byte-identical index and bundle
fetches, counts attestations by declared organization, redacts webhook credentials, pins Bleavit
genesis, and requires exact finalized hash/height/channel agreement across at least three
operator/origin-distinct RPCs. Gateway identities are stable operator IDs with pairwise-distinct
normalized origins, every raw path manifest must agree, both immutable and named browser root routes
must serve the verified manifest-index payload, and any resolver or route dissent is unhealthy. The
documented residuals remain honest:
transport agreement is not a storage/finality proof, all endpoints can collude, and declarative
identities can lie.

Release workflows pin every third-party action to a full commit and build reproducibility pairs in
two distinct digest-pinned Node/Debian images. Runtime profiles likewise build the primary/recovery
pair through one digest-pinned OCI wrapper with a read-only source mount and environment identity
recorded in build-info v3. Historical v2 artifacts are not relabelled; only a genuine clean-source
OCI rebuild may produce v3 evidence.

## Metadata-hash mode 1 is bound to the final runtime artifact
authorized_by: This session implementing the existing SQ-594 ruling and B21
docs_touched: 10, 11, 12 and release-tool documentation; the monitoring-only release API remains outside contract 02

All release runtime profiles enable `substrate-wasm-builder` metadata-hash generation for `VIT`, 12
decimals. A release-only runtime API returns the exact implicit digest used by
`CheckMetadataHash`; extraction calls it on the booted final `:code`, independently computes RFC 78
from the extracted metadata and token identity, and refuses disagreement. Assembly recomputes the
shipped metadata digest and checks both computed and embedded fields. This binds the runtime bytes,
Rust builder, independent JS/Python calculation and published release record rather than merely
checking a well-shaped hash.

## Reusable client report retention has an explicit bounded lifecycle
authorized_by: This session under R-1 (implementation of 16 §9/§12 and I-36)
docs_touched: 16 and the client integration documentation

The client pallet now separates replay protection from retained report rows. Governance may advance
a monotone prune floor and remove reports at or below it with work always charged at `MaxReports`;
ingress rejects replay at or below the floor. The bounded translate avoids mutating a live storage
iterator, and conservative portable weights cover the sample runtime. A production client runtime
must still generate its own measured weights before adopting the pallet.
