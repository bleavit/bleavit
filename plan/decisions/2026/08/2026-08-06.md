## `derive` joins `meet` in `packages/chain-client`'s…
authorized_by: implementation (no normative text moved)
docs_touched: none — `10 §2.1/§2.2` already licence the operation; `.claude/rules/app-code.md` rule 2's description of the single mint site is unchanged

`derive` joins `meet` in `packages/chain-client`'s barrel, and no spec changed (R-1 not engaged; implementation decision recorded because it touches a 10 §2.1 control).

The brand's home exported a combinator for **two** finalized reads and none for one, so 10 §2.2's *"computed client-side purely from such values"* had no spelling for a decode or a projection — which is what produced V-182's hand-built status object. `derive(read, compute)` takes a `Finalized<A>` and returns a `Finalized<B>`; `meet(a, a, (v) => f(v))` is exactly it, so the capability was already reachable from the barrel and this widens nothing. Three properties make it safe to export where `finalize` is not: the caller must **already hold a read** (there is no path to a `Finalized<A>` that does not go through the transport, `readmitFromLeader`, or the withheld `finalize`); `compute` receives the payload and **not** the whole read, so a projection cannot see the pin and stamp an unrelated value with it; and the pin is carried over rather than re-taken, asserted by `tests/chain-client/provenance.test.ts` including against a mutant that shifts the block number. The alternative considered and rejected was leaving the unary case unspelled and having each reader call `meet(x, x, …)` — same power, worse legibility, and the pressure that produced the defect stays in place.

## S3's trade screen renders 02 §4's two published figures…
authorized_by: implementation (no normative text moved)
docs_touched: none — 11 §11.5 P-1, 11 E6 and 04 §6.1 already state this; `app/src/features/tx/src/market-trade.tsx` carries the reasoning

S3's trade screen renders 02 §4's two published figures on both sides with 04 §6.1's per-direction combination beneath them, rather than one charge per side (no spec change; a reading of 11 §11.5 P-1 and E6 recorded because the earlier screen was defensible and wrong).

The previous screen showed one `Amount` for *"what the chain says this costs"* and one `Derived` for the client's recompute. That satisfies E6's *"the client's own recomputed quote beside the chain's"* on its face and defeats it in the case that matters: 02 §4 publishes `cost` and `fee` separately, 04 §6.1 debits `cost + fee` on a buy and credits `cost − fee` on a sell, so a chain answer of `(100, 3)` and a client answer of `(101, 2)` **agree** on a buy's total while disagreeing on a sell's net by 2. A user comparing one figure per side would see agreement for a pair that blocks the ticket under `FE-CHAIN-005` — and E6's whole point is that this disagreement is a contract defect with nothing to retry. So both fields render on both sides (six figures), with the direction's combination — the figure `max_cost`/`min_proceeds` is compared against — labelled per direction: a sale's *"net credited"* must not read *"total debited"*, which reverses the sign of the trade for a reader. The alternative of one combined figure plus an itemization behind a disclosure was rejected: 11 §11.2 constraint 3 permits progressive disclosure but not for *"any fact that changes the meaning of the signature"*, and which of two numbers disagrees is exactly that.

## The snapshot format's array order is normative and…
authorized_by: Implementation ruling (R-1; the user owns both sides of 02 §13's sign-off and has delegated it, 2026-07-25)
docs_touched: `10-frontend-architecture.md` §8.2

The snapshot format's array order is normative and checked

(10 §8.2) — F9's producer surfaced a hole in F9's format, one day apart. §8.2 promises exports *"reproducible byte-identically by anyone"*, and the serializer it reuses — 10 §13.1's canonical JSON — orders object **keys** and leaves array members exactly as given. So `vaults`, each vault's `branches` and `balances` each had two legal spellings, and `coverage` had two more, since the existing check permitted `10..11` beside `12..13` **and** `10..13`. Two honest producers reading one chain do not enumerate vaults or accounts in the same order, so each would have published a different pin for the same history — making the promise false, making `FE-PROV-004`'s two-producer cross-check fire on every honest pair, and surfacing to a user as *this correct snapshot is corrupt*. 10 §8.2 now states the rule (set-valued arrays ordered by Unicode code point over their identifying tuple, no duplicates; coverage ordered, non-overlapping and **maximally merged**; movements in **chain order**), and `admitSnapshot` **checks** it — a rule two producers must follow and nobody verifies is a rule they will diverge on. `ops` is deliberately exempt and the exemption is the substantive part: its order is semantic, because the conservation replay is order-sensitive, so sorting movements would let an invalid history be reordered into a valid-looking one. Scope: no `02` surface, no D-n, so no `INTEGRATION_CONTRACT_VERSION` bump — the snapshot format is not part of the chain↔frontend contract. `byCodePoint` was **exported** from `handoff-envelope` rather than reimplemented beside the new rule: a second comparator agrees on every ASCII label and diverges at the first astral character, which is the *two producers, two digests* failure that module exists to close.

## A failure-path fallback wears no read's badge: an…
authorized_by: Implementation ruling (R-1; the user owns both sides of 02 §13's sign-off and has delegated it, 2026-07-25)
docs_touched: none (`docs/architecture/` untouched). Code: `app/packages/chain-client/src/{provenance,index}.ts` (`derive`), `app/src/application/src/{chain-reads,shell,boot}.tsx?`, `app/src/features/tx/src/{funding-reads,funding,funding-screens,proposal-reads}.ts?`, `app/src/features/handoff/src/review.tsx`; gate `app/tools/check-provenance-mints.ts`

A failure-path fallback wears no read's badge: an undecodable value is absent, not a substituted zero (implementation ruling under R-1/R-7; no spec change).

The question was whether badging a manufactured `0` `verified-finalized`, with the failure reported in a sibling `undecodable` array, satisfies INV-FE-15's *"either absent with an explanation or present and labeled"*. **It does not, and the spec settles it without needing an amendment.** 10 §2.2 is the controlling text and is unconditional: *"`verified-finalized` status is assigned **only** to values read through smoldot with storage proofs checked, or computed client-side purely from such values."* A substituted zero is neither, so the badge is a false statement rather than a weak one. INV-FE-1 says the same from the other side — the obligation binds *"anything rendered as being true of the chain"*, and 10 §2.3 forecloses the escape in as many words (*"a value does not become 'chosen' because a user typed it: if the client will render it as true of the chain … it is sourced"*). INV-FE-12 supplies the replacement behaviour directly: *"undecodable data renders as raw SCALE with an explicit warning,"* and the application *"**never guesses at encodings**"* — a substituted value is that guess. **The sibling-array defence fails on INV-FE-9, not on taste**: the invariant attaches the status to *"every displayed data item"*, so the label is a property of the datum; an explanation held in a different field is not that datum being labelled, and a renderer showing the field and not the array shows an invented number as a chain answer. **INV-FE-15 is cited here as consistent, not as controlling** — its scope is *historical acceleration* (snapshots, providers, historical analytics degrading gracefully), and the shell header is none of those; the three texts above bind directly and agree with it. So: every failure path yields `undefined`, which is what `phaseFlags` had always done and what the three fields beside it now do too, and consumers fail closed on the absence (`depositBlocks`/`withdrawBlocks` block; the withdraw dust check is skipped rather than computed from a balance nobody stated). **No status is added and none is needed**, so this does not reopen SQ-592: that question is about a value derived from a **release constant**, which exists and has no label; here there is no value. **No contract bump and no joint sign-off** (02 §13 rule 9): no SCALE type, storage item, call, constant, encoding or bound moved, no INV-FE text was amended, and `docs/architecture/` is untouched.
