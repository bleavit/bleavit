## Item

**The chainHead recorder's strict failure counted only half of what it gates on, and its "deterministic" transcripts embedded a session counter** (two defects, found while building F2's replay suite)

## Spec ref

02 §11; 15 §4.7

## Status

verified 2026-08-03, both fixed

## Result

**(a) The failure message.** `record-chainhead-fixtures.py` computes `strict_ready` from the primary *and* paired-recovery missing lists, but printed only the primary's count. Recording with no recovery runtime built therefore failed with *"0 required surface items missing"* — a message that names no cause, reads as a tool bug, and invites `--allow-missing`, which is the one response that would ship the half-recorded artifact. It also rendered an *absent* recovery metadata file as 220 entries claiming the recovery runtime lacks `FutarchyApi`, when in truth no recovery runtime existed; absent and defective are now different messages. **(b) Determinism.** `transcript.py` normalizes subscription ids, operation ids and timestamps, but not the JSON-RPC envelope `id` — a client-chosen counter running across the whole recording session. So the same call recorded while gathering two different surfaces carried two different ids: **39 recordings of one block header produced 39 distinct responses**, the artifact bytes depended on the order surfaces were recorded in, and a replaying consumer could only read it as a conflict. Fixed by renumbering per transcript like the others, keyed on the sibling `jsonrpc` so chain data that legitimately contains an `id` field is untouched; two regression tests, one for each direction. Found by the mock-runtime replay engine's own conflict check on its first run — the consumer that had never existed.
