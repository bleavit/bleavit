## Item

**`release.json` could never be parsed by its own consumer — a field defined, unfillable, and asserted on the wrong object**

## Spec ref

12 §1.2; INV-FE-11

## Status

**found by Codex review, confirmed and fixed 2026-08-05**

## Result

The served document always carried `releaseTxid: null` while `parseReleaseDocument` **required** it, so every real two-pass deployment was refused as `unpublished` and the verification panel could never recognise a production release. The field is not merely unset — it is **unfillable**: `releaseTxid` names the final manifest `M′`, which addresses a manifest *containing this file*, so writing it in changes the file and therefore changes `M′`. A fixed point in a hash, not an ordering problem a third pass would solve. **12 §1.2 already resolved this** — *"`release.json` records the asset-tree manifest and the app resolves its own base TXID at runtime from `location`"* — so the repair was to the consumer (pin `arweaveManifestTxId`, observe `M′` via the new `resolveBaseTxid`), not to the format. Two things about how it hid are the transferable part: it was a **second-round fix applied from the wrong side** (a previous review round added `releaseTxid` to the producer, which looked like a repair), and the test asserted on the driver's **returned object** rather than the **uploaded bytes** — an object the driver was free to decorate with fields no one receives, and did. The suite now parses `result.releaseBytes` and requires it to `deepEqual` the returned object
