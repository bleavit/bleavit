## Item

Does seeding a `Constitution::Params` genesis row move committed benchmark weights, and how far does the change reach?

## Spec ref

15 §4.5; 13 §1

## Status

complete (2026-08-04), both defects fixed

## Result

**Yes, deterministically — and the sweep that bounded it found a second defect that is not this branch's, behind a gate that has never run.** Raised by PR #232's red `Benchmark smoke`. Seating `svc.client_bond`/`svc.price_cap` adds two leaves under the `Constitution::Params` prefix, which lengthens the trie path for the key `pallet_xcm::claim_assets` reads through the inflow-cap adapter: `Measured` 2,004 → 2,037, estimated PoV **5,469 → 5,502**, reads/writes unchanged at 6/4. CI and this workstation produced the *same* 5,502, so it is layout and not jitter. **Causation was measured, not inferred:** a differential build of the identical tree with only the two `row(...)` calls removed measures 5,469 back. Regenerated at the canonical 50×20. **The reach within this branch is exactly one function.** 107 committed weight functions read `Constitution::Params`; 97 are constant-weight and therefore hard-gated by the per-commit 2×1 run, which named exactly one; the other 10 were re-checked at 50×20 (`pallet_epoch`, `pallet_execution_guard`, `pallet_oracle`, `pallet_question_service`) and none moved. **The second defect predates the adoption.** Sweeping all **17** pallets carrying a fitted component at 50×20 — the release job's own scope — found two stale committed weights, both reproduced by the differential build and therefore not caused here: `pallet_execution_guard::qualify_recovery_image` **understates** worst-case PoV by 34 B (4,297,464 against 4,297,498) and `pallet_collator_selection::add_invulnerable` **overstates** by 99 B (12,218 against 12,119). Both files were generated before N7 (2026-08-02) added the `QuestionService`/`ServiceLedger` prefixes to `construct_runtime!`, which restructures the global trie; `qualify_recovery_image` reads no `Constitution::Params` key at all, which is what ruled the values adoption out as its cause. **Nothing could have caught either one.** Both are component-bearing, so `benchmark-smoke` at 2×1 demotes them to advisory *by design*, and the only gate that hard-gates them — `release.yml`'s `Component weights at committed fidelity` — is release-blocking, and `git tag` is still empty. That is the SQ-490 shape reached through the component-bearing door, and it covers ~50 functions across 17 pallets whose committed values no executed gate has ever compared against the runtime they ship with. A caution the numbers make concrete: the 2×1 advisory figure is not a weaker version of the truth but a different number — CI reported `add_invulnerable` at 12,043 where the canonical run gives 12,119. Both regenerated here on the user's instruction (2026-08-04); the durable fix is a per-commit component check, raised as SQ-584
