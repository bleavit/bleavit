## Result

Codex (`gpt-5.6-luna`/`max`) raised four on PR #237. All four were real, and verifying them against the runtime rather than against the report changed two of the answers. **(1) P1 — provider backfill recorded as light-client verified.** `ingestBlock` derived row provenance from `headerOrigin` and then minted a `selfRange` **unconditionally**, so a block ingested behind an `operator` header stored rows labelled `provider` beside coverage labelled `self`, and `isVerifiedAt` answered `true` for it — the promotion 10 §2.2 gives no path for, reached through backfill rather than a merge. The comment three lines above asserted the two were derived from one argument. The existing test read the *rows*, and the rows were always right, which is why it passed. Repaired by making the state unrepresentable: `HeaderSource` carries the provider id for every non-`self` origin (two operators are two sources, and a range that cannot name which one cannot be invalidated without taking honest ranges with it), and `rangeForSource` is the only chooser — kept out of the barrel for the same reason `selfRange` is. **(2) P1 — `decoded-payload` granted for a channel `sign()` never used.** An earlier review had already 'fixed' this by making the grant conditional on the extension exposing `signTx`; that changed which *counterparty* the claim followed and not which channel signs, so `sign()` still called `signBytes` and the user was still told their wallet had rendered a call it never saw. The missing condition is about the client: `SignTxFn` takes call data, signed extensions, metadata and a block number as four arguments, a `TxPreparation` carries one opaque `scaleHex`, and **the app has no extrinsic encoder at all** — the only `scaleHex` literal in the tree is `'0x00'` in the transition enumerator. So the capability is absent per INV-FE-12, and a test now reads *which function was called* rather than only inspecting the descriptor. A second defect the report missed: the probe took `signTx` off `getAccounts()[0]` while `sign()` matches a different account by address. **(3) P2 — P-12's expedited exemption, and the spec defect under it.** The exemption carried no `anyOf`, so it read as mandatory and the client refused the emergency upgrade during exactly the freeze the D-9 lane exists for — fail-closed. **The suggested repair (one group over the freeze clauses and the exemption) is fail-open**: `anyOf` is a flat any-of, so *no migration halt* alone would have satisfied the whole obligation, waiving the dead-man latch. The runtime settles it — check §1.2(10) is two `ensure!`s, and only `ledger_freeze_active() || MigrationHalt` is waived, which 09 §3.1 states in as many words (*'treats the **triggering** freeze as satisfied'*). See the Decision log for the 11 §11.5 repair this forced. **(4) P2 — fourteen gates and 296 assertions never ran in CI**, including `foreign:check`, the 02 §7.7 gate the report did not name. `tools/ci/tests` checked that every wired step names a real script and never the inverse — the direction that fails silently, since a suite nobody invokes passes locally forever. Now bidirectional, exemptions carrying a stated reason and validated both ways so a stale entry cannot pre-approve whatever later takes the name. **Two errors of my own, both caught by running rather than reading:** the first parser read one `pnpm run` per line and reported three *wired* witness legs as unwired (a checker that cries wolf is switched off as surely as one that never fires); and a `grep -qE '^OK'` verdict matched a checker's own `OK:` stdout, so I reported `tools/ci/tests` green while four dispatch-mirror mutation tests were red against the renumbered rows. **10 mutations across the four fixes, 0 survived** — including the suggested fix for (3), which the dead-man assertion catches. 41 CI-wired app gates green, 13 python gates/suites green, derived design-kit copy of doc 11 regenerated and asserted byte-identical.
