## Item

**The client's `execute` window was `grace_end` for every mandate, and the runtime's is not — in both directions**

## Spec ref

`pallets/execution-guard/src/lib.rs:1956–1962`; `crates/execution-guard-core/src/lib.rs:41`, `:784–787`; 09 §1.2(1); 05 §2.1 T18/T22/T23

## Status

**measured against the pallet, 2026-08-06**

## Result

`do_execute` matches on `failed_at`: `None ⇒ ensure!(now <= grace_end)`, `Some(f) ⇒ ensure!(now <= f + RETRY_WINDOW)`, where `RETRY_WINDOW = kernel::EXECUTION_RETRY_WINDOW_BLOCKS = 3 × BLOCKS_PER_DAY = 43,200`. So the retry clock **replaces** `grace_end` and the substitution is **not monotone**: a failure early in the grace window closes the door *sooner*, one near its end holds it open *later*. The review named the second direction only — a lawful retry after `grace_end` classified `past-grace`, marked terminal and disabled. The first is worse and nobody reports it: a mandate whose retry window closed inside `grace_end` read as live, so the client offered a signature the runtime refuses with `GraceExpired`. **Neither document said so.** 09 §1.2(1) read `maturity ≤ now ≤ grace_end` unqualified and 11 §11.5 row 2 mirrored it, while 05 §2.1's T18 (*"retry window 72 h, then T22"*) and T23 (*"within the 72 h retry window; full dispatch re-validation repeats"*) had said otherwise since the transition table was written — an internal contradiction, not an omission, which is why it is corrected under R-1 rather than raised. The value had **no values-layer home at all** (13 §2 now carries it) and **no client-readable surface** (SQ-790, fail-closed)
