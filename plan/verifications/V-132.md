## Item

**A hostname cannot carry a base64url TXID — my own new code returned a well-formed wrong address**

## Spec ref

12 §1.2; INV-FE-12

## Status

**found by my own test and fixed the same hour, 2026-08-05**

## Result

The first `resolveBaseTxid` read the first hostname label of `https://<txid>.arweave.net/`. DNS labels are case-insensitive and `new URL()` **normalizes the host to lowercase**, so a case-sensitive base64url TXID does not survive: the function returned a *lowercased* address that is well-formed, fails every comparison it feeds, and would have **appeared to work** for a coincidentally all-lowercase TXID — an intermittent defect in the one comparison meant to catch a substituted bundle. Arweave sandboxes to a **base32** subdomain for exactly this reason. INV-FE-12 forbids guessing at an encoding, so the path form is the only one read and an unrecognised host is refused with a stated reason rather than approximated. The test pins the *mechanism*, not the symptom: it asserts the lowercased label is **still TXID-shaped**, so a label-reading version would have accepted it. Recorded because the lesson is about test design — the fixture is mixed-case **on purpose**, and an all-lowercase one would have made the bug invisible
