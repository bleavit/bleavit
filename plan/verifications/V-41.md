## Item

**Zombienet keep-alive for the closing try-state check** — `zombienet test` tears its network down on completion, which is why SQ-204 had no per-suite closing leg

## Spec ref

15 §1; 15 §4.7

## Status

verified 2026-07-21

## Result

Read from the **pinned tag's own CLI source** (`zombienet v1.3.133`, the `ZOMBIENET_VERSION` pin) rather than from upstream docs, which have been wrong about this CLI before (the `pause`/`resume` native-provider case, V-24). Three facts: (1) `-m, --monitor` — *"Start as monitor, do not auto cleanup network"* — is declared on the **`spawn`** command only; (2) `test` declares **no** such option but takes `[runningNetworkSpec]`, *"Path to the network spec json, for using a running network for running the test"*; (3) the orchestrator writes that spec to `${tmpDir.path}/zombie.json`, so `-d <dir>` fixes its location. Hence the implemented two-phase shape: `spawn --monitor -d <dir>` → wait for `<dir>/zombie.json` → `test <drill.zndsl> <dir>/zombie.json` → closing check → group teardown. Unit-tested against a fake zombienet asserting the exact `spawn`-then-`test` order; **the real CLI's behaviour under this pairing is unexecuted here** (no binary, no built node) and is confirmed at first real execution — the design fails closed if it differs, since an unreachable endpoint fails the closing check and blocks evidence
