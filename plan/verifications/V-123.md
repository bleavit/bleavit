## Item

**The loop's invariant was in-memory only; making it durable needed one transaction, and the test proves it by mutation**

## Spec ref

10 §6.5, §7

## Status

**verified 2026-08-05**

## Result

`ingestBlock` returns advanced coverage only after the write resolves — true, and only half the property. Persisting the rows and the coverage as **two writes** has two orderings and only one is safe: *rows then coverage* leaves coverage **behind** the data after a crash, costing a re-ingest that is free because ids are deterministic and replay is idempotent (asserted); *coverage then rows* leaves `isVerifiedAt` answering `true` **forever** for a block with nothing behind it, in the exact structure the client consults to decide it need not re-fetch. Leaving that ordering to whoever writes the adapter is a coin-flip in the one place this package cannot afford one, so `BlockWrite` now carries `coverageAfter` and `storeWriter` commits events, rows and coverage in **one Dexie `rw` transaction** — neither ordering exists. The suite runs against a real IndexedDB rather than a stub, because the property under test *is* transactional atomicity and a stub grants it for free while proving nothing; and it is mutation-proven in the way that matters — rewriting the adapter as coverage-first-then-rows **fails** the rollback test, so the test is testing atomicity and not merely that a write happened
