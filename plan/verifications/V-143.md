## Result

Splitting row 12 into the never-waived dead-man latch and the expedited-waivable PB-LEDGER-FREEZE updated the client, `check-dispatch-mirror.py` and that checker's tests — and missed `reference-model`'s `lifecycle.py`, which parses the *same table* independently and had no binding to the mirror checker. **Three tests failed on PR #237's Reference model job**, and the local Rust/app gates I had run could not have caught it: the module is Python and lives outside every gate the app slice touches. The repair is not a bumped count, because the module models the relation by **atom**: backend item 10 gains a third atom (`triggering-freezes`), since §1.2(10) is two `ensure!`s of opposite waivability and the frontend now legitimately states it in three rows, so `backend:10:split` reports frontend rows (11, 12, 13) and backend 11 lands on frontend 14. The retired `apply_authorized_upgrade` row moved 14 → 15, and its classification is **deliberately kept alive** so the SQ-552 witness can reinstate it and watch the diff go red — without the entry the parser raises `ScheduleError` and the witness passes for the wrong reason. Mutation-proven: dropping the new atom from backend 10 fails the suite, so the mapping is still load-bearing. **The class is worth naming, because this is its third appearance in this line of work**: a spec table with more than one consumer, where updating the obvious ones leaves a quiet one asserting the old shape — and nothing binds the consumers to each other.
