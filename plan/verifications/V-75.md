## Item

**The release tooling published metadata v14 — the one version that cannot describe a runtime API** (found while producing F2's feed)

## Spec ref

02 §3, §11; 10 §5

## Status

verified 2026-08-03, fixed

## Result

`tools/release/extract-metadata.py` read the metadata through `state_getMetadata`, which is the **legacy** RPC and returns **v14** whatever the runtime supports. Metadata v14 predates the runtime-APIs section entirely, so the blob 02 §11 designates as the input to *descriptor regeneration* was structurally incapable of describing a single one of 02 §3's frozen thirteen `FutarchyApi` methods. Measured on this runtime: `Metadata_metadata_versions` advertises **14, 15 and 16**; the v15 blob carries **19 runtime APIs including `FutarchyApi`**, the v14 blob **zero**. Fixed by fetching the newest version the decoder supports through `Metadata_metadata_at_version`, failing closed below v15 rather than emitting an unusable artifact. This is also the root cause of the committed `keeper/.../runtime-metadata.scale` being v14 — a symptom, not an independent defect. **Residual:** the runtime also offers v16 and PAPI reads v16 straight from the wasm, but `tools/release/scale_metadata.py` decodes only v14/v15, so the repo's own decoder cannot read the best metadata the runtime serves. Not blocking (v15 carries every surface the manifest freezes) and recorded rather than fixed.
