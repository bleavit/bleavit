## Item

**The reference corpus's raw 64.64 integers exceed `Number.MAX_SAFE_INTEGER`, and `JSON.parse` corrupts them silently** (found while building F5's differential)

## Spec ref

04 §5; 15 §4.4/§4.8

## Status

verified 2026-08-03

## Result

`reference-model/fixtures/vectors.json` stores `raw_64x64_nearest`, `cost_raw_64x64_nearest`, `price_raw_64x64_nearest` and every `transcendental_corpus` `in`/`out` as JSON **numbers**, and they run up to ~3.2 × 10³⁸. JavaScript parses those to `float64`: V1's raw `9453860324986718414640` loads as `9453860324986719305728`, off by 891,088 — over 100,000× the 04 §4 bound the suite is asserting, so a *wrong* implementation would have passed and a right one failed. This is not a corpus defect (the file is exact, and the schema is normatively owned by 04 §5, which does not require string encoding) but it is a trap for every JavaScript consumer of it. Resolved in `app/tests/protocol/corpus.ts` (`.js` until the 2026-08-05 TypeScript migration): unsafe integers are recovered from the parser's own source text via the reviver's third argument, `bigFrom` **refuses** an unsafe `number` rather than rounding one, and `loadCorpus` probes V1's raw and throws if it did not arrive as text. All three failure modes were exercised — reviver disabled and corpus absent both fail closed with a named diagnostic. Any future JS/TS consumer of this corpus (F2's fixture suites, the `simulation` package) must load through the same discipline.
