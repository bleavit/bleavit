## Item

Does the snapshot content pin address the **file**, and does §8.4's re-derivation reach every reachable covered block?

## Spec ref

10 §8.2, §8.4, §4.2

## Status

complete (2026-08-06), both defects fixed

## Result

**Neither held, and each failed silently.** (1) The pin was computed over `serializeSnapshot(parsedDocument)`, not over the bytes handed in. Measured: a file with one space added parses to the identical document, so it hashed to the publisher's pin and **passed the pin screen** — only the canonical screen beside it objected, and the finding's own sentence (*"the file hashes to …"*) named a hash the file does not have, which is the string a user compares against a publisher's page. Now taken over the file's bytes; a trailing newline (which `JSON.parse` ignores) is caught by the canonical walk's end-of-text check. (2) `SPOT_CHECK_MAX_BLOCKS = 128` **ended the walk and returned a clean report**, so a forgery below the 128th-newest reachable block was never handed to the checker and the document was admitted with `findings: []` and rows badged `sampled: true`. 10 §4.2 states peers prune state at **~256** blocks, twice the number the pass ever asked about. The walk now terminates on the checker's own `out-of-reach` (and not before its first comparison — a document ahead of this device's head answers unreachable at the top, where stopping would compare nothing), under a ceiling of 2 × 256 whose only effect is a refusal
