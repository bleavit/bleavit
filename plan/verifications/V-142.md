## Item

**PLAN.md's Verification log had no id-uniqueness check, and four ids each name two different findings**

## Spec ref

15 §4.8

## Status

**found and gated 2026-08-05; the four legacy pairs are grandfathered, not fixed**

## Result

Surfaced by resolving this session's rebase conflicts: `main` and this branch had both appended rows at the same place, and keeping both sides — the correct resolution for an append-only log — is exactly how a collision is admitted when the two branches picked the same number. `check-spec-question-batches.py` already exists for this reason and says so in its own docstring (*"a collision survived a merge, because nothing checked id uniqueness"*); the Verification log had the same hole and nothing watching it. **V-72, V-73, V-98 and V-99 are each two unrelated findings** — V-72 is both the pnpm reproducibility probe and the N10 client integration kit — so a citation to any of them resolves to neither, and PLAN.md, the architecture docs and commit messages all cite findings this way. Verified the duplicates pre-date this session by reading `pre3/split-5-docs-and-tooling`, which already carried two of each, so the rebase preserved the count rather than creating it. **Gated rather than renumbered, deliberately:** ten citations reference these four ids and each must be read to learn which finding it meant, so renumbering half of them is worse than the duplicate. The four are enumerated in `check-plan-tables.py` with the reason, any *new* duplicate is fatal, and the list **expires mechanically** — an entry naming an id that is no longer duplicated is itself an error, so a stale waiver cannot pre-approve the next collision to take that number. Both directions mutation-proven. Renumbering the four remains open.
