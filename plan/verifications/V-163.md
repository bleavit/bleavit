## Item

**The SS58→32-byte encoding I recorded as "the only unbuilt input" was already built — and the obvious way to build it would have been wrong**

## Spec ref

02 §7.4/§7.7; 11 §11.9.1

## Status

**measured 2026-08-06**

## Result

The previous session's resume note named SS58→32-byte account encoding as F18's one remaining primitive. It is not: **PAPI's per-position key codec takes the SS58 string directly** (`inner[1].enc('5Grwva…')` → the 32-byte public key, measured), so no encoder was needed at all. **The more useful half is what a hand-written one would have got wrong.** `getSs58AddressInfo` reports `isValid: true` for public keys of 20 and 33 bytes as well as 32 — those are valid SS58 addresses, just not `AccountId32`s — so the natural implementation (*check `isValid`, take `publicKey`*) would hash a 20-byte key into `System.Account` and produce a **well-formed key that returns no value**, which the deposit screen renders as *this account holds nothing*. PAPI's codec refuses both with `Invalid public key length`, distinct from the `Invalid checksum` a malformed address gets. Both are now pinned, and the second test had to be repaired to prove anything: the address I first used to represent *valid but not 32 bytes* was itself `isValid: false`, so it passed by throwing `Invalid checksum` — the assertion now names `Invalid public key length` specifically, and the fixture address is generated with a real 2-byte blake2b checksum. Measured in the same pass: the 02 §7.7 confusion is loud rather than silent — handing `ForeignAssets.Account`'s key 0 the Asset Hub `u32` `1337` instead of the XCM Location **throws** inside the Location codec rather than encoding something.
