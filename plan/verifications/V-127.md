## Item

**10 §6.5 already mandated the ingest atomicity I derived independently — and names a single-writer lock the client does not have**

## Spec ref

10 §6.5, §4.4

## Status

**verified 2026-08-05 by reading §6.5 after building against it**

## Result

Two findings from reading the section *after* implementing the loop, which is the order that tests whether an implementation and a spec agree by accident. (1) §6.5's own words: *"Ingest writes remain idempotent (deterministic PKs, **cursor-range advance in the same IndexedDB transaction**)"* — the atomicity V-123 arrived at from first principles is **already normative**, and `storeWriter`'s single `rw` transaction satisfies it rather than exceeding it. Worth recording because the reasoning and the spec converged independently, which is the cheapest available evidence that neither is wrong. (2) The same sentence continues *"single-writer via the leader's `fut-ingest` lock (§4.4)"* — and **no such lock exists anywhere in the client**: `navigator.locks` appears in no package. Two tabs both ingesting would double-write and race on the coverage row; the transaction makes each write atomic but does nothing about two writers advancing coverage from different positions. A **real F8 gap**, not a design question — §4.4 already specifies the mechanism, and FE-P3's open half is about Web Locks *on Safari*, not about whether to use them. Recorded in F8's row
