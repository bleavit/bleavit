## Item

**The JSX import is invisible to BOTH firewall gates, and `jsxImportSource` at a workspace package is what closes it**

## Spec ref

10 §10.1, §10.2

## Status

**verified 2026-08-04 by `tsc --traceResolution` and by cruising a handoff `.tsx`; the row's own earlier premise falsified**

## Result

**This row previously said the handoff screens "cannot compile" under the default `jsxImportSource`. That is wrong, and the correct finding is worse.** Measured, not reasoned: (i) `tsc -b` on a handoff-unit file importing `react/jsx-runtime` **succeeds** — `--traceResolution` shows it resolving to `node_modules/@types/react/jsx-runtime.d.ts` at the workspace root, so a types package declared once at the root satisfies the compiler for **every** project regardless of the isolated `node_modules` layout that 10 §10.2 names as the enforcement; and (ii) dependency-cruiser cruises **source** with `tsPreCompilationDeps`, while the JSX import exists only in emitted output — cruising a handoff `.tsx` reports zero errors and the edge is absent from the graph entirely. So the *primary* gate and the *redundant* one are both blind to it, and a handoff screen written the obvious way would have carried an external import into the D-21 trust domain under fully green CI, first failing at `vite build` as a packaging error. The repair is unchanged and still costs nothing — `jsxImportSource: "@bleavit/ui"` makes the emitted specifier a workspace one, so §10.1 stays literally true and the gate keeps full sensitivity — but it is now backed by a gate rather than by a compile error that does not happen: `pnpm run check:handoff-emitted` (+ `:witness`) reads the **emitted** trees, which is the only artefact reflecting source *and* compiler.
