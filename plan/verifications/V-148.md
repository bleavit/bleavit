## Item

**`ReleaseIdentity` typed two content-hash fields as `0x`-prefixed while the producer has always emitted bare hex, and three `as Hash32` assertions held the lie up**

## Spec ref

12 §1.1; INV-FE-11

## Status

**fixed 2026-08-05**

## Result

Found by putting `tests/release` under `tsc` for the first time (task #31). `packages/verify`'s `Hash32` is `` `0x${string}` `` and `ReleaseIdentity` used it for all five hash fields — but `parseReleaseDocument` validates `perFileHashes` and `descriptorMetadataHashes` against `SHA256_HEX` (`/^[0-9a-f]{64}$/`, **no** prefix) and then asserts them into the prefixed type, and `build.ts` emits exactly that bare form. So the type was wrong for every value that ever flowed through those two fields, and the only reason nothing broke is that both sides compared with `===` under the same convention: it would break the moment any consumer acted on the prefix the type promises — stripping it before a comparison, or rendering it. Repaired by splitting the two spellings: `Hash32` keeps the `0x` chain hashes (genesis, chain-spec), a new `Sha256Hex` names the bare content hashes, and all three assertions are deleted. The `tests/verify` fixture had been written in the prefixed spelling throughout, so it described a document no producer emits — which is what kept the mismatch invisible on both sides at once. **The class is the one this repo keeps meeting**: a producer and a consumer describing the same bytes differently, with nothing comparing the two descriptions — the same shape as the `releaseTxid` field whose story is recorded in that interface's own doc comment.
