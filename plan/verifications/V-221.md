## Item

**Which `ProposalState` variants does this runtime have, and do the client's two lists name them?**

## Spec ref

02 §2; 05 §2.1; 11 §11.2

## Status

**measured 2026-08-07** (doc 02's frozen enum against `futarchy-primitives`, both agreeing)

## Result

**Neither list did, in both directions.** The enum has fifteen variants: `Submitted, Screening, Qualified, Trading, Extended, Queued, Suspended, Rerun, Rejected(RejectReason), Executed, FailedExecuted, Measuring, Settled, Cancelled, Expired`. `proposal-reads.ts`'s `STATS_REQUIRE_SEALED` named seven, of which **three are not variants at all** (`Measured`, `Delayed`, `MandateExpired`) while `FailedExecuted`, `Cancelled`, `Expired` and `Suspended` — all post-decision — were absent; `trade-ticket.ts`'s `ProposalState` union named ten, of which **five do not exist** (`Seeded`, `Deciding`, `Resolved`, `Withdrawn`, `Voided`) while nine real ones were missing. Both errors were **fail-closed** and neither was harmless: an unmatched state renders no decision statistics, so a decided proposal in one of the four missing sealed states was told *“there are no decision statistics yet”*, which is a confident false statement about the chain rather than a refusal; and the union could not type a reader's decoded value at all, which is why the defect surfaced only when a composition root had to produce one. Both lists are now derived from doc 02's own block at test time (`tests/screens/screen-composition.test.ts`), brace-matched rather than line-scanned — doc 02 writes some enums on one line, where a line-based cut runs into the next declaration and silently returns two blocks joined.
