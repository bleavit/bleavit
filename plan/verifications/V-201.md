## Item

**A wholesale merge resolution had silently dropped one side in four more files than the four that conflicted, and every one of them was invisible to the suites**

## Spec ref

`app/pnpm-lock.yaml`; `app/tsconfig.tests.json`; `.github/workflows/ci.yml`; `tools/ci/tests/test_workflow_wiring.py`

## Status

**measured 2026-08-07 while finishing `integration/track-f-v2`**

## Result

The four conflicted files were resolved by reading both sides, `rerere` off. What the merge had not reported is the useful half. **The lockfile lost three workspace links** — `tests/platform`, `tools/desktop` and `tests/screens`' `@bleavit/protocol` — at `667baa0d` (the `track-f/perf-budgets` merge, one merge after the branch that added the first two), so `pnpm install --frozen-lockfile` refused outright: the *first* command of every `app/` gate, and the reason this was found at all. Re-locking restored exactly those three links and moved nothing else, which is what confirms the cause. **`tsconfig.tests.json` lost a comma**, because two branches each appended to its `include` array and the resolution concatenated the two lists — so `check:types` had been failing with `TS1005` rather than type-checking the tests. **`ci.yml` was not valid YAML**: the `perf-budgets` branch's artifact-budget and render-budget lines were welded into the *next* step's `run:` scalar with the step header dropped, so the whole workflow would have failed to parse on every push, and both budget gates would have run nowhere. Only `tools/ci/tests/test_workflow_wiring.py` could see the last one — it parses the workflow rather than running it, and it is the reason that suite exists (V-90). **The general lesson is about which files a bad merge damages *quietly***: a source file that loses a side usually stops compiling, while a lockfile, a tsconfig and a workflow each fail somewhere no suite is looking — at install time, in a gate nobody re-ran, and on a server. After the repair: 276 `tools/ci` tests green, `--frozen-lockfile` clean, `check:types` clean, and the workflow parses. **Two further instances are recorded and deliberately NOT repaired here**, because both need a decision this session was told not to take. (1) PLAN.md's milestone table carries **duplicate rows** — F7b ×2, F8 ×3, F9 ×2, F22 ×2 — from the same append-and-keep-both resolution, and the two F22 copies **disagree on status** (✅ and ⬜), so the table states two things about one milestone and `tools/monitoring/check_alert_coverage.py` is red on it. `check-plan-tables.py` cannot see this: every copy is well-formed. The sibling branch `integration/track-f` already carries the user's own remedy (`e880e72d`, *collapse the rows ten parallel branches each extended*), which keeps the longest copy and never decides a status; it is not an ancestor of `integration/track-f-v2`. (2) `tools/limit-coverage/check-limit-coverage.py` is red because `EXECUTION_RETRY_WINDOW` reached 13 §2 with V-186 (`d23ca9d7`, the F7b stack) and was never classified in `registry.toml` — 15 §4.6's gate doing exactly its job. Classifying it is an R-2 judgement about a parameter this session did not introduce. Both predate this merge: `728b28ec` shows all of them.
