## Item

**A mutation harness restored files with `shutil.move`, which carried the backup's older mtime, so `tsc -b` skipped the rebuild and the next mutation ran against the previous one's compiled output**

## Spec ref

15 §4.8

## Status

**fixed 2026-08-05**

## Result

The sweep over `storage-keys.ts` reported the last mutation *killed by 3* and then printed `restored: FAIL`. Both were the same defect. Restore was `shutil.copy` to a `.bak` then `shutil.move` back; `copy` does not preserve mtime, so the backup carried the time it was **created** — before the mutation — and `move` is a rename that keeps it. `tsc -b` compares source mtime against `dist/`, judged the restored file older than its own output, and skipped it. The mutated `storagePrefix` (pallet and item transposed) therefore stayed compiled while the *source* on disk was correct, which is why `git diff` showed nothing wrong and the suite still failed. Two consequences, and the second is the one that matters: the final "restored" check was a true negative that looked like a flake, and **the fixture mutation that ran next was attributed kills it did not earn** — its three failures were the previous mutation still in `dist/`. Repaired by writing the original text back (`target.write_text(original)`), which stamps a fresh mtime, and re-running: all eight mutations killed, zero survivors, none killing every test. **The general lesson is that a mutation harness needs its own control**, and this one had it by accident — the closing `restored:` line is what surfaced the contamination. A sweep whose restore is not verified reports on a tree that no longer matches the code being tested, and it reports *confidently*: every number in the first run was plausible.
