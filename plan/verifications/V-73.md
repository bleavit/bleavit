## Item

Polkadot Product SDK — does `@parity/product-sdk` exist, and can it carry Bleavit? (the user-required architectural proof, six questions)

## Spec ref

10 §4; 15 §2

## Status

desk research complete (2026-08-03); PROD-1…6 open

## Result

**It exists** — `@parity/product-sdk@0.20.0`, Apache-2.0, Parity-published, `polkadot-api ^2.1.6`; the signing codec carries raw `method` bytes, `signedExtensions`, `metadataHash`/`mode` (RFC-0078) and `assetId`, so every Bleavit extrinsic fits and custom descriptors are unconstrained. **CORRECTED 2026-08-03:** the first reading of this — *"the host is a WebSocket RPC proxy, not a light client"*, inferred from zero `smoldot` hits in the SDK source — **was wrong**. The connection layer supports **both** (*"one underlying WebSocket (or light client) per chain"*) and ships a full smoldot recipe; the zero-hit result meant the wiring is a recipe for the host implementer, not that the capability is absent. The conclusion survives on a sharper fact: smoldot there needs a chain spec, `polkadot-api` ships built-in specs for **relay chains only**, and the README states outright that **"parachains fall back to WebSocket"** — any other genesis hash throws *Light client for chain X is not supported*. That is the same fact as "chain specs are not accepted" seen from the other side. So a host-routed **Bleavit** connection is WebSocket-backed ⇒ `provider` forever under 10 §2.2 ⇒ **a host-routed Product build cannot sign in normal mode** — not for want of light-client capability, but because there is no channel to supply the spec it would need. Whether the *deployed* devnet host enables even the relay light-client path is **not publicly determinable** (the docs say only that a config service distributes "RPC endpoints") — that is PROD-2. Chain support is operator-configured and runtime-detectable; chain specs are not accepted. Report: `app/docs/product-sdk-compatibility.md`. Conclusion: Product stays an **optional** target; the standalone adapters are canonical
