## Item

**Three CI steps ran `pnpm` from the repository root, and the fallout was worse than a failed step**

## Spec ref

10 §10.1 (rule 13, pinned versions); R-12

## Status

found + fixed 2026-08-03 by the first CI run of PR #229

## Result

The `app` job's steps carry a **per-step** `working-directory: app` and the job declares no `defaults`, so the three steps F4/FE-P4 added inherited nothing and ran from `/home/runner/work/bleavit/bleavit`. pnpm reported `ERR_PNPM_NO_IMPORTER_MANIFEST_FOUND` — but the line above it is the one that matters: *"Corepack is about to download pnpm-11.20.0"*. With no `app/package.json` in scope there is no `packageManager` field to honour, so the pin app-code rule 13 exists to enforce was silently not applied. A step in the wrong directory does not merely fail; it loses the version pin first. **Why nothing caught it locally:** `check-ci-parity.py` runs each *gate* in a CI-shaped checkout and compares behaviour — it never reads the workflow, so a correct gate invoked wrongly passes it, and I ran it and got PASS on 13 gates. The workflow that invokes every gate was the one artifact in the repository nothing verified. Closed with `tools/ci/tests/test_workflow_wiring.py` (CI tooling-suites job): every `pnpm`/`npx`/`node` step in a subdirectory job must run from that directory, every `pnpm run <script>` must name a script `app/package.json` actually defines, and R-12's `cancel-in-progress` must keep exempting `main` — where each run is the record for its own commit. All three assertions mutation-tested.
