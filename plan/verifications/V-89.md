## Item

**FE-P5: the probe half is NOT answerable from the pinned tree, and the fallback it names is already shipped**

## Spec ref

10 §4.2, §9.3, §12; 02 §11

## Status

attempted + recorded 2026-08-03

## Result

Recorded because the attempt failed, and a failed verification is worth a row: the next session would otherwise repeat it. FE-P5 asks whether historical metadata is retrievable via the light client at depth. I tried to settle it the way V-82 and V-87 were settled — by reading the lockfile-pinned package — and **it cannot be**: `smoldot@3.3.2`'s JS wrapper contains **no JSON-RPC method names at all** (`grep` for `archive_`, `chainHead_v1` and every `*_v1_*` form returns nothing across `dist/mjs`), because the request dispatch lives inside the WebAssembly module and the JS side only shuttles opaque strings through `sendJsonRpc`/`nextJsonRpcResponse`. So 10 §4.2's *"smoldot exposes the `chainHead` JSON-RPC group only — there are no `archive_*` methods"* stands as the specification's own established claim, and the code comments in `packages/chain-client` cite it as such rather than as something this repository has verified. Settling it needs either the smoldot Rust source or a live probe (the B7 drills). **What is settled is the consequence**, which is what the gate exists for: FE-P5's stated fallback is *"else ship bounded metadata blobs per supported spec_version (§9.3)"*, and F2 committed exactly those — `app/fixtures/chain-feed/{2,3}/metadata.scale` for both live-capable versions — with F4's `SUPPORTED_RUNTIMES` binding each to its descriptor set and `surface:check` comparing the pair against the feed in both directions. Backfill decode therefore has metadata for every supported version **without** the light client retrieving any at depth, so the gate blocks nothing regardless of how its probe resolves.
