## Item

**FE-P6's load-bearing half needs no hardware, and the answer is that the *chain* is the blocker**

## Spec ref

11 §11.13; 10 §12; 02 §8

## Status

**verified 2026-08-05 against the pinned `frame-metadata-hash-extension-0.10.0` and the runtime's own build**

## Result

10 §12 files FE-P6 as *"hardware test"* — Ledger Generic App + `CheckMetadataHash` for a custom chain. Reading the crate settles it: `RUNTIME_METADATA` is `option_env!("RUNTIME_METADATA_HASH")`, a **compile-time** variable `substrate-wasm-builder` sets only when metadata-hash generation is enabled, and `implicit()` returns `Err(UnknownTransaction::CannotLookup)` for mode `Enabled` when it is `None` (lines 150–156; the crate's own docs say so at line 115). Bleavit's `runtime/bleavit-runtime/build.rs` calls `WasmBuilder::build_using_defaults()` and **no `metadata-hash` feature exists anywhere in the repo** — so the variable is never set and **every transaction submitted with mode 1 is rejected today**. The hardware test would therefore have come back confusing: the device behaves correctly and the chain refuses the result. This is the *declared-and-unreachable* class at runtime level — `CheckMetadataHash` sits in the frozen `TxExtension` stack, so a reader concludes hardware signing is supported. Ruled as **SQ-594** and routed to new milestone **B21**, with the two build values *derived* rather than chosen: `enable_metadata_hash("VIT", 12)` from the 02 §8 chain-spec properties `validate-chain-spec.py` already asserts. **The client was already right** — `packages/signing` grants no `metadata-hash` capability and has no function that could, and two suites pin it; what changed is that their stated reason is now a verified chain fact rather than an open prototype gate
