## Item

**The 64-transcript storage corpus records prefix-only keys, so it can verify half of a key builder while looking like it verifies all of it**

## Spec ref

02 §11; 10 §4.1; 15 §4.8

## Status

**measured 2026-08-05, before building on it**

## Result

F18's remaining step needs storage **key encoding** (`Assets.Account(assetId, who)` and three others), and `app/fixtures/chainhead/` looked like a ready-made oracle: 64 storage transcripts, each carrying a real `chainHead_v1_storage` key **and** a `metadata_presence.expected_layout.hashers` list, across eight distinct hasher combinations up to three keys deep. Measured before relying on it: **65 of the 67 recorded key items are exactly 32 bytes** — corrected 2026-08-05, see V-159; the original text said *every*, which was false and was believed for a day — — `twox128(pallet) ++ twox128(item)`, the map prefix — because the recorder issues `descendantsValues` over whole maps and never a single-entry read. So the corpus exercises the prefix and **one hasher, on one key type, in one pallet** — not the eight combinations its layouts declare, and not the zero this row first claimed. That is V-155's shape one layer up: a rich-looking oracle that cannot distinguish the property under test. The prefix formula itself **is** confirmed against it — a naive filename→pallet mapping matched 58/65, and each of the seven misses was the mapping rather than the formula (`ConditionalLedger`, `ParachainInfo`, `ForeignAssets` reproduce their recorded prefixes exactly). Also measured, because it is the obvious shortcut and it does not work: PAPI 2.1.8's `getTypedCodecs` gives each storage entry as `{ args, value }` (`dist/src/index.d.ts`), where `args` is the **SCALE codec for the key arguments only** — it applies no hasher and prepends no prefix, so it cannot produce a storage key. **The consequence for the next session is a design constraint, not a caveat**: the hasher half needs known-answer vectors from outside TypeScript, and this repository already has the pattern twice — `runtime/bleavit-runtime/fixtures/multisig-derivation.json` and `crates/market-core/fixtures/chain-quote-agreement.json`, each written by the Rust side and read in place. Deriving the vectors from `@polkadot-api/substrate-bindings` instead would test that library against itself.
