## Item

Does the `ClientRegistry::ClientBond` metadata constant track the genesis-seeded `svc.client_bond` row, or is it fixed when the runtime is built?

## Spec ref

02 §9; 02 §11; 13 §1

## Status

complete (2026-08-04)

## Result

**It tracks storage, so a values adoption moves a frozen release surface.** Raised by the automated Codex review of PR #232 and checked rather than accepted. Three links, each verified at its own layer: `frame-support-procedural` 40.0.0 emits a constant's metadata `value` as `Encode::encode(&<Pallet<T>>::client_bond())` — *called* when `pallet_constants_metadata()` runs, not baked at build time; `extract-metadata.py` obtains metadata by `state_call("Metadata_metadata_at_version")` against a **booted node**, so that call executes against genesis state; and `RuntimeClientBond` reads `live_balance_param(b"svc.client_bond")`, which — alone among the constants' sources — has **no `default_param` fallback**, so it cannot mask an absent row with the compiled genesis default the way `u32_param_or` does. **Measured end to end:** a chain booted from this commit publishes `Some(100,000,000,000,000,000)`; the manifest froze `0x00`. **The scope is exactly one surface**: diffing the entire manifest against the fresh metadata gives 1 drift in 220 layout-checked entries. Note the artifact-level evidence was *not* decisive on its own and was nearly mis-read — `QuestionService::MaxLive` also reads a `Params` row yet would publish 16 either way, because its `u32_param_or` default equals the genesis seed. Only the fallback-free constant discriminates
