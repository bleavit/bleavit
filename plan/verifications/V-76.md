## Item

**PAPI 2.1.8 generates descriptors from a metadata file, and from the runtime wasm, with no node and no network**

## Spec ref

10 §5; 02 §11

## Status

verified 2026-08-03

## Result

The premise F4's milestone note rested on, checked rather than assumed — the same assumption was already wrong once (V-75). `papi add <key> -f <metadata.scale>` and `papi add <key> --wasm <runtime.wasm>` both succeed offline; the wasm path yields metadata **v16**, which is newer than anything the node RPC serves. Generation is faithful: descriptors built from the stale keeper blob contain `Market`/`Constitution` and contain **no** `ClientRegistry`/`QuestionService`/`ServiceLedger`, matching the blob rather than the runtime. Two integration details for F2's Stage 2: `papi add` runs `npm install` during codegen unless `--skip-codegen` is passed, which matters in a pnpm workspace gated on `--frozen-lockfile`; and `.papi/polkadot-api.json` records an **absolute** metadata path by default, which must be rewritten relative before the artifact can be committed. `papi generate` is idempotent and reports *\"no changes needed\"* when nothing moved, so the descriptor-drift gate is regenerate + `git diff --exit-code`. **End-to-end proof against the committed feed (2026-08-03):** generating from `app/fixtures/chain-feed/2/metadata.scale` yields **all thirteen** frozen `FutarchyApi` methods — `epoch_status`, `proposal_summaries`, `quote`, `decision_stats`, `account_positions`, `execution_queue`, `welfare_current`, `params`, `nav`, `recent_cohorts`, `open_oracle_rounds`, `hosted_report` and v23's `service_positions` — plus `ServiceIdBase`, `ServiceLedger` and `QuestionService`. From the v14 keeper blob the same generator produced **zero** runtime APIs, which is V-75's defect measured on the output side rather than argued. Generated output is ~1.8 MB per `spec_version` (`dist/` d.ts + js), which is the figure the \"committed generated descriptors\" requirement of 10 §5 has to carry.
