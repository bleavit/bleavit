## Item

**A CI gate's own source had never been type-checked, and merging the migration surfaced four latent errors in it**

## Spec ref

15 §4.8

## Status

**fixed 2026-08-06**

## Result

`app/tools/check-smoldot-surface.ts` (#242, F1/FE-P2) was written as TypeScript and *ran* as TypeScript — Node 22.18 type-strips — but `tools/*.ts` only entered `tsconfig.tests.json`'s `include` on the migration branch, so on `main` nothing ever compiled it. Merging `main` into that branch put the two together for the first time and produced four `noUncheckedIndexedAccess` errors: `dirs[0]` after a `length !== 1` guard (which convinces a reader and not the compiler), and three regex captures typed `string | undefined`. None was a live bug — the guards make the indices safe in practice — but the file is a **gate**, and a gate that throws `TypeError` instead of reporting its verdict fails open at exactly the moment it matters. Fixed by binding to locals with explicit refusals rather than by assertion. **The general point is about where a checker's coverage boundary sits**: `.ts` that merely *runs* is unchecked, and a tool directory is the easiest place for that to hide, because tools are executed by CI rather than imported by a suite. The migration's value here was not the syntax — it was extending `check:types` to `tools/*.ts`, which is what made the gap visible.
