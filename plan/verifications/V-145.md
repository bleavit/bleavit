## Item

**`app/release-out/` was never gitignored, so a `git add -A` committed 3,712 lines of generated release artifact — and the later `.gitignore` fix changed nothing**

## Spec ref

12 §1.1; repo layout

## Status

**fixed 2026-08-05**

## Result

AGENTS.md describes `dist/` and `release-out/` as *derived and gitignored*. `.gitignore` covered `app/dist/` and had no rule for `app/release-out/` at all, so my own `git add -A` swept `release.json` (90 lines) and the CycloneDX `sbom.cdx.json` (3,622) into a commit whose real content is 48 lines — against the explicit goal of the PR split, which was to reduce machine-generated added lines. The second half is the part worth keeping: a **later branch in the same stack had already added the `.gitignore` rule, and it fixed nothing**, because a `.gitignore` entry does not untrack a file already in the index — so the artifacts stayed tracked on every branch above it while the rule made them *look* handled. The repair is therefore two acts, not one: `git rm --cached` **and** the rule, both moved onto the commit that introduced the files. The SBOM matters most: 12 §1.1 derives it **from the lockfile**, so a committed copy is a second artifact that silently disagrees with the recipe the moment dependencies move. Verified `0 tracked` on all five branches afterwards.
