## Item

FE-P10 — how large is the runtime-upgrade extrinsic the client must submit, and can smoldot carry it?

## Spec ref

10 §9; 11 §11.8.4

## Status

**demand half complete (2026-08-04); capacity half open**

## Result

**4 MiB, exactly.** `MaxRuntimeCodeBytes = ConstU32<{ pallet_preimage::MAX_SIZE }>` (`configs.rs:10451`), and `pallet-preimage 49.0.0` pins `MAX_SIZE = 4 * 1024 * 1024`. So 11 §11.8.4's `system.apply_authorized_upgrade` path submits an extrinsic of up to **4 MiB** — the gate's "multi-MB" is now a number rather than an adjective. **The capacity half is not answerable from the pinned tree**: smoldot's transaction-pool and gossip size limits, its peer-banning behaviour on oversized transactions, and mobile memory headroom live in the Rust wasm, not the JS package (`smoldot@3.3.2`'s `dist/mjs` exposes no such surface). Same shape as **FE-P2** — one half readable, the other riding the B7 drills — and the same wall **FE-P5** hit. Recorded rather than assumed: a client that took the payload as obviously-fits would learn otherwise during a governance-mandated upgrade, the worst possible moment
