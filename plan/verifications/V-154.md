## Item

**A test-suite comment asserted `assert.equal` cannot narrow a discriminated union; measured, it does**

## Spec ref

tooling (`@types/node` 22.18)

## Status

**corrected 2026-08-05**

## Result

`tests/ui/derive.test.ts` justified its `stated()`/`incomparable()` helpers with *"`assert.equal(result.kind, 'stated')` does not narrow — it is not an assertion signature"*. Measured under this repo's own toolchain with a two-case probe: **`node:assert/strict`'s `equal` is an alias for `strictEqual`, which carries `asserts actual is T`, so it does narrow**, while plain `node:assert`'s `equal` (`==` semantics) does not. Every suite here imports the strict namespace, so nothing was broken by the wrong rationale — but it would have sent the next author reaching for a helper they did not need, or, worse, concluding that narrowing is unavailable and reaching for a cast, which is the one move `as unknown as` is banned across `app/` to prevent. Found because the *same* fact fired in the opposite direction in a new suite: `assert.equal(connection.kind, 'unavailable')` narrowed so effectively that the next line became a TS2367 *"no overlap"* error. The helpers stay — their real value is the **failure message**, since they report the refusal's own reason where a bare `assert.equal` reports only that two strings differ — and the comment now states the measured distinction instead. **The lesson is about where a claim like this belongs**: a statement about compiler behaviour written in prose is unfalsifiable in place, and the cheap repair is to measure it and record the measurement rather than the conclusion.
