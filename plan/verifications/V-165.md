## Item

**Two real events would have been missed by any account table built from FRAME's own field names**

## Spec ref

10 §6.5; 02 §6

## Status

**found 2026-08-06 by the cross-check that was built to test the opposite**

## Result

F8's account extractor discriminates by **metadata type id** (`sp_core::crypto::AccountId32`, resolved from the blob, exactly one such id in this runtime). To check that premise rather than assert it, the suite re-derives the same answer from a **different** input — the `typeName` text FRAME emits (`T::AccountId`, `Vec<T::AccountId>`) — across every event field the runtime declares. **Two disagreements**, both in the same direction and both real: `Session.ValidatorDisabled.validator` and `Session.ValidatorReenabled.validator` are typed `T::ValidatorId`, which reaches the account type and does **not** contain the string `AccountId`. Verified against the runtime rather than inferred: `runtime/bleavit-runtime/src/configs.rs:1781` and `:1809` both declare `type ValidatorId = AccountId`. So the walker is right and the name-based derivation is wrong — which is the entire argument for taking the discrimination from type ids, arriving as evidence instead of as reasoning. A hand-written table, or a `typeName` scan, would have dropped two events from every affected user's history and produced no error doing it. The asymmetry is now the assertion: *named ⇒ reachable* must hold absolutely (a failure there means the walker misses what even a table would catch), while *reachable but not named* is the **alias** set, pinned by name so a new one is surfaced rather than absorbed.
