## Result

A read-only `gpt-5.6-luna`/`max` compliance review of the round-3 diff returned **not clean** with four material findings. I verified each against the source rather than accepting it; all four hold. **(1) Blocker, NOT fixed here — SQ-566.** The partition bounds *dispatch*, not *transport*. XCM queue servicing, decode, barrier and origin conversion are `Mandatory` `on_initialize` work attached to no dispatch, so §8.5's own residual fold books them to `PrimaryUsed`; and a message whose call the safe-call filter refuses consumes primary weight with **zero** external reservation, because the resource dispatcher is never reached. That made the amended §8.5 and 15's PT-10 mutually inconsistent. Ruled (R-1): PT-10's byte-identical property is **scoped to dispatch-attributable** work, and the transport residual is now stated in both documents with its three bounds — the queue's `ServiceWeight` cap, `H`'s clamp below the 40 % target, and the fact that inbound execution is **priced** by the 09 §6 trader, so it is not the unpriced channel I-24 forbids. Not a merge blocker: the residual is pre-existing and this PR strictly narrows the primary side. **(2) Fixed.** `8r/2w` was enumerated for the signed-extension path and then reused for the XCM adapter, which performs **8r/4w** fixed (`before` read, reservation, `register_extra_weight_unchecked` r/w, `physical_delta`, the refund mutate, and settlement). The declaration is now the max over both paths and both enumerations ship as tables. **(3) Fixed.** The wrapper walk recurses, so a batch performs one `Markets` lookup **per market leaf** — up to 16 — while the extension declared one. Charging a flat worst case would tax every transaction for the rare batch, so the reads are now declared **per call** via the `call` argument `TransactionExtension::weight` already receives, and `market_leaf_count` is asserted at 0/1/15. **(4) Fixed.** The wrapper walk bounded depth by `MAX_NESTED_CALLS` (16) instead of the projection's `MAX_NESTED_LEVELS` (4), so a 5-deep tree passed the partition, reserved primary capacity, and then kept the reservation when the base filter rejected it. Now refused by the partition itself, with a regression that nests past the bound. The review also confirmed, by enumeration, that the refusal path blocks nothing legitimate: guardian playbooks and recovery use raw `dispatch_bypass_filter`, production scheduling is closed by `InternalSchedulerOnly`, and XCM wrappers die at the safe-call filter first. Two gates were **RED** on the first run and both were my errors: `all_gt` on a `reads_writes` weight can never hold because `RuntimeDbWeight` populates ref_time only and leaves proof_size 0; and both new spec cross-references cited `09-xcm-and-rollout.md`, which does not exist — the file is `09-execution-upgrades-and-rollout.md`. **Two residuals the review named and this row now records rather than losing.** (a) `validate` checks the wrapper refusal *before* `DispatchClass`, while §8.5 exempts Operational/Mandatory from the refusal path — latent only because every hosted dispatchable is Normal today, so there is no reachable Operational-hosted wrapper; it becomes live the moment one is reclassified, and the fix is a two-line reorder. (b) The external quota can be exhausted by an unauthorized signer, filed as **SQ-569**. Final: `cargo fmt --all` 0; workspace clippy `-D warnings` 0; runtime **443/443**, welfare **108/108**; fuzz-workspace nightly fmt 0; doc links (97 files), PLAN tables and spec-question batches pass.
