## Item

**FE-P2's sync-progress half, resolved by executing smoldot rather than reading it — and the read alone would have given the wrong answer**

## Spec ref

10 §3.1, §12; 11 §11.13

## Status

**verified 2026-08-05 by execution (offline, pinned smoldot 3.3.2)**

## Result

10 §3.1's `SyncDegraded` transitions are specified in **peer counts** (*0 relay peers > 60 s*, *0 para peers > 30 s*), and that state exists because *"previously the machine could only degrade after `Ready`, leaving the most common real-world failure (cannot reach peers on first load) stateless"*. FE-P2's second clause — *sync-progress introspection* — is what says whether the client can read them, and it had never been worked; V-89 had ruled the method surface unanswerable because smoldot's JSON-RPC dispatch lives in the wasm. **The wasm is in the package.** Decoding the three base64+zlib chunks yields 5,224,329 B of module whose string table carries the dispatch names, and `system_health` and `system_peers` are both in it, inside the alphabetically sorted `system_*` run a Rust `match` compiles to. **That is where a careful-looking answer would have been wrong.** Executed against the pinned package offline, `system_localPeerId` — equally present in that table — returns `-32000 "Not implemented in smoldot yet"`. Presence proves the dispatcher knows the name, not that it serves it, so only running it settles the question. **Running it:** `system_health` **is** served and returns `{isSyncing: true, peers: 0, shouldHavePeers: true}` — the zero-peer reading, which is the one the transition needs and the one a *connected* test could never produce. Also served: `system_name`, `system_version`, `system_chain`, `system_properties` (Bleavit's real `ss58Format` 7777 / `VIT`), `system_nodeRoles` (`["Light"]`), `chainSpec_v1_genesisHash`, `chainSpec_v1_chainName`. **The measured cost, and my hypothesis corrected by the second run:** the *first* `system_health` answered at **30.0 s** and head-of-line blocked the chain's whole JSON-RPC queue for that window — a trailing `system_name` that answers in milliseconds was released at the same 30.0 s instant. I took that for a per-call cost, which would have made the peer count unusable for a transition evaluated every 30–60 s. It is not: a second `system_health` sent at 45.0 s answered at **45.0 s**, immediately, and so did its trailer. The 30 s is a **one-time** wait for smoldot's sync service to publish a first status with no peers, not a polling cost. The design rule that follows is exact: never put `system_health` first on a chain's queue and never let boot gate on it, because the app's chainHead reads share that queue — but polling it thereafter is free. **The standing defect this exposes:** `peers-lost` and `peer-acquired` are declared in `boot.ts`'s event union with **zero producers** anywhere in the app, so `SyncDegraded` is unreachable in the shipped client and the repair 10 §3.1 made is not in force. Same shape as `FE-HANDOFF-010` and `FE-HANDOFF-012`: a code defined and never emitted, which no green run distinguishes from one that never fires. **Residual, stated rather than waved at:** this was measured offline with zero peers on a synthetic raw chain spec (smoldot rejects the `runtimeGenesis` form the pipeline emits), so it establishes the no-peer branch and the queue behaviour, not latency on a healthy connection; and the surface is reachable from PAPI only through `client._request`, which its own doc comment calls an *escape hatch* for *endpoints that are not spec compliant* and marks *"Unstable: the stability of this API is not guaranteed across minor versions"* — SQ-597.
