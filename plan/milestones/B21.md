**Raised 2026-08-05 by SQ-594 / V-122.** The runtime already carries `frame_metadata_hash_extension::CheckMetadataHash` in its frozen `TxExtension` stack, but `build.rs` calls `WasmBuilder::build_using_defaults()` and no `metadata-hash` feature exists — so the compile-time `RUNTIME_METADATA_HASH` env var is never set, `RUNTIME_METADATA` is `None`, and **every transaction submitted with mode 1 is rejected `UnknownTransaction::CannotLookup`** (verified in the pinned `frame-metadata-hash-extension-0.10.0`, `implicit()` lines 150–156). The extension is therefore *declared and unusable*: a reader of the stack concludes hardware signing is supported. **Recipe** — add `metadata-hash = ["substrate-wasm-builder/metadata-hash"]` to `runtime/bleavit-runtime/Cargo.toml`, switch `build.rs` to `WasmBuilder::init_with_defaults().enable_metadata_hash("VIT", 12).build()` under that feature, and enable it in the release profile. The two values are **derived, not chosen**: `tokenSymbol=VIT` / `tokenDecimals=12` are the 02 §8 chain-spec properties `tools/deploy/validate-chain-spec.py` already asserts. **Blast radius, stated because it is the reason this was not done in-session**: the wasm bytes change, so the committed `app/fixtures/chain-feed/`, `app/packages/papi-descriptors/` and `tools/release/surface-manifest.json` must all be regenerated and `surface:check` / `check-chain-feed.py` / `descriptors:check` re-run, plus the exhaustive Rust gate. Metadata *content* does not change, so no `INTEGRATION_CONTRACT_VERSION` bump is implied
