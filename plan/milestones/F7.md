**Started and largely built 2026-08-04. React 19 enters the client here, and the surfaces plus their controls are in and mutation-proven; what remains is the read layer that feeds them.** **The entry blocker was worse than recorded, and the correction is the main finding — see V-109/V-110.** The row previously said the handoff screens *"cannot compile"* under the default `jsxImportSource`. Probing it falsified that: `tsc` resolves `react/jsx-runtime` to the root `@types/react` and **compiles clean**, and dependency-cruiser cruises *source* so a compiler-injected import is absent from its graph entirely — so the primary gate and the redundant one are **both blind**, and a handoff screen written the obvious way would have carried an external import into the D-21 trust domain under fully green CI. The `jsxImportSource: "@bleavit/ui"` repair stands and still needs no spec amendment, but it is now backed by a **new gate over the emitted trees** (`check:handoff-emitted` + witness), which is the only artefact reflecting source *and* compiler. **`packages/ui` carries the two obligations a screen forgets.** INV-FE-9 is made structural by a fact about React rather than by a convention: `Verified<T>` is an **object**, `ReactNode` does not accept one, so a model whose leaves are `Verified<T>` cannot reach the screen except through a `ui` component that derives the badge from the status it was handed — the corpus carries the fixture. The residual (`{x.value}` by hand) is stated rather than papered over. 11 §11.2 constraint 3's five never-defer facts are enforced **twice**, because either alone is weak: `AboveTheFold` is an object so a `Disclosure` cannot take one at compile time, and `AlwaysVisible` **throws** under a disclosure context, which is what catches the indirect form handed down three components. The fact list is bound to the **section citations in doc 11's own paragraph**, so a sixth fact fails the suite rather than silently not existing. **Two spec rules made unreachable by construction rather than remembered.** S2's `ProposalView` is a discriminated union whose `pre-decision` arm has **no field** for decision statistics — verified, not assumed: TypeScript narrows by the discriminant before excess-property checking, so an in-Trade uplift preview does not typecheck. And the confirm summary is built from a **branded `DecodedCall`** whose only producer takes a hex string, so 11 §11.3's anti-substitution rule is a property; the surface additionally **refuses** a decode whose `fromHex` is not the preparation's, which is the attack in its exact shape. **Two defects found in work that was already green.** F11's `main.ts` ran `document.getElementById` at import and `index.ts` re-exported from it, so importing the application package in Node threw — invisible until something imported it, and F7's suite was the first thing that did (split into `boot.tsx` + a three-line entry). And S22 badged the **encoded** limit `external-proposal` unconditionally, telling the user a tool asked for a number the client itself computed; it is now derived from `boundBy`, which surfaced **SQ-592** — a policy-bound value has no status in the lattice, so it **fails closed** rather than wearing a label that misdescribes it. **20 mutations, 0 survived** (3 re-run because the first attempt was caught incidentally by `noUnusedLocals` rather than by a suite). New: `tests/ui` 20, `tests/screens` 28, 4 firewall fixtures (18), 2 gates. Full app suite 665 tests + 28 gates green; `@vitejs/plugin-react` **dropped** after a byte-identical rebuild proved it does nothing (V-111). **S1's read layer landed in the same session** (`src/application/src/chain-reads.ts`). The **decode is injected**, because `chain-client` is the only package that may import `polkadot-api` — the same discipline `decodeForConfirm` follows — and that is also what makes it testable with no chain. Two properties are enforced rather than assumed. **One screen, one block:** `assertOnePin` re-checks the finished model against the reader's pin, because a header showing the epoch at one block and the phase at another is not a stale display but a *view that never existed*, and nothing on screen tells them apart. It is **exported so a test can reach it** — no input to `readShellState` can produce a mixed model, so a test driving the public API could only assert two hashes it wrote itself were different, which is the vacuous shape this repo keeps finding; the first version of that test was exactly that and was replaced. **And undecodable is a first-class outcome:** the decoder returns a result rather than throwing, the raw bytes reach the screen through `ui`'s `Undecodable` (deliberately **not** a seventh `VerificationStatus` — the bytes are authentic and it is the *interpretation* that failed, and one label answering two questions is how "verified" stops meaning one thing), and an unreadable `Constitution.PhaseFlags` yields `undefined` rather than a substituted 4, so INV-FE-12 keeps the sudo banner up. 6 further mutations, 0 survived. **The hash-route outlet landed too, and its interesting part is what it does with the screens that do not exist yet.** Most of the inventory belongs to later milestones, so a navigation linking to them today links to nothing. Hiding those links is the worse option in a specific way — it makes the gap invisible, and the release that finally ships would carry no mechanical record of which screens were never built. So the outlet renders a placeholder that **names the owning milestone**, and `PENDING_SCREENS` is a declared set the suite counts **against the inventory in both directions**: a screen quietly dropped from the client cannot hide among the pending ones, and pending ∪ built must cover the inventory exactly. The set shrinks to empty as Track F closes, at which point the placeholder branch is dead — the intended end state, not a wart. `implemented` is a map assembled at the **composition root** rather than imported inside `routes.tsx`, because `tx` and `handoff` may not see each other (10 §10.2); one outlet renders either without the units gaining sight of one another. `screenForHash` now delegates to `screenFor` after briefly being a second implementation of one lookup — a drift that would have highlighted one screen in the nav while rendering another, with each half correct in isolation. 4 more mutations, 0 survived (1 refused by `noUncheckedIndexedAccess`, which is the type system enforcing the property rather than an incidental catch). **S2's reads landed on the same shape, and the rule they encode is one a plain implementation gets wrong.** *"Render the statistics if the runtime API returned some"* is one chain-state anomaly away from doing exactly what 11 §11.2 forbids — and because both reads come from **one pinned block** it would not be a race but a contradiction, with two readings and only one of them safe to act on. `viewFor` returns the **pre-decision** arm and reports an anomaly: being wrong that way costs a user a wait, being wrong the other way puts a projected outcome on an open market, which is a trading signal the client may not give. The state check is an **allowlist** (`STATS_REQUIRE_SEALED`), not a denylist, so a lifecycle state from a newer runtime — or one a plausible-but-wrong decode produced — renders nothing, per INV-FE-12; a denylist admits it. The list read goes through `crossCheckedCall`, whose prefix is derived from the API rather than supplied, which is FE-P2's conservative default and the reason the pairing cannot be got wrong at a call site. And a prefix key carrying **no value** is reported rather than filtered away: dropping it shortens the list, every remaining entry decodes perfectly, and the screen shows fewer proposals than the chain has with nothing saying so. 7 more mutations, 0 survived (2 re-run to compile). **The confirm surface's gate wiring closed too, and it found a defect in my own test.** `confirmProps` returns **`undefined`** outside the two states where a gate result exists, because a confirm screen is a statement that the chain was re-read at a named block and in `Draft`/`Prepared`/`Refreshing` that statement is not yet true — nothing to render beats a screen with remembered rows. `Blocked` shows the **failures only** (rule 5's diff view), and `mayOfferSigning` reads the **state**, never *"every row passes"*: `FE-TX-007` blocks with an **empty** `failed` array, so that predicate is vacuously true of the one case where the bytes themselves are stale. **Mutation M34 survived on the first pass** — the test built a `Blocked` session with no `signingWindow`, so a controller preferring the window fell back to `failed` and passed. The dangerous session is `Blocked` reached *after* a gate once passed, carrying a full set of rows true at a block B′ has moved past; the test now builds exactly that, and the fix was to the test rather than the code. 3 more mutations after the repair, 0 survived. **The decode layer landed the same day, and it needed neither a client nor a new dependency.** The scoping note above pointed at `@polkadot-api/metadata-builders`; checking before adding it found **`getTypedCodecs` is a root export of `polkadot-api` itself**, which `chain-client` may already import — so `packages/chain-client/src/codecs.ts` builds the codecs from the committed descriptors with **no chain, no provider and no network**, measured rather than assumed. The descriptors are an *argument*, so `chain-client` gains no edge to the generated package. **Three things were wrong in the first version and each was caught rather than reasoned away.** (i) It used `as unknown as`, which is banned across `app/` — `check:casts` failed it, and the repair is better than an exemption: the lookup is by *string*, so no static type relates the argument to the result, and `unknown` plus a **runtime type guard** is the accurate typing. The guard is now load-bearing at compile time too — remove its narrowing and the code does not typecheck. (ii) The codec surface is a **Proxy that throws** on an unknown name rather than returning `undefined`, so both `=== undefined` guards were dead code; the lookup moved inside the `try`, and only the two distinguishable failures are reported, because a throwing Proxy cannot tell *no such pallet* from *no such item* and inventing that detail would put unestablished claims in a message. (iii) A mutation binding `storageDecoder` to a **different item** survived, because the test only asserted that decoding `0x` fails — true of every item; it now binds a nonexistent name and requires the failure to name it. 7 mutations, 0 survived. **The per-item value mapping closed it, and getting the shape from the runtime rather than from the prose is what exposed the session's worst defect.** `Epoch.EpochOf` decodes to `{index, phase: {type}, phase_start_block}` and `Constitution.PhaseFlags` to a plain `number` — both established by running the **recorded** fixture bytes through the real codecs. The second one is the finding: the shell had modelled `PhaseFlags` as a governance *phase number* and tested `>= 4`, where 02 §7.3 freezes a **bitset** whose *bit* 4 is sudo-present. The recorded value is `17`, so `17 >= 4` would have **hidden the sudo banner on a chain running sudo** — and re-reading the spec prose would not have caught it, because the prose says *"Phase ≥ 4 (sudo removed)"* and the code said `>= 4`. The bit table now lives in `phase-flags.ts`, is tested **by name** so no call site invents an index, and is bound to 02 §7.3's own sentence — which immediately caught my table for shortening one flag's name. `test:screens` carries the **whole path with no node**: recorded bytes → real PAPI codecs → read layer → screen model → rendered banner. 14 further mutations, 0 survived; two of them found real gaps (a decode failure being relabelled with a shape reason, and `sudoActive`'s own `undefined` branch never being reached because every test went through `sudoBannerFor`), and one found **dead code** — the `>>> 0` sign normalisation could not fail, since every named bit is 0–7, so it was deleted rather than kept as decorative caution. (The S2↔S3 link needs S3, which is F7b.) 693 app tests green

Rooted at **`app/`** (10 §10.1, amended 2026-08-03); the `frontend/` placeholder is retired.

**Phase grouping** (2026-08-03). **Phase 0** = F19, the spec batch and its two proofs. **Phase 1**
= F0, F2–F6, F20, F21, F7, F10, F11, F22 — web + PWA canonical plus a **direct-download** desktop
Tauri build; no app store, no iOS, no Android, no Product target, therefore **no INV-FE-8/-10
amendment needed**, since store re-signing is the only thing that makes those texts false.
**Phase 2** = F7b, F8, F9, F12, F14, F16–F18 + mobile shells. **Phase 3** = the store question
(scope INV-FE-8/-10 to the canonical channel, add INV-FE-16 channel honesty) + the Product target,
which ships fail-closed read-only until PROD-1/PROD-2 pass.

**Handoff-first navigation** (user ruling, 2026-08-03 — 11 §11.2). The client's two *primary*
surfaces are **prepare a capsule** (S21) and **review/confirm/sign** (§11.3–§11.4 + S22); the
analytical depth and the whole FE-14/FE-15 set sit behind **Advanced**. This reorders Phase 1 —
the handoff packages and the Skill set (F20/F21) now precede the screens (F7) instead of trailing
them — and it is a **presentation change only**: every screen in the 11 §11.2 inventory still
ships, still works with no external tool present, and the no-infrastructure certification run
still executes with the handoff surfaces disabled. Demoting a surface is permitted; removing one
would falsify INV-FE-4 and the 15 §2.1 reading that admits the handoff at all. **Two consequences
are not free and are tracked, not assumed:** SQ-552 (the missing 09 §1.2 ↔ 11 §11.5 precondition
diff) now blocks a *primary* surface rather than a deferrable one, and doc 14's TH-74 residual was
re-assessed for its enlarged exposure (§3.9 preamble).
