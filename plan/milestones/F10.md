INV-FE-8/11. Generated from `tools/release/surface-manifest.json`, never hand-listed. **Core landed 2026-08-04 (17 tests, 2 mutations caught).** `packages/verify` carries INV-FE-11's pin set as a **required** field group — an identity record missing a pin is not a partial identity but a bundle that cannot prove one of the things the invariant says it proves, and an optional field lets that ship. Three properties are load-bearing and each is tested as a property. **(1) A genesis mismatch is terminal, and that is not `restricted`.** INV-FE-12's reduced modes are for a runtime whose *surface* is partly unknown — the same chain, further along. A wrong genesis means a *different chain*, where no subset of functionality is safe and every balance shown belongs to someone else; so the verdict carries no severity to compare and no override to pass, and there is no path from it to any operating mode. **(2) Chain-spec and genesis are separate obligations**: the spec hash proves the bytes handed to smoldot are the release's own (app-code rule 13), the genesis hash proves those bytes describe the intended network, and the spec check runs *first* — otherwise a tampered spec is reported as the chain being wrong. **(3) Divergence is surfaced, never repaired** (INV-FE-8's own closing rule), enforced **structurally**: the package exports no repair/refetch path and a test asserts it, because re-fetching asks the channel that just served wrong bytes for better ones and the user sees a flicker instead of a warning. The self-check reports `unexpected` served files as their own finding — the direction a manifest-driven loop cannot see, and how a payload arrives with nothing signed having changed. `buildPanel` is **synchronous and takes no chain handle**, because 10 §3.2 lists the panel among what still renders under `FE-BOOT-002` when smoldot never started — the moment a user most needs to know what they are running. **The `release.json` binding closed 2026-08-04 with F11** (`parseReleaseDocument`, 9 tests). It is its own module because the join is exactly where the two halves disagreed once already — the producer emitted `arweaveManifestTxId` while this package required `releaseTxid`, and the producer-side test compared the document against a list kept beside the producer. The binding is now checked against the **document the build actually emits**, the same one-artifact-two-checkers discipline the vector corpus and the multisig fixture follow, and renaming the producer's field turns a test red. Every path **refuses rather than repairs or partially fills**, and three refusals are load-bearing: an **unpublished** record (`releaseTxid: null`, what the builder emits before 12 §1.2's second pass) has no content address, so there is nothing a user could compare the bytes they received against; a record with **unresolved readiness blockers** is refused outright, because rendering the fields that *are* present shows a panel of green rows whose absent neighbours are the reason it is not a release — and that is the state today's build is genuinely in, asserted as such; and a **present-but-malformed pin** is refused exactly like an absent one, since `verifyChainIdentity` compares pins against a live chain and a malformed pin is a comparison that can never match, shipped in a record claiming to be complete. **The rendered component landed 2026-08-05, unblocked by F7's shell — F10 is complete.** It sits in `src/application`, not `packages/ui` as this row previously guessed: `ui` holds components that know about *provenance*, and a panel that understands `ReleaseIdentity`, self-check divergence and a checkpoint bound is domain furniture, so pushing it into `ui` would make the render layer depend on the release layer for one screen. 10 §10.1 puts the shell at `app/src/{application, …}` and that is where a screen belongs. It takes **no chain handle**, because 10 §3.2 lists this panel among the surfaces that still render under `FE-BOOT-002` when no verified read exists at all. Two renderings are deliberate and **both survived their first mutation because my tests were wrong, not the code**: pinned-vs-observed is distinguished **in words per row** (a colour is not a fact — and the first test searched the whole document for the two phrases, which also appear in the notice above the list, so deleting the row label left it green); and a **fresh** checkpoint renders *nothing at all* (a green *"checkpoint is current"* line is a claim about the future, since the bound lapses on a clock the client does not control — and the first test only checked three warning phrases were absent, which any other reassuring wording passes). Both are now asserted structurally: per-row, and by **byte equality** against the panel with no checkpoint supplied. 5 mutations, 0 survived after the repairs. Platform hashing stays deliberately the caller's: `SubtleCrypto`/node/Tauri differ, while the comparison that decides whether a user is warned is identical everywhere and lives here

**Phase grouping** (2026-08-03). **Phase 0** = F19, the spec batch and its two proofs. **Phase 1**
= F0, F2–F6, F20, F21, F7, F10, F11, F22 — web + PWA canonical plus a **direct-download** desktop
Tauri build; no app store, no iOS, no Android, no Product target, therefore **no INV-FE-8/-10
amendment needed**, since store re-signing is the only thing that makes those texts false.
**Phase 2** = F7b, F8, F9, F12, F14, F16–F18 + mobile shells. **Phase 3** = the store question
(scope INV-FE-8/-10 to the canonical channel, add INV-FE-16 channel honesty) + the Product target,
which ships fail-closed read-only until PROD-1/PROD-2 pass.

**Handoff-first navigation** (user ruling, 2026-08-03 — 11 §11.2). The client's two *primary*
surfaces are **prepare a capsule** (S21) and **review/confirm/sign** (§11.3–§11.4 + S22); the
analytical depth and the whole FE-14/FE-15 set sit behind **Advanced**. This reorders Phase 1 —
the handoff packages and the Skill set (F20/F21) now precede the screens (F7) instead of trailing
them — and it is a **presentation change only**: every screen in the 11 §11.2 inventory still
ships, still works with no external tool present, and the no-infrastructure certification run
still executes with the handoff surfaces disabled. Demoting a surface is permitted; removing one
would falsify INV-FE-4 and the 15 §2.1 reading that admits the handoff at all. **Two consequences
are not free and are tracked, not assumed:** SQ-552 (the missing 09 §1.2 ↔ 11 §11.5 precondition
diff) now blocks a *primary* surface rather than a deferrable one, and doc 14's TH-74 residual was
re-assessed for its enlarged exposure (§3.9 preamble).
