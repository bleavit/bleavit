Implementation complete 2026-08-02; **held open on 16 §12's live-network requirement.** The client runtime pallet owns question budgeting, fee envelope, positional XCM, report provenance and local handling; the runtime-independent ABI freezes register/open/seal/settle plus the builder; the TypeScript facade owns finalized proof-backed reads and typed submissions. Bleavit's production runtime is unchanged, and the lockfile delta is purely additive (70 insertions, 0 deletions, no existing dependency version moved), so the `=`-exact stable2606 pins are intact. **Red residual, now diagnosed rather than merely declared — drill 10 WAS spawned and the blocker is not N10's code.** The full pipeline was made runnable (pinned zombienet + relay binaries fetched, `bleavit-node` built, all eight relay/drill specs and `bleavit-client-local.json` generated and validated), drill 10 spawned a live relay + two parachains + five collators — and **both parachains stall at block #0** while the relay is healthy (best #144, finalized #142): `cumulus-pallet-parachain-system-0.29.0/src/lib.rs:1362` panics `assertion left == right failed: DMQ head mismatch`, so `set_validation_data` traps and no parachain block is ever built. **The correlation across the whole drill suite is exact and it is a project-level finding, not an N10 one: every topology declaring `hrmp_channels` has never executed successfully, and every topology without them passes.** `bleavit-local`/`fast`/`fast-coretime`/`migration` carry zero HRMP channels and own drills 01–06 and 09, all passing; `bleavit-xcm` (2 channels, drill 07), `bleavit-client-para` (2, drills 10/12/13) and `bleavit-client-no-return` (1, drill 11) have never produced a parachain block. **This also corrects drill 07's recorded attribution**: it was filed as the pinned Paseo `asset-hub-paseo-runtime` trapping on its parachain-system inherent, but the trap here is in **`bleavit-runtime`** on both a Bleavit and a client parachain with no Asset Hub involved — different runtime, same inherent, same topology feature, so the common cause is HRMP-channels-at-genesis and "Paseo-CSG issue" is at best incomplete. That matters out of proportion to its size: Bleavit-as-a-service is entirely cross-chain, so the drills that would prove ingress, egress and registration work are precisely the ones that have never run. **Root-caused 2026-08-02 (source-proven, SQ-567), and it is an upstream SDK defect rather than a Bleavit misconfiguration.** Relay genesis `preopen_hrmp_channels` calls **both** `init_open_channel` and `accept_open_channel` (`polkadot-runtime-parachains-28.0.0/src/hrmp.rs:904/1443/1532`), and each sends a DMP notification via `send_to_para` → `queue_downward_message` (hrmp.rs:1892/1903) — stamped `sent_at = 0`, because genesis runs at block zero. The collator **does** fetch them (`retrieve_dmq_contents` over the unfiltered relay API, `runtime_api_impl/v13.rs:355`); the parachain runtime then discards them. `do_create_inherent` (`cumulus-pallet-parachain-system-0.29.0/src/lib.rs:1291`) falls back to `InboundMessageId { sent_at: last_relay_block_number, reverse_idx: 0 }` when `LastProcessedDownwardMessage` is `None`; on the first candidate `LastRelayChainBlockNumber` is still 0 (ValueQuery, written only in `on_finalize`), so the sentinel is `{0, 0}`. `drop_processed_messages` (`parachain_inherent.rs:95`) scans **in reverse**, matches the LAST `sent_at == 0` message, and `drain(..=idx)` removes **every** genesis message. The MQC head is then rebuilt from an empty list, stays zero, and mismatches the relay's non-zero head at lib.rs:1362. **The sentinel cannot distinguish \"nothing processed yet\" from \"all block-0 messages already processed\"** — opposite states, and it picks the wrong one on the only block where the ambiguity is reachable. Verified **byte-identical in cumulus-pallet-parachain-system 0.22.1 / 0.23.0 / 0.23.2 / 0.26.0 / 0.29.0**, so no pin bump in range escapes it; the DMP/MQC hash chains agree between relay and cumulus, so it is not version skew; and the HRMP `max_message_size` is checked against a different field than the DMP limit, so it is not a limits problem. **Fix not implemented and not verified** — the preferred shape is to clear the relay's genesis DMP queues in the spec this repo already generates (a channel genesis both opened *and* accepted needs no notification), which needs neither relay sudo nor a zombienet feature; `force_open_hrmp_channel` after both paras produce blocks is the alternative but needs `ChannelManager`/Root, which a Paseo-derived relay spec very likely lacks. Verification requires a live spawn. Fixing it also unblocks drill 07 and the Phase-3 gate. **CLOSED 2026-08-02 — all four client drills now pass on live networks.** SQ-567 (post-genesis HRMP open, the user's chosen bypass) and SQ-568 (`num_cores` overshooting the validator count) were both fixed and proven by spawn; drill **10 = 5/5**, **12 = 6/6**, **13 = 4/4** (all eight malformed positional programs refused at the BARRIER, `ProcessingFailed` on every one), **11 = 4/4**. Two correlation defects common to the drill helpers were fixed: `polkadotXcm.Sent.message_id` and the receiver's `messageQueue` id are different quantities so an id match never fires, and the post-genesis HRMP open injects relay DMP notifications that a first-event-in-range match mistakes for the client's message — both are now resolved by filtering on the queue ORIGIN (`Sibling(4343)` vs `Parent`). Drill 11 is re-scoped to what an inert service can witness and files **SQ-570** for the rest: the full lifecycle is unreachable because `svc.client_bond` is deliberately `[VERIFY]`-unset and no drill-reachable admission path exists, so I-36's push half stays unwitnessed and is recorded as such in the artifact. **Status cell flipped ⬜→✅ on 2026-08-03 (N12 session).** The row had said "CLOSED 2026-08-02" in its own prose since the drills passed while the status column still read 🔨 — a self-contradicting row, and precisely the stale-status shape R-10 calls technical debt with interest, since a reader scanning the status column would see open work that the row's own text says is finished. Nothing new was verified to make this flip; the evidence was already here and only the cell was wrong.

<!-- source track narrative -->

Opened 2026-08-01 on the "make the futarchy infrastructure accessible to other parachains,
smart contracts and services via XCM" work order. Bleavit hosts conditional decision markets
for external clients and **sells price discovery, not decisions**: it publishes the conditional
TWAPs with provenance plus a manipulation-cost bound, and the client's own on-chain rule decides
and executes locally. Bleavit never runs foreign code, and no external state reaches any Bleavit
decision, welfare or settlement input. v1 scope by user decision — the spec batch, contract bump
and threat rows land together. Full approved design: `.claude/plans/` (session plan, 2026-08-01).
