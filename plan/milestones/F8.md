INV-FE-7. Phase 1 ships the minimal slice only. **Coverage core landed 2026-08-04 (16 tests, 2 mutations caught).** The load-bearing operation is the one an index normally gets for free: **merging**. 10 §6.3's *"never silently spliced"* forbids joining adjacent ranges of different provenance, and the reason is the same one that keeps `Finalized<T>` out of `shared-types` — a merged range must claim **one** origin, so claiming `self` promotes provider blocks to light-client-verified, which §2.2 says has no promotion path at all, and claiming `operator` demotes verified data. Neither is available, so the boundary survives to be rendered. `addRange` joins only same-origin **and** same-provider ranges (two operators are two sources; one lying does not implicate the other), keeps **both** ranges where provenances overlap — those blocks really were ingested twice, and a reader asking "is block N verified?" must still find the `self` range — and recomputes holes on every mutation. `isVerifiedAt` is deliberately not a general `isCovered(origin)`: the question a caller almost always means is *may I treat this as verified*, and a general predicate makes that one option among four. Two consequences pinned by test rather than left to be discovered: the **1,200-block gap 10 §6.3 says cannot be closed** stays open (the withdrawn "history continuous" promise), and **merging coarsens invalidation** — once same-provenance ranges join, the joined range is the unit and corruption anywhere in it drops the whole span, with no sub-range surgery. **Ingest and backfill landed 2026-08-04 (33 more tests, 3 mutations caught).** §6.5's design rests on one claim — *"blocks containing none of the user's extrinsics never trigger a body fetch; worst-case overhead is proportional to the user's own activity, not chain activity"* — and **both ways of breaking it are silent**. Attribute too narrowly and history is *filtered*, which looks exactly like history that is *empty*. Attribute too broadly and the client fetches a body for every block the chain produces, on a light client, on a phone, while every "does it find my transactions" test stays green. The easiest way to do the second is to treat `System.ExtrinsicSuccess` as attribution, since it is emitted for every extrinsic in every block — so it is enumerated as **correlation, never attribution**, by event name rather than by pallet (a rule of *ignore System* drops `NewAccount`/`KilledAccount`). **My first version of that test was vacuous and the mutation run said so**: the fixture gave the correlation events `accounts: []`, which is what the runtime really emits, so the assertion held because of the empty list rather than because of the rule and deleting the rule killed nothing. The realistic break is a decoder that helpfully fills in the extrinsic's signer, and only a fixture that does the same can tell them apart. Also pinned: a `Finalization`/`Initialization` event **never** attributes (it belongs to no extrinsic, so it would fetch a body for a block the user never touched and leave no index to decode); an index outside the block's extrinsic count is **refused rather than clamped**, because a decode at a bad index does not throw — it returns a *different* extrinsic, and the client renders someone else's transaction as the user's; and `bodyProvenance` takes the **header's** origin and has arity 1, so there is no argument by which a caller could promote a backfilled body (the extrinsics-root check proves the body matches the header, and at depth the header itself is layer-2). **Backfill is a re-derivation, not a restatement**: §6.4 exists because the reviewed text was inconsistent three ways (50 blk/s claimed, "~9 days per hour" where that rate gives 12.5, 20 blk/s budgeted elsewhere), so the suite computes 72,000 blocks = 5.0 days/hour and 432,000 blocks = 6.0 hours and asserts them against the published table — the check the inconsistency needed and did not have — and keeps the superseded figure as a regression. The rate is a **required argument everywhere** because it is `[VERIFY]`-tagged to FE-P4. A plan past the 30-day operator window is **refused, never truncated** (truncating yields a shorter plan that completes and reports success having never fetched what was asked), and the window is measured from the **live head**, or a plan validated against a stale one creeps past it a session at a time, each step looking lawful. **And the 10 §5.4 gate caught my own module on the way in**, which is the first thing it has found in live code: `BLOCKS_PER_DAY = 14_400` collides with `Epoch::DecisionWindowFloor`, and the collision is not a coincidence to waive — a module carrying that number is one governance change away from computing a day of backfill against a day that no longer exists. Blocks-per-day is now a **required argument** read from chain metadata like the ingest rate, `operatorWindowBlocks` is a function of it, and the literal lives in the suite, which is where a test asserting 02 §8's published cadence belongs. **Candles and the §9.2 ladder landed 2026-08-04 (11 more tests, 3 mutations caught).** §9.2's title is the specification — *degrades depth, never correctness* — and the second half is where a storage manager quietly lies. It names the exact lie: *"an evicted range becomes a labelled 'downsampled' range, not a hole, and never a silent splice"*. Those are **three** misinformations, not one: a *hole* says nobody ingested these blocks, which is false and (per §6.3) invites a provider refetch that could add no detail; a *silent splice* draws the coarse line as though nothing changed; *downsampled* is the truth. So `DownsampledRange` is a **distinct type rather than a flag** — a boolean defaults to the silent-splice reading in every component that forgot to read it. The ladder is data (`raw → 1h → 4h → 1d`) because the **order is the degradation guarantee**: applied out of order it frees the same bytes and destroys more resolution than it had to. `candles1d` returns `undefined` rather than throwing, since *nothing left to give up* is the answer the quota manager needs in order to stop. **Open and close are decided by time, never by array order** — §6.4 requires backfill newest-first, so reversed input is the ordinary case, and an inverted candle is not visibly wrong: it is a plausible bar pointing the other way. Roll-up composes exactly (asserted against re-folding the same samples) and refuses an equal-or-finer target, which would fabricate resolution the data never had. Two defects found in my own work while proving this: the grouping used a **NUL byte as a composite-key separator** — the Write-tool trap this session already hit once, which makes the file invisible to `grep` and made a mutation run report a false *0 kills*; it is now nested maps, so there is no separator to guess at, and the whole `app/` tree was swept for stray NULs. And the 10 §5.4 gate objected to `14_400` seconds colliding with `Epoch::DecisionWindowFloor` blocks — a genuine unit coincidence, **derived from the hour rather than waived**, because a waiver would sit in the classification file forever explaining a number that did not need to be there. **The §7 Dexie store landed 2026-08-04 (7 more tests, 3 mutations caught)**, on the 01 §9 `dexie` 4.4.4 pin and exercised against a real IndexedDB (`fake-indexeddb`) rather than a stub — the properties worth testing here are the ones a stub grants for free. **The sharp edge is the database *name*.** §7 names it `futarchy@<paraGenesisHash-prefix8>`, and a single shared database would let a client that connected to Paseo yesterday and Polkadot today read yesterday's rows as today's chain: positions, prices and history belonging to a different network, with nothing downstream able to notice, because the rows are well-formed and the ids collide — both chains number their proposals from one.
