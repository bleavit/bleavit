INV-FE-10. pnpm recipe pre-proved in F19. **The verdict and the registry landed 2026-08-04 (18 tests), unblocked by F11.** These rules are only ever exercised on outcomes a healthy release never produces, so that is what the suite is. **Three floors, each counted the way that is easy to get wrong.** §1.4's signature floor is *≥ 2 valid signatures from **distinct active keys of the current keyring generation**, counted **after excluding revoked keys***: three conditions, and dropping any one passes a release that should be refused — two signatures from one key is one key; a previous-generation signature verifies against a keyring this release did not publish; and counting before revocation is precisely the case §2.3 exists for, since **the compromised key is the one still signing**. §1.4 gate 2 is counted **by organization**, because two attestations from one org is one reproduction and independence is the entire claim — an attestation with no declared organization is refused rather than counted. The file comparison **reuses `packages/verify`'s `runSelfCheck`** rather than reimplementing it, so the CLI and the in-app check cannot disagree about what *matches* means, including the *unexpected* served file a manifest-driven loop cannot see. **`diff-scope` compares both directions**: §1.5 requires every out-of-scope file to be *byte-identical*, and a deletion is not that — a loop over the candidate tree alone would report a deleted `app.js` as an admissible descriptor-only delta. **The disjointness check's load-bearing clause is *over natural persons*:** intersecting **key identifiers** passes unconditionally and forever, since a minisign key id is never also an Arweave address — the checker would report success having compared nothing. That is why §2.2 point 1 demands the operator mapping first, and why an unmapped key is **refused rather than skipped**: it is not outside the check, it is invisible to it. Three populations, not two (a monitor operator who is also an ArNS controller is watching their own repoint), while attestors may overlap release signers. An **empty population is reported separately from a clean separation** — disjoint *for want of members* is a different claim, and `--strict` refuses it. §4.2's single-key ANT custody is a launch blocker the registry surfaces before any ceremony. `compare` deliberately **does not exist yet and says so** (it needs a published keyring and FE-P7's gateway behaviour); a verification tool that returns OK having verified nothing is the failure this repository keeps designing against. **Minisign verification landed 2026-08-06** (`app/tools/verify-release/minisign.ts`), and it closed a `valid` boolean **nothing produced**: `countReleaseSignatures` counted §1.4's floor over `{ keyId, generation, valid }` while that third field was the caller's word — a signature check that defaults to whatever the caller believes, the `admitIntent`/`admitEvidence`/`admitSnapshot` shape for the fourth time. `releaseSignatureFrom` is now its only honest producer. **The load-bearing rule is the second signature**: a `.minisig` carries two Ed25519 signatures over *different* messages — the primary over the artifact (or its BLAKE2b-512 digest under the `ED` tag) and the **global** one over `primary ++ trusted_comment` — and the trusted comment is covered by nothing else, while being the only part a person reads to decide *what* they are trusting. Skip the global check and every file check still passes with that claim unauthenticated: anyone holding a validly signed artifact can restate the comment as anything. The refusal **names which signature failed**, and `ReleaseSignature.why` carries the reason into the rejection list, because *"the signature does not verify"* would send an operator to check bytes that are intact. An unrecognised algorithm tag **refuses** rather than defaulting to a scheme this code implements. **The oracle is the other implementation** — every case runs through `tools/monitoring/attestation_monitor.py` as well and the two must agree, two parsers and two Ed25519 stacks (OpenSSL vs pure-stdlib RFC 8032), which is the only available check on the *reading of the format* given minisign is not installed here. **The mutation run found a hole in the suite rather than in the code**: deleting either packet-length check left everything green, because a *short* packet fails further down anyway — the case the guard really carries is the **over-long** one, where base64's permissiveness plus `subarray(10, 74)` would verify a signature file with bytes appended *identically to the original*. 8 mutations, **0 survived**. **The two-environment run is not remaining, and this row said it was until 2026-08-08 (F27's audit).** `ci.yml` carries a required check literally named *Two-environment byte-identical release (12 §1.1, INV-FE-10)*: the `desktop-shell` job is the second environment — it checks out to `second-environment/`, installs into its own store, and builds the release tree because `src-tauri/build.rs` cannot link without it — and `release-reproducibility` compares the two manifests file by file. The stated axis is the **absolute build path**, which is deliberate rather than incidental: pnpm's virtual store lives in the project, so every emitted relative path encodes the store layout, and the comparator **fails when the two manifests agree on every recorded axis**, so deleting that one line turns the gate red instead of quietly making it a repeatability check. This row kept listing the run as external for four days after it became a required check, which is the decayed-park pattern rather than a wrong fact — a park is a claim and it needs re-reading, not repeating. **Remaining:** the key ceremony and `SIGNERS.md`'s human mirror (people and organizations — §1.4 gate 2 counts attestations *by organization*, so one operator cannot reach the floor), and `compare`'s fetch half (live gateways). Both external. **2026-08-08 — that sentence was half decayed, and this is the second time this row has said "external" about something buildable.** `SIGNERS.md` did not exist anywhere in the repository, and only the **names** were ever external: the document, its schema, its bidirectional checker and its fail-closed empty-state reporting were all buildable, and they now ship (`SIGNERS.md` at the repository root, `tools/deploy/check-signers.py`, 30 tests, wired into `ci.yml`'s `docs` job beside `check-ops-handbook.py`). The part that matters at **zero entries** is that the checker binds the document's populations, entry schema, floors, disjoint pairs and seated counts to `POPULATIONS` / `ENTRY_KEYS` / `SIGNATURE_FLOOR` / `ATTESTATION_FLOOR` / `checkControllerQuorum` / `DISJOINT_PAIRS` and to `signers.json` — every extractor **raises** rather than comparing two empty sets, so a registry that describes nobody cannot read as agreement. `--strict` refuses an empty population outright, restating §2.2's own point that *disjoint for want of members* is a different claim. `compare` was the other half and it was **partly** true: the live gateway call is genuinely external and is one four-line function, while the fetch loop, the byte comparison against the signed map, the cross-gateway divergence check, minisign verification, the counting and the verdict are all decisions over bytes and now run per commit against a constructed transcript (`app/fixtures/gateway-transcript/`, whose README says constructed rather than recorded, and why). The old refusal also cited *"a published keyring"*, which was a **refusal rather than a gap**: with no keyring the floors count over zero and the verdict is `MISMATCH` by counting. **One real defect fell out**: `countAttestations` took no keyring, so §2.3's explicitly named *"attestation counting"* could not exclude a **revoked** key and §5.2's *"against the current keyring generation"* had no field to read — while the sibling implementation `attestation_monitor.py` does exclude them, so two implementations disagreed and only one was right. The keyring is now a required parameter. The registry schema gained `organization`, `generation` and `revocationIndex`, each with a consumer, and refuses unknown fields (`organisation` would silently mean *independent of nobody*). Verification: 172 `tools/deploy` tests, 377 `tools/ci` tests, 169 `tests/release`, 31 `test:verify`, doc-link and PLAN-table gates, every `app/` gate listed in the report; `compare` reaches all four outcomes end to end including exit **3** for *matched, with unchecked conditions*, which §2.3 requires rather than a silent pass. **38 mutations, 0 survived** — the first sweep had 2, both real gaps in the suite and both closed (a blank holder on **both** sides matches itself; a non-2xx response carrying the **correct** bytes must fail on status rather than on content). **Remaining: the ceremony itself, the real names and keys, and `liveGateway`.** Nothing else
