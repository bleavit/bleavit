## Question

**Two §6.3 table-2 rows lack a defined observable.** (a) "update missing 600 blocks after repoint": no on-chain observable marks the repoint block — O5 anchors the lag at the first finalized head where the gateway-majority ArNS target diverges from `ReleaseChannel.manifest_txid`. (b) Served-state window: "window < 30 d on the joint fleet" has no defined aggregation over per-operator retention — O5 alerts on `max(per-operator retention) < 30 d` (the joint window, since all windows end at now), leaving per-operator sub-alerts to O3. Confirm or correct both operationalizations.

## Status

**resolved 2026-07-20 (B5 ratification; both operationalizations confirmed, (b) with an honesty correction).** 12 §6.3 now carries both. (a) The repoint lag is anchored at the first finalized head where the gateway majority and `ReleaseChannel.manifest_txid` **disagree**, since no on-chain observable marks the repoint block; ratified with the detail the row omitted — the clock also starts when the gateways reach *no* strict majority, deliberately, because an inconsistently resolvable name is not healthy. (b) The joint window is the **maximum** per-operator retention, valid precisely because every window ends at now; per-operator shortfalls above that floor belong to the bootnode program (§6.2). Correction: the row says O5 "alerts on" it — the rule exists but `bleavit_bootnode_served_state_retention_days` is an **O3 seam with no producer**, so `max()` over an empty vector cannot fire. The spec fixes the rule; O3 still owes the feed. `deploy/monitoring/README.md` corrected to say so.
