## Question

**The competing-venue security gate cannot resolve the threshold it is stated against, and the artifact now says so rather than implying otherwise.** 15 §4.9's criterion is per-class decidable-harm false-pass **< 1 %**. At the affordable sample the arming rung carries **PARAM 12**, TREASURY 75, META 91, CODE 98 decidable-harm proposals, so the smallest non-zero rate each class can express is **8.3 %**, 1.3 %, 1.1 % and 1.0 % — every class `gate_is_all_or_nothing`. A published `0.000000` therefore means *'no false pass observed'*, never *'rate measured below 1 %'*, and for PARAM it cannot distinguish a true 5 % rate from zero. This is why the block publishes a `resolution` object and why the composite `arming_ready` boolean was **removed** rather than renamed: a gate that is really a screen must not be consumable as a measurement (see the Decision log). Reaching genuine sub-1 % resolution needs ≳ 100 decidable-harm proposals per class at the arming rung; PARAM's decidable-harm fraction is ≈ 4 %, so that implies ≈ 2,400 PARAM proposals — i.e. the **full population at every rung**, roughly 4 × the primary run (~8 h) on top of it. Is a screen the intended standard for a Phase-4 arming input, or must the arming evidence be a full-population run at each rung? The direction of error matters: a screen that reports clean while under-powered is optimistic, which is the unsafe direction for a gate

## Status

**open** — a cost/rigour ruling, not an implementation question; the machinery to run it at full population already exists and only the wall-clock is at issue
