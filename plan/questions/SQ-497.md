## Question

**The welfare pallet's whole-state mirror makes every mutation O(state), and cohort settlement repeats an identical computation once per proposal.** Two costs with one cause. (a) `Pallet::persist` removes and re-inserts *every* spec set, snapshot and (since SQ-493) snapshot context on each mutation, so adding one snapshot writes ~80 keys; SQ-493's parallel map moved `record_snapshot`/`record_daily_gate`/`register_spec` writes 60 → 80 (+33 %) for one added entry per retained snapshot. (b) `Pallet::compute_settlement` runs once per settled item and reloads the whole state each time, then — under 07 §10 — recomputes the identical `(W', W')` pair, because `epoch-core` enforces a single `metric_spec` for the whole cohort (`TryStateViolation` if they differ). Measured cost of (b): `settle_cohort`'s per-proposal ref_time 517 → 677 µs (+31 %); affordable at ~2 % of the normal-class block budget at the cohort bound, which is why SQ-493 shipped without hoisting. Both are efficiency, not correctness: settlement mutates no welfare state, so the repetition is provably redundant rather than semantically load-bearing. Candidate fixes: a diff-based `persist`, and hoisting the drop set + recomputed pair to once per `settle_cohort` call through the `CoreWelfareOps` seam.

## Status

**✅ resolved 2026-07-26 (batch X)** — both legs implemented, both measured. **(a) `persist` writes the difference**, not the whole mirror: `record_snapshot` 102 r / 80 w → **104 r / 6 w**, `record_daily_gate` 98 / 81 → **99 / 6**, `register_spec` **77 w → 2 w**. The trade is +1–2 reads for ~75 fewer writes, and the reads are nearly free because `load()` already iterated all four maps in the same call — only a key being *created* costs a genuinely new read. Equality is decided against **stored** state rather than against `pre`, because the core → stored conversions change representation and comparing core values would be comparing something other than what is written. **(b) the settlement recompute is hoisted** to once per `settle_cohort` batch via a batched `WelfareOps::compute_settlement` taking the targets — passing the *targets* rather than the score is what keeps 05 §6's rule intact (epoch can request a settlement, never choose its score). Per-proposal ref_time slope **711 → 363 µs** (−49 %); worst case at the `n = 12` cohort bound **11.30 → 7.71 ms** (−32 %), the one-time whole-state load moving from the slope into the intercept (2.77 → 3.35 G). Below n = 2 the batch is marginally dearer, which is the shape a hoist has and is harmless. No behaviour change: `settle_cohort` already wrapped the whole batch in one storage layer, so collapsing the per-target layers changes nothing a caller can observe; the 07 §10 core events now deposit once per batch, matching the one computation they describe
