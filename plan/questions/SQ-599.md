## Question

**P-14's *"round open"* precondition cannot be evaluated by any client, because 02 freezes no field saying whether a round is already challenged.** `oracle_core::Oracle::challenge` enforces `ensure!(r.counter_value.is_none(), Error::AlreadyChallenged)`, and `open_oracle_rounds()` keeps returning a round after somebody has challenged it — so a canonical client shows a live Challenge control on a round whose next challenge is guaranteed to revert. The fact exists in state (`RoundState.challenger`, `RoundState.counter_value`) but §7.2 says the FE reads the `OracleRoundView` projection rather than that struct, and the projection carries neither. **02 §4 already anticipated exactly this and ruled the obvious substitute out**: `escalated` is `round > 1`, *"MUST be false for a round-1 report even while that round has a live challenger, and MUST NOT be interpreted as 'currently challenged'; any future view of that distinct fact requires a separately named field."* So the surface half is a named 02 §4 addition, not an interpretation of an existing field. Same shape as SQ-580 — a client read docs 10/11 mandate that 02 never froze — and the reason `check-client-surface-obligations.py` exists; it did not fire here because §11.5's P-14 row says *"round open"* in prose and names no `Pallet.Item`

## Status

**open — raised by Codex review on PR #248 and verified against `oracle-core`.** The unsafe reading is the tempting one: `escalated` is present, looks like the answer and is normatively *not*. Until a field exists the client must state that it cannot establish the condition rather than implying it holds — the `bondUnknown`/`uncheckable` device this console already uses twice (SQ-564, SQ-598) — because a Challenge button that silently reverts teaches the user nothing about why.
