## Question

**May a live indexer's `specVersion` be compared against this client's, and with what consequence?** 10 §8.5.2's route table said `GET /chain` served *"the compatibility check before any range read"*, and no section defines such a check — the phrase is removed rather than guessed (F24, 2026-08-07). The answer is not derivable, because the analogous comparison is **forbidden** one section away: §6.3 refuses to compare a *snapshot's* `spec_version` on the ground that §6.4 assigns snapshots history predating the current runtime, so comparing would refuse every deep snapshot after the first upgrade. An indexer is different in a way that may or may not matter — its live binding is current, while the ranges it serves may span several runtimes, so the version it reports describes the server rather than the rows.

## Status

**resolved 2026-08-07 (§8.5.2)** — **read and display, never refuse.** The §6.3 analogy was the wrong axis: it forbids the snapshot comparison because §6.4 gives snapshots history predating the runtime, which does not carry to an indexer whose reported binding is current. The comparison fails for a simpler reason — **it would protect nothing.** A page is a §8.2 document, self-describing JSON with canonical decimal-string amounts, so a client decodes one **without runtime metadata** and a version difference cannot make a page unreadable. That is exactly what separates this from 10 §13.1's exact-equality rule over the three *handoff* formats, each of which describes one block and **is** decoded against runtime metadata, where an undecodable version really does make the document unreadable. Refusing here would deny history over a difference that changes nothing. Both fields travel and render as an advisory line — the treatment `admitSnapshot` already gives a snapshot's versions — and §8.5.3's probe answers on `genesisHash` alone, now because that is the whole of what matters rather than pending this row
