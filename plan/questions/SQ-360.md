## Question

**09 §6.1 and §5.2 disagree about whether a cap refusal may re-create a remote-keyed trap.** §6.1's trapped-assets row states absolutely that, with both caps enforced at the mint leg, "no cap refusal can produce a remote-keyed trap at all". But §5.2's mint-step scope (SQ-253) exempts trapped-imbalance reconstruction from the prospective gate and requires "the beneficiary deposit leg of any recovery [to remain] fully metered by both keys" — so an **inbound** `ClaimAsset` from Asset Hub against an over-cap beneficiary necessarily fails at the deposit leg and re-traps under Asset Hub's origin. The implementation follows §5.2 (the barrier's pre-mint gate deliberately skips programs whose only USDC source is `ClaimAsset`, because a refusal there returns the assets to the trap they came from and strands nothing *new*). Which sentence governs — does §6.1 need a recovery carve-out, or does §5.2 need a pre-mint gate for recovery too?

## Status

**resolved 2026-07-24 (ratified as implemented)** — §6.1 gains an explicit recovery carve-out. Its absolute sentence now bounds **new** stranding: an inbound `ClaimAsset` recovery whose beneficiary is over the per-account cap refuses at the metered deposit leg and returns the holding to **the same trap, under the same origin**, so nothing is stranded that was not already trapped. That is exactly why the barrier skips the prospective pre-mint gate for `ClaimAsset`-only programs — a refusal there would consume the trap entry while yielding no holding. No behavioral gap existed; the code was right and the text was absolute where it should have been scoped.
