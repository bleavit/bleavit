## Question

**CodeQL alert 19 is alert 18's structural twin in the `Instance1` differential, and the SARIF shows why a source-targeted code fix would not hold.** `rust/cleartext-logging`, **high**, sink at `pallets/conditional-ledger/tests/instance1_differential.rs:121` — the `assert!(std::hint::black_box(false), "{message}")` inside `fixture_failure`. Pulled the analysis SARIF rather than reading the summary line, and the flow is exact: `program.params.protocol_accounts.iter()` (:936–939) → `.map(|name| account(name))` (:940) → `fn account`'s `other =>` fallthrough (:183) → `fixture_failure`'s `message` (:120) → `panic_fmt` (:121). So the "sensitive information" is **the label of a holder the corpus does not define**, printable only if `ledger_fee_scenarios[].params.protocol_accounts` ever names something outside `alice`, `bob`, `carol` — and across the committed corpus that field holds exactly **one string, `carol`**, in 1 of 11 rows, `[]` in the other 10. **Three facts make it the same naming false positive SQ-521 ruled on.** (1) The file carries **13 structurally identical fallthrough helpers** — branch, gate, scalar side, position kind, position family, two operation dispatchers, two error classes, worked row, error witness, sweep family — and only the one fed through a field matching CodeQL's `.*acc(ou)?nt.*` heuristic is flagged. Same shape 13 times, one alert. (2) Alert 18 in the frame-free twin has the **same two endpoints**: the `protocol_accounts` corpus field into the unknown-holder fallthrough (`holder()` there, `account()` here). This is one finding reported once per differential suite, the core's and the FRAME shell's, not two defects. (3) CodeQL classifies the instance `["test"]` and no test binary ships in the runtime. **The new evidence SQ-521 did not have: the reported source moves under a fixed sink.** Alert 18 was described at raise time as flowing from line 273's `string(args, "account")`; today's SARIF for that same still-open alert reports line 1028's `for account in &scenario.params.protocol_accounts`, with no intervening change to the helper. The alert is anchored to the shared `fixture_failure` sink that **many** name-matching fixture fields reach, so removing the one source the message happens to name re-anchors it to the next — the narrow code fix is not merely a contortion, it is **unreliable**. The reliable code fix is to stop interpolating fixture labels into failure messages across all 13 helpers here and their twins, which strictly degrades a normative differential suite's ability to diagnose a corpus/replayer mismatch (15 §4.4; I-37)
