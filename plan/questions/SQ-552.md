## Question

**The 09 §1.2 ↔ 11 §11.5 diff that both documents mandate does not exist, and it fails on five rows.** 09 §1.2's 13-item dispatch check list is "normative and canonical"; 11 §11.5 "MUST mirror it item-for-item"; 15's contract tests are said to diff them. Parsing both: 13 backend items against 14 frontend rows, nine one-to-one. Backend item 1 maps to FE 1–2; item 10 to FE 11–12; backend items 12–13 have no FE precondition; and **FE row 14 (`DescriptorLeadTime`) is an `apply_authorized_upgrade` precondition per 09 §2.2, not an `execute` one** — so it can wrongly block a valid `execute`. Separately, 09 §1.2(11) names `Rejected(BadPreimage)`, but `BadPreimage` is a `pallet_execution_guard::Error` and **not** a member of the frozen `RejectReason` set: that terminal state cannot be constructed, the runtime returns `Err`, and the proposal stays `Queued` until T15 `Expired` — so clients may treat a still-live queued mandate as terminal. One further row: 05 §5.5's `Valid fail` publishes `HurdleNotMet` where normative §5.4 returns `ConvergenceFailed`. **Ruling needed:** add the variant to the frozen set (contract bump) or change the disposition

## Status

**Resolved 2026-08-03 (F6), four rulings.** **(1) The mirror is over checks, not items.** 09 §1.2 items 12–13 are *dispatch* and *record* — the effects of passing, with nothing to pre-check — so the FE mirrors items **1–11**, and two of those deliberately expand into two rows each (BE 1 → queued/window; BE 10 → gate flags/dead-man). 11 backend checks, 13 frontend rows, and the 15 §4.x contract test diffs checks to checks over the stated mapping rather than list lengths; a length diff could only be satisfied by inventing frontend rows for effects, which is how a client acquires a precondition the runtime does not have. **(2) FE row 14 deleted.** 09 §2.2 binds `DescriptorLeadTime` to `system.apply_authorized_upgrade`, where `authorized_at` is the block of `UpgradeAuthorized` — which the guard emits *as a result of* a successful `execute`. At `execute` dispatch the timestamp does not exist for that proposal, so the row was unsatisfiable or reading an earlier authorization's clock; it could block a valid `execute`. Its home is §11.8.4, tightened at the same time to read the stored **`PendingUpgrade.applicable_at`** rather than re-derive it: §2.2's SafetyFilter denies on that field, and a client re-deriving it from a separately-read registry value would refuse or admit on a number the filter is not using. **(3) `Rejected(BadPreimage)` → the disposition changes, not the frozen set.** Verified against the shipped runtime: `RejectReason` has no such variant, and `pallet_execution_guard` returns `Error::BadPreimage` inside `with_storage_layer`, so the run rolls back and the proposal stays `Queued` until T15 `Expired`. 09 §1.2(11) now says that — the same correction SQ-163 made to item 4, for the same reason: a dispatch-time check that *errors* is not a transition. One difference is now stated for clients, because it is the one that misleads: a malformed preimage is **permanent** where an unpassed referendum is transient, so the mandate is doomed while its on-chain state still reads `Queued`. Recording it terminally instead — which item 7's own retry-bounding reasoning would favour — needs a `RejectReason` variant and therefore an integration-contract bump plus runtime work, so it is **left open as SQ-578** rather than smuggled into a frontend milestone. **(4) 05 §5.5's `Valid fail` row was wrong in two directions.** §5.4 evaluates steps 6–8 and dispatches on the **triple**; the row treated them as short-circuiting. With 6 and 7 disagreeing the engine returns **`Extend`** (or `SecondExtensionFailed`), not a hurdle rejection at all; with 8 also failing it returns **`ConvergenceFailed`**, because an unconverged series is not evidence the hurdle was genuinely missed. `HurdleNotMet` is correct only for `full_pass = tail_pass = false ∧ converged`. One row replaced by five.
