## Question

**The runtime exposes a second permissionless upgrade-apply door that the specification never describes, and the client will have to choose between them.** 09 §2.2, §2.4 and §7 and 11 §11.8.4 step 5 name exactly one call — `system.apply_authorized_upgrade(code)` — and 09 §2.2 describes its gating as *the SafetyFilter consults `PendingUpgrade` and denies `apply_authorized_upgrade` while `now < applicable_at`*. The runtime implements that (`direct_system_upgrade_allowed`, which reproduces every artifact-dependent guard precondition) **and also** ships `ExecutionGuard.apply_authorized_upgrade` (call index 1): likewise `CallDomain::Public`, likewise carrying the full image, performing the same checks in-pallet and then forwarding to the frame-system call. The second door appears nowhere in `docs/architecture/`, so it has no R-2 trace, and 02 freezes neither call. **It is not redundant.** An ineligible submission through the system door is a *filter denial* (`CallFiltered`, opaque); the guard door returns `DescriptorLeadTime`, `UpgradeHashMismatch` or `UpgradeVersionMismatch` — genuinely better for an operator surface whose whole job is telling a user why a signature would fail. That is a good reason to keep it and a bad reason to leave it unwritten. **Ruling needed:** name the guard door in 09 §2.2 beside the system one with the error-surface difference stated; decide which call 11 §11.8.4 step 5 tells the canonical client to submit (the typed-error one is the better operator surface; the system one is what the spec says today); and decide whether either belongs in 02's frozen call surface — the same question SQ-577 asks of the calls 10 §5.2 names. **The class defect this row was found through is already fixed** (V-136): both doors are `Operational`, so what is left is diagnostics and documentation, not capacity
