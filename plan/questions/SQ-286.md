## Question

Should an active `PB-LEDGER-FREEZE` **force-reject `Queued` proposals, or let them wait the freeze out**? SQ-98 fixed the *disposition* (tick and decide now agree: T20 `ProcessHold` + par void) but deliberately left the *swept set* as shipped, which includes `Queued` and `FailedExecuted`. Two spec texts pull the other way: 06 §6.3 scopes the effect to "decision windows overlapping a freeze", which is a trading-side notion that does not obviously reach an already-adopted mandate; and 09 §1.2(10) gates `execute()` on "no active PB-LEDGER-FREEZE", which reads as *queued items wait* — a gate that is near-vacuous if the sweep destroys them first (it survives only as a same-block belt-and-braces check). G-1 cuts both ways: force-rejecting is status-quo in the sense that nothing executes, but it also destroys a legitimately adopted decision because of an unrelated ledger emergency, and the freeze is bounded (≤ 14 d + one renewal) so waiting is feasible if grace windows are extended. A coherent reading exists — sweep the trading-side states (their books are frozen, so they genuinely cannot produce decision-grade signal) and let execution-side `Queued` items wait — but it needs a grace/maturity extension mechanism for freezes that does not exist today (the dead-man has one; a freeze does not). **Second, adjacent, sub-question found while fixing SQ-98:** the freeze sweep in `tick` sits *before* the dead-man/recovery no-op (`crates/epoch-core/src/lib.rs:1456` vs `:1475`), so a freeze coinciding with a dead-man pause or a recovery epoch force-rejects live proposals — contradicting both that block's own comment ("in each case tick is a no-op ... never decided or force-rejected") and the SQ-90 ratification that recovery holds transitions. With SQ-98's fix `decide` refuses with `BadPhase` during recovery while `tick` still destroys, so the outcome converges on tick rather than diverging, but the precedence between the two emergency regimes is unstated in 05 §4.8 and 06 §6.3 and should be ruled with the scope question.

## Status

**resolved 2026-07-20 (ratified as shipped; delegated ruling).** Both halves ruled, both normative in 06 §6.3 now. **Sweep scope:** the freeze sweep covers every live non-terminal state, `Queued` included. Force-rejection *is* the status quo (the payload does not dispatch either way), and letting a mandate wait would need maturity/grace extension machinery that exists only for the dead-man (05 §4.8), not for a freeze — without it a waiting mandate just expires mid-freeze, the same terminal outcome reached later and with a worse bond disposition. 09 §1.2(10) is **not** left vacuous: the keeper sweep is per-proposal and bounded, so between activation and the sweep reaching a given mandate there is a real window in which `execute()` must refuse. **Precedence:** the freeze wins over a concurrent dead-man pause. The two answer different failures — the dead-man is a *liveness* pause that preserves state, `PB-LEDGER-FREEZE` a machine-checked *solvency* anomaly (I-4 drift) in which backing is in doubt — and a stalled clock is not a reason to keep live proposals standing over a possibly-unbacked ledger. This is the shipped ordering (`crates/epoch-core/src/lib.rs`: the sweep precedes the dead-man hold), so the code comment added with SQ-98 is now backed by spec text. No code change.
