## Question

**10 §5.2 names calls as part of `CRITICAL_SURFACE`, and doc 02 freezes no calls at all.** Raised while building F4's compatibility classifier. 10 §5.2 defines `CRITICAL_SURFACE` as \"every storage item, event, **call**, constant and runtime API the app uses\", and 10 §3.2 makes `restricted` mode's signing **per-surface** — whose unit, for signing, is exactly the call. But doc 02 has no extrinsic section: its frozen surface is APIs, view types, events, storage, constants and identity, and `tools/release/surface-manifest.json` accordingly carries 0 `call` entries against 222 others. App-code rule 7 requires `CRITICAL_SURFACE` be generated from that manifest and never hand-listed, so there is nothing to generate a call surface from and nothing to probe one against. **Consequence, and the interim behaviour taken:** `callIsProven()` answers `false` for every call outside `full` mode. That is INV-FE-12's reading — an unproven capability is *absent*, and absence disables the dependent surface with a named reason — and the alternative (permit every call in `restricted` because none is *known* broken) would sign against a call surface that was never checked. It is fail-closed, and it is also a placeholder: a real `restricted` mode is supposed to keep the compatible half of the app signable. **Two readings.** (a) 02 is right to freeze reads only — the call surface is metadata-checked by PAPI at encode time, so it needs no separate contract, and 10 §5.2/§3.2 should say `CRITICAL_SURFACE` covers reads while per-surface signing is decided by the encoder. (b) 02 is incomplete — the calls the app signs are as much a frozen contract as the storage it reads, and the manifest should gain call entries with their argument layouts (which F6's transaction builder needs regardless). Reading (b) has force: the per-surface signing gate is a *safety* control, and delegating it to encode-time failure means discovering incompatibility after the user has committed to a transaction. Resolve during **F6**, whose builder needs the layouts either way; the placeholder's own test asserts the manifest still has no `call` kind, so closing this question fails that test rather than leaving the placeholder behind
