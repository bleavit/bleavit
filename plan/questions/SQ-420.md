## Question

**The epoch→welfare tick seam now carries more than its name says, and the `tick` weight does not price it.** SQ-201's bounded epoch-roll prune was wired into the runtime's `WelfareSettlement::prune_xcm_traffic` impl because that is the only seam `pallet_epoch::tick` already invokes on every successful roll — deliberately, so no `pallets/epoch` change was needed on a branch that does not own that pallet. Two residuals: (a) the trait method's name in `pallets/epoch/src/lib.rs` is now stale and should be renamed to something neutral (e.g. `roll_maintenance`), which is a cross-cluster edit; (b) `tick`'s generated weight predates the added prune and understates it by up to `EPOCH_ROLL_PRUNE_MAX_EPOCHS` epochs of bounded key removals plus the snapshot/gate/sampled-day key scans, so the B5 benchmark for `pallet_epoch::tick` must be regenerated before release. Neither affects correctness — the work is bounded (I-20) and the retained set is unchanged — but (b) is a real PoV/weight understatement.

## Status

**resolved 2026-07-24** — half the row was already stale. **(b) is false at HEAD:** `pallet_epoch::tick`'s generated weight does *not* predate the SQ-201 prune — it records `Welfare::XcmTrafficEpochs (r:1 w:1)` and `Welfare::XcmTraffic (r:512 w:512)`, and 512 is exactly `EPOCH_ROLL_PRUNE_MAX_EPOCHS` (2) × 256 days, so the benchmark measured the prune and there is no PoV understatement and nothing release-blocking. **(a) is real and done:** the epoch→welfare seam is renamed `prune_xcm_traffic` → **`roll_maintenance`**, with the contract stated at the trait — it began as an XCM-traffic prune and is now the general roll-maintenance hook, because it is the only seam `tick` already invokes on every successful roll, so naming it for one callee misdescribed it. `pallet-welfare`'s own concrete `prune_xcm_traffic` keeps its name: that one *is* accurately named for what it does.
