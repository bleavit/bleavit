## Question

**10 §8 mandates a *provider UI* and 11 §11.2's screen inventory does not contain one, so the surface that carries §8.4's normative disclosure has no id, no route and no presence obligation.** §8.4 states the depth limit *"is disclosed in the provider UI"*, §8.1 requires accepting a suggestion to be *"an explicit user action with a disclosure"*, and §8.3's closing sentence describes an all-providers-down state a user is shown — three obligations attached to a surface. Doc 11's inventory has 22 rows, S1–S22, and none of them is it; the only non-`S` row the client carries is `confirm`, which §11.3–§11.4 own by section. The consequence is mechanical rather than cosmetic: **11 §11.2 constraint 1's *"present, reachable and complete"* rule is scoped to the inventory**, so a provider UI that is never built, or built and never routed, violates nothing and `app/tests/screens`' count cannot see it — and `PENDING_SCREENS` is keyed by inventory id, so the surface cannot even be *declared* as pending with an owner. F23 built the surface (2026-08-07) and deliberately did **not** add a row to `SCREENS`: that table is bound to doc 11's own parsed inventory, and inventing an id there would be this client writing a normative row into a document. A ruling should say whether the provider UI is an inventory screen (an `S23`, with an area, a placement and constraint 1's presence obligation), a section-owned surface like `confirm`, or a settings surface deliberately outside the inventory — and if the last, what makes its absence detectable
