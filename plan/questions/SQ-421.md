## Question

**A keeper-unsampled gate window has no *automatic* VOID trigger — recovery is late re-sampling or a manual guardian `PB-ORACLE-VOID`.** SQ-79 makes gate settlement refuse a cohort whose e+1 or e+2 carries no daily observation (correct and status-quo-safe: nothing settles, no claim is created, G-1 holds). Its 05 §4.7 disposition points at 07 §10's "a failed gate input VOIDs affected cohorts", but 07 §10 itself says the *oracle-driven* VOID trigger for on-chain inputs arises only via R-adjacent determinism failures or `PB-ORACLE-VOID` — a day nobody recorded raises no oracle deadline/no-report/quorum event, and the runtime's automatic `oracle_deadlock` trigger is unfed outside benchmarks (`configs.rs` `RuntimeGuardianTriggers::current`). So the only *wired* recoveries are (a) a late `record_daily_gate` of the missed epoch — the common transient case, which clears the refusal — and (b) for genuine permanent data loss, a **manual** guardian `PB-ORACLE-VOID`; until (b) fires the cohort holds an I-21 non-terminal slot. Is the manual guardian path (plus late-sampling) the intended resolution, or should 05 §4.7 / 07 §10 name an automatic settlement-deadline VOID for a keeper-unsampled gate window? Overlaps SQ-233 (unfed trigger feeds) / SQ-251 / milestone B15.

## Status

**resolved 2026-07-24 (stale — verified against HEAD)** — the row's load-bearing claim is false: the automatic detector exists and is production-fed. `pallet_epoch::settle_cohort` computes `gate_deadlocked` from exactly the row's condition (`!gate_window_sampled(e+1) || !gate_window_sampled(e+2)`), latches `PendingOracleVoids`, emits `OracleDeadlockLatched`, and `RuntimeGuardianTriggers::oracle_deadlock(epoch)` reads that map in production — the benchmark arm only *adds* a constant. Late `record_daily_gate` clears the latch automatically (`OracleDeadlockCleared`). So the shipped lifecycle is three-part: **auto-latch → auto-clear on late sampling → guardian `PB-ORACLE-VOID` for genuine permanent loss** — and 05 §4.7 already documents exactly that under its own "SQ-79/SQ-421 resolution, 2026-07-23" paragraph. What is deliberately *not* automatic is the destructive VOID itself, because no mechanism can distinguish a late keeper from permanently lost data; the I-21 slot is bounded by `MAX_NON_TERMINAL_COHORTS_BOUND` at latch time. No amendment and no code owed.
