## Question

**The cohort-escrow exposure fold is unweighted on two money-bearing calls.** `StakeAtRisk`/`Exposure` walk `pallet_epoch::CohortSchedules` and up to five `pallet_conditional_ledger::Vaults` per schedule — bounded at `MAX_NON_TERMINAL_COHORTS` (4) × 5, i.e. **≤ 28 reads** counting the twice-walked `has_exposure` pre-pass. Neither consumer's generated weight measures it, because the runtime's `runtime-benchmarks` impls return a fixture *instead of* walking: `oracle::report` declares 87→492 reads and `registry::file` declares **87**, so the omission is up to **~32 %** on `file`, well past the 15 §4.5 10 % regression threshold. **Pre-existing on `report` since SQ-174** (which is when `stake_at_risk` stopped being a two-valued sentinel and started reading vaults) and newly applicable to `file` under SQ-296. Partially mitigated 2026-07-25: the registry fixture now *executes* the fold and discards the result, so a benchmark reaching that arm measures the walk — but it remains behind `has_exposure`, so the fix is incomplete. Closing it needs the runtime benchmark setup to **seed the worst case** (4 cohorts × 5 vaulted proposals) for both calls and the generated weights regenerated from a real benchmark run; a hand-written addend is the fallback if seeding proves impractical, but the number must be derived from the 13 §4 bounds and stated as derived, never as measured. Understating dispatch weight on a permissionless call is a block-capacity DoS surface (R-7), so this blocks SQ-296's closure.

## Status

**resolved 2026-07-25 (A12)** — the fold is measured, not estimated, and the estimate would have been wrong. Worst-case exposure (4 cohorts × 5 vaulted proposals) is now seeded through the existing `prime_epoch` benchmark seam and **both** fixture short-circuits are gone, so `frame-omni-bencher` measures the walk. Three findings the regeneration produced that no green gate could: **(1)** this row's own derived \"≤ 28 reads\" was an under-estimate — the raw measurement was 32, so the hand-written addend this fix deliberately avoided would have shipped a still-understated weight while looking rigorous. **(2)** The two registry instances share one `WeightInfo`, and only the Incident fixture had been removed, so Incident measured 119 against Milestone's 99 — and `--unsafe-overwrite-results` let the 99 overwrite the 119, silently restoring a 20-read undercharge on the live path. Both arms now walk the fold. **(3)** `challenge_filing` rose 12 reads without touching the fold: `RegistryParams::bond_bps()` was routing one value through the 12-key `OracleParams` aggregate, so every aggregate-loading call paid 11 wasted `Constitution::Params` reads. Fixed to a single-key read with the same helper and default, which also revealed the fold's true cost is **21** reads, not 32. Final: `file` 87→108, `challenge_filing` 80→81, `crank_close` 88→89, `report` 492→515. **Two of the three acknowledged regressions were already on main and both are mine:** `reserve_probe_result`/`crank_reserve_probe` omit `Epoch::Schedule`, `Welfare::XcmTrafficEpochs` and `Welfare::ReserveProbeDaily` — the last added by SQ-195 in PR #159, merged with the *declared* pallet weight adjusted and the *generated* runtime weight left stale. Each ack carries its own reason rather than one blanket justification. Exhaustive gate exit 0; weight regression PASS WITH ACKNOWLEDGEMENTS.
