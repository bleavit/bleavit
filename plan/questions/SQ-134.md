## Question

**02 §12 writer field-scoping is ambiguous.** `constitution.set_release_channel` (writer (b)) accepts an arbitrary 168-byte value and can therefore overwrite the guard-owned pending fields (offsets 112–120, flag bit 2) . Is the per-writer field enumeration **normative** (⇒ `set_release_channel` must preserve guard-owned offsets) or informative? **Hardened 2026-07-17 (final verify + PR #65 bot P1):** both guard clears — abort AND applied — are now tolerant (a mismatched channel is left untouched as writer (b)'s newer authoritative value; guard state still clears), so a mid-flight rewrite can no longer wedge `PendingUpgrade` on either path; regressions `relay_abort_cleanup_survives_a_writer_b_release_channel_rewrite` + `applied_cleanup_survives_a_writer_b_release_channel_rewrite`. Residual: a rewrite still erases the FE-visible pending display until the ruling lands.

## Status

resolved 2026-07-21 (batch C, contract v6) — **the batch's highest-severity ruling; text and code landed together.** 02 §12's self-contradiction is fixed by ruling offset 112 `spec_version` to be the **currently installed** runtime version, always, never the target — the direction the field exists for, since a stranded metadata-less reader uses it for runtime compatibility. Field ownership is now **normative**: the guard exclusively owns offsets 112–119 and flags bit 2; `set_release_channel` MUST preserve them and now *merges* rather than replacing the whole record. The guard's three occasions are enumerated exhaustively (authorize / applied / **relay abort**, which §12 omitted), the clears are unconditional on the guard's own pending state, and the content predicate that latched them is deleted. New **I-30** binds `PendingUpgrade.is_some()` ⟺ `pending_authorized_at != 0` ⟺ bit 2, enforced in try-state; 09 §2.3's "neither writer exclusive title" statement is reversed. §12's risk text is corrected too: writer (b) could previously **suppress a live pending upgrade**, not merely raise a false banner. **The row's own claim was overstated and is not ratified:** the phantom was persistent-until-next-write, not permanent — writer (b) could clear it directly and a later authorization overwrites it. All eight combinations of (`PendingUpgrade`, `pending_authorized_at`, `URGENT_UPGRADE`) were reachable; the shipped regressions covered only the zero-pending arm, so tests for both bad directions were added.
