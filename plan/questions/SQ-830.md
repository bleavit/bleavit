## Question

**INV-FE-9 has no status for a value this user chose, so a selected account renders under a badge that names an external tool.** 10 §5 lists *"a selected account"* among the chosen values that *"can never be represented as verified"*, and 10 §2.1 gives exactly one answer for a chosen value displayed as a data item — `external-proposal`, *"the bottom of the lattice"*. That answer was written for the handoff path, where the value really was authored elsewhere, and the in-bundle badge copy says so in as many words: *"A value an external tool asked for."* Applied to the account a user picked in their own wallet, that sentence is false in the opposite direction to the defect V-183 repaired — the badge no longer over-claims, it misattributes. The client renders such an account in S20's panel subject and will render more of them as the composition roots land. Three dispositions are available and only the first is free: widen the `external-proposal` badge copy to cover any value the client did not read (a `ui` copy change plus the 10 §2.1 sentence behind it); add a seventh status for a locally chosen value (an INV-FE-9 enumeration change, 15 §2 and D-21 — the same weight as the amendment that added `external-proposal`); or rule that a chosen account is chrome rather than a data item and render it unbadged (which puts an unlabeled string on screen and needs INV-FE-9's "no unlabeled rendering path" narrowed in writing). **Nothing ships wrong today**: no composition root supplies this datum yet, so the status is chosen only in `app/tests/screens`
