## Question

**At the shipped `pol.budget_epoch` the chain cannot fund a CODE runtime upgrade at any NAV.** 08 §5.3's Ask-scaled `pol.b` is what §5.4(a) calls "the one that holds", and composing it with §3's commitment and §4.4's shrink-to-fit makes commitment/budget → **1.6233485828** for CODE and **1.3808096786** for META; at §5.4's own worked CODE point it is 189,577.34 against a 103,972.08 budget, so the proposal is dropped every epoch. Not upgrade-specific — a maximum lawful TREASURY ask carries the same slope (fundable 684,616.09 against an outflow cap admitting 1,250,000 at NAV 25M). The smallest budget that funds CODE at all is **1.2175115 %**; at the 1.5 % kernel ceiling it funds above 7,361,153.03 NAV. **Two further §7/§4.4 findings ride this row:** shrink-to-fit is a greedy bond-priority prefix rather than a packing, so adding one META to four PARAMs above every §4.1 floor cuts funding **4 → 1** while four still fit (exhaustive over 756 cases; **4 → 0** with a scaled CODE upgrade); and §7's closing "every path costs five figures per epoch" is wrong by **12.8×** — five earlier-PID PARAM entries blank an honest PARAM slate for **500 USDC/epoch** from two funding accounts, and two consecutive epochs take the honest proposals terminal via T6 then T26. **Ruling needed:** is the commitment charged at the scaled `b` or the floor `b`, and if scaled stands, what must `pol.budget_epoch` become?
