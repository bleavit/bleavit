## Question

**R's welfare binding + definition conflict (blocker-driven):** 05 §4.3 defines R as the fail-static trigger flag while 07 §8 defines `R_daily` = per-probe-day pass/fail with "absence is never healthy"; a binding reading the current `ReserveUnhealthy` latch is **fail-open** (no probe ⇒ healthy; latch trips only at 2 consecutive fails; recovery rewrites history). v1 therefore binds **X only** and leaves R unbound — a spec set registering R fails the crank status-quo-safe, like the other pending C_onchain inputs; the A8 v1 `MetricSpec` registration must exclude R until a day-resolved probe-outcome store exists (or that store must be specified). Which value enters the daily C flag, and where does the store live?

## Status

**resolved 2026-07-25 (A12/A13)** — the row's blocker (an inert probe feed) closed with SQ-380, so the ruled store is now implementable and implemented. `ReserveProbeDaily` is a bounded `(epoch, day) → bool` map keyed exactly like `XcmTraffic`, sharing its epoch index and retired by the same cursor-bounded walk (I-20/I-21). An oracle `probe_outcome` seam fires on **every scored slot** — success response, error response, folded timeout and folded no-attempt slots — with day attribution through the established `xcm_traffic_epoch_and_day` precedent. The `R` binding honours the row's own fail-destructive warning exactly: it is **unavailable before `ReserveProbeArmed`**, because scoring absence as 0 on an unarmed chain would set the C breach flag out of a mechanism that never ran; once armed, 1 on a recorded pass and 0 otherwise, since 07 §8 has no benefit-of-the-doubt branch. A failed day stays failed, so recovery is never retroactive. **Normative gap closed:** 07 §8 defines only `R_daily`, but 05 §4.4's settlement-time `C_e` needs an epoch-level `c_j` — the projection is the **minimum over recorded days**, the only aggregation consistent with §8's fail-static rule, since any averaging would let a passing day mask a proven-unreachable reserve. **Vacuity guard (2026-07-25, found by inspection rather than by the suite):** `expected_days = epoch.length / BLOCKS_PER_DAY` is **zero** wherever an epoch is shorter than the frozen 14,400-block day — which the default-off `fast-timing` build produces, since it compresses `MIN_EPOCH_LENGTH_BLOCKS` while `BLOCKS_PER_DAY` stays frozen. `passed >= 0` would then report an epoch healthy with **no probe recorded at all**. Release timing never reaches that branch, but a compressed drill runtime would have been handed false confidence, so the expected count is floored at 1 and `sq195_sub_day_epoch_still_requires_a_recorded_pass` pins it (verified to fail without the floor).
