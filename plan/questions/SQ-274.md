## Question

**The 09 §3.2 migration-failure control surface (`[VERIFY]`) does not exist, so the PB-MIGRATION drill cannot run.** Drill 06's `force-failure`/`retry` branches dispatch `migrations.force_failure`/`migrations.retry`, but upstream `pallet-migrations` exposes only `force_set_cursor`/`force_set_active_cursor`/`force_onboard_mbms`/`clear_historic` and B6 added no drill control calls — and without a forcible failure the `MigrationHalt` trigger can never go live, so the guardian playbook activation correctly refuses `TriggerInactive` (first execution 2026-07-18 proved the whole 5-of-7 workflow up to that refusal). Options: (a) a bounded Root-only drill-control extrinsic in the runtime (R-7 concern: a production runtime carrying a force-failure surface); (b) re-spec the drill to stage a genuinely stalled MBM via `force_set_active_cursor` + B6's >900-block stall detector (SQ-132 bridge — no new calls, but ~90 min of stall per run, **and** the SafetyFilter classifies the migration-admin calls as D-13 nobody rows — `CallFiltered` bare and under every wrapper incl. sudo — so (b) additionally needs an authorized staging route or a filter ruling; adversarial-review catch); (c) a non-release test-runtime feature (violates 15 §5 "against exactly those artifacts"). Drill 06 is re-gated on this SQ meanwhile (release-tier, so evidence stays fail-closed with attribution).

## Status

**RESOLVED 2026-07-20 (G1, decide-yourself ruling).** No production `force_failure`/`retry` surface — option (a) rejected (R-7: the release runtime must not carry a fault-injection surface); a real stuck FRAME cursor trips the MBM lockdown that pauses the very guardian workflow the drill exercises, so option (b) is unsatisfiable (the B12-flagged tension); a test-runtime feature violates 15 §5, rejecting (c). Resolution: the drill stages the guard trigger `pallet_execution_guard::MigrationHalt=true` at genesis via a new benign `pallet-execution-guard` **`migration_halt` genesis field** (defaults false; drill spec stays PLAIN so the pinned zombienet schedules the para — a raw storage-injected spec is not schedulable), decoupled from a live cursor so extrinsics flow and the guardian calls dispatch. **Passed end-to-end 2026-07-20 (3/3):** `assert-halt` verifies the staged trigger (storage-key self-checked); the guardian 5-of-7 recovery runs `propose_action` + four `approve_action`s and the dispatching approval **correctly fails closed** — the runtime's `playbook_calls(Migration)` returns `DispatchError::Other("PB-MIGRATION cursor retry has no EmergencyPlaybook-safe runtime call")` (retrying a stuck cursor needs Root-only controls; fabricating Root would widen the EmergencyPlaybook origin, R-7). With the trigger ACTIVE this is `Other`, distinct from the pre-SQ-274 `TriggerInactive` (trigger never engaged) and from a successful activation (none exists — the freeze arm is the automatic halt-source bridge, the retry/rollback the ratified expedited-CODE lane). The 09 §3.2 [VERIFY] is thereby confirmed: pallet-migrations' native controls are the (correctly D-13-filtered) surface; the `force-failure`/`retry` legs are undemonstrable-by-design and removed.
