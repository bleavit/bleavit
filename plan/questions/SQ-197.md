## Question

**`phase3.*` caps are structurally ordinary META+values params (adversarial F5):** 09 §5.2 mandates "raised only by phase gates", but generic `set_param` accepts the class origin, both rows are `0..=u128::MAX` with no Δ/cooldown, and META's `SetCapability` chain could raise a cap to the unbounded sentinel outside a phase-advancement upgrade — containment-weakening. Should `set_param` refuse `phase3.*` during Phases ≤ 3 (PhaseFlags-gated), or should the caps move to a phase-transition-only monotonic writer? Lowering (tightening) is the safe direction and remains legal today.

## Status

**resolved 2026-07-24** — the wave-1 backout's premise was **false**: a phase-transition writer does exist (`transition_phase_four`, via `apply_phase_four_plan`'s ordinary `set_param`), so the caps were never permanently un-raisable. Implemented per 09 §5.2 without foreclosing 13 §115: `set_param` refuses an **increase** to `phase3.tvl_cap`/`phase3.dep_cap` while PARAM is unarmed (Phases ≤ 3) with the dedicated `PhaseCapRaiseRefused` — deliberately **not** `BadOrigin`, since the origin is authorized and only the value direction is not. Lowering (tightening) stays legal at every phase (G-1), and from Phase 4 the row behaves exactly as 13 §115's sentinel note describes, which is how the Phase-5+ sentinels are installed. `transition_phase_four` now writes the arming bits **before** applying its cap plan, so its scheduled raise passes the same ordinary gate every later amendment does rather than needing a carve-out — all inside one storage layer, so no observer can see the ordering.
