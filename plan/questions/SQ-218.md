## Question

**`epoch_status()` hydrates the whole epoch aggregate for a 7-scalar view.** The read goes through `pallet_epoch::epoch_state()`, which loads all proposals, cohorts, the 32-entry ring, resource locks, rollovers and params (~130 storage reads) to produce a ≤128 B view 02 §3 calls O(bounded-collection) — correct, but this is the most-called view (countdowns/phase headers) and every read enters the `chainHead_call` proof a light client downloads (D-6). Worth a narrow `status_view` reader over `EpochOf`/`Schedule` + the three flags?

## Status

**resolved 2026-07-24 (code).** Added the narrow pallet reader over `EpochOf`, `Schedule`, Guardian dead-man state and the two Constitution flags, with a frame-free projection that keeps the existing boundary arithmetic. Runtime `views.rs::epoch_status` uses it; core and pallet parity tests cover all eight phases, and the full runtime view regression remains green. No contract or network change.
