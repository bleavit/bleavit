## Question

**Snapshot retention with no settleable cohort:** the spec ties the full welfare prune to cohort reap only; after ~20 consecutive cohortless epochs snapshot recording jams at the window bound (and `SampledGateDays` grows meanwhile), ultimately tripping the dead-man. Is an epoch-roll prune of snapshot/gate state not referenced by any live cohort intended (analogous to the B4-residual XCM-traffic roll prune), or is a 20-epoch cohortless stretch out of scope?

## Status

**resolved 2026-07-21 (A12).** Prior disposition: batch **X**; **RULED 2026-07-21 (batch X)**, code owed. Verified: this is a deterministic liveness failure, not idle storage — a long cohortless interval never exercises the full welfare prune, so snapshot recording reaches its hard bound and wedges. **Ruled: authorize bounded epoch-roll pruning** of welfare state unreferenced by any live cohort — on each roll retain every epoch the bounded live-cohort set needs and prune older unreferenced snapshots, breach flags and sampled-day state. The spec must define the protected set and pruning ownership before implementation; declaring long cohortless periods "unsupported" was rejected as a chain wedge dressed as a constraint. Verified: `pallets/epoch/src/lib.rs:1206` is the sole `T::Welfare::prune` caller and sits inside `settle_cohort` behind the cohort-reap branch, while the tick path (`:1067`) drains only XCM traffic — so a cohortless epoch is unreachable by cleanup. Spec first: 05 §3.3 gained the pruning-ownership paragraph fixing the protected set to the *existing* `current - 19` window, so the roll path can retire nothing reap would have kept. `pallet_welfare::prune_epoch_roll` implements it — cursor-bounded at `EPOCH_ROLL_PRUNE_MAX_EPOCHS` (I-20), oldest-first, snapshot-deadline epoch protected — wired from the runtime `prune_xcm_traffic` seam that tick already calls every roll, so **no `pallets/epoch` change was needed**. No storage item added or reshaped, so no migration. Pre-fix behavior captured verbatim: 120 cohortless rolls grew gate history to peak 120 against a bound of 20, and the 21st snapshot failed `TooManySnapshots`.
