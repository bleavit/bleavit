## Question

**`reconcile_insurance` was the only sanctioned permissionless keeper crank that paid no rebate.** Raised as P2 by the #196 round-4 Codex review. 08 §6.3's closed decision-critical list puts every *other* sanctioned permissionless keeper crank on the ≤ 20 % general tranche and names reap/dust sweeps explicitly; this crank was omitted, which mattered more once SQ-518 made it the sole backstop for the un-interceptable direct-transfer case

## Status

**resolved 2026-07-29 (milestone E4).** `reconcile_insurance` now calls `do_keeper_rebate(&who, CrankClass::General)` when `overflow_insurance()` returns a **non-zero** surplus. The `> 0` condition is the orphan-Baseline precedent from the same section — a crank requests a rebate only when it changes state — so the idempotent no-op at or below target stays unrebated and repeated cranking cannot drain the meter. Mutation-proven in both directions: removing the rebate fails the middle assertion, and dropping the `> 0` condition fails the first, which is the half that actually needed a test. **Weights regenerated, and the fixture was under-measuring.** I shipped the rebate without regenerating `pallet_futarchy_treasury`, and CI's `benchmark-smoke` caught it — correctly, and at the cheap 2x1 fidelity, because `reconcile_insurance` is a **constant-weight** function and those are hard-gated at any fidelity. That is the case AGENTS.md says a per-commit run does catch, working exactly as designed. Regenerating then exposed a second, subtler defect in the fixture itself: it seeded the surplus but not the keeper meter, so `do_keeper_rebate` short-circuited and the run charged the rebate's parameter **reads** with none of its payout **writes** (`FutarchyTreasury::State` appeared as `r:1 w:0`). Adding `prime_keeper_rebate()` — the established pattern the other rebating treasury cranks already use — moves writes 4 -> 8 and ref_time +46.7 %. Final: reads 5 -> 17, writes 4 -> 8, PoV 7,404 -> 26,846. No acknowledgement is required because the crank was introduced on this branch and has no merge-base baseline to regress against. Verified at CI's own fidelity: `--check --steps 2 --repeat 1` PASS
