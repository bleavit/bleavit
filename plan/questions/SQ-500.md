## Question

**The guardian's per-block maintenance hook settles an unbounded-by-design 128-review sweep against a weight declaring roughly one-sixth of it, and the fixture that should have caught this excludes its own worst case.** `run_maintenance` (`pallets/guardian/src/lib.rs:1755`) collects every review matching `!ratified && !recall_scheduled && epoch > deadline_epoch` and settles each one in its own storage layer: `restore_due_review_fronting` (`ReviewFrontingOf`, `ReviewReferenda`, `VetoReviewReferenda`) then `settle_failed_review` (`ReviewFrontingOf`, `VetoReviewReferenda`, `FailedActions`, `Members`, `PendingBondReleases`, plus up to `GUARDIAN_THRESHOLD` bond slashes) plus a `load`/`persist` pair and its events — **at least 10 storage reads per overdue review**, and `reviews` is bounded at `MAX_REVIEWS = 128`. The saturated case is not hypothetical and not rare: `deadline_epoch = current_epoch + review_deadline_epochs` (`crates/guardian-core/src/lib.rs:798`), so **every review created in one epoch shares one deadline** and all of them fall due in the same block. A council that proposes and approves 128 actions inside one epoch therefore chooses which block carries a >= 1,280-read hook — and a captured council is precisely doc 14's threat model, so this is adversarially reachable, not merely a tail. The declared `on_initialize` weight is the hand-written fallback envelope **220 reads / 150 writes / 1.95 ms**, short by roughly 6x. Two further findings in the same hook: the sweep opens with `VetoReviewReferenda::iter_keys().collect::<Vec<_>>()`, a full map scan into an allocation whose size is storage-determined and whose cost is not in the declared 220 either; and the benchmark that exists (`pallets/guardian/src/benchmarking.rs:349`) fills `ReviewDeadlines` to `MAX_REVIEWS` but sets `ratified = true` on every filler, which the overdue filter excludes — so it measures **one** settle and its comment calls the saturated case "unreachable fronting records for 128 simultaneous failures", which the shared-deadline derivation above refutes. Found while discharging SQ-490 item (4)'s owned follow-up ("extend the guardian `on_initialize` benchmark to the saturated sweep"); that framing is **wrong and is superseded here** — extending the fixture alone would only make the undercharge visible, and charging the true saturated weight would hand a mandatory per-block hook a large slice of the block. The fix is runtime-code rule 3: bound the settles per block with defined overload behaviour (cursor + remainder to the next block, the idiom the epoch and oracle cranks already use), which also bounds the `iter_keys` scan, then benchmark the bounded batch at its worst case and drop the `tools/ci/generated-weight-overrides.toml` entry. Needs 06 §5.1 text for the bound and its overload behaviour, a 13 §1/§2 home for the batch bound, and its limit-coverage key. **Do not regenerate `pallet_guardian` before this lands** — it would replace the 220-read envelope with the one-settle measurement and make the undercharge worse.

## Status

**✅ resolved 2026-07-26 (batch X)** — implemented, and the row's *mechanism* was wrong in a way worth recording: the §5.2 per-epoch allowances (delay-once 2, force-rerun 1, pause-intake 1 per 4 epochs) mean a council cannot in fact approve 128 actions inside one epoch. `SuspendOnGate` carries no allowance and the epoch clock can advance several indices in one crank, so the saturated case stands — but it is reached by accumulation, not by one epoch's burst. New 13 §2 kernel bound `GuardianMaintenanceBatch` = 10, **derived**: the count the allowance-capped powers *can* bring to one shared deadline (2 + 1 + 1 + one activation of each of the six playbooks). A 128-review backlog drains in 13 blocks. The batch **rotates** behind a `MaintenanceSweepCursor`: settling is what drops a review out of the overdue filter, so a fixed `take(10)` would re-select one prefix forever and a batch-wide prefix of reviews that cannot settle (a stuck deposit refund) would suppress every review behind them permanently — a skip wearing the shape of a carry (Codex P2, correct). **The measurement corrected my framing twice.** First: "weight-neutral" was true of three dimensions and false of the fourth. Second, after Codex's P1: the fixture reused one approver set, and *which* seats approve decides how many settles can fund a recall referendum from the slash pool — reusing funds two, rotating funds six. The rotated fixture measures 105 r / 110 w / 125,304 B / 6.08 ms against 100 / 101 / 125,304 / 5.63 ms, i.e. the first fixture understated a *mandatory* hook by 5 reads, 9 writes and 8 % of ref_time. Against the hand-written 220 / 150 / 183,055 B / 1.95 ms it replaces, the bound *lowers* storage and PoV and *raises* ref_time to a measured 0.30 % of the 2 s block. Overload **carries the remainder, never skips** (06 §5.4, new normative paragraph): dropping a due review forfeits an accountability action, deferring one only delays a slash. The `VetoReviewReferenda::iter_keys()` map scan is gone — the snapshot is now built from the already-loaded pending set, which is what the core actually asks about, and is bounded by `MAX_PENDING_ACTIONS`. `reap_failed_actions` is bounded by the same batch behind a `FailedActionReapCursor`, because hash-order iteration plus a plain `take(n)` would re-examine one prefix forever and starve the rest — a bound that looks correct and silently reaps almost nothing. Benchmark fixture rebuilt to saturate both batches; `tools/ci/generated-weight-overrides.toml` entry dropped
