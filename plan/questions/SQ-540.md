## Question

**Six external-outflow findings from the first exhaustive sweep of every path that moves protocol funds to a non-protocol account.** Beyond SQ-538/SQ-539: (a) **the ORACLE-line rebate is genuinely unmetered** — 11 crank sites (reporter `report`/`challenge`/`counter_report`, watchtower `ack_observed`, registry filing/challenge), bounded only by the funded line, with no `oracle.budget_epoch` analogue of `keeper.budget_epoch`, no exhaustion latch and no alarm; the sweep judged it the clearest 08 §10.1 omission (extends SQ-533). (b) **Proposer rewards and collator compensation bypass the reserve-health haircut** — 08 §1.2 sets spendable NAV to 0 under the `R` flag with **exactly two** named carve-outs (coretime, reserve probe); the code has **four**. (c) **250M VIT community vesting** is reachable through a *PARAM*-class decision with no per-epoch cap or NAV gate — **RULED NOT A DEFECT 2026-07-31.** 08 §2.2 already calls `create_community_schedule` "the one bounded exception to the ordinary treasury-outflow origin" and enumerates its purpose-built control set; the code implements all six bounds exactly (Phase-4 armed start, beneficiary ≠ pot, `amount ≥ min_vested_transfer`, `amount ≤ remaining`, `count < MaxCommunitySchedules`, `per_block > 0`), with the vested transfer executed **before** the remaining allocation is decremented. "Escaping every treasury control" is the same category error as (a): the NAV-based rolling caps are USDC-outflow controls and VIT is marked 0 in NAV *by design*, so the allocation gets a finite-pot + lifetime-count bound instead of a rate bound. One non-obvious property worth recording since the spec states it only implicitly: because the only size bound is `amount ≤ remaining`, **a single schedule may take the whole remaining allocation** — deliberate (§2.2 says "no greater than the stored undistributed allocation"), and each one still needs a passed PARAM decision. (d) **POL T13 rerun top-ups** double a book's `b` with no `pol.budget_epoch` charge — **half ruled, half fixed 2026-07-31.** The uncharged top-up is not a defect: 08 §4.4 states it normatively and defends it (`delayed_once`/`rerun` are one-way flags, so exposure is structurally bounded at 2× rather than budget-bounded). **The surviving half was real and is now closed**: §10.1's divergence row is the `rerun_fraction = 0` corner and nothing said so, so the published cost base understated by up to its own divergence row. Divergence is `b·[ln2 − H(p)]`, linear in `b`, so a fully rerun slate costs **+18,830 USDC/yr = +17.2 % of `C`**, cutting the zero-revenue runway 34.3 → **29.2 yr**; at the 12-collator ceiling `C` reaches 188,986 and the runway **19.4 yr** under the cheap coretime policy. Modelled (`pol_divergence_with_reruns`, 4 tests) and labelled in §10.1. An understated `C` flatters every runway figure, which is the reason this mattered at all. (e) **XCM `TakeRevenue = ()`** — the chain charges incoming XCM at the governed 13 §1 rates and then **discards** the payment; foregone income, which for a `R(V) ≥ C` criterion is the same distance from the crossover as avoidable cost

## Status

**resolved 2026-07-31 (E7) — all five disposed: (a) ruled not a defect, (b) ruled + spec corrected, (c) ruled not a defect, (d) half-ruled + the surviving half modelled, (e) implemented. Three of the five did not survive contact with the owning spec section or the code; the sweep's value was the two that did.** (a) was built — an `oracle_meter` mirroring the keeper meter, core + pallet compiling — and then **withdrawn on reading the owning spec text**, which already answers it: 08 §1.1's normative *Where per-line budgets bind* says each line's per-epoch budget is enforced by its consuming mechanism and that "lines carrying a `[VERIFY]`-gated budget in 13 §1 are **allocation-only** until Phase-2/3 ops sizing", and §10.6 lists the `ORACLE` line among the eight "not sizeable from any evidence in this repository". So the funded balance *is* the specified bound, an `oracle.budget` value would have been fabricated against an explicit refusal to size it, and metering buys no cost reduction — governance controls refills either way. The sweep's "clearest omission" ranking was wrong because it compared against `keeper.budget_epoch` without checking why the ORACLE line has no counterpart. **(b) RULED 2026-07-31: the code is right on both paths and §1.2's "exactly two" was the defect — but they are right for DIFFERENT reasons, and the sweep's "enumerate four" framing would have lost both.** **Collator compensation is a third maintenance carve-out**, on D-9's own wedge logic one layer down: unpaid collators stop authoring, an unauthored chain runs no reserve probe, and the flag could then never clear — the coretime carve-out keeps a core, this one keeps something willing to use it. Bounded to the dedicated `COLLATOR` pot exactly as the probe carve-out is bounded to its line. **Proposer rewards are NOT a carve-out**: they are a crystallized obligation belonging with the "existing stream claims are unaffected" clause §1.2 already carries. Decisive check, and the same one that caught two P1s on the collator work — is a refused payout *deferred* or *lost*? `mark_executed` calls `let _ = do_proposer_reward(...)` one-shot and discards the result, deliberately, so a valid payload is never retried forever. Gating it on the flag would therefore **destroy** the reward, not defer it: a proposer would forfeit permanently over a reserve condition they neither caused nor can influence, which is the opposite of the direction G-1 and R-7 require. Landed in 08 §1.2 with both rationales and pinned by `the_reserve_haircut_still_pays_collators_and_proposers_and_08_1_2_says_why`, which asserts the flag genuinely blocks discretionary `spend` first so the two positives cannot pass vacuously. **(e) QUANTIFIED 2026-07-31 and it is material — 206 inbound messages/day covers the entire launch cost base.** Every input is anchored in-repo: `UnitWeightCost = (10⁹ ref-time, 64 KiB proof)` per instruction under `FixedWeightBounds`, and the 13 §1 rates 50 USDC/s + 5 USDC/MiB, giving **0.3625 USDC/instruction** and **1.45 USDC** for a minimal four-instruction inbound reserve transfer. Break-even **206/day** at the launch base and **321/day** at the 12-collator ceiling; 100/day is already ≈ 48 %. Landed in 08 §10.2 as the third instrument with both caveats stated — the level is a property of the *weigher* (the flat 64 KiB proof term is **86 %** of the fee, so benchmarked bounds would cut it materially, and the model asserts that split so a weigher change cannot silently invalidate the claim), and the volume is market behaviour the protocol does not control. **IMPLEMENTED 2026-07-31.** The first attempt used `mint_into`, which **adds USDC issuance** and was caught by `production_xcm_remote_keyed_trap_…`. Two non-obvious requirements it missed, both found by tracing where the money would actually land: (i) the sink is the AssetTransactor's `deposit_asset` into the treasury `MAIN` custody account, **and** (ii) it must be paired with `Pallet::credit_main(amount)` — the existing `PendingMainCredit` seam, already used by the transaction-fee caller — or the revenue lands in the pot, never reaches `main_usdc`, and therefore **never appears in NAV at all**, which is the only place a runway benefit could show. Doing (i) without (ii) also trips the §6.3 pot-vs-line drift alarm. DOT-denominated fees take (i) only, since 08 §1.2 marks DOT at 0 in NAV. Routing through `CappedInflows` consumes 09 §5.2 inflow-cap budget, which is arguably correct (it is a real asset movement) and cannot regress today's behaviour, since a refused deposit drops the fee exactly as `()` already does. **Shipped as `bleavit_xcm::trader::FeesToTreasury<Assets, TreasuryMainLocation, TreasuryXcmFeeCredit>`**, bound through `XcmConfig`'s own generic `Assets` so the capped production executor and the recovery executor each route through the transactor they already use. Three library tests (USDC deposits+credits, DOT deposits only, failed deposit recognizes nothing) and the runtime trap-recovery regression rewritten to assert *where the fee went* rather than that it vanished. Gates: workspace `cargo test` green (**417** runtime, **62** bleavit-xcm), fmt + workspace clippy clean. **Two things this deliberately does not do, recorded so they are not mistaken for oversights.** (1) The `Drop`-time deposit and counter write are outside the XCM weigher's accounting — the same position upstream's own `XcmFeesToAccount` occupies, and comfortably covered by `FixedWeightBounds`' 1 ms + 64 KiB per instruction, but it is unaccounted weight and should be revisited if the weigher is ever tightened to benchmarked bounds. (2) No spam concern is introduced: paying real USDC to raise treasury NAV is a donation, not an attack, and the phase-3 caps still bind
