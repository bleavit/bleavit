## Question

**CodeQL `rust/cleartext-logging` fires high-severity on a differential-test helper, and it is a naming false positive — but the repo has no CodeQL waiver mechanism.** Alert 18 on `crates/conditional-ledger-core/tests/differential_vectors.rs:143`, "This operation writes account to a log file", introduced by `1f81a31` (E2/E3/E4) and blocking #196's `CodeQL` check. **The evidence that it is spurious is conclusive and structural.** That line is `other => panic!("unknown vector holder class: {other}")`, the fallthrough of a three-arm match over the literals `alice`/`bob`/`carol`; the taint source is line 273's `string(args, "account")`, a JSON key in the committed vector corpus. The file contains **seven structurally identical helpers** — `unknown branch`, `unknown gate`, `unknown scalar side`, `unknown position kind`, `unknown position family`, `unhandled vector operation`, `unknown Python ledger error class` — and **only** the one whose field happens to be named `account` is flagged. Same shape seven times, one alert: the query is keying on the identifier name, not on any property of the data. CodeQL classifies the instance itself as `["test"]`, the values are three hardcoded labels in a public committed fixture, and the binary never ships in the runtime. **Why the code fix is the wrong answer**, having considered it: removing the interpolation would make one of seven identical helpers strictly worse at diagnosing a corpus/replayer mismatch, for a reason no future reader could infer from the code — and renaming the `"account"` field is not available either, since that key is part of the shared vector schema the reference model writes (changing it means regenerating the corpus to dodge a heuristic). Contorting code to satisfy a false positive is precisely what this repo's annotated-waiver culture (`ghsa-waivers.toml`, `generated-weight-overrides.toml`, `weight-preservation.toml`) exists to avoid. **Why it is not simply waivable either:** CodeQL here runs under GitHub **default setup**, which has no in-repo config file, and inline `// codeql[rule-id]` suppressions are honored by the CodeQL CLI/SARIF path but **not** by default setup (github/codeql#11427, #9298; the `advanced-security/dismiss-alerts` Action exists to bridge exactly this gap). So the two mechanisms that would actually clear it are both repo-administration acts: dismiss alert 18 as a false positive, or move CodeQL to **advanced setup** with a config excluding test paths — the latter also giving the repo a reviewable, in-tree waiver surface consistent with every other gate here

## Status

**resolved 2026-07-29 — alert 18 dismissed as `used in tests`; and my first recommendation was wrong, which is the part worth keeping.** The user delegated the call, and working it through reversed it. I had recommended **advanced setup with test paths excluded** on the grounds that it is durable and prevents the next spurious alert. That reasoning ignored what it costs: excluding test paths permanently blinds CodeQL to an entire category of code **across the whole repository** in order to settle one naming false positive. Dismissing a single alert is surgical, reversible, uses the mechanism GitHub designed for exactly this, and **preserves full scanning coverage on test code**. For financial infrastructure the narrow action is the safer one, so the broad remedy was the worse remedy — I had ranked durability above blast radius. It also avoids touching a default-setup/branch-protection surface mid-PR, where a check-name change could have blocked every PR in the repo, but that is a secondary benefit and not the reason. **Reason chosen deliberately:** `used in tests` rather than `false positive`, because it is the more precise of the two and it **self-invalidates** — it ties the waiver to a fact that would change (the code being a test) rather than to a standing judgement about whether logging an account is safe. If this helper ever moves out of `tests/`, the stated ground stops holding and the alert should be reopened; that is the property an auditor needs and a `false positive` dismissal would not give. The API caps dismissal comments at 280 characters, so the comment states the finding and points here: **PLAN.md is the durable in-tree record**, which is the same division of labour every other waiver in this repo uses. No code changed — see the seven-siblings argument in the question column
