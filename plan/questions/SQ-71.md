## Question

"milestone points ÷ **target**" (05 §4.4, 07 §7) gives `target` no numeric home in 05/07/13. A6 reads it from the frozen MetricSpec via `EpochContext::milestone_target` (a per-spec field, I-16) — is that the intended home, vs a 13 parameter? And is the `min(·, 1)` clamp normative?

## Status

resolved 2026-07-20 (batch B3), **with the row's central premise corrected.** *Ratified:* `target` is a frozen per-MetricSpec field, never a 13 key (a global tunable could retroactively renormalize milestones a live cohort is already measuring, against I-16), and the `min(·,1)` clamp is normative (05 requires component values in [0,1] before aggregation, and sibling metrics already write explicit clamps). 07 §7 gained a *Milestone normalization* note; 05 §4.3's A-pillar row now reads `min(1, milestone points ÷ target)` with the home stated. *Row corrected twice:* the cite is 05 **§4.3** (metric-set table), not §4.4; and "A6 reads it from the frozen MetricSpec" is **false** — `milestone_target` is an `EpochContext` **trait method** (`pallets/registry/src/lib.rs:128`), `MetricSpec` has no such field (`crates/welfare-core/src/lib.rs:152-171`), and the production adapter returns 0 (`runtime/bleavit-runtime/src/configs.rs:3920-3925`). Adding the field remains SQ-175's work. **New defect found:** a zero target yields aggregate **0.0** silently instead of rejecting (`crates/registry-core/src/lib.rs:729-731`), contradicting both `configs.rs:3923`'s own comment and SQ-175's text; 07 §7 now requires `register_spec` to refuse such a spec → **SQ-291** (X).
