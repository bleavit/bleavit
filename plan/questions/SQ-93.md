## Question

Apply-mechanism: 09 §2.2 says `apply_authorized_upgrade` is a permissionless **direct** `system.apply_authorized_upgrade` gated statelessly by the SafetyFilter reading `PendingUpgrade`, but I-10 / 06 §3.2 / 09 §2.1(3) limit internal Root to the **single** `authorize_upgrade`, while `.claude/rules/runtime-code.md` rule 6 says the guard has **two** allowlisted upgrade calls. A11 keeps a guard `apply` extrinsic (value-add hash/version re-derivation) but dispatches it **non-Root** (apply is permissionless in `frame-system`) so internal Root = `authorize_upgrade` only. B1a must reconcile the direct-vs-guard-wrapped mechanism (and whether the base filter enforces the lead-time on a direct call).

## Status

**resolved 2026-07-21 (batch X)** — **overtaken by B6.** Bare `system.apply_authorized_upgrade` is now dynamically admitted at descriptor maturity, while bare `authorize_upgrade` stays filtered and only the guard constructs its internal-Root dispatch. The guard wrapper survives as an alternative application path but no longer displaces the specified direct permissionless crank, which is what the row asked for. Sole residual is a misleading test name (`bare_system_upgrade_calls_stay_denied_when_guard_descriptor_matures`, whose body correctly asserts that apply *becomes* admitted) — tidiness, not protocol work.
