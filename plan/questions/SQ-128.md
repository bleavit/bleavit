## Question

09 §7.1 Phase-1 exit "Zombienet: 3 unattended epochs": at the 13 §1 default `epoch.length` = 302,400 blocks that is a ~63-day real-time soak (907,200 blocks); the only uncompressed route to floor-length 201,600-block epochs is an on-chain META decision after boot. Drill 09 targets 3 × the release default and is labeled the G1 long-soak. Is a genesis `Params` override to the 201,600 floor acceptable for the *local drill* profile (it is a legal 13 §1 value), or must the drill run at the release default?

## Status

**RULED 2026-07-20 (G1, user-selected).** The 63-day literal soak is both infeasible and redundant — G2 (Phase-2 Paseo exit) already requires ≥6 real epochs on a live Paseo testnet, which IS the release-cadence unattended-epochs evidence. Neither knob compresses it while running the exact release artifact: `epoch.length`'s kernel floor (`MIN_EPOCH_LENGTH_BLOCKS = 201,600`) is still ~42 days at 6 s, and the 6 s Aura slot cannot realistically go sub-second (Bleavit is fully block-denominated, R-2). **Resolution (split):** the G1 local drill 09 runs a **compressed machinery proof** via a feature-gated fast-timing test runtime (small epoch length + proportionally scaled kernel timing constants; real Aura+relay consensus; ~minutes; a documented test-only build, not the release binary) proving the epoch machine cranks 3 cycles unattended; the **release-cadence "3 unattended epochs" is subsumed by G2's ≥6-epoch Paseo run**. **IMPLEMENTED 2026-07-20 (G1).** A two-Explore-agent coupling audit showed the empty-progression drill needs a far smaller set than the ~15-constant pre-estimate: the default-off `fast-timing` cargo feature gates only two kernel floors (`MIN_EPOCH_LENGTH_BLOCKS`, `DECISION_WINDOW_FLOOR_BLOCKS`) and three `constitution-core` registry seeds (`epoch.length`/`dec.window`/`dec.trailing`), all derived from one knob `kernel::FAST_DAY_BLOCKS = 4` ⇒ `epoch.length = 84` (21 × FAST_DAY); forwarded `futarchy-primitives` → `constitution-core` → `pallet-constitution` → `bleavit-runtime`. `BLOCKS_PER_DAY` and every emergency/execution/oracle/dead-man window stay at production values — they cannot fire inside a 252-block drill, and `attack_cost_hat`/`t_dec` is never invoked with no proposals, so D-4 security economics are untouched. Each `cfg(not(fast-timing))` arm is textually identical to the frozen 13 §1 value; release-invariance is proven under default features by the `production_epoch_timing_floors_are_frozen` guard test, the unchanged `genesis_registry_matches_13_1_row_encodings` byte-assert + genesis-keys fixture, and the fact that `cargo test --workspace` never enables the feature. The wasm builds into a separate `target/fast-timing` dir (`generate-relay-specs.sh` → `bleavit-drill-fast.json` + `zombienet/networks/bleavit-fast.toml`); `chain-spec-builder --verify` re-runs `EpochParams::validate` over the compressed genesis. Drill 09 boots it and asserts three real epochs (`epoch.epochOf().index ≥ 3`, `epoch.schedule().length` read live) under genuine Aura+relay consensus with the keeper cranking `Epoch.tick`. Release-cadence "3 unattended epochs" stays subsumed by G2's ≥6-epoch Paseo run.
