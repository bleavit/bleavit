## Question

**Protocol-keyed trapped-asset recovery cannot pass proposal admission.** 09 §6.1 routes traps keyed to protocol/remote origins through a TREASURY-class `claim_assets` call; B10 wires and dispatch-tests the origin conversion and the trap/claim mechanics, but a real TREASURY proposal carrying `pallet_xcm::claim_assets` is unreachable: `derived_treasury_ask` rejects the call shape and the SQ-172 admission layer holds every non-empty payload. A zero-valued treasury-ask admission rule was deliberately NOT invented (beneficiary/outflow treatment is solvency-sensitive). Rule needed for the admission treatment of value-recovering (non-outflow) treasury calls.

## Status

**RESOLVED 2026-07-21** (batch X wave 2), jointly with **SQ-316** — same defect, one ruling, one patch. The row's "zero-valued ask still needs a ruling" premise is **stale**: doc 06 already rules recovery a zero-outflow Treasury action. The live admission defect remains, and its resource-lock identity was genuinely unspecified, so R-1 forbade inventing it in code. **Ruled: a new singleton canonical resource-domain family `0x0A` for XCM trap recovery** (05 §1.4) — recovery is rare, so serialising it is safe, and a singleton avoids the encoding/version aliases and truncated-hash collisions a per-trap key would risk under-locking. `derived_treasury_ask` accepts `claim_assets` at exactly zero while still rejecting all other unknown leaves. **Implemented:** wave 1's 05 §1.4 `0x0A` amendment is now in code — a singleton footprint arm in `runtime/bleavit-runtime/src/classifier.rs`, a zero-outflow `derived_treasury_ask` arm (the one admissible zero-outflow Treasury leaf; every other unknown leaf still fails closed), and the Treasury-only `leaf_enabled` arm. Regression: full submit→screen→qualify→queue→execute lifecycle test plus negative class, capability and mismatched-resource-declaration tests; all 5 failed pre-fix.
