## Question

**15 §4.5 names RustSec as the supply-chain mechanism, and RustSec has a demonstrated coverage gap.** §4.5 requires "a clean `cargo-audit` (RustSec) pass"; for crates.io the GitHub Advisory Database is a strict *superset*, so an advisory can exist with no RUSTSEC id and cargo-audit is then **structurally blind** to it — not misconfigured, blind. The worked example is live: of the 25 open Dependabot alerts, `yamux 0.12.1` / **GHSA-vxx9-2994-q338 (CVE-2026-32314, HIGH** — remote unauthenticated panic, one frame) has **no RustSec counterpart at all**, so the §4.5 gate is green and silent on it and always was. (Triage: not reached — every `sc-network` call site builds `yamux::Config::default()`, which `libp2p-yamux` maps to yamux **0.13**; the 0.12 path needs the deprecated `Config::client()`/`server()` constructors, used nowhere. Linked, never instantiated.) This session implements the minimal closure — a pinned `osv-scanner` leg gating **exactly** the complement (findings carrying no RUSTSEC id or alias), leaving everything RustSec covers to cargo-audit/`.cargo/audit.toml` so the lists never duplicate and the informational (`unmaintained`/`unsound`) classification is not lost; waivers are per-entry annotated and **expire mechanically** (a waiver matching no finding fails the gate — the SQ-155 discipline). Ratify this strengthened reading, or amend 15 §4.5 to name RustSec **+ GHSA/OSV** as the normative advisory sources.

## Status

resolved 2026-07-20 (batch B6): 15 §4.5 now names **RustSec + GHSA/OSV** as the normative advisory sources, with the partition rule and mechanically-expiring waivers. Ratified text is stricter than the row described: an alias confers coverage only if it is itself a RustSec record for the same package
