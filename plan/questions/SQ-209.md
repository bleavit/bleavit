## Question

**`RatificationStatus::Pending { referendum }` is unreachable, and "no referendum yet" has no spelling.** 06 §2.2(2) has the chain learn of a ratification referendum only when it *passes* (the scheduler dispatches `execution_guard.ratify`), so no on-chain record exists for an in-flight one. B2 therefore renders a ratification-requiring proposal with no record as the guard's fail-closed `Failed { referendum: 0 }` from submission onward — including Intake/Trading, where 06 §2.2(1) says the referendum legitimately may not exist yet. Conservative (and it replaced a genuine `NotRequired` defect), but neither variant means "absent". Should 02 §2 gain an `Absent`/`NotSubmitted` variant (pre-genesis), or is `Failed { referendum: 0 }` the intended encoding?

## Status

resolved 2026-07-21 (batch C, contract v6) — `RatificationStatus` is restructured pre-genesis to **`NotRequired`, `NoPassedRecord`, `Passed { referendum }`**. `Pending { referendum }` was **unreachable by construction** — 06 §2.2(2) has the chain learn of a ratification referendum only when it passes, so no on-chain record of an in-flight one exists — and freezing dead surface is worse than removing it before genesis. `NoPassedRecord` is deliberately agnostic between "none submitted", "ongoing" and "failed", because the guard's only write is the passing record and it **cannot prove** the stronger fact; that is why it is not named `NotSubmitted` or `Absent`. It replaces the shipped `Failed { referendum: 0 }` encoding, which rendered a normal Intake/Trading proposal as though its ratification had failed. The frontend derives the referendum lifecycle from `pallet-referenda`, as 11 already requires.
