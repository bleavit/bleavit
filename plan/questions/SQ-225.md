## Question

**No normative SCALE decode-depth bound at the guard's preimage `Decode` boundary.** `MAX_NESTED_LEVELS = 4` (06 §3.3) is a *post-decode* filter bound; the guard's `decode_batch` (`RuntimeBatch<T>::decode` over preimage-sourced bytes) had no depth limit, so a hash-committed ≤`MAX_BYTES` preimage encoding one deeply-nested call recurses in `Decode` until the wasm stack-height trap (native: abort) — a G-1/rule-1 violation in audit-scope-A code, surfaced by S2's decode-fuzz work and confirmed by both reviews. **S2 ruling (G-1 fail-closed):** added kernel `MAX_PAYLOAD_DECODE_DEPTH = 256` (substrate's conventional extrinsic decode-depth limit; ≫ the ≤4 semantic nesting, ≪ the stack budget) and switched `decode_batch` to `decode_all_with_depth_limit`; over-deep input → `BadPreimage`. Runtime regression `deep_preimage_batch_decode_fails_closed_at_the_depth_limit`. Should 09 §1.2/§2 pin the decode-depth invariant normatively (rather than leaving it an implementation detail)?

## Status

**resolved 2026-07-20 (batch B2 · ratified).** The spec was genuinely silent — no decode-depth bound appeared anywhere in 09, 13 §2 or 15 §4.5 — so 09 §1.2(11) now pins it normatively (depth limit `MAX_PAYLOAD_DECODE_DEPTH`, mandatory full consumption of the committed bytes, `Rejected(BadPreimage)` on violation, and an explicit statement that `MAX_NESTED` is a *post-decode* bound that cannot bound the decode), with a new 13 §2 kernel row so the 15 §4.6 / I-22 limit-coverage extractor can see the constant. Verified before ratifying: **all four** preimage-fetch boundaries route through the single depth-limited `decode_batch` — no second unguarded site — and 256 is not an invention but substrate's own `MAX_EXTRINSIC_DEPTH`, used by the SDK's preimage realize path; SCALE depth accounting is effective for every `RuntimeCall` nesting form via `Box`/`Vec` `descend_ref`.
