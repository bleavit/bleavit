## Question

**11 §11.8.2's *"power-specific forms"* reads as five call shapes and the runtime has one call with five argument sets.** The row says *"power-specific forms for `pause_intake`, `delay_once`, `force_rerun`, `activate_playbook`, `suspend_on_gate`"*, which a client can implement as five extrinsics or as one extrinsic over an enum. Reading the runtime settles it: `guardian.propose_action(power: GuardianPower, justification_hash: H256)` is a single dispatchable, and `guardian_core::GuardianPower` is an enum whose variants carry the fields — `PauseIntake { until }`, `DelayOnce { pid }`, `ForceRerun { pid }`, `ActivatePlaybook { id, trigger, expiry, target }`, `SuspendOnGate` (no fields). Two consequences the sentence does not carry: `suspend_on_gate` takes **no** arguments, so a generic form renders an empty one that reads as a load failure; and `ActivatePlaybook.target` is accepted by **only** the VOID playbook and rejected by every other, so a form offering it generally builds a call the chain refuses after signing. Client posture: `PowerArguments` is a discriminated union over the runtime's own field names, and `proposeFormBlocks` refuses a target on a non-VOID trigger.

## Status

**resolved 2026-08-07 (contract v29).** 11 §11.8.2 now says *one call, five argument sets*, and states the two things the old sentence lost: `SuspendOnGate` carries no fields, and `ActivatePlaybook.target` is accepted by the VOID playbook alone
