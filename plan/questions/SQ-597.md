## Question

**The only surface that can satisfy 10 §3.1's peer-count transitions is a deprecated JSON-RPC API reached through an escape hatch both vendors mark unstable.** Measured, not assumed (V-137): smoldot 3.3.2 serves `system_health` and returns the zero-peer reading `SyncDegraded` needs, and the new JSON-RPC interface spec — the one `chainHead_v1_*` belongs to — publishes **no** peer or sync-progress surface at all. So the client must either use the legacy API or leave the state unreachable. Both halves of the path carry an explicit warning. smoldot logs, on every call: *"The JSON-RPC client has just called a JSON-RPC function from the legacy JSON-RPC API (system_health). Legacy JSON-RPC functions have loose semantics and cannot be properly implemented on a light client… will be deprecated and removed in the distant future."* PAPI reaches it only via `client._request`, documented as *an "escape hatch" to allow access to debug endpoints… that are not spec compliant*, marked *"Unstable: The stability of this API is not guaranteed across minor versions."* **Ruling needed**, and the choice is real rather than rhetorical: (a) depend on it, and say so in 10 §3.1 with the dependency named and a pinned-version obligation, since an unstable API the release pins is a different risk from one it tracks; (b) drop the peer-count transitions and re-specify `SyncDegraded` on an observable the new API does publish — time since the last `chainHead_v1_follow` event, which is weaker (it cannot distinguish *no peers* from *a stalled chain*) but is spec-compliant and needs no escape hatch; or (c) both, with the legacy reading as an enrichment that may be absent. **This is not hypothetical drift**: the state is unreachable today because nothing emits `peers-lost`/`peer-acquired`, so whichever way it is ruled, code is owed. Note the asymmetry that makes (b) tempting and (a) honest — the diagnostics panel §3.1 specifies (*per-bootnode dial results, port-443 note, add-bootnode*) is peer information, so re-specifying the transition without peers would leave the panel describing data the client cannot obtain

## Status

**RESOLVED 2026-08-05 — ruled (a)+(c) and implemented.** 10 §3.1 gains a normative note naming the dependency, its pinned-and-gated mitigation, and the rule that an unreadable count is `indeterminate` and never zero; `packages/chain-client/src/health.ts` is the driver, and `check:smoldot-surface` is the bump-time gate. Option (b) was refused on writing it out: before `initialized` there are no follow events by definition, so a no-progress timer fires on every cold start slower than the window. V-138.
