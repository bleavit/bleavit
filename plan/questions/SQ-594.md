## Question

**RULED 2026-08-05 (R-1) — the runtime MUST generate its metadata hash; routed to B21.** FE-P6 asked for a *hardware test* of "Ledger Generic App + `CheckMetadataHash` flow for a custom chain". Reading the pinned crate answers the load-bearing half with no device: `RUNTIME_METADATA` is `option_env!("RUNTIME_METADATA_HASH")`, set only when `substrate-wasm-builder`'s metadata-hash generation is enabled, and `implicit()` returns `Err(UnknownTransaction::CannotLookup)` for mode `Enabled` when it is `None`. Bleavit's `build.rs` calls `build_using_defaults()` and no `metadata-hash` feature exists anywhere in the repo — **so every transaction this runtime receives with mode 1 is rejected, and the metadata-hash path 11 §11.13 names for air-gapped and hardware signers cannot work as built**. The ruling is not a judgement call: the extension is already in the frozen `TxExtension` stack, so the intent is expressed and only the build configuration is missing — leaving it is the *declared-and-unreachable* defect at runtime level. What still needs hardware is narrower and now stated as such: whether a given Ledger app falls back to blind signing when a chain offers no digest, which is exactly the outcome the mechanism exists to prevent and which the client must not rely on. The client is already correct — `packages/signing` grants no `metadata-hash` capability and has no function that could.
