## Question

**§11.9.1's D-13 row is structurally unpassable: nothing in `app/` reads the Phase-3 caps.** `depositBlocks` needs global-TVL and per-account headroom, and no module reads `phase3.tvl_cap` / `phase3.dep_cap` from `Constitution.Params` or 02 §7.4's `CumulativeDeposits`. Confirmed live by drill 14's funding leg: **every** bootstrap-era deposit blocks on *"the deposit caps could not be read"*. Fail-closed and therefore safe, and also a row that can never pass.

## Status

**resolved 2026-08-09 (F18/F26).** The row was unpassable because the surface it needs was never in the manifest, not because the read was hard. `InflowCaps.CumulativeDeposits` is frozen in 02 §7.4 and was absent from `surface-manifest.json` and `CRITICAL_SURFACE`; its `layout` is now **derived** from the committed runtime metadata by `scale_metadata.surface_layout()` — the same derivation `check-chain-feed.py` uses for the other 301 — and its chainHead transcript is **recorded** by `record-chainhead-fixtures.py` against a booted node, never hand-written. `depositBlocks` reads it, both cap parameters and `ForeignAssets.Asset(USDC).supply`, and blocks with the cap shown. **Two corrections the work produced, both worth keeping:** the entry was first written `query: "map"`, the only such value among 302 — the recorder maps anything but `prefix` to a `value`-typed read, which on a map prefix returns nothing and would have recorded a fixture certifying nothing; and the reader's first headroom guard (`used >= cap ? 0n : cap - used`) could not fail, because `bigint` is signed, so it was replaced with the runtime's own `used + amount > cap`
