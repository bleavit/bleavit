## Question

**A lawful parameter amendment can retroactively under-collateralize an already-admitted attested component.** 07 §6.3 gates admission on `(2^R_max − 1) · orc.bond_bps ≥ Δs_max`, evaluated once, at `register_spec`. §6.1 freezes a *game*'s schedule at round one, so an amendment cannot reprice an open dispute — but nothing re-checks the **admission** rule when `orc.bond_bps` or `orc.rounds` is later lowered within its 13 §1 bounds (`orc.rounds ∈ [2,4]`, `orc.bond_bps ≥ 150`). A component admitted at `(3, 250)` — coverage 1,750 bps — keeps settling money at `(2, 150)`, coverage 450 bps, which may be far below its declared `Δs_max`. §6.3's whole purpose is that a lie costs more than it can move; after such an amendment it silently does not, with no event, no gate and no try-state signal. 07 §6.1 names the hazard for open games ("would let a lawful amendment retroactively under-collateralize a component that was admitted under the §6.3 coverage rule") and solves only that half. Two candidate closures: a constitution-side screening obligation on the two keys (reject an amendment that would break coverage for any live admitted component), or a re-check at snapshot time that flags/neutralizes the component instead. The first is fail-closed at the governance boundary and cheaper; the second is more permissive but needs a defined disposition for the newly-uncovered component. Adjacent to SQ-303.

## Status

**resolved 2026-07-25** — closed at the **governance boundary**, the fail-closed half of the two options the row named: an amendment to either coverage input is refused (`CoverageBreaksAdmission`) if the resulting rate would fall below the `Δs_max` of any already-admitted attested component. Screening there rather than at snapshot time avoids ever having to define a disposition for a component that has become under-covered mid-life — it would have to either neutralize a component whose data is fine or let it settle uncovered. Built on the existing `BudgetDerivationGuard` seam (`CoverageGuard`, `()` permits, runtime binds), with the key set single-homed in `constitution-core::is_coverage_input` and the rate derivation still single-homed in `oracle_core::coverage_bps`. **Scope is every *registered* version, not only the frozen ones:** a version registered today activates later, and its components were admitted against today's ladder, so screening only the frozen set would let an amendment land in the window before activation and bite exactly when the component starts settling money. Directional — raising coverage is always legal, and with nothing admitted the screen stands aside entirely. **Two defects the implementation itself produced, both caught by its own tests.** (i) The first cut compared the proposed `orc.bond_bps` raw — it is a `Perbill`, parts per **billion**, against a `Δs_max` in **basis points** — so every proposed rate read ~100,000× more generous than it is and the screen waved through precisely the amendment it exists to refuse. This is SQ-212's trap recurring; the conversion now rounds **up**, matching `perbill_bps_param_or`, so rounding never overstates coverage. (ii) The `set_param` benchmark used a synthetic `bench.param` key, which short-circuits the screen — so the first regeneration reported *no* regression while measuring a call that never does the work (the SQ-489 shape, third occurrence). With a real coverage key and a saturated MetricSpec set the measurement is **3 → 21 reads**; acknowledged, and the benchmark now charges every `set_param` the worst case. Mutation-checked.
