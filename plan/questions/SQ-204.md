## Question

Locus of the 15 §1 try-state-in-env-CI obligation: the evidence runner does not execute the READMEs' mandatory closing `try-runtime … --checks try-state` leg (needs a pinned `try-runtime-cli` + a keep-alive mode `zombienet test` lacks) — the standing "15 §4.7 snapshot try-runtime-cli leg lands with B7/B8" follow-up still owns it. Is that deferral acceptable, or must evidence emission mechanically gate on per-suite try-state?

## Status

**resolved 2026-07-21 (O6).** Verified real: `TRY_STATE_CHECK` was required by `validate_release_evidence_completeness` but **no code path ever added it** to a row's checks, so evidence emission was structurally impossible, not merely deferred. Fixed on both legs. **Pin:** `try-runtime-cli` v0.10.1 + its SHA-256 now live in `tools/env/pins.env` (the release publishes no digest sidecar, so the digest was computed from the fetched musl asset — V-40) and `fetch-binaries.sh` installs it; in evidence mode the binary must match the pin and `--try-runtime-binary` forces report-only. **Keep-alive:** resolved from the pinned Zombienet's own CLI source rather than assumed (V-41) — `--monitor` ("do not auto cleanup network") exists on `spawn` only, and `test` takes a running-network spec as its second positional, so the runner now spawns with `--monitor`, runs the drill against the published `zombie.json`, runs the closing check, then tears the process group down. Chopsticks needs no keep-alive: the runner owns that process and checks before teardown. The endpoint is resolved from the drill's own topology `rpc_port` and **fails closed** when none is pinned (`bleavit-xcm.toml` pins none). `try-state` is recorded only on a zero exit.
