## Question

**10 §6.5 requires an undecodable block's events to be kept raw and 10 §9.1 forbids retaining exactly that, so the one path §6.5 mandates is the one path §9.1 rules out.** §6.5: *"undecodable rows stored raw, 'N events pending decoder', never guessed"*. §9.1: the index retains *"**only events attributing to the user's watched accounts**"*, and *"a chain-wide trade tape is a bounded windowed read, never a retained table"*. A `${block}:raw` row is a whole block's `System.Events` value **regardless of the watched set** — chain-wide event data by construction — and it is the *expected* state of any backfill across a runtime upgrade, so the collision is the normal case rather than an edge. §9.2's events share has one rung (compaction of settled+reaped proposals) and `compactSettledEvents` cannot reach these rows, since they belong to no proposal. F8 bounds them against the **events share §9.2 already publishes**, oldest-first, with the disposal written to `meta` in the delete's own transaction — no new parameter, and the conservative direction (the blob is discarded, never guessed at). **Ruling needed:** whether §6.5's raw row is exempt from §9.1's retention rule, or bounded as F8 bounds it, or replaced by something that keeps only what the watched set can attribute — the last is not implementable, because attributing is what the missing metadata prevents

## Status

**open — raised by the R-6 re-review of F8.** No unsafe direction in the shipped reading: bounding discards data that was already undecodable, and the discard is labelled rather than silent. Filed to **B7**
