## Question

08 §4.1 NAV-floor rounding is internally inconsistent and its tolerance is unstated: the displayed floors derive from *whole-USDC-rounded* commitments for PARAM/META (13,863/0.0075 = 1,848,400; 159,424/0.0075 = 21,256,533) but from the *exact* commitment for CODE (103,972.08/0.0075 = 13,862,944). No doc states the ~10-USDC tolerance the reference model relies on (its `nav_floor` case-fits per-class rounding behind a SPEC-NOTE). Which commitment (exact vs whole-USDC) do §4.1 and the runtime `NavFloorUnmet` arming gate use?

## Status

**resolved 2026-07-20 (B4 ratification).** 08 §4.1 gained a normative *Rounding and tolerance* paragraph. The floors are **frozen constants** returned verbatim (`crates/futarchy-treasury-core/src/lib.rs:1050-1058`), not re-derived; they do mix conventions (TREASURY/META from the whole-USDC commitment, CODE from the exact one, PARAM from neither — ~7.8 USDC above its own exact quotient), so the doc now fixes the **direction** instead of inventing a rounding rule: every class floor sits at or above the exact requirement, so the gate is never more permissive than the arithmetic. Conformance accepts ±10 USDC (the shipped `NAV_FLOOR_DISPLAY_TOLERANCE`); the two multi-slot rows are named as §2.5 illustrations, not arming gates.
