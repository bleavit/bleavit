## Question

**`FE-PROV-001`'s trigger has two arms and §8.3's ladder makes only one of them emittable, so a client either raises a user-visible refusal per transient timeout or leaves an arm with no call site.** 10 §8.4's table binds the code to *"a provider fails its §8.3 health probe — **unreachable**, or `Failing` after consecutive errors"*. §8.3 makes `Failing` count **consecutive** failures precisely so *"one timeout in a healthy series cannot ratchet the ladder"* — and a code emitted on the first unreachable probe is that ratchet in a different costume, raising an error-family entry for every network blip, which is the fastest way to teach somebody to ignore the family. Emitting only at auto-disable is the conservative reading and is what ships; it leaves the first arm bound to nothing. The client covers the situation the first arm describes through `fleetState`, which reports **all-providers-down** with this same code and §8.3's incomplete-history explainer — a statement about the fleet, which is what a user can act on. What 10 owes is a ruling: either the first arm is a *display state* rather than a refusal (in which case §8.4's table should say so), or `FE-PROV-001` fires per unreachable probe and §8.3's anti-ratchet sentence needs the exception written down.
