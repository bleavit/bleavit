## Question

**Five co-indexed daily prefix families are cleared or folded by dispatches whose benchmarks seed one of them, so a permissionless crank charges a fraction of its own bounded work.** Three sites, one shape, all verified against HEAD on 2026-07-27. (1) `prune_xcm_traffic` (`pallets/welfare/src/lib.rs:1073-1093`) `clear_prefix`es every family co-indexed on `XcmTrafficEpochs` for each retired epoch, but `seed_xcm_traffic_history` (`pallets/epoch/src/benchmarking.rs:83-102`) seeds **only** `XcmTraffic` — so `pallet_epoch::tick` declares `Welfare::XcmTraffic (r:512 w:512)`, exactly `XCM_TRAFFIC_PRUNE_MAX_EPOCHS = 2` x 256 days, and declares **nothing** for `ReserveProbeDaily`, whose `clear_prefix` is the next line of the same loop. That is 512 reads and 512 writes uncharged on `main` today, and A14 makes it five unmeasured families against one measured: #187 adds `CollatorAuthorship`, #190 `BlockProduction`, #191 `BlockWeightSamples` and `IntegrityFailures` — up to **2,560 uncharged reads and writes** beside a charged 512, so `tick` would pay for one sixth of its prune leg. None of the four branches touches the epoch benchmark, and no single PR review can see this: each branch adds one family to a fixture that was already short by one. (2) and (3) inside `record_snapshot`: `xcm_traffic_epoch` folds up to 256 `Welfare::XcmTraffic` keys and `reserve_probe_epoch_value` reads up to 256 `Welfare::ReserveProbeDaily` keys, and **neither family appears anywhere** in `runtime/bleavit-runtime/src/weights/pallet_welfare.rs` — the call declares 104 reads, none of them these. Instance seven of the fixture-understates-the-work class, and the first one that is *cross-branch*: the defect is not in any branch's diff but in the sum. `tick` is permissionless, so this is a block-capacity surface under R-7, and the growth-only weight-regression gate cannot see work that was never measured. **Measured input from #187 (2026-07-27):** adding just `CollatorAuthorshipEpoch::remove` to the shared reaper already moves the *existing* epoch fixture — at 2×1 fidelity `pallet_epoch::tick` worst-case writes **640 → 642** and `settle_cohort` writes **1,344 → 1,346** with proof_size **552,103 → 568,303 B (+2.9 %)**. Advisory at that fidelity, so per-commit CI stays green, but the release-blocking committed-fidelity job would see it. #187 deliberately did **not** regenerate `pallet_epoch.rs` — three branches regenerating one generated file is the conflict this row exists to avoid — so that regeneration folds into this PR. **Fix as one PR after the A14 queue drains** (three branches touch the same generated weight file, so three parallel fixture edits would conflict and a mis-resolved generated file reads as a weight *decrease*): extend the epoch fixture to seed **every** co-indexed family with an in-body worst-case assertion, give the traffic fold the same on-write epoch total #190 gave the block-production series, give the probe cover check a per-epoch summary of its own, then regenerate `pallet_epoch` and `pallet_welfare` and verify no function decreased against the committed file.

**open** — raised from two independent findings that turned out to be the same defect: my read of the reaper fixture, and #190's agent reporting the two uncharged folds in `record_snapshot`. Both verified directly against the committed weight files before this row was written, not taken on report.
