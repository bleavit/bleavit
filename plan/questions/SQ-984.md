## Question

**Does `GET /range` page ascending only, and does that match how the client actually backfills?** 10 §8.5.2 says a page covers *"some prefix of the requested span"*, which reads as ascending from `from`. 10 §6.4's backfill walks **newest → oldest in 1,000-block chunks**, so the one caller that would drive a ranged read wants the opposite order.

## Status

**resolved 2026-08-07 (§8.5.2)** — **pages are ascending, and the two orderings never meet, because they order different things.** §6.4 orders the *spans a client asks for*; this route orders the *pages inside one span*. A client that asks for the newest chunk first and reads it front to back takes its early-stopping from the chunk sequence, which is where §6.4 puts it. The residual cost is bounded by one chunk — which is what choosing a chunk size is for — and admitting a direction parameter would buy it back at the price of a second paging mode every operator must implement and every client must test
