## Question

**RULED 2026-08-05 (R-1) — the scan's `extrinsicCount` is optional and the guard moves to the fetched body.** 10 §6.5 has the loop consume *headers + `System.Events`*, fetching a body **only** for blocks with a watched extrinsic — the whole cost claim — so at scan time there is usually no body and no count, and §6.5 names no other source. Three options, and two are worse than they look: **deriving** the count from the events (max index + 1) makes the index check **vacuous by construction**, a check that cannot fail, which is the defect class this client keeps finding; **always fetching** a body to learn the count breaks the cost claim outright. So the count is optional, `attributedExtrinsics` bounds the index only where one is known, and the **authoritative** guard is in `loop.ts` against the fetched body — which is where decoding happens and therefore where *"decoding at that index reads a different extrinsic"* can actually occur. **The ruling introduced a latent bug on the way in, caught by mutation**: with the count optional, `bodies.length !== scan.extrinsicCount` compares against `undefined` and is always true, and every existing fixture supplied a count so nothing evaluated it. Split into two checks — a declared count that disagrees with the body, and an attributed index beyond the body's length — with a boundary case (index N against N extrinsics), because a comfortably-out-of-range fixture lets an off-by-one survive in **both** directions.
