## Question

**Reserve health never reaches the treasury: 08 §1.2's fail-static NAV is not enforced (high).** `pallet-oracle::reserve_unhealthy()` is the authoritative `R` flag (07 §8), and `pallet-futarchy-treasury::set_reserve_impaired(flag)` exists with the comment "wired at B1a" — but **no production caller connects them** (only core tests call it). So while the oracle reports unhealthy reserves, `Treasury.reserve_impaired` stays false, `nav()` reports `haircut_flag: false` with an unhaircut `spendable_nav`, and every 08 §4 minimum-viable-NAV gate keeps admitting new commitments — the opposite of 08 §1.2(2)'s "spendable NAV for all new commitments is 0 … fail-static". This is a chain-behavior gap, not a view defect: B2's `nav()` faithfully reports the flag the admission checks themselves use (B2 deliberately did NOT override it in the view, which would have made the API disagree with what the chain enforces). Note the observable symptom: `welfare_current().reserve_flag` (authoritative oracle) and `nav().haircut_flag` (unwired mirror) can disagree, though 02 §4 says the latter follows the former. Wire the seam transactionally (oracle probe result → treasury), or single-home the flag so both read one source. Fails a release closed via the manifest `release_blockers` row `treasury.reserve_health_unwired`.

## Status

**resolved 2026-07-24 (stale — verified against HEAD)** — production binds `type ReserveHealthSink = RuntimeReserveHealthSink`, whose `ReserveHealthToConstitutionAndTreasury` composes `note_reserve_health` + `set_reserve_impaired` atomically on the health edge inside the oracle's explicit storage layer. `nav()` reads the treasury state, so `haircut_flag` and a zeroed `spendable_nav` follow the oracle flag as 02 §4 requires. The blocking condition the row recorded (SQ-380's inert one-way probe) no longer holds.
