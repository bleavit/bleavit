## Question

**Screening does not mirror the guard's `enqueue` preconditions, so `epoch.decide(pid)` can revert permanently after an Adopt.** 09 §1.1 states queue-time preconditions are "enforced by the decision path **before** `enqueue` succeeds", but the guard's `enqueue` additionally requires every declared domain to satisfy `domain_allowed(class, domain)` and to exclude `InternalRootApplyUpgrade` (`pallets/execution-guard/src/lib.rs:906-912`), and `queue_time_check` (`runtime/bleavit-runtime/src/configs.rs:3236-3248`) checks neither. Concretely reachable: a CODE payload `[utility.batch_all([system.authorize_upgrade(h)])]` — the wrapper 05 §96 explicitly blesses — passes screening (the classifier only matches `authorize_upgrade` at top level via `is_sub_type`, so nested it projects to `InternalRootApplyUpgrade`), wins Adopt, and then makes `epoch.decide(pid)` fail with `CapabilityDenied` inside `with_storage_layer`, **reverting the whole decide every time** until the 7-day T20 stale path force-rejects with a full refund. Bond is refunded so no funds are stranded, but 13 days of market and a decided Adopt are lost. Two questions: must `queue_time_check` be a superset of the guard's `enqueue` preconditions (making `decide` total), and is a nested `system.authorize_upgrade` intended to be admissible at all — 09 §2.1 describes a multi-item upgrade payload, which the top-level-only matcher cannot express? Guard-queue fullness (`MaxLiveProposals`) is likewise unmirrored.

## Status

**RESOLVED 2026-07-21** (batch X wave 2). Verified real at HEAD, then fixed: the nested-authorization path did repeatedly revert `decide`. **The queue-fullness rider is false** in healthy state — the epoch's 32-live bound includes the deciding proposal, so the guard queue cannot already hold 32 legitimate entries. And the intended multi-item upgrade payload is expressible as multiple **top-level** calls, so nested `authorize_upgrade` need not be admitted at all. Fix: a shared domain-admission helper that re-derives every call, requires `domain_allowed(class, domain)` and rejects `InternalRootApplyUpgrade`, called from `static_check`/`queue_time_check` and reused in the epoch→guard enqueue adapter — making `decide` total. **Implemented:** `rederive_call` on `utility.batch_all([system.authorize_upgrade(h)])` yields `InternalRootApplyUpgrade` (the classifier matches `authorize_upgrade` only at top level), which `enqueue` refuses — while `static_check` returned `Eligible`, pinned by a test that failed pre-fix with exactly that. Fixed with the ruled shared helper `domains_admissible` in `configs.rs`, applied in `static_check` (T4 `SlashAll(ConstitutionViolation)`, matching the adjacent capability-failure disposition) and re-applied in the epoch→guard enqueue adapter, making `decide` total. The canonical top-level upgrade payload stays eligible, pinned by a positive test so the mirror cannot over-reject. **Review round corrected the disposition:** the first cut returned `SlashAll(ConstitutionViolation)` by analogy with the adjacent capability failure. 05 §2.1's T4 taxonomy governs and says otherwise — "confiscation requires a verified culpable act", and "the refund arm is the default and the two slash arms are the enumerated exceptions". This failure is in neither exception (footprint matches, capability passes, call re-derives cleanly); the only fault is a classifier projection artifact on `utility.batch_all`, a wrapper 05 §1.4 explicitly blesses. Now `Refund(ProcessHold)`. Taxonomy gap raised as SQ-362; the §1.1 enumeration gap as SQ-363. A later review round found that the false-footprint slash sat *after* the domain refund, letting a false declaration escape the T4 slash by co-occurring with a domain fault — fixed under SQ-480.
