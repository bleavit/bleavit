## Question

**Measurement context is many-version while registry asks for one version, and several economic inputs lack owners.** Concurrent cohorts may freeze multiple MetricSpec versions for one measurement epoch, but `registry::EpochContext::frozen_spec_version` returns one `u16`; no bounded epoch-indexed source retains historical epoch-end timing; additionally no runtime storage presently owns `StakeAtRisk(c,m)` cohort escrow, registry milestone targets, welfare normalized on-chain/relay daily counters, or the certified `InCapPrize` envelopes for PARAM/CODE/META. Should the registry key become versioned and which pallets own these bounded inputs/timing?

## Status

**resolved 2026-07-25 (contract v14)** — ruled 2026-07-21 (batch X), code landed 2026-07-25; owner **A12**. Verified: the historical-timing claim is **stale** (B1b added a bounded, tested timing archive); the single-version registry premise is real and fails closed. 07 still keys `Aggregates` by epoch alone while §2 requires per-version games, so code could not pick a representation without a ruling. **Ruled: version the complete registry lifecycle by `(epoch, spec_version)`** — under G-1 it cannot silently combine claims governed by different frozen targets or formulas. **Scoped 2026-07-25 — the implementation's biggest risk is not the key change but what it makes reachable.** `incident_multiplier`'s miss-arm returns `FixedU64(1e9)` — "no incidents", the *favourable* value, as 07 §7 itself flags. That arm is near-unreachable today because `frozen_spec_version` returns `None` for any epoch with more than one live version, so a filing is either matched or refused. Once `Aggregates` is keyed by `(epoch, spec_version)`, a reader that asks for the wrong version — or asks before that version's `close_epoch` has run — silently gets full-strength `C_attested` for a cohort whose incidents were filed under the sibling version: a G-1 violation reached purely by a key change, with no error, no event and no try-state signal. The re-keying therefore needs a **fail-closed reader**, not a version-blind `get`. Two further notes: the re-key flips `file` from fail-closed to admissible at activation boundaries (intended, but it is a closed→open transition worth pinning), and 07 §7's storage table still reads "≤ 4 keys live", which the ruling contradicts and which must be amended to 4 × ≤2 versions. Registry **events** are the only 02-frozen part of the blast radius (`(epoch, filing_id)` stops being unique); making `FilingId` unique per *instance* would avoid touching them entirely. The ruling also assigns the orphaned inputs: epoch → timing; a snapshot owner over epoch/ledger state → `StakeAtRisk`; `MetricSpec` → milestone targets; the welfare/treasury producers → daily counters and certified capability envelopes. **Resolved 2026-07-25 (contract v14).** The lifecycle is keyed by `(epoch, spec_version)`, and the scoping above was right about the risk but wrong about the blast radius in a way that made the change much smaller. **Only `Aggregates` is re-keyed** (`MAX_AGGREGATES` 4 → 8): `Filings` and `FilingCount` stay epoch-keyed, so filing ids stay unique and **none of the ten 02 §6 filing events is touched** — only `RegistryEpochClosed` gains the version. Dropping the shared count at the first version's close is safe for a reason worth recording, because the counter looks like a hazard: `file` requires `now ≤ filing_window_end` and `close_epoch` requires `now > filing_window_end`, so **no filing can arrive for an epoch once any version has closed**. The two windows are disjoint by construction. The **fail-closed reader** landed, and refining it produced the sharpest finding: an unconditional refusal on a miss would have **wedged the chain**, because `close_epoch` deliberately refuses a never-filed epoch (anti-griefing) so most epochs never get a record at all and no snapshot could ever be taken. The rule is therefore two-way — no registry footprint ⇒ the neutral 1.0 is honest; a footprint that lacks *this* version ⇒ refuse — and 07 §7 was corrected from the absolute form I first wrote. **An independent review of the re-key then found a hole the re-key itself opened**, and it ran in both directions at once: because the first close drops the epoch-wide `FilingCount`, reaping that version while a sibling still held a non-terminal filing erased the epoch's only remaining evidence of having been filed, leaving the sibling permanently uncloseable *and* making the reader take the neutral branch for a version whose filings were still in storage. Closed by ordering the reap behind sibling closes (`ReapNotDue`), pinned by a mutation-checked regression — **and writing that regression turned up two more defects of the same family**, both mine. (i) The `try_state` partition asserted a filing is *either* counted-live *or* aggregated, which was exhaustive before versioning and is not now: the first close releases the epoch-wide count, so a sibling's filings are legitimately neither, and try-state failed on a healthy chain. The invariant is restated as its two real properties — never in two stages, never in none — with the third state recognised. (ii) The reader's evidence was scoped to the **epoch** rather than to the version, which stranded a version that legitimately has no filings: an incident filed under the sibling leaves an epoch footprint, so a version whose cohorts had nothing filed against them would refuse indefinitely unless a keeper cranked a close for a version with nothing to close — putting a safety read behind off-chain liveness for no gain. **SQ-175's consumer half landed with it**: `milestone_target` is a real per-version read of the frozen spec, and `cohort_exposure(Milestone, ·)` is determinable for the first time. Weights regenerated for four pallets with nine scoped acknowledgements; the `pallet_epoch` hand-edit trap (SQ-490) was re-spliced and the function set diffed before and after.
