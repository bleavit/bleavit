## Question

`ledger.position_deposit` is a live META tunable (13 §1, default/K-floor 0.1, max 1 USDC), but 03 §4/§9 assume one deposit value and the ledger has no hook (03 §10) to rebase already-held deposits. A governance raise makes the L-6 equality `DepositsHeld == position_deposit × entries` fire for entries created at the old value, and refunds at the new unit would over-draw the sovereign (L-2). Is `position_deposit` frozen-in-practice, or how does a change reconcile existing deposits (a migration)?

## Status

resolved 2026-07-21 (batch X, A13) — ruled and implemented this session. Verification sharpened the row: "every count-decreasing call fails immediately" is too absolute, and the real hazard is worse than the stated one — before `checked_sub` ever underflows, a transfer that deletes one entry while creating another charges the recipient at the new unit and over-refunds the old owner, so **L-2 stays algebraically balanced while pooled deposits are misappropriated between users**. No test covers a value change with live entries. **Ruled: freeze the key** — set the registry maximum equal to the minimum/default (0.1 USDC) and amend 13 to match. Per-entry deposit vintages (the only design that preserves live tunability) would require unbounded migration and is refused under R-7; it becomes a dedicated milestone only if tunability is later shown to be needed. Freezing is the sole option that cannot retroactively levy users or over-refund old entries. **RESOLVED 2026-07-21 (batch X, A13):** `constitution-core::genesis_params` seeds `ledger.pos_dep` with `max == min == default == 0.1 USDC` (`crates/constitution-core/src/lib.rs`), and 13 §1 + a new 13 §2 *Position-deposit freeze note* record the single-point interval and the L-2/L-6 rationale. Pallet regression `sq_36_ledger_position_deposit_is_frozen_at_its_kernel_floor` (fails pre-fix: max was `1_000_000`). No stored-shape change; genesis fixture unchanged for this key (value already 0.1).
