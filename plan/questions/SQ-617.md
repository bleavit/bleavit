## Question

**Three documents give the registry calls three different names, against a runtime with two instances and no pallet called `Registry`.** 11 §11.2's S19 row and §11.8.6 write `registry.file_incident(...)` / `registry.file_milestone(...)` / `registry.challenge(filing_id)`; 06 §5.1 uses the same family; 07 §7 writes `challenge_filing(epoch, filing_id, evidence_hash)`. The runtime has neither: `pallet-registry` is instantiated **twice** (`IncidentRegistry`, `MilestoneRegistry` — 02 §6 freezes the events under both) and its calls are `file(epoch, class, points, evidence_hash, spec_version)` and `challenge_filing(epoch, filing_id, evidence_hash)` (`pallets/registry/src/lib.rs:559`, `:603`). This is V-169's defect one level up: that one was an *ingest filter* bound to a pallet that does not exist and it rejected every real event; this is the **call** side, where a client following any of the three documents builds an extrinsic that cannot dispatch. It also hides a real precondition — §11.8.6's challenge row lists a bond and a window and no evidence hash, while the call requires one, so a client following the row cannot encode the call at all.

## Status

**resolved 2026-08-07 (contract v29).** Doc-trued to the runtime's own `file(...)` / `challenge_filing(...)` under `IncidentRegistry` and `MilestoneRegistry`. The repair landed in 06 **§3.2** (the authority matrix), not §5.1 as first cited. §11.8.6's challenge row carries the `evidence_hash` the call requires, which the row had omitted
