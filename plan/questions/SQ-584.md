## Question

**The weight gate that can see a component-bearing function has never executed, and ~50 functions depend on it.** 15 §4.5 splits weight drift across two runs on measured evidence: constant-weight functions agree across sampling fidelities and are hard-gated by the per-commit `benchmark-smoke` job at 2×1, while component-bearing ones do not agree — a 2-point fit can lose a linear term outright — so they are gated only by `release.yml`'s **`Component weights at committed fidelity`** (`--check --components-only --steps 50 --repeat 20`). That job is release-blocking, `git tag` is empty, and no release has ever been produced, so **the second half of the rule has never run**. Measured 2026-08-04 by executing it: 2 of 17 pallets carry a stale committed weight, one of them **understating** a block-bounding dimension (`pallet_execution_guard::qualify_recovery_image`, 34 B). Both drifted when N7 added pallet prefixes to `construct_runtime!` and neither is visible per-commit, because at 2×1 the same functions are advisory *by design* — and the advisory figure is not merely noisier, it is a different number (`add_invulnerable` reads 12,043 at 2×1 against 12,119 canonical), so raising the 2×1 verdict to hard would produce false failures rather than coverage. The gap is structural, not an oversight in the rule. **Ruling needed:** whether the component check must run per-commit for pallets whose *runtime storage layout* could have moved — which is not the same selector as `--changed`, since neither stale pallet's own source was touched — or on a schedule, or as a required leg of any PR that adds a pallet to `construct_runtime!`. Cheapest correct trigger is likely the third: a `construct_runtime!` addition changes the global trie and therefore every recorded proof in the runtime
