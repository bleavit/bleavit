## Question

15 §4.7 requires the XCM suite to cover "trap, and recovery", but the amended 09 §6.1 trapped-assets row permits self-scoped `claim_assets` only for *self-keyed* traps; an inbound AH-message failure keys the trap under Asset Hub's origin, recoverable only by an inbound `ClaimAsset` program from that origin. Which route must the published drill exercise?

## Status

**RESOLVED 2026-07-21** (batch X wave 2). The 2026-07-20 ruling stands and is now implemented. Verification: the original routing ambiguity is **stale** (spec and drill both select remote Asset Hub `ClaimAsset` recovery), but the implementation residual is confirmed **and test-pinned in the wrong direction** — `phase3.dep_cap` still fires *after* minting and creates a remote-keyed trap, stranding an ordinary depositor from Bleavit-side recovery. Bounded fix: a pure `inflow_admissible(who, amount)` read in `pallets/inflow-caps`, exposed through `runtime/bleavit-xcm/src/caps.rs`, plus a `DenyOverCapInflows` entry in the barrier deny tuple that extracts `DepositAsset` beneficiaries under the existing decode-depth/instruction budget and refuses **before** VM construction. Beneficiary-conversion failure must fail closed. **Implemented:** the spec side was already normative (09 §5.2, "Both caps MUST be enforced before any local mint", SQ-129 resolution 2026-07-20) — only the code lagged. Added a pure `inflow_admissible` read to `pallets/inflow-caps`, a `usdc_inflow_admissible` method on the `InflowCaps` seam, and a `DenyOverCapInflows` entry in the `BleavitBarrier` deny tuple that extracts `DepositAsset` beneficiaries under the existing decode-depth/instruction budget and refuses **before** VM construction; beneficiary-conversion failure fails closed, and the per-account bound uses the total minted amount (a sound upper bound on what any single deposit can move, so never laxer than the deposit leg). `ClaimAsset` is deliberately untouched — 09 §5.2's mint-step scope (SQ-253) exempts trapped-imbalance reconstruction — and `phase3.tvl_cap` keeps its binding mint-leg enforcement point unchanged. Regression: 5 tests in `runtime/bleavit-xcm/src/tests.rs` (3 failed pre-fix) plus `production_xcm_account_cap_refuses_before_mint_and_never_traps`, which keeps the `phase3.dep_cap` limit-coverage marker and now covers **both** live enforcement points. The prior test asserting `trapped_assets_events() == 1` is deleted: it pinned exactly the permanent stranding the spec forbids. **Review round (spec-reviewer, 2026-07-21) found two blocker evasions in the first cut of the barrier and both were fixed before commit:** (a) the gate keyed only on `ReserveAssetDeposited`, so a `WithdrawAsset`-fed program — filling holding from the sender's local sovereign account with no mint — walked past it and stranded the holding at the deposit leg; (b) `DepositReserveAsset{dest}` is a *second* metered local deposit leg, and with no `DepositAsset` present the beneficiary list was empty and the `all()` vacuously true, so the mint executed and the refusal trapped. The gate now sums every local USDC holding source (`ReserveAssetDeposited` + `WithdrawAsset`) and binds every local deposit target (`DepositAsset{beneficiary}` + `DepositReserveAsset{dest}`) against the whole holding; `TransferReserveAsset` is excluded on evidence (`transfer_asset` is unmetered by `CappedInflows`, so it can never produce a cap refusal). Four adversarial regressions added, three of which failed against the first cut. Surface questions raised as SQ-360/SQ-361. A later review round found the beneficiary bound measured the full pre-fee holding rather than the post-fee amount `deposit_asset` meters, wrongly rejecting USDC-fee-paying inbound programs — fixed under SQ-481.
