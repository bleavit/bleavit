## Question

**Guardian review/recall scheduling and effect dispatch cannot be atomic through the frozen seams.** `GuardianReviewScheduler`/`GuardianRecallScheduler` return infallible `u32` after the guardian action has already been persisted, so a failed stock-referenda submission cannot roll the action back; guardian storage also reaps the action→proposal binding needed by `review_window_closed(pid)`, and the pallet records an approved action without a sibling-effect dispatch seam. Should these traits become fallible/transactional and retain the pid binding, or should a separate bounded machinery crank own submission/effects?

## Status

**resolved 2026-07-20 (triage sweep — code-verified).** B1b made both seams fallible and transactional: the traits return `Result<u32, DispatchError>` with the contract stated inline — "scheduling failure must roll back the maintenance step" (`pallets/guardian/src/lib.rs:146-182`); the runtime performs a real `Preimage::bound` → `Referenda::submit` → `place_decision_deposit` and returns the actual referendum index (`configs.rs:4459-4489`, `:4511-4540`); every dispatchable that can reach it is wrapped in `with_storage_layer`, so a failed submission un-persists the guardian action. The action→proposal binding moved out of reapable guardian storage into epoch-owned `GuardianReviewDeadlines` (`configs.rs:2812-2816`), and effects dispatch through `EffectDispatcher`/`ProposalVeto`. No `u32::MAX` sentinel survives.
