## Question

**No A8-owned crank connects the oracle money deadline to neutralization.** The oracle pallet exposes `force_neutralize_expired`, but the epoch/reporting integration has no bounded path that guarantees the no-report component is neutral-settled by the money deadline before cohort settlement. Assign the keeper/tick trigger and prove the deadline ordering.

## Status

**resolved 2026-07-25 — and the row's own "assign the trigger" framing understated it twice.** The oracle side was finished and uncalled, so the money deadline was unenforced end to end; the missing piece was the **seam**, and `pallets/epoch::OracleAccess` now carries `note_settle_deadline(m)` and `note_epoch_boundary(ended)` alongside `any_open_dispute_touching`, both **undefaulted** so a runtime cannot leave either unbound invisibly. A new `drive_oracle_boundaries(index, phase)` runs from all three clock-syncing entry points (`tick`, `decide`, `settle_cohort`), driving a bounded, resumable `OracleDeadlineCursor` — `OracleSettleDeadline(m) = start of epoch(m+1) Housekeeping`, so Housekeeping of `N` makes every `m <= N-1` due and earlier phases only `m <= N-2`. **The ordering the row asked me to prove is not the one it names.** `settle_cohort` never reads `ComponentValues`; it reads the welfare *snapshot*. The consumer is `pallet-welfare::record_snapshot(m)`, which fails `MissingComponent` while a contested component has none, so the real chain in Housekeeping of `N` is `note_settle_deadline(N-1)` → `record_snapshot(N-1)` → `settle_cohort(N-3)`, each fail-closed against the one before. An adversarial review caught my first inline justification stating the wrong consumer; the comment and 07 §11(1) now state the true chain. `settle_cohort` additionally drives its **own** cohort's due measurement epochs, which is what makes the guarantee hold by construction instead of resting on the catch-up budget. **A12's "d20 retained rounds" does cover the bond-only late-verdict half** — `force_neutralize_expired` retains the `Rounds` entry and marks it `money_settled`, per §11(1) — but the doc comment above it still claimed a later verdict "finds no round", a leftover from before retention landed; corrected. **Design notes.** The cursor deliberately defaults to 0 rather than being migrated abreast of the clock: a cursor that starts at the current index claims coverage it never provided, and the per-cohort leg trusts it to decide whether a mid-flight cohort's earlier epochs still need driving — an upgraded chain replays from 0 at bounded no-op cost instead. The catch-up bound is `MAX_NON_TERMINAL_COHORTS`, **derived not picked**: a round can exist only for a measurement epoch some live cohort consumes (`report` requires `is_expected_spec_version`), so that is exactly the number of epochs that can carry non-trivial work; rowed in 13 §2 with a limit-coverage classification and marked test. **One live defect fixed in passing, surfaced by the review:** `expected_components` returned every component of the spec, so the newly-live deadline crank would have written neutral **flagged** `ComponentValues` rows for class-1/2/3 on-chain components — the declared input to §10's two-consecutive-flag renormalization, and for gate inputs its VOID escalation. Filtered to `SourceClass::Attested`, the predicate `onchain_components` 200 lines above already used. try-state gained a phase-aware ceiling on both cursors (a first pass admitted `cursor == index` in any phase, i.e. `m = N-1` neutralized before its deadline). Five mutations each fail exactly one new test. **Restructured after the Codex review (3 P1, all valid).** The driver is now a permissionless crank of its own, `epoch.drive_oracle_boundaries` at call index 17, removed from `tick`/`decide`/`settle_cohort` — the review showed the epoch benchmarks never prime oracle storage, so the generated weight recorded **one** `Oracle::Rounds` read against a 128-entry bound, and priming it honestly is arithmetically impossible inline: 13 §5 pins `decide` at 231,055 B of proof under a 384 KiB ceiling while the oracle aggregate alone measures 356,514 B. Nothing was lost, because the ordering never rested on intra-dispatch sequencing — `record_snapshot` fails closed on `MissingComponent` — and 07 §11(1) calls this a *crank* while §13 gives the oracle no hooks, so a crank is the shape the spec asked for. It is benchmarked with the oracle aggregate primed to bounds, wired into the SafetyFilter matrix as a Public leaf, and planned by the keeper. The review's other P1 here was **the cursor is not evidence for a cohort**: a cohort forming after one of its measurement deadlines was driven had no `CohortSchedule` when `expected_components` resolved, so that drive covered none of its components — my `measurement >= cursor` guard then skipped exactly the epochs that needed re-driving, wedging `record_snapshot` permanently. The guard is gone; the crank re-drives every live cohort's due epochs unconditionally.
