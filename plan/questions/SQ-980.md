## Question

**Must a history query state the verdict of §6.3's per-range integrity checks, or only the facts its edges record?** §6.3 declares `CoveredResult<T>` as `data` + `span` + `ranges` + `holes`, and it declares the three checks and their `ok`/`invalid`/`unchecked` verdicts one bullet apart — but the verdict lives in `CoverageVerification`, which `verifyRanges` returns to the **boot** path, and no history answer carries it. So a surface rendering a query's coverage can honestly say what an edge **records** (a `checked` edge holds a hash and a spec version, so the range *can* be compared) and cannot say what the chain answered, while F25's boot surface lists the very same range under *"Ranges this client could not check"*. Both statements are true and a user meets them one screen apart. §6.3 forecloses the cheap fix in as many words — *"an `ok` verdict must never be inferred"* — so the choice is between a read path that carries the verdict and a read path that is explicit about not having one. **Ruling needed:** does §6.3 oblige `CoveredHistory`/`CoveredResult` to carry the range's last verdict (which makes the verdict part of the query contract and needs a shape change, plus a rule for a verdict that has gone stale since it was recorded), or is the capability wording the correct terminal answer?

## Status

**open — raised clearing the R-6 review's blocker on F23; the review raised it as its question B.** Safe wording shipped: the column states what the edge records and `EDGE_IS_NOT_A_VERDICT` states that the answer carries no verdict, so nothing infers `ok`. Filed to **B7**
