## Question

**The epoch-VOID Baseline settlement writes a terminal marker without latching, permanently wedging the Baseline book.** Found by applying B4's newly-ratified 04 §2 / 03 §5.4 reap-ordering rule to `d77b6f5` (SQ-92's fix). Every other terminal path composes marker + latch atomically — `configs.rs:3452-3455` (`void`), `:3695-3702` (`settle_scalar`), `:3721-3730` (`settle_baseline` → `observe_baseline_terminal`). The VOID path does not: `configs.rs:3415-3416` delegates straight to `pallet_welfare::settle_baseline_void`, which calls `T::Ledger::settle_baseline` (`pallets/welfare/src/lib.rs:736-745`) with **no** `with_storage_layer` and **no** `observe_baseline_terminal` — and that observer has exactly one production call site (`configs.rs:3730`), which this path never reaches. Consequences under the ratified rule: `pol_obligation_live` stays true forever, `reap` (which requires the latch) can never fire, and the Baseline book's POL commitment stays a live NAV obligation — one per voided epoch, monotonically accumulating — while the ledger sweep deletes the marker after `ledger.archive_delay`, so nothing can reconstruct it. SQ-92 closed a stranded-funds leak and opened a standing-obligation one. Fix: compose the VOID path like the other three.

## Status

**resolved 2026-07-21 (batch X)** — **row premise disproved; the row stopped tracing one layer too early.** `settle_baseline_void` does not name the observer, but the `LedgerSettlement` implementation it dispatches through does: `WelfareLedger::settle_baseline` (`runtime/bleavit-runtime/src/configs.rs:3757-3766`, the binding at `:3787`) wraps `with_storage_layer` around `ConditionalLedger::settle_baseline` **and** `observe_baseline_terminal`, and that one adapter serves both ordinary and VOID settlement. The composition landed in B10 (`80d6bb9`), before this row was raised. The alleged marker-without-latch state is not produced at HEAD and was not produced by `d77b6f5`; `sq92_epoch_void_with_a_live_baseline_book_keeps_market_try_state_green` pins it.
