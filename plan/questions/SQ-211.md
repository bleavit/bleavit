## Question

**"Active MetricSpec version" is never defined, and `0` is overloaded.** 02 §3 promises `welfare_current()` reports the "active MetricSpec"; 05 §4.6 gives only `activation_epoch ≥ current + 2` and I-16. B2 now routes the view through the same canonical selector the qualification path uses (greatest `activation_epoch`, unique, else fail-closed `None`), but the view's total return forces a sentinel `spec_version: 0` for "no active spec" — and `0` is a legal `MetricSpecVersion`. Which selector is normative, and how should "none active" be encoded?

## Status

resolved 2026-07-21 (batch C, contract v6) — `WelfareView` gains a trailing **`active_spec_available: bool`**; `spec_version` is meaningful only when it is true, and it is true even when the selected version is `0`, which stays a legal `MetricSpecVersion`. This retires the overloaded `spec_version: 0` sentinel rather than outlawing a legal identifier to preserve it. 05 §4.6 now states the shipped selector normatively — among versions whose complete component set is active at the queried epoch, the unique version with the latest activation epoch; no candidate, or a tie, means no active spec — which is already the one selector shared by the qualification path and the view.
