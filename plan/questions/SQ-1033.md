## Question

**`chainLabel` is a pin-matching key wearing a display label's name.** `classifyForeign` resolves the release pin by `pins.find(p => p.label === chainLabel)`, so a caller naming a chain the release does not pin gets **`unreachable`** — for a chain that answered every probe — and `unreachable` invites a retry that cannot ever succeed. F18 hit it live: `boot.ts` passed the *spec id*, and every development Asset Hub classified `unreachable` where the truth was `wrong-chain`, which is terminal.

## Status

**resolved 2026-08-08 (R-1) — the instance is fixed and the class is closed at the type level.** An unresolvable label is a **release-manifest defect**, not a chain condition, so `classifyForeign` must refuse it rather than fold it into a mode: the three foreign arms `wrong-chain`, `unsupported` and `unreachable` are each claims about a chain, and *"this release pins nothing by that name"* is a claim about the release. Two changes follow, and the second is what stops the mistake recurring: the function takes a `ForeignChainPin` **by value** wherever the caller has one, and where it must take a name, an unresolved one throws the same way `classify`'s coverage refusal throws. F18 shipped the caller fix (`assetHubLabel()` reads the label off `FOREIGN_CHAIN_PINS`); the signature change is a named follow-up on F26's branch, since it touches the classifier rather than the funding leg. Recorded because the shipped fix repairs the instance and a string-keyed lookup is exactly the binding this repository keeps finding one layer under a green gate.
