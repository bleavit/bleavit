## Question

**10 §9.4 budgets three bundled chain specs and the release format pins two, so the Asset Hub spec has no pin for the client to verify its bytes against.** §9.4's chain-spec row reads *"relay + para + Asset Hub"*, and 11 §11.9.1 opens a second light client against Asset Hub, whose `startTopology`/`attachAssetHub` path calls `verifyBundledChainSpec(assetHub.chainSpec, assetHub.pinned)` — a `PinnedChainSpec` with a `sha256` and a `genesisHash`. `release-sources.json`'s `chainIdentity.chainSpecHashes` carries `relay` and `para` only, and `packages/verify` threads that pair through `readPair`, `verifyChainIdentity` and the verification panel, so there is nowhere to put the third pin and no role a budget gate could require. Found by F14's review round while binding every pinned role to an emitted spec by SHA-256: the binding is exact for the two roles that exist and silent about the one that does not. `build.ts` now emits a mechanically expiring readiness blocker naming it, so no release can be assembled without the gap being stated. The work is a format change plus its consumers (F10/F13/F18 territory), not a values call.
