## Question

15 §4.5 demands "a clean `cargo-audit` pass under the 01 §9 exact-pin regime", but the pinned stable2603 tree carries 24 RustSec vulnerabilities (16× `wasmtime 35.0.0`, `hickory-proto`, `rustls-webpki 0.101.7`, `ring 0.16.20`, `tracing-subscriber =0.3.19` — the last pinned by `sc-tracing 45.0.0` itself) with **no fix available inside the pin regime**. B8 implements the only workable mechanism: per-entry-annotated `.cargo/audit.toml` ignores (each names the pinning SDK component + the obligation to clear it at the next stable2603 maintenance bump), keeper workspace audited with no inherited exceptions, and the full waived-ID list disclosed in every release manifest. Ratify this waiver mechanism (or amend 15 §4.5 to name it); the standing obligation to re-triage at every SDK bump stands regardless.. **Re-triaged 2026-07-17** against the 25 open Dependabot alerts: the waiver list is *exactly* precise (1:1 with the 23 firing ids — zero stale, zero missing) and every entry is still pin-forced, with `cargo update --precise` attempted per family and the verbatim blocker recorded. Two refinements: (1) `lru` RUSTSEC-2026-0002 correctly needs **no** exception (`informational = "unsound"` → an allowed warning), so the gate is green rather than under-configured; (2) the mechanism had a **structural hole** — RustSec is a strict subset of the GitHub Advisory DB for crates.io, so `yamux` GHSA-vxx9-2994-q338 (HIGH, remote panic) was invisible to it entirely; closed by the GHSA-only leg under **SQ-219**. The *"remove at the next stable2603 maintenance bump"* obligation every entry carries now has a named owner: **B11** — **executed 2026-07-17 (D-19 stable2606 line move)**: from-scratch re-triage deleted the 16 `wasmtime` entries; the 7 survivors + the yamux GHSA entry were each re-proven pin-forced on the new lockfile and re-annotated under per-family exit criteria (libp2p-forced / litep2p-forced / sc-tracing-forced)

## Status

**resolved 2026-07-20 (B5 ratification; waiver mechanism ratified into 15 §4.5).** The tension is real and now stated: the exact-pin regime and a clean advisory gate genuinely conflict when a pinned SDK component forces a vulnerable version, so "clean" means clean **under a declared, annotated exception set** subject to five normative conditions — per-entry annotation naming the forcing component *and* a per-family exit criterion, recorded pin-forced proof, mechanical expiry plus from-scratch re-triage at every train bump, blast-radius containment for workspaces outside the SDK closure, and disclosure in every **publishable** release manifest. Waiver count is explicitly never a gate. Deliberately **source-agnostic**: which advisory databases are normative stays open as SQ-219 (batch B6), so this ruling cannot pre-empt it. Verified against the tree (7 annotated ignores + 1 GHSA waiver, keeper audited from its own root, `bleavit.supply-chain.v2` carried in the manifest); one nuance recorded rather than ratified — keeper isolation rests on cargo-audit's CWD config discovery, contained by the version pin, not by a structural guarantee.
