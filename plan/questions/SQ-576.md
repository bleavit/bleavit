## Question

**A `[VERIFY]`-unset registry row whose consumer short-circuits is benchmarked on its inert path, so adopting the row silently under-declares weight.** Found while implementing N15, by a *false* PASS from the weight gate. `register` calls `scarcity_multiplier`, which returns before invoking the 16 §8.7 probe when `svc.price_cap` is `None`; the row ships unset, `prime_params` did not seed it, and the benchmark therefore measured the branch that does **no** scan. `regenerate-weights.py` reported *"committed storage dimensions match a fresh measurement"* — true, and meaningless, because the measured path was not the reachable worst case. The under-declaration would have arrived the day the values layer seeded the row, with **no code change and no CI signal**, which is the same shape as SQ-490 (`remove_for_cause` declaring 8 reads while performing 261) reached through a different door: there the generator was never re-run, here it was re-run against a fixture that could not exercise the work. **Fixed for this row** — `prime_params` now seeds `svc.price_cap`, so the measured case is the armed one and the inert state is merely over-charged (the safe direction). **What stays open is the class, not the instance:** every `[VERIFY]`-unset row whose consumer takes an early return has this shape, and nothing in the repository detects it. `svc.fee_bps` is seeded and so is safe by accident of an earlier author's care, not by a rule. Wanted: a sweep of the unset rows against their consumers' branch structure, and — better — a mechanical check, since "remember to seed the unset row" is exactly the kind of obligation the weight-gate lineage exists to stop relying on

## Status

**open — instance fixed, class unswept.** Not a live defect: the affected consumer is inert while the row is unset, and the row is unset. It is a **latent** one that arms on adoption, which is why it is filed rather than closed
