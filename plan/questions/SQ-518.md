## Question

**08 §1.2's automatic INSURANCE overflow reaches one of the three inflow classes it names.** §1.2 requires that USDC above `T_ins` overflow to `MAIN` automatically, in the same transaction as the inflow, for **every inflow that executes treasury code** — naming *slash proceeds*, swept ledger residue and the E1 fee streams, and explicitly saying no crank is needed for those. `overflow_insurance()` is reached from `note_swept_residue` and from the `reconcile_insurance` crank, but **neither USDC slash adapter calls it**: the epoch intake-bond slash and the oracle reporter-bond slash push USDC into INSURANCE with no treasury-side overflow, so above-target NAV-bearing capital sits there until someone cranks. Direction is safe (capital is retained, not lost) but §1.2's "automatically … no crank" is not delivered. A second, narrower instance sits alongside it: a `sweep_dust` whose residue is zero but which forfeits deposits performs no treasury call at all, since `note_swept_residue` is invoked only when `residue > 0`

## Status

**resolved 2026-07-29 (milestone E4) — landed in #196, not as its own PR; the separate-PR plan rested on a fact I had not checked.** No ruling was needed; 08 §1.2 already answers it, so this is a code defect. Its bullet is explicit: USDC above `T_ins` "MUST overflow to `MAIN` **automatically**, in the same transaction as the inflow that created it, **for every inflow that executes treasury code** — slash proceeds, swept ledger residue, and the E1 fee streams. No governance act, no proposal slot, **no crank for those**." The permissionless crank is introduced one bullet later for *direct transfers*, which cannot be intercepted because `ForeignAssets.transfer` is a public call — it is a backstop for the un-interceptable case, not the intended path for inflows that do run treasury code. Fixed by a named `note_insurance_inflow()` seam called from both USDC slash adapters. Unlike swept residue it does **not** raise `T_ins`: a slash is not a liability the reserve backs, so the whole inflow is surplus on arrival, the same reading §1.2 gives forfeited deposits. Best-effort at the call site by design — the slash is the security-critical act and no invariant breaks if the overflow does not run, since above-target USDC is exactly what the crank clears; propagating would let a cleanup failure void a confiscation (G-1). **VIT slash proceeds are deliberately untouched** (§1.2 scopes target and overflow to USDC; §2.2 marks VIT at 0 in NAV). **Implemented and reverted from #196 on purpose; lands as its own PR.** The `note_insurance_inflow()` seam and both adapter call sites are written and correct, but verifying them showed the change is milestone-sized rather than a patch: **6 runtime tests fail**, all asserting INSURANCE's *end-state* balance after a slash (e.g. `missing_preimage_terminal_path_slashes_the_live_param_fraction_to_insurance`). Their expectations encode the pre-fix routing. The routing itself is unchanged and correct — the slash still lands in INSURANCE, and §1.2's above-target surplus then overflows to `MAIN` in the same transaction — so the end state is INSURANCE at `T_ins` and `MAIN` credited, and it is the assertions that are stale. Landing it properly means rewriting 6 economic assertions **and** regenerating `pallet_epoch`/`pallet_oracle` weights, since the seam adds storage access to every slashing dispatch. That does not belong bolted onto a twice-reviewed 53-file PR, on the #197 precedent. **That reasoning was wrong on its premise, and checking took one command.** #197 was a hotfix for a defect that existed **on `main`**, which is what made a separate branch possible. Here `git log -S "fn overflow_insurance"` shows the entire `T_ins` machinery — `overflow_insurance`, `note_swept_residue`, `insurance_target`, `reconcile_insurance` — is introduced by `1f81a31`, a commit `git branch --contains` places on **this branch only**. So there is no code on `main` to fix: a separate PR would have had to be *stacked* on #196, which is precisely the configuration already recorded as making a PR's weight gate blind to every function its own base introduces. The size argument was real but did not survive the provenance check, and size is not a reason to put a change where it cannot correctly be built. **Landed here.** `note_insurance_inflow()` is called from both USDC slash adapters, best-effort and each inside its own `with_storage_layer` — that layer is load-bearing rather than defensive: `overflow_insurance` credits `main_usdc` *before* moving custody and relies on the dispatch to undo the credit if custody refuses, so swallowing the error without a layer would keep the credit and overstate NAV against custody that never moved. The 6 stale runtime assertions were rewritten to be **stronger**, not merely moved: each now asserts the confiscation against `INSURANCE + MAIN` (invariant under where §1.2 parks the money) **and** that INSURANCE is left at exactly `insurance_target()`, which is the half that proves the automatic overflow ran — the sum alone would still hold if it silently stopped. All 6 fail under mutation with the two adapter calls removed
