## Question

**Two reporter-console preconditions are not client-readable, so a frontend cannot stop a guaranteed-failing registration.** Raised by Codex review of the SQ-543 fix. The retained 07 §3 offense record lives in a pallet-internal store that 02 §7 deliberately does not freeze — the v19 entry says so explicitly — so a frontend cannot re-read *"carries a retained ejection"* (`ReporterEjected`) or *"entry closed by saturation"* (`ReporterRecordsSaturated`) at `B′`. 11 §11.8.1's precondition row listed only balance and not-already-registered, and 02 §7's catch-all says unlisted storage is not guaranteed decodable, so the client cannot check either condition before signing

## Status

**open — the documentation half is closed, the surface half is deferred deliberately.** 11 §11.8.1 now names both preconditions, states the gap, and requires the console to render both errors explicitly rather than as a generic failure. The *readable indicator* is a 02 §7 addition and therefore a contract bump with joint sign-off, which must not ride inside a security fix — and its cost/benefit is genuinely marginal: both states are rare (three adjudicated-false findings; 64 distinct chain-wide ejections) and the worst case is one wasted transaction fee against a typed error. Whoever takes it should decide between a frozen storage row and a cheaper `FutarchyApi` predicate; the API method is probably right, since the quantity is a *precondition* rather than durable state a client indexes.
