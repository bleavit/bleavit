## Question

**Nothing in CI re-measures generated weights, so committed weights drift silently understated.** `check-weight-regression.py` compares the *committed* file at HEAD against the *committed* file at the merge base — it detects a regeneration, never its absence. The `Benchmark smoke` job executes every benchmark but at `--steps 2 --repeat 1` and does not compare against the committed values, so it cannot see drift either. Consequence, measured on this branch: regenerating `pallet_execution_guard` alone moved 6 functions past the 10 % gate, up to **+30.5 %** ref_time (`ratify`) and **+33 %** reads (`commit_recovery_image`), and a second benchmark run with the tree reset to main reproduced every one of those values — so **main is shipping understated weights for that pallet today**, accumulated since the file was generated 2026-07-23 (B19 attestor revocation/liability storage, the epoch security-terms rows, `PendingRatifications`). Understating a permissionless call is a block-capacity DoS surface (R-7; 15 §4.5). This is the **third instance today of one shape** — the artifact and the thing it describes stop agreeing where no gate looks: SQ-195 (declared weight adjusted, generated weight never regenerated), SQ-489 (a `runtime-benchmarks` fixture arm returning a value instead of doing the work), and now stale committed weights. Options: a periodic (or release-gated) full regeneration that fails on any diff beyond a noise band; or extend the existing job to regenerate and diff the pallets whose sources changed. Both need a noise tolerance, since ref_time varies a few percent run to run on the same machine. Whichever is chosen, the other 30 weight files have never been checked for the same drift.
