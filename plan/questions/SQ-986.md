## Question

**Which state does a page's `balances` describe, and against what is it sampled?** 10 §8.5.2 (2026-08-07) rules them *"read from state at the **page's last block**"* and justifies it by §8.4's sampling having *"nothing to check against unless those rows are real current holdings"*. Those are the same value only when the page's last block **is the head**. For a page over blocks 15..19 of a chain at height 10⁶, balances at block 19 compared against live chain state disagree on every honest page — the identical failure mode the ruling gives as its reason for rejecting the fold, so the derivation does not reach its own conclusion. §8.4 offers a second target the derivation never uses: *"or against the **self-ingested overlap window**"*. Three readings survive and §8.5.2 excludes none: (i) balances at the page's last block, sampleable only where that block is inside the overlap window; (ii) balances as of serving time, which destroys the byte-reproducibility §8.5.2's own cursor-in-header ruling rests on; (iii) the fold, which §8.5.2 rejects. **The code implements (i)** — `stateSlice` folds every movement up to `span.toBlock` — because it is the reading §8.5.1 already states for a producer, and because it is the only one that keeps a page byte-identical to the snapshot covering the same span. **The sampler's own types foreclose the fix, which the re-review added and which matters more than the wording**: `ChainRead` takes a key and no block, and neither `ProviderRow` nor `SampledRow` carries one, so the comparison §8.5.2 mandates is **not expressible** — a page behind the head mismatches on every account that has moved since, and §8.4's *"any mismatch"* rule then auto-disables an honest operator. Whichever reading wins, the sampler needs a block on the row and on the read, or `samplingPages` must refuse to project a page whose `toBlock` is not the caller's pinned head. Raised by the R-6 review of the ruling itself.
