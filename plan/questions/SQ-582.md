## Question

**The committed chain-feed is stale against the runtime, and `check-chain-feed.py` passes anyway.** Built the runtime at HEAD and extracted metadata (2026-08-04): the fresh blob is **468,432 bytes against the committed 466,703**, and decoding both shows the runtime now publishes two storage items the feed does not — **`QuestionService.LiveExternalDepth`** and **`QuestionService.ScarcityMultiplier`**, from Track N's N15 scarcity price response. Same `spec_name`, same **`spec_version` 2**, same contract **v23**, same 45 pallets — so the gate sees nothing: it checks metadata version, contract version and the *pallet set* against `construct_runtime!`, never the **surface set**. Two different runtimes therefore both claim spec 2, and any consumer that trusts the feed is reading a description of a runtime that no longer exists. **This is the defect F2 was built to prevent, recurring one level up**: F2 found a keeper metadata blob that sat wrong for eleven days under green CI, and the fix — the feed plus its drift gate — is itself now stale under its own gate. It also bounds SQ-581: regenerating the feed to admit the 36 missing constants necessarily picks these up too, which is correct rather than incidental. **Ruling needed:** extend `check-chain-feed.py` to diff the *surface set* between the committed metadata and the runtime source (not merely the pallet set), and regenerate the feed. Note the checker cannot do this from source alone — it would need the built runtime, so the cheap per-commit leg may only be able to compare the committed blob against the committed manifest, with the full surface diff living on the release-blocking leg

## Status

open **Confirmed on both halves and the pipeline verified end-to-end (2026-08-04).** Built both runtimes and extracted both metadata blobs: primary `2/` (bootstrap) and recovery `3/` (bootstrap-recovery) are each distinct from the other — coincidentally equal in length, different in hash — and **each is stale by the same two storage items**. So the pairing 10 §5.1 gates is intact; what has drifted is both members of it. **Deliberately NOT regenerated, and the reason is not cost.** The stale feed *is* the evidence for this row: regenerating it now would make the defect unreproducible before the gate that should catch it exists, and the next session could not then verify that the extended checker actually fires. The ruling comes first, the regeneration second — in that order, so the fix is testable. It also keeps SQ-581 (a manifest reconciliation) from being bundled with a 222-fixture feed rewrite, which are two changes with two different review questions. **RESOLVED 2026-08-04.** `check-chain-feed.py` gained a surface-set leg that parses `#[pallet::storage]` from in-repo pallet sources and diffs against the feed's metadata — source-parsed rather than diffed against a fresh build, which is what lets it run on **every commit** instead of once a release. Watched it fire on the live stale feed (both halves, exactly the two items) *before* regenerating, then regenerated. Four mutations caught; the first attempt's tests covered the parser and **not** the comparison, so deleting the check broke nothing — fixed by extracting `stale_storage()` and testing it directly.
