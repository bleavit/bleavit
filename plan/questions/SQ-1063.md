## Question

Both app build jobs use the same mutable runner image and `actions/setup-node@v7`; the second job's
declared isolation is chiefly a checkout-path change. No workflow runs the required digest-pinned
container, and runtime release tooling also records an unpinned build image. A compromise or drift
in the common runner/action can therefore produce identical injected output and preserve the green
tree-hash comparison.

## Status

**resolved 2026-08-12.** Third-party workflow actions are full-SHA pinned and
mechanically checked. App reproducibility uses distinct digest-pinned Node/Debian
images; runtime primary/recovery builds run through one digest-pinned OCI wrapper
with a read-only source and build-info v3 environment identity. Genuine artifact
regeneration also exposed a downstream substitution the initial closure missed:
both chain-spec stages rebuilt the primary on the host after the OCI build, and
the environment stage overwrote the first specs a second time. Both generators
now accept the exact prebuilt primary, release CI passes the OCI path through
both stages, ordinary drill specs use it too, and a behavioral regression proves
release mode does not rebuild the runtime once the pinned spec builder is present.
The same closure pass found that release-tier N10 suites declared a separately
built client-parachain spec which the workflow never generated, while the
evidence producer's broad name prefix would have compared that client runtime to
the primary. Release CI now generates the client spec before evidence; declared
topology paths are prerequisites, primary names are exact, separate client/fast
runtimes are explicit, and unknown Bleavit spec names fail closed.
Historical v2 evidence is not relabeled.
