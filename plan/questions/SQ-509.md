## Question

**The redemption fee's charged set has an arbitrage hole: a complete-set holder escapes instrument B entirely, for free, in `Resolved`.** 03 §5.1 admits `merge_scalar` and `merge_gate` in `Resolved`, and every `merge*` is fee-exempt (§5.3a(1)). A holder of a complete `LONG_w + SHORT_w` set therefore converts it to winning branch-USDC at **no charge** anywhere in the `Resolved` window — `resolve` at d18 through `settle_scalar` at cohort settlement e+3, roughly three epochs — and then exits through the **also-exempt** `redeem`. A cross-branch `Accept+Reject` pair escapes more directly still through the exempt `merge` at par. So instrument B reaches the **fragmented** holder and not the **assembled** one — the exact inversion §5.3a(1) claimed to prevent when it justified charging the pair calls; `redeem_scalar_pair`'s charge is reachable only for a set assembled *after* `ScalarSettled`. **Recommended fix:** bar `merge_scalar`/`merge_gate` in `Resolved`. They are already barred in `ScalarSettled`, they are value-neutral there by §5.1's own text, and barring them strands nobody — a set holder waits for `ScalarSettled` and uses `redeem_scalar_pair`, or, if the vault voids, both calls are available again in `Voided`. **Not done in E1**, deliberately: it changes a scope-A vault state machine whose `Resolved → Voided` interaction §6.4's conservation argument depends on, and that deserves its own analysis rather than a late edit to a milestone already closing. E1 instead corrected the false claim in 03 §5.3a(1), kept the pair charge (which stands on its own anti-fragmentation ground), and recorded the sizing consequence: 08 §10.2's β = 0.50 is an **upper** estimate and instrument B's realized base is smaller by an unquantified amount

## Status

**open** — owner Track E; blocks no milestone, bounds the β figure and any revenue claim resting on it
