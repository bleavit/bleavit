## Question

**The `delta + 1pp` force-rerun rule lacks a unique producer/binding.** Confirm whether guardian force-rerun sets the same durable rerun flag as T13 and which decision window consumes the increment.

## Status

**resolved 2026-07-20 (B1 tail; verified against `epoch-core`, then documented).** Both halves answered, and the answer is that the code was already correct and unique — only the spec was silent. **Producer:** both rerun kinds set the *same* durable `Proposal.rerun` flag. T13 rerun-open sets it (`crates/epoch-core/src/lib.rs:1171`) and the guardian `force_rerun` sets it too (`:1141`) — notable because force-rerun goes `Trading`/`Extended`/`Queued → Extended` **directly**, never passing through the `Rerun` state, so it would have been easy for it to be a second unflagged regime. It is not. **Uniqueness** is enforced on the producer side: `force_rerun` is admissible only while `!p.rerun && !p.delayed_once` (`:1136-1137`), which is the code form of 06 §5.3's "at most one guardian rerun of either kind per proposal, ever". **Consumer:** `decide_engine` reads the flag once (`:1786`) and applies `+ ONE_PP` to the class δ (`:1861`), so there is exactly one consuming site. **Which window:** the rerun's own Extended window and only that one — each producer sets `decide_at := now + DECISION_EXTENSION` and `extended := true` in the same transition, so one `decide()` runs under the raised hurdle and step 6 (`!p.extended`) forbids a further extension; the hurdle can neither leak into a later window nor be inherited by a non-rerun proposal. Spec trued: 05 §5.4 gained a normative paragraph pinning the one-flag/one-window binding, and 06 §5.3's "covers both rerun kinds" sentence now says explicitly that this includes the δ+1 pp regime. No code change.
