## Question

**Is the live-indexer HTTP interface in scope for this repository at all?** §8.2 says live indexers implement a *"minimal read-only HTTP interface; reference implementation in `optional/indexer/`"*, and INV-FE-15 restates it as *"live providers implement a minimal open read-only interface anyone can operate"*. Neither names a route, a page shape, a row identity, a pagination scheme, or an error contract — so implementing it means inventing the interface, which R-2 forbids, and inventing it *badly* is worse than leaving it out: a published interface is a compatibility surface every operator then builds against. `optional/indexer/` does not exist in the repository layout (AGENTS.md), and F9's client half is complete without it — the sampler compares rows through an injected `ChainRead` and needs no protocol knowledge to do so. Two things are owed: whether the reference implementation is this repository's deliverable or a separate one, and if it is, which document specifies the interface. Until then the client can consume an indexer only through an adapter somebody else writes.

## Status

**resolved 2026-08-07 (F24, 10 §8.5.2)** — in scope, and the invention the question rightly feared is avoided by not inventing a format at all: an indexer serves **§8.2's own snapshot document restricted to a range**. Every reason §8.2 gives for making canonical serialization normative applies unchanged, and a second shape would additionally leave `FE-PROV-004` unable to diff a snapshot against an indexer — the cross-check §8.4 calls the only one available at depth. Two routes satisfy INV-FE-15: `GET /chain` (the `binding` object plus served coverage) and `GET /range?from=&to=&cursor=` (one page, plus `nextCursor` when more follow). Three consequences each **remove** an invention: the error contract is that there is none (any non-200, and any body that is not a canonical §8.2 document, is a failed read counted by §8.3's ladder), the cursor is opaque and a client never constructs one, and **coverage comes from the documents, not the cursor** — absence of `nextCursor` is the same species of server claim as `storageDone` **CORRECTED 2026-08-07, same day, by the R-6 re-review.** Two claims above are retracted. (a) `FE-PROV-004` was **not** widened by the one-format ruling and does not diff a snapshot against an indexer — §8.4's table and §2.3 both scope it to *"two independent **snapshots** covering the same range"*. The one-format ruling stands on canonical serialization alone, which is sufficient. (b) A failed read is **not** *"counted by §8.3's ladder"*: that ladder is probe-driven, and letting data reads ratchet it would make auto-disable fire faster for a user who reads more. A failed read is reported with `FE-PROV-003` and does not move the ladder. Also added since: a page owes canonical form and §8.2's ordering but **not** §8.4's conservation replay (§8.4 assigns that screen to snapshots and gives indexers sampling), and `bleavit-next-cursor` is the frozen header the cursor travels in.
