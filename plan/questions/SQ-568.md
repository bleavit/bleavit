## Question

**`num_cores` exceeded the relay's validator count, so two backing groups were empty and the paras scheduled onto them could never be included.** Surfaced by the first drill spawns that got past SQ-567 — invisible until then, because nothing produced any block at all. Symptom: only **one** parachain per topology is ever included; the others build locally to #3, stall, and rebuild from genesis forever. Asset Hub showed the byte-identical signature to the client para despite running the pinned upstream `polkadot-parachain` binary, so it was never a Bleavit defect. **Root cause, read from live relay state** (a throwaway diagnostic over `paraScheduler` and `coretimeAssignmentProvider`): `validatorGroups = [[0],[1],[2],[3],[],[]]` against `numCores = 6` and four validators — the validator set is split across the cores, so every core past the fourth gets an **empty** group — while the claim queue scheduled `core 3 → 4242`, `core 4 → 1000`, `core 5 → 1005`. A para on an empty-group core has nobody who can back its candidate, which is why the failure is total rather than intermittent, and why it stops at exactly `async_backing_params.max_candidate_depth = 3`. The arithmetic: `generate-relay-specs.sh` seeded `num_cores = 3` and zombienet adds **one core per parachain** on top, giving `3 + n` cores against a fixed four validators — so 1 para (4 cores) fits, 2 paras (5) leaves one empty group, 3 paras (6) leaves two. That matches the committed topologies exactly: the four single-para ones have all passed drills, the three multi-para ones never have

## Status

**diagnosed; fix in verification.** The G1 comment that chose 3 reasoned that the seed needed *"headroom for the largest topology"* — backwards, because the per-topology headroom already comes from zombienet's bump, so the seed adds to it instead of covering it. The seed's only job is to be non-zero (a zero `num_cores` wedges group construction, which is the original G1 finding and still holds). Seed corrected to **1**, keeping total cores at `1 + n ≤ 4` for every committed topology, with the binding constraint `seed + parachains ≤ validators` written into the generator so a future raise cannot silently re-break it. **Relay state re-read at the corrected seed confirms it, and confirms the +1-per-para model that was inferred from a single data point:** `numCores = 4` (1 seeded + 3 paras), `validatorGroups = [[0],[1],[2],[3]]` with **no empty group**, and the claim queue placing 4242, 1000 and 1005 on cores 1, 2 and 3 — every para on a core that has a backer. **Fix confirmed by drill 07:** `asset-hub-collator-1` reaches height 10 in 89.7 s where it had timed out at 300 s, the post-genesis HRMP open (SQ-567) passes, and the first reserve-transfer leg runs — 1/8 → 4/8, with the four remaining failures in the drill helper's own XCM-version assertion rather than in transport or scheduling. **The single-para regression leg has NOT run yet** and the seed lives in the **shared** relay spec all seven topologies consume, so it is still owed: drill 01 died at spawn on a missing `keeper/target/release/bleavit-keeper` (an unbuilt artifact in this worktree, not a regression), and every single-para topology needs the keeper. **Regression leg now run and clean: drill 01 passes 10/10** against the corrected seed (para 4242 to height 10 in 126 s), so the single-para topologies are unaffected. That matches the structural expectation — 1 para gives `1 + 1 = 2` cores over four validators, so groups become `[[0,1],[2,3]]`, fewer and *larger* than the previous `[[0],[1],[2],[3]]`, which is strictly better for backing — but the drill is the evidence, not the argument. **Worth carrying forward:** drill 01 first died at spawn because `keeper/target/release/bleavit-keeper` does not exist in a fresh worktree, and all four single-para topologies mount the keeper. It is a 46 s `cargo build --release --locked` in the separate `keeper/` workspace; anyone running drills 01–03, 05, 06, 08 or 09 in a new checkout needs it first
