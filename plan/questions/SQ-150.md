## Question

**`constitution.amend_registry` has mutually inconsistent scope signals and the runtime crosses them.** 06's authority matrix assigns non-kernel rows to FutarchyMeta and also names a ConstitutionalValues kernel-bounds path, while 13 rule 7 says kernel-bounded rows are immutable and must be refused outright. The runtime classifier projects every amendment as Meta, `is_values_enactment_leaf` admits every amendment, and the pallet accepts either Meta or ConstitutionalValues before reading the target; consequently ConstitutionalValues can successfully amend a non-kernel Meta row. **Both sides have explicit spec text:** 06 §2.1's `constitution` track scope column *explicitly authorizes* ConstitutionalValues `amend_registry` within meta-bounds (the textual basis of `constitution-core::can_amend_registry`), while 06 §3.2's exclusive columns and 13 rule 7 read against it — a three-way contradiction (06 §2.1 vs 06 §3.2 vs 13 rule 7); the I-8 crossing (one call in both values and belief scope) is real today under either resolution. S5 pins the I-8 mismatch, both candidate target-scope policies, and the real-dispatch cross-origin effect in three ignored regressions (the scope-matrix pin encodes the §3.2/rule-7 branch as ONE candidate, not "the" matrix). Which canonical policy should a production fix implement: non-kernel Meta-only + kernel denied (13 rule 7 + exclusive §3.2), dual-authority within meta-bounds (06 §2.1, current pallet behavior) with a target-aware classifier/values gate, or a narrowed kernel ConstitutionalValues amendment path?

## Status

resolved 2026-07-21 (batch X) — ruled and implemented this session. Verified: the contradiction is live in *both* spec and implementation — the pallet lets `ConstitutionalValues` amend a non-kernel META row while the classifier simultaneously calls that call Meta-domain. **Ruled: non-kernel registry rows are META-only and kernel-bounded rows are immutable.** This matches 13 rule 7 and the exclusive authority matrix, minimises authority, and cannot weaken a kernel defence through an ambiguous values path. Implementation: amend 06 §2.1, make `can_amend_registry` target-aware, remove blanket values-leaf admission, and replace the cross-origin success test with positive META/non-kernel and negative values/kernel cases. **RESOLVED 2026-07-21 (batch X):** `constitution-core::ConstitutionOrigin::can_amend_registry` is now `FutarchyMeta`-only (kernel rows immutable at `checked_amend` → `KernelBoundImmutable`); `is_values_enactment_leaf` no longer admits `amend_registry` (I-8 crossing closed); 06 §2.1 (`constitution`+`entrenched` tracks) and §3.2 rows 4/5 trued so no values/track path amends registry. Verified per-origin dispositions: non-kernel row → META `Ok`, all others `BadOrigin`; kernel row → META `KernelBoundImmutable`, all others `BadOrigin`. The three `#[ignore]`d S5 regressions were **replaced** by real non-ignored dispatch/classifier pins (`sq_150_amend_registry_is_futarchy_meta_only_in_the_runtime`, `sq_150_kernel_bounded_rows_are_immutable_*`, `sq_150_amend_registry_projects_meta_*`, `i8_inventory_values_and_belief_scopes_are_fully_disjoint`) plus pallet `sq_150_*`; the `AmendRegistryScope` conditional was retired.
