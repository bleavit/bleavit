## Question

**02 §4's `QueuedExecutionView` omits the one queue field that moves the execution deadline.** The view publishes `maturity`, `grace_end`, `cancelled`, `ratification` and `meters_clear` — every input to 11 §11.5's window row except `failed_at`, which is what decides whether `grace_end` is the deadline at all (SQ-790). The consequence is not a gap but a duplication: a client serving S6 must call `execution_queue()` **and** separately decode the raw `ExecutionGuard.Queue` entry for one `Option<BlockNumber>`, which is a second decoder over a structure the view exists to spare it, maintained against a layout the view does not track. The canonical client does exactly that today, taking the stamp from the FE-P2 cross-check witness it already fetches, so nothing is unsafe — but the *projection* is incomplete for the row it was built to serve. **Question:** append `failed_at: Option<BlockNumber>` to `QueuedExecutionView` (a 02 §4 change and therefore a contract bump), or state in 02 §4 that the field is deliberately storage-only and 11 §11.5 row 2 reads the stored entry. The first is the smaller surface and the second is the smaller change; either is a ruling, not an implementation choice
