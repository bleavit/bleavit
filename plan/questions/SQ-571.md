## Question

**Can the canonical app trade an external (hosted-question) book, and if not, where does 16's "organic trader activity" come from?** Raised while checking whether Track N is reflected in the client design. It is — but only as an *exclusion*, and the exclusion has a hole. Three protections exist and all hold: 02 §6 says external-book discovery is `QuestionRegistered` + `Questions.markets`, never `MarketCreated`, and a consumer **MUST NOT** synthesize a `MarketKind`/proposal/epoch for one; 02's v20 entry says the service `Instance1` prefix "is not canonical-frontend ingest"; and the design kit forbids inventing a hosted-service canonical screen. **But doc 11 never mentions Track N at all.** S3's read list is `Market.Markets` — one physical map holding *both* partitions (02 §7.1) — with no `BookKind` filter stated, and S4 reads `Positions`/`account_positions()`, which name instance `()` only. Meanwhile 16 §393 has an underfunded client acquiring its certificate out of **"organic trader activity"**, i.e. ordinary traders taking real positions in external books, and those positions land in `ServiceLedger` (Instance1). So the two readings are: **(a) deliberate** — external books are the hosted client's own business, their own UI serves them, and doc 11 should say so explicitly plus have S3 refuse an external `MarketId`; or **(b) a gap** — Bleavit traders *are* the organic activity, the canonical app is the only client that exists, and it therefore needs the `Instance1` reads that 02 currently excludes. Reading (b) has real force: if no shipped client can trade an external book, 16's funding story has no supply side. **Consequence for the handoff:** S21 exports "the union of the S2/S3/S4 reads", so under (b) a capsule could carry an external book's prices beside a governance market's with nothing distinguishing them — which would put doc 16's central separation claim (*Bleavit sells conditional prices with provenance, not decisions or endorsements*) into a file and out the door. Under either reading doc 11 needs a rule and the capsule needs a labelled `kind`. **Not created by the handoff-first ruling — this predates it**; that ruling only made the capsule path a reason to care sooner.

## Status

**resolved 2026-08-03 — reading (b), by user ruling** (*"The canonical app should serve external books too."*). Implemented as **N13**. The investigation the ruling triggered found the gap was worse than the question stated: it is not only that the client lacked *scope* to serve external books, it is that every other layer already admitted Bleavit accounts into them — `market.buy` is a `CallDomain::Public` call, `LedgerRoute::for_book` routes such a trade into `Instance1` with no caller-visible difference, and `quote()` already prices external books through the shared `Markets` map — while 02 §7.1 alone forbade reading the resulting position. The canonical client could therefore route a user's money into a hosted book and then be structurally unable to show it. Landed: 02 §7.1 reversed, thirteenth API method `service_positions` (separate from `account_positions` because `MAX_ACCOUNT_POSITIONS` is per **instance**, so one shared vector could truncate real holdings), contract **v23**, and the four bounding rules in 11 §11.2a — visible domain via the `SERVICE_ID_BASE` bit test, **no merged portfolio total** (I-4 is per instance), external activity never rendered as governance or protocol health, and the §11.3–§11.4 rituals unrelaxed. The capsule-labelling half of the question is inherited by **F20** as a `kind` obligation, now with a normative rule to encode rather than an open choice
