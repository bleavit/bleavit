## Question

**The SQ-282 dead-man re-scope assigns a pure relay GRANDPA *finality* stall (relay best advances, GRANDPA lags, parachain keeps building on the unfinalized best) to an off-chain relay best-over-finalized monitor, but 12 §6.3 has no such alert.** The only Epoch-progress alert (`bleavit_chain_tick_lag_blocks > 600`) reads the *parachain* finalized head and would freeze (never fire) during a relay finality stall, so it does not cover the SQ-282 blind spot the spec now points at. Add a relay best-over-finalized-lag alert to 12 §6.3 + the O5 monitoring stack (exporter + `series-inventory.toml` + the `check_alert_coverage.py` gate), or ratify that the finality-stall residual is accepted as bounded by XCM isolation (I-24) + the relay's own GRANDPA finality-gadget security with no Bleavit-side detection. The on-chain re-scope (SQ-282) is complete and verified; this is only the off-chain layer.

## Status

**resolved 2026-07-21 (O6)** — batch **X** discharged; ruled 2026-07-21 (batch X), code now landed. Verified: the blind spot is real, but an instantaneous `best − finalized` difference is unusable as an alert (small lag is normal) and reusing the 600-block parachain tick threshold would invent a cross-domain parameter. **Ruled: add a doc-12-owned operational alert** firing when relay best keeps advancing while finalized stagnates for a ruled persistence window — independently configured relay RPC, exporting best height, finalized height and stagnation duration, failing closed on collection errors, bound to RB-KEEPER with Infrastructure escalation. Accepting the blind spot was refused: it would require deleting positive monitoring obligations that docs 05 and 14 already carry. **Persistence window is `[VERIFY]`** — Ops must set it from observed healthy relay behaviour. **resolved 2026-07-21 (O6).** Verified real with file:line evidence: the whole chain-exporter scrape is anchored on the *parachain* `chain_getFinalizedHead` and its loop is driven by `subscribe_finalized`, so during a relay GRANDPA stall `bleavit_chain_tick_lag_blocks` freezes at its last value and can never cross 600; a repo-wide search found zero relay-derived series anywhere in the monitoring stack. Implemented: a **separate** exporter `tools/monitoring/relay_finality_monitor.py` (separate process, endpoint and failure domain — folding it into the chain exporter would couple the relay signal to the very connection a relay stall degrades; it polls rather than subscribes, because a finalized-head subscription is silent during exactly the event being monitored), exporting relay best height, relay finalized height and finality stagnation seconds, failing closed to **absent** series on any collection error. 12 §6.3 gains a 21st row *Relay finality* bound to `RB-KEEPER` with Infrastructure escalation, plus a normative Row-semantics bullet;
