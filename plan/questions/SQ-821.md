## Question

**10 §6.3's `CoveredResult<T>` has no field for *covered but no longer held*, so a consumer cannot tell *complete* from *emptied* — the distinction §6.3's opening rule exists to preserve.** Its three answer fields are `ranges`, `holes` and `span`, all of them about what was **ingested**; the rule they serve says bare rows must never be returned *"because bare rows render as a complete series and 'there were no observations in this window' and 'we never ingested this window' then arrive as the same empty answer"*. A tier emptied by the §9.2 ladder or by a migration produces a **third** empty answer that all three fields report as complete. Three repairs are available and they are not equivalent: `CoveredResult` gains a field; `CoverageRange` is trimmed on discard (which §9.2 forbids for the ladder — the range must not become a hole — and which would also lose the fact that the blocks were seen); or every history read is obliged to consult `meta.downsampled` and its siblings, which is an obligation no consumer can be made to remember. **F8 ships the conservative form pending this ruling**: the store's query path returns a `CoveredHistory<T>` **containing** §6.3's own `CoveredResult` beside the two labels, so the published interface is untouched and the old bare-rows shape no longer typechecks. `CoveredResult` is **not** frozen in 02 — it is declared in 10 §6.3 only — so this is a doc-10 ruling rather than an integration-contract bump. **Ruling needed with SQ-820:** which of the three, and does §6.3 publish the answer type it obliges every history query to return?
