## Question

**When does a T10-rejected proposal release its resource-domain locks?** 05 §1.4 says locks "are released **only at terminal transitions**", while 05 §2.1's *Terminal states* paragraph classifies `Rejected` with a healthy (non-`Voided`) vault as **transient** — terminal only at `Settled`, ~3 epochs later via T21 measurement. Read literally, a rejected proposal holds its resource domain for the whole measurement window, blocking any other proposal touching the same domain from qualifying. Batch X wave 1 changed this in code (releasing at T10 unconditionally) and the change was **reverted** as out-of-scope and undeclared — it is safety-neutral (no rejected payload can dispatch) but shifts T5/T6/T26 contention by ~3 epochs, which is an economic change that needs a ruling, not a silent patch. Is the intended rule "released at the state-terminal point" or "released once no dispatch is reachable"?

## Status

**resolved 2026-07-24 (ruled + implemented)** — the row's own framing is answered by the rule's title: 05 §1.4 is **"Lock persistence to dispatch"**, and a `Rejected` proposal can never dispatch. Verified in code, which disproves the obvious counter-argument: **neither rerun entry admits `Rejected`** — `force_rerun` takes `Trading`/`Extended`/`Queued` and `schedule_rerun` takes `Suspended` — so no path carries a rejected proposal back to a dispatchable state. Holding the domain through the ~3-epoch measurement window that §2.1 makes this state transient for therefore protects nothing while blocking every other proposal touching the same domain, which §1.4's own collision paragraph already names as the pure **liveness cost** the design avoids where it buys no safety. Ruled **"released once no dispatch is reachable"**: T10 now releases the locks in both arms. The wave-1 change was right; what it lacked was the ruling and the evidence, both of which are now recorded. The Phase-0 simulation models no resource-lock contention at all, so no calibration evidence is invalidated.
