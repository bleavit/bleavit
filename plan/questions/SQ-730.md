## Question

**11 §11.8.2 makes the playbook trigger a precondition and never binds a `PlaybookTrigger` variant to the item that answers it.** The propose row requires the activation trigger *"verifiably active at B′"* and names five conditions in prose — gate breach, depeg, dead-man, VOID, the I-4 drift flag for PB-LEDGER-FREEZE. The trigger is not a property of a registration, as an earlier reading of SQ-616 had it: `guardian_core::GuardianPower::ActivatePlaybook { id, trigger, expiry, target }` carries it as a **call argument** the proposer chooses (SQ-621), so the client holds the variant and must decide which frozen item establishes it. Every candidate read exists — `Constitution.PhaseFlags` bits 5/6/7, `Welfare.GateBreachFlags`, the vault state — so this is not a missing surface; it is a **mapping the specification does not state and a client would therefore invent**, five ways, on the one action that costs a 5-of-7 signature before the chain refuses it. Client posture: `UNREADABLE['O-4']` is `blocking` and `TriggerState.unread` is treated exactly as `inactive`

## Status

**resolved 2026-08-07 (contract v29), and the gap was wider than the question stated.** `PlaybookTrigger` carries **eight** variants and §11.8.2's prose named five, so three were not mentioned at all. §11.8.2 now carries one row per variant naming the frozen item that establishes it, on the one action that costs a 5-of-7 signature before the chain refuses it
