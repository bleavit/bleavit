## Question

02 §3/§4 spell the API collection bounds as FRAME's `BoundedVec<T, ConstU32<N>>`, but 02 §2 + rule 9 / 01 §5.2 require every view type to live in the frame-free `futarchy-primitives`, whose `BoundedVec<T, const N: u32>` cannot take the sp type — the spec's spelling and the crate-layering rule are in literal tension. De-facto accepted since M1 (all Track-A pallets + the B2 `FutarchyApi` declaration use the primitives type); wire-format equality with `bounded_collections::BoundedVec<T, ConstU32<N>>` is now pinned both directions by `api_collections_encode_identically_to_frame_bounded_vec` (runtime-api). Residual: the **TypeInfo/metadata shape** differs (derived composite vs FRAME's sequence-like info), which generated frontend descriptors will surface — B1a's `impl_runtime_apis!` golden-metadata test must decide whether to keep the composite shape (and bless it in 02 §3's wording) or hand-implement a sequence `TypeInfo`.

## Status

resolved 2026-07-21 (batch C, contract v6) — 02 §3/§4 now spell every API collection `futarchy_primitives::BoundedVec<T, N>` and freeze the shipped composite metadata form and type path. **The row's load-bearing residual is false:** FRAME's `bounded_collections::BoundedVec` renders in the real runtime metadata as a *composite* wrapper around `Vec<T>` exactly like the primitives type — only the type path differs, so there is no composite-versus-sequence decision to make and no hand-written `TypeInfo` is needed. Wire equality was already pinned both directions.
