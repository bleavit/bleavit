## Question

**`unchecked` conflates *never checkable* with *not checkable right now*, and only one of them ever clears.** §6.3 states the asymmetry precisely — *"a check that cannot be performed keeps the range"*, and *"a range that appears in neither the invalidated nor the unchecked set is one that genuinely passed"* — so the set must be rendered or the ranges in it read as ranges that passed. But `CoverageVerification.unchecked` is one flat list fed by two causes with different futures: a provider range whose edge is `unverifiable` carries no hash and no spec version and can **never** be compared (§2.2 gives it no promotion path), while a chain this client cannot reach becomes comparable the moment it can. A user told *"this could not be checked"* about the first is owed *"and never will be"*; about the second, *"try again when this device is connected"* — which is the same distinction 10 §8.4's `reach` field was added for one section over. F25 renders each range's own `RangeEdge` arm, which distinguishes them today by accident of what the datum carries rather than by anything §6.3 obliges. **Ruling needed:** does §6.3 require the two causes to be distinguishable in the verification result, or is *cannot say* one state with one sentence?

## Status

**open — raised by F25.** Conservative reading shipped: the surface says only what is true of both, so no ruling can make the shipped sentence false. Filed to **B7**
