## Question

**Doc 10 §9's budget model is built on a book count 6.32× the chain's real one, and omits the event stream 02 §5 freezes as mandatory.** §9.1 publishes "the chain permits 196 active books" and concludes that deep raw history "is not achievable within the caps". The sustained *observing* count is **31**: `crank_observe` admits only `Trading`/`Extended`, but the `MaxLiveMarkets` slot is released at the vault terminal latch, so live-but-closed books count against 196 and provably emit nothing. Both models agree exactly on the per-book rate (891.428571 rows/book/day), which localises the whole discrepancy to that one number. Corrected cells: desktop raw depth 8.5 d → **54.28 d**, mobile 2.1 → 13.57, hourly candles 106 d → **672 d** — capacity-safe, but the published limitation is false. The unsafe half: §9.1 models only `Observed` while 02 §5 freezes `Traded + Observed`; sized from the committed `buy()` weight **including the DbWeight addend** (77 reads / 67 writes ≈ 88 % of ref_time), **proof size binds at 36 fills/block against ref_time's 153**, and `Traded` alone consumes the desktop event share in 17.36 h. Also: §9.3's metadata caps exceed their own §9.2 shares (16 > 15 MB desktop, 6 > 3.75 MB mobile) while the real committed blob is **0.107 MB** gz against a stated "~1–2 MB"; release-shipped fallback metadata has no §9.4 bundle row; and of seven "normative value(s): 13-parameters.md" citations in doc 10, the **300 MB / 75 MB quota caps do not resolve** — doc 13 contains no such row

## Status

**RULED 2026-08-06 (R-1) — 10 §9 corrected throughout, and the derivation made executable.** The observing count is `epoch.slots·6 + 1` = **31**, which 13 §5 item 4 already derived for the keeper crank load from the same parameters; it is a *maximum* because 13 §5 item 2's frozen 52-vault envelope makes the occupancy screen refuse every `epoch.slots` raise above 5. Corrected cells stand as filed (raw desktop 54.3 d, mobile 13.6 d, candles1h 672 d / 168 d) and §9.2's *"not achievable within the caps"* is withdrawn as false. **The filed fill ceiling was wrong in the unsafe direction**: 36/block assumed a 5 MiB PoV, but `polkadot-primitives 25.0.0` pins `MAX_POV_SIZE` at 10 MiB, and the true dispatched figure is **70** — `buy`'s `#[pallet::weight]` adds two reads and `EXTERNAL_TRADE_ROUTE_PROOF_SURCHARGE` over the generated weight, which alone moves it 72 → 70, so the pin is measured through `get_dispatch_info()` rather than read off the weight file. `Traded` is therefore ~121 MB/day and drains the desktop events share in **8.9 h** (mobile 2.2 h), from which §9.1 now rules that the index retains **watched-account events only** — §6.5's existing *"proportional to the user's own activity"* rule applied to storage as well as body fetches; a chain-wide trade tape is a bounded windowed read, never a retained table. §9.3's caps are cut to the §9.2 metadata share (15 / 3.75 MB) against a measured 0.14 MB gz blob; §9.4 gains the missing release-shipped-metadata bundle row; the 300/75 MB caps drop their doc 13 citation and are stated as client-local values §9 owns, since a browser quota is not a chain parameter. Bound in CI by `tools/ci/check-frontend-budgets.py` (25 cells, 16 mutation tests) plus the runtime pin `pov_budgets::traded_event_ceiling_per_block_pinned_for_frontend_budgets`
