## 2. Frontend invariants INV-FE-1…15 — normative texts (F-3)

The superseded FRONTEND_PLAN.md cited INV-FE-1…15 at ~79 sites and certified against them (§32) without ever stating their texts (review F-3). The texts below are published as normative. **From this document forward, frontend certification (§6) binds to these texts and to nothing else.** Provenance of each text is declared in §2.2; where the source usage was too thin to pin a text exactly, the text below is the most conservative statement consistent with every citation site.

> **INV-FE-1 (authoritative reads).** The client-embedded light client is the only authoritative read path. Every transaction-critical value — any value whose incorrectness could change what a user signs or their understanding of what signing does — is ultimately obtained from **finalized** chain state whose proofs the light client verified, or computed client-side purely from such verified inputs. This binds every value the client **sources**: an observation, a derivation, or anything rendered as being true of the chain. It does not bind what the user **chooses** — an amount, a limit, a fee asset, a selected account, or a request imported from an external tool — because such a value asserts nothing about chain state; a chosen value MUST NOT be represented as verified, MUST NOT satisfy any precondition, and MUST be evaluated against `Finalized<T>` chain values before it can reach a signature; where it is *displayed as a data item* — as an imported ceiling is, beside the chain-derived value it is clamped to — it carries `external-proposal`. No RPC endpoint, indexer, provider, cache, or best-head datum may be the source of a transaction-critical value. Data obtained over the quarantined RPC fallback is **never promoted** to verified status; verified status requires a light-client re-read (D-6/F-2, [10-frontend-architecture.md](10-frontend-architecture.md)).
>
> **INV-FE-2 (pre-sign revalidation).** Immediately before signature, every declared precondition of the transaction is re-read at a single finalized block, and the live runtime version is re-checked against the version the payload was built for; any failure blocks signing with a diff of expected vs actual. This refresh is structural on every submit path — no code path can reach a signer without it.
>
> **INV-FE-3 (acceleration firewall).** Optional acceleration (community indexers, snapshots, any historical provider) is never transaction-critical: provider-supplied data never satisfies a precondition, never renders a protocol-outcome state ("passed / settled / mature / final / safe") without a direct chain read, and is barred from the transaction path **structurally** — by build-time package dependency boundaries enforced in CI, including inside the application package itself — not by reviewer vigilance.
>
> **INV-FE-4 (zero-infrastructure operation).** Every protocol workflow — epoch/proposal discovery; proposal detail including reading the exact committed proposal payload bytes and hash-checking them client-side; trading; positions, split/merge/transfer and every redemption path including `Voided`; proposal submission; oracle reporting and challenges; execution-queue interaction and permissionless cranks; governance referenda (vote/delegate/unlock, ratification, `OracleResolution`); operator workflows; and USDC funding/withdrawal ([11-frontend-workflows.md](11-frontend-workflows.md)) — operates against finalized, light-client-verified chain state with **zero optional infrastructure available**: no indexer, no RPC endpoint, no provider, cleared local storage.
>
> **INV-FE-5 (no key custody).** The application never holds, derives, stores, or transmits private keys or any signing secret. Signing occurs exclusively in the user's chosen wallet (browser extension or raw-payload external signer); the application boundary carries only encoded payloads outward and signatures inward.
>
> **INV-FE-6 (serverless client).** The canonical frontend is a static, content-addressed bundle: no application backend, no server-side rendering, no required RPC endpoint, no required indexer, and no feature whose correctness depends on any server operated for the application. Features that inherently require servers are out of scope rather than centralized.
>
> **INV-FE-7 (disposable local storage).** Browser-local storage is a non-authoritative cache and derived-history store. Its loss, corruption, or eviction is a performance and convenience event only: the transaction path never reads it, protocol workflows are unaffected, and the application rebuilds it automatically from chain data.
>
> **INV-FE-8 (single-operator tamper evidence).** No single operator — Arweave gateway, ArNS controller, RPC host, chain peer, indexer, snapshot publisher, or the CI system — can silently alter the application or its interpretation of chain state. Every such channel carries a detection mechanism: content-hash verification and the signed release self-check (distribution), light-client proof verification and quote double-derivation (chain), sampling and snapshot diffing (acceleration), multi-gateway resolution cross-checks (naming). Detected divergence is surfaced to the user; it is never silently repaired.
>
> **INV-FE-9 (provenance labeling).** Every displayed data item carries an explicit, typed verification status (`verified-finalized`, `verified-best`, `derived-local`, `provider`, `stale-cache`, `external-proposal`). Unfinalized/best-head data is display-only and never transaction-critical. There is no unlabeled rendering path: UI data components reject unlabeled values by type.
>
> **INV-FE-10 (reproducible releases).** Every release is reproducibly buildable: independent parties following the published recipe obtain byte-identical output whose tree hash equals the published, multi-party-signed release manifest; release identity is content-addressed. A user can independently verify *which* application they run, from source commit to served bytes, without trusting the release team or CI.
>
> **INV-FE-11 (pinned identity, visible provenance).** The bundle pins the complete identity of what it is and what it talks to — release content address (TXID), source commit, per-file hashes, descriptor metadata hashes, supported spec-version range, chain-spec hashes, and relay + parachain genesis hashes — verifies the chain identity at boot (genesis mismatch is terminal), and displays all of it in an always-available verification panel.
>
> **INV-FE-12 (fail-safe under unknown runtimes).** When the runtime surface is unknown or partially incompatible, the application fails safe into explicit `restricted` or `read-only-incompatible` modes: signing is disabled wherever compatibility is unproven, reads continue only where compatibility probes pass, undecodable data renders as raw SCALE with an explicit warning, and the application **never guesses at encodings**.
>
> **INV-FE-13 (no telemetry, no remote configuration).** The application emits no telemetry or analytics of any kind, and has no remote-configuration channel: every provider suggestion, locale, bootnode list, default and text ships inside the signed release; user settings live only on the device. Application behavior changes only by shipping a new, independently verifiable release.
>
> **INV-FE-14 (signing transparency).** Everything a user signs is fully inspectable before signing: a human-readable summary, a structured decoded tree, and the exact raw SCALE bytes with their payload hash — all derived from the same bytes that will be signed, never from UI form state — plus signed-extension details. Expert mode exposes the raw storage keys and SCALE values behind every precondition.
>
> **INV-FE-15 (replaceable, reproducible, labeled acceleration).** Historical acceleration is optional, user-selected, and interchangeable: snapshots are deterministic, content-addressed exports that anyone can reproduce and verify byte-for-byte; live providers implement a minimal open read-only interface anyone can operate; every provider-derived row carries its origin to the pixel; providers are sampled against chain state where feasible and auto-disabled on mismatch. Historical analytics **degrade gracefully**: verified data is shown as verified; everything else is either absent with an explanation or present and labeled — gaps are first-class and visible, never silently spliced (D-6).

### 2.1 Amendment discipline

These texts are normative and version-controlled with this document. Amending any INV-FE text requires the same joint sign-off as [02-integration-contract.md](02-integration-contract.md) changes. D-11 extended the *workflow list* inside INV-FE-4 (governance, operator, funding surfaces) without amending the invariant's obligation — that reading is ratified here.

**Amendments and ratified readings (D-21, 2026-08-03).** The external-tool handoff of [10 §13](10-frontend-architecture.md) / [11 §11.14](11-frontend-workflows.md) required **two INV-FE texts to be amended**, and the joint sign-off above was given by the user, who owns both sides under R-1. An earlier draft of this batch claimed no text needed amending and carried the two changes as "ratified readings"; an adversarial review called that special pleading and was right. The distinction is not bookkeeping — a reading that changes what an invariant *requires* is an amendment, and §6 binds certification to these texts and to nothing else.

**Amendment 1 — INV-FE-1 distinguishes sourced values from chosen values.** As published, the invariant bound *"any value whose incorrectness could change what a user signs"* to finalized chain state. A user-typed amount satisfies that antecedent, so the text as written forbade the transaction screens themselves — a **pre-existing defect**, independent of the handoff, that the handoff merely made impossible to keep ignoring. The amendment states the distinction the design always relied on: the obligation binds what the client **sources** (observations, derivations, anything rendered as true of the chain) and not what the user **chooses** (an amount, a limit, a fee asset, an account, an imported request). Nothing is loosened for sourced values, and three obligations are newly stated for chosen ones — a non-verified status, no precondition may be satisfied by one, and evaluation against `Finalized<T>` before signature.

**Amendment 2 — INV-FE-9's enumeration gains `external-proposal`.** A requested ceiling rendered beside its chain-derived clamp is a displayed item, and the five-status enumeration had no label for it, so the honest options were to add one or to forbid rendering imported values at all. `external-proposal` is the bottom of the lattice: no block reference, because there is nothing it is true *at*; satisfies no precondition; never promoted; never persisted; and the payload is built from the clamped result rather than from it. This strengthens the *"no unlabeled rendering path"* obligation rather than relaxing it — but it does change the enumeration, which is why it is recorded here as an amendment and not as a reading.

**Two readings are ratified, and they change no obligation:**

1. **An external analysis tool is not infrastructure** under INV-FE-4 and INV-FE-6. No workflow's correctness depends on one; every INV-FE-4 workflow completes with none present; and the handoff adds no workflow to INV-FE-4's list, because analysis assistance is not a protocol workflow. INV-FE-6's *"features that inherently require servers are out of scope rather than centralized"* is what **selects** the file/clipboard/share transport, so the design is an application of the invariant rather than an exception to it.
2. **A user-initiated export is not telemetry, and an imported request is not remote configuration**, under INV-FE-13. Export first: the application collects nothing, chooses no destination, and emits nothing unbidden. Import is the harder half, and the reading rests on three properties rather than on the action vocabulary being closed — *a narrow control channel is still a control channel, so narrowness is not the argument*. An imported document is not remote configuration because **(a) the application never fetches it** — it arrives only by an act the user performs, from a party the user chose; **(b) it persists nothing** — no setting, default, preference, or record of any kind survives it; and **(c) it cannot alter any later operation** — the release's behavior on the next operation is bit-identical whether or not anything was ever imported. Property (c) is why [10 §13.3](10-frontend-architecture.md) carries **no replay memory at all**: a stored set of seen digests would make a later import behave differently, falsifying (c) to buy a guard that one changed byte defeats. Three adjacent things *would* violate the invariant and are prohibited by name: any fetch to check for a newer Skill or prompt set; any counting, sampling, or reporting of exports and imports, including locally aggregated; and any inbound document that carries a setting rather than a request.

## 4. Testing and verification regime (merged BE §24 + FE §23)

### 4.1 Backend: mock-runtime, integration, model checking

Per pallet: mock-runtime unit tests covering every extrinsic × every error path × origin misuse.

**Two-identity obligations (normative; added 2026-07-31, milestone E6).** Where a right and its cost are split across two identities ([05](05-welfare-and-decision-engine.md) §1.5's author/funder), the suite MUST bind **each** incidence to **its own** identity and MUST NOT infer one from the other. Concretely, for the proposal record: the [08](08-treasury-and-economics.md) §1.1 reward reaches the author and not the funder; the [06](06-governance-and-guardians.md) §4 refund and 10 % slash reach the funder and leave the author's balance exactly unchanged; `epoch.withdraw` succeeds for author and for funder and fails for a third account; `epoch.bind_ratification` fails for the funder. A test that exercises only the collapsed case — author == funder, which is every pre-v18 state — proves none of these and MUST NOT be counted toward them.

**Splitting an identity creates a try-state obligation, not only test obligations.** Wherever a custody record names one of the two identities, `try-state` MUST bind that name to the identity the proposal record carries. The binding was previously implicit — with one identity nothing could diverge, so nothing had to check — and the divergent state is representable from the moment of the split while every other assertion still passes: a bond keyed to the author is fully collateralized, sits within its liability bound, and is not orphaned, yet its refund and its slash both reach the wrong party. This is the general rule the proposal record instances as `ProposalBond.funder == Proposal.funder`.

**The rate-limit obligation is a regression, not a property, and it has a falsifiability condition.** [06](06-governance-and-guardians.md) §4 rule 4 keys the per-account intake cap to the funder because an author-keyed cap is free to evade. The suite MUST drive N distinct authors against one funder and require the cap to bind on the funder's count — and that test MUST be shown to **fail against the author-keyed predicate**. A regression whose pre-fix behavior was never observed does not evidence the defect it claims to close; this is the same standard [04](04-markets-and-pricing.md)'s mutation-proven tests already meet. Cross-pallet integration tests on the full runtime: complete lifecycles for all proposal classes — including the T21/T22/T23 paths (`Rejected → Measuring`, retry exhaustion/success) and the rerun `Extended` path ([05](05-welfare-and-decision-engine.md)) — with all worked examples of [09](09-execution-upgrades-and-rollout.md) scripted as regressions. TLA⁺ (or Quint) models of the proposal machine and ledger resolution prove I-3, I-14, I-15, I-18, I-26/I-27 over all interleavings including guardian, oracle-dispute, `void` and T20 events.

**Baseline settlement liveness (normative; SQ-320).** The proposal-machine model MUST additionally carry the property that **no reachable state leaves an epoch's Baseline vault permanently unsettleable**: from every reachable interleaving prefix for an epoch that opens a Baseline vault, some admissible continuation reaches `BaselineState::Settled` — specifically including prefixes in which every one of the epoch's proposals is force-rejected (T20) before any reaches `Measuring`, so that no cohort ever forms and the measured e+3 settlement is never scheduled. This family is exactly what the per-extrinsic suites and the conservation properties structurally cannot see: a stranded Baseline vault is fully collateralized, satisfies I-1 and I-4, and lets full-pair holders exit at par via `merge_baseline`, so nothing but a liveness statement detects that its single-sided holders can never redeem. The three discharge paths are measured T19 plus the two neutral transitions owned by [05](05-welfare-and-decision-engine.md) §7(5)–(6).

### 4.3 Ledger property-test set (restated over the enlarged set)

- **PT-1 conservation:** random op sequences (10⁶ cases) maintain the per-branch I-1 identities, for proposal vaults (both branches, gate terms included) and Baseline vaults.
- **PT-2 annulment (restated per D-1/D-3):** (a) **cross-branch** complete pairs recover exactly par through `merge`; (b) a **real** wrapper-buyer portfolio — the purchased target scalar leg plus `cost` mirror branch-USDC ([04](04-markets-and-pricing.md) §6.1) — recovers its exact D-1 **neutral value** after pair-first netting, so net principal delta is `neutral recovery − cost − fees`; (c) deliberately unpaired holdings recover the D-1 half/quarter schedule exactly. **"Net principal delta = −fees only" is a target for normal losing-branch annulment, NOT for protocol VOID** (SQ-171): an isolated buy recovers `floor(amount/4) + floor(cost/2)`, and ignoring dust the non-fee term is `(amount/2 − cost)/2` — zero iff the *realized average execution price* is 0.5, which a finite LMSR buy opening at that quote never achieves. These are **obligations the suite MUST satisfy**: PT-2 MUST drive real `market-core` buys, isolated and mixed, rather than reconstructing wrapper bookkeeping at synthetic prices. The old "no loss of principal for any single-branch holder" claim is **not** a test target — it was false. **PT-2's target is PRESERVED by milestone E1, and the suite MUST now prove that it stays preserved (normative; added 2026-07-29).** The "net principal delta = −fees only" target for **normal losing-branch annulment** survives the [03](03-conditional-ledger.md) §5.3a redemption fee unchanged, and it survives for exactly one reason: `redeem` — the par leg the D-3 wrapper credits the buyer — is **exempt** from the charged set, so the mirror branch-USDC still settles 1:1 in the winning branch and "fees" still means *trade* fees alone (I-2, G-3). Because that preservation rests on an exemption rather than on structure, the suite MUST additionally assert the same target **with a non-zero `ledger.redeem_fee` configured**: that assertion is the regression that catches a future widening of the charged set into the par leg, which would falsify G-3, D-3, I-2(b) and this property simultaneously and would otherwise show up nowhere, since a zero-rate suite cannot see it. Paths (b) and (c) are likewise asserted at both rates: (b)'s target scalar leg is charged and (c)'s `redeem_void` is exempt, so a fee that leaked into `redeem_void` would move (c) and nothing else.
- **PT-3 rounding (bound restated net of the fee, 2026-07-29, milestone E1):** under a **pair-first** full-redemption schedule, Σ **net** payouts over all holders ∈ `[E − r − F, E − F]`, where **`F` is the total [03](03-conditional-ledger.md) §5.3a fee retained over the same schedule** (`F = 0` in `Voided` and for any schedule at `ledger.redeem_fee = 0`, since every `Voided` operation is exempt) and `r` counts the **non-zero residual redemptions that apply an independent floor, per residual `PositionId`** — not per distinct account (SQ-168: one account holding several independently-rounded instrument classes loses dust once per class, so an account count is not a sound bound). The suite MUST therefore cover an account holding several residual `PositionId`s and a residual holding redeemed across several calls. Exact pair redemptions contribute 0 to `r`; splitting one residual holding across several calls increases `r`. Paired redemptions (`redeem_scalar_pair`, gate pairs) pay exactly `a` per set **gross**; every unpaired floor rounds against the claimant (covers the B-5 counterexample class). **`E − F` remains fully accounted**: the fee moves value between claimants and the protocol without leaving the accounted total, so `Σ net payouts + F` is bounded exactly as the pre-E1 form bounded `Σ payouts`, and the suite MUST assert that identity rather than merely the shifted interval — a fee that were drawn twice on escrow, or credited from anywhere other than a completed payout, breaks it while leaving the interval satisfiable (I-31).
- **PT-4 no-mint-outside-declared-ops:** supply changes occur only in the enumerated minting operations, per instrument kind including `GateYes`/`GateNo` and Baseline positions.
- **PT-5 reap safety:** claimant reap never executes while any position balance > 0 unless the archive delay elapsed; archived residue equals Σ outstanding claims valued at settlement. Market reap at the same boundary discards only its two protocol owners' bounded inventory (≤28 proposal or ≤4 Baseline cells), leaves claimant rows/vault collateral untouched, and is tested under both market-first and ledger-first interleavings. Signed post-VOID transfer into a protocol destination rejects without mutation before, during and after registration; the predicted-future-address poisoning regression and origin-gated MarketAuthority ingress are both covered.
- **PT-6 VOID reachability and conservation:** from `Open` and `Resolved`, `void` succeeds; repeat `void` in `Voided` and `void` from `ScalarSettled` error without state change (`Voided` is terminal — [03](03-conditional-ledger.md) §2.3). Run at a **non-zero `ledger.redeem_fee`** the payouts MUST be byte-identical to the zero-rate run: `redeem_void` and every `merge*` are exempt, so no D-1 ratio moves and the §6.4 valuation argument is re-verified rather than restated (I-32(c)). A divergence here is a fee that leaked into the emergency path.
- **PT-7 pair and gate exactness (restated relative, 2026-07-29, milestone E1):** `redeem_scalar_pair`/`redeem_baseline_pair` pay exactly `a` **gross** — i.e. `a − fee_pair(a)` net under [03](03-conditional-ledger.md) §5.3a(2a), where `fee_pair` is the sum of the fees the same holdings would pay leg by leg, and exactly `a` for a `ProtocolAccounts` caller or where every leg's waiver fires. Generated over both instances × the full ledger operation alphabet, including the adversarial cases: a transfer whose destination is the other domain's book address (MUST fail atomically), a vault id from the other band (MUST error `UnknownVault`), and a service-instance deficit (MUST NOT latch I-4 on the primary).

### 4.5 Fuzzing, benchmarks, weights

cargo-fuzz on SCALE decoding of payload batches, nested-wrapper filtering (incl. `proxy_announced`, `as_multi_threshold_1`), and LMSR trade paths. `frame-benchmarking` for every call, hook **and transaction extension**; CI gates on > 10 % weight regressions; PoV-size tracking against the active-196/retained-2,240 budgets derived in [13-parameters.md](13-parameters.md). **Supply-chain gates (TH-34):** every backend CI run asserts the committed lockfile (`cargo --locked`) and a clean advisory pass under the [01 §9](01-system-overview.md) exact-pin regime; the §5 release pipeline MUST NOT publish artifacts from a run with either gate red.

**Advisory sources (normative; amended 2026-07-20, SQ-219).** The normative advisory sources are **RustSec *and* the GitHub Advisory Database (via OSV)**. RustSec alone is insufficient and the insufficiency is structural, not operational: for crates.io the GitHub Advisory Database is a strict *superset*, so an advisory may exist with no RUSTSEC id at all, against which `cargo-audit` is blind rather than misconfigured. The two legs MUST partition the space rather than overlap — `cargo-audit` gates everything RustSec covers (preserving its `unmaintained`/`unsound` informational classification and its annotated exception file), and a pinned OSV leg gates **exactly the complement**: a finding is treated as RustSec-covered only when it carries a RUSTSEC id itself, or an alias that is itself a RustSec record *for that same package* — an alias pointing at a RustSec record for a sibling package confers no coverage. Waivers on the complement leg are per-entry annotated, keyed to `(id, package, version)` so a version bump cannot silently inherit one, and **expire mechanically**: a waiver matching no live finding fails the gate.

**The three fuzz areas are exhaustive by construction (normative; amended 2026-07-20, SQ-226/SQ-227).** The areas named above are the complete `cargo-fuzz` obligation; an invariant not named here is verified by its own method in §1's Verification column, not by an unstated fuzz duty. Fuzz targets MAY be built against the **frame-free functional cores** rather than the aggregate runtime types: the fuzz workspace is deliberately isolated (its own nightly toolchain, outside the runtime workspace's exact-pin closure) so that libFuzzer and nightly can never perturb the pinned SDK line, and linking the aggregate `RuntimeCall` would dissolve that isolation. Where a target fuzzes a core type **whose production counterpart has a different decode or dispatch shape** — so that the fuzzed type is a *model* of the production boundary rather than the boundary itself — that production boundary MUST carry its own hardening plus a named regression test in the runtime suite; for payload batches that is the SCALE decode-depth limit and its fail-closed regression (SQ-225). Model-type fuzzing without that runtime-side pairing is **not** a sufficient discharge. Where the core *is* the production path the pallet delegates to (LMSR trade paths), no such pairing arises and none is required.

**Weights and the regression gate (normative; amended 2026-07-20, SQ-147/SQ-148/SQ-149).**

- The > 10 % gate is discharged by a deterministic **diff of the committed generated weight artifacts** against the merge base — worst-case totals (ref-time, proof-size, reads, writes) evaluated at each revision's component high bounds, over the generated weight files the runtime actually dispatches with. Three qualifications are deliberate and normative: a regression whose *absolute* delta falls below a per-dimension noise floor does not trip the gate; an intentional regression passes only under a committed, justified acknowledgement that **expires mechanically** (a stale acknowledgement fails the gate, as does an unacknowledged removal); and CI does **not** force benchmark *regeneration* when benchmarked source changes — regeneration is an authoring and release-time duty. Since 2026-07-26 (SQ-490) the per-commit job proves more than executability: it verifies the **calibration of every storage dimension** against a fresh measurement (next bullet), so "executability, not calibration" now holds of ref-time alone. Because the gate measures *growth*, it cannot see absolute headroom: the complementary standing obligation is that every production-dispatched call and per-block hook, at its worst component arguments, fits its dispatch class, with the [13](13-parameters.md) §5 per-call PoV estimates pinned as regression ceilings. `try-runtime`-only `try_state` hooks are snapshot audits rather than block calls: their saturated weights remain generated and regression-gated, but the normal-class inclusion ceiling does not apply.
- **The absence of a regeneration is gated, per function (normative; added 2026-07-26, SQ-490).** The growth diff above compares two *committed* artifacts, so it detects a regeneration and never its absence: benchmarked source may move for weeks while the committed weights keep describing the previous storage layout, with every gate green — the state in which a permissionless call shipped declaring 8 storage reads while performing 261. A per-commit job therefore **re-measures every pallet and diffs the result against the committed artifact function by function**, never by file date: a file header attributes all of its functions to a single generation event, which is exactly how two hand-appended functions hid inside an otherwise-generated file. The comparison is on **worst-case totals** (base + slope × the component's high bound), never on the intercept and slope separately: the generator splits one measured cost between the two, and that split is not stable across sampling fidelities even where the total is. What may be gated *hard* is then dictated by measurement, and the boundary is the presence of a fitted component. **A constant-weight function's storage totals are invariant to sampling fidelity** and are hard-gated at any fidelity — which is what makes a cheap per-commit re-measurement worth running, and is the class the 8-versus-261-reads defect belonged to. **A component-bearing function's are not**: a 2-point fit may redistribute a linear term or lose it entirely (a measured case reports worst-case writes 100 at 50/20 against 3 at 2/1), and since losing it *understates*, those functions are hard-gated only when the run's sampling matches the committed artifact's recorded fidelity, and are advisory otherwise. **Ref-time is advisory always** — the same benchmark on unchanged code has been measured moving 127 % between runs — consistent with the noise floor above. Full-fidelity re-measurement of the component-bearing functions is therefore a release-time obligation, and its absence at reduced fidelity MUST be reported rather than presented as coverage. Two obligations follow: one benchmark fixture that cannot be satisfied in this runtime MUST NOT discard the other functions of its pallet, and any function carried forward without a fresh measurement MUST carry a marker that the gate reads and reports, so that "measured long ago" is never silently indistinguishable from "measured now".
- **Generated weight files stay generated; unbenchmarkable terms are decomposed, not spliced.** A weight term MUST NOT be hand-written into, or hand-added inside, a `frame-benchmarking`-generated file. The generator does not emit such edits, so a regeneration deletes them — and the deletion presents as a weight **decrease**, which a growth-only gate is structurally unable to see. Where a call's worst case cannot be exercised by any single fixture (for example a term that fires only on an epoch crossing, while the call's heaviest fixture by construction crosses nothing), the term MUST be benchmarked separately — a non-dispatchable benchmark over the work itself is permitted and expected — and composed into the call's declared weight at its `#[pallet::weight]` attribute. Moving such a term into a delegating wrapper outside the generated files is **not** an acceptable alternative: the > 10 % gate parses the generated artifacts, so a wrapper removes the term from gate coverage entirely. Any consumer that pins a call's weight (PoV budgets, dispatch-class fit) MUST read the **dispatched** weight, since a composed call's generated function is only one addend of what the chain charges.
- **Charged weight of a payload-executing extrinsic.** [09](09-execution-upgrades-and-rollout.md) §1.2(11) bounds a batch's *declared* weight; it does not fix what the executing extrinsic charges. Such an extrinsic MUST **pre-charge** its own overhead at the call-count bound plus the full declared payload ceiling, and refund actuals via post-dispatch info. Where the dispatcher does not surface inner post-dispatch weight, the refund MUST fall back to the **declared** inner weights — never to a value that could undercharge. The no-undercharge property rests on the pre-dispatch check that the declared sum is within the payload ceiling, not on any debug-only assertion.
- **Batched cranks are weighed worst-case heterogeneous.** A batch extrinsic is benchmarked and charged as if **every** item carries a distinct, maximal payload; a shared or undersized fixture is forbidden, since it collapses the per-item proof slope (the shared-preimage fixture that undercharged PoV ≈ 4× is the standing justification).
- **Transaction extensions are weighted in this runtime, not upstream (normative; added 2026-07-30, SQ-523).** A `TransactionExtension` is neither a call nor a hook, and the mandate above now names it explicitly because that omission is how an unweighted path shipped. Where the runtime substitutes its own type into an extension's generic slots — a `HandleCredit`, an `OnChargeTransaction`, a currency or asset adapter — the upstream pallet's reference weight ceases to describe what this chain executes, since that measurement was taken against the *reference* runtime's substitution. Whenever such a substitution performs storage work, the owning pallet MUST be benchmarked **in this runtime** and its `WeightInfo` bound to the generated artifact rather than to `()`; a pallet whose only benchmarks are extension fixtures is in scope of every rule above, the per-function re-measurement included. Two properties make an understatement here worse than for an ordinary call, and are why this is stated separately. First, **a post-dispatch refund does not make the declared weight self-correcting.** Extensions do have a refund path, but in the SDK idiom it is computed from the *same* `WeightInfo` that was charged — the unspent amount is the declared weight minus the weight of the branch actually taken, both read from that trait — so on the charged path it is identically zero. The mechanism corrects a mis-predicted *branch*; it is structurally blind to a mis-measured one, and an understated function is charged and refunded at the same understated value. A refund therefore MUST NOT be treated as slack that absorbs measurement error; where an extension computes its refund from some independent measure, that MUST be shown rather than assumed. Second, it is charged on **every** extrinsic that takes the path rather than on one feature's users, so the error scales with block occupancy rather than with adoption. A further obligation follows from the fixture side: upstream fixtures are written against the reference runtime's admissible inputs, so where this runtime **narrows** them (an asset filter, an origin filter, a governed rate that must exist), the fixture MUST be re-pointed at an input this runtime accepts and its preconditions seeded. Otherwise one of two things happens, and both fail this section. If the fixture **asserts** that the extension succeeds — as the SDK's do — the narrowed input makes validation refuse, the assertion trips, and the benchmark **aborts**, producing no weight at all; that is the safer failure, but it presents as a tooling error rather than as a missing weight, which is how one went unfixed for a session. If the fixture does **not** assert success, it silently measures the **rejection** path — a cheap early return — and the resulting weight understates by construction, which is the direction this section forbids everywhere else.

**Waiver discipline (normative; added 2026-07-20).** The exact-pin regime and a clean advisory gate are in genuine tension: an advisory can be un-actionable inside the pin regime because the vulnerable version is forced by a pinned SDK component, and unpinning to clear it would breach [01 §9](01-system-overview.md). "Clean" therefore means *clean under a declared, annotated exception set*, subject to all of:

1. **Per-entry annotation.** Every waived advisory names the component that forces the vulnerable version and a **per-family exit criterion** — the upstream condition that clears it. A waiver with no exit criterion is not admissible.
2. **Pin-forced proof.** Each entry is admissible only while the pin genuinely forces it; an attempted `cargo update --precise` (or equivalent) MUST be recorded with its blocker. An advisory that is merely inconvenient to fix is not waivable.
3. **No stale waivers.** A waiver MUST NOT outlive the finding that forced it: the advisory-complement leg fails on a waiver matching no finding, and the exception set as a whole is **re-triaged from scratch at every SDK train bump** — never carried forward unexamined — so an entry whose pin has moved cannot survive one.
4. **Blast-radius containment.** A waiver is scoped to the workspace whose pins force it. A separate workspace outside the pinned SDK closure — the keeper workspace, [01 §9](01-system-overview.md) — is audited from its own root, so no SDK-forced exception can mask a vulnerability there.
5. **Disclosure.** Every **publishable** release manifest (§5) carries the full waived-advisory list; a release whose manifest omits it is not publishable.

Waiver *count* is never a gate — a small list of well-understood pin-forced entries is healthier than a green gate bought by silence. This clause governs the waiver mechanism only; which advisory databases are normative sources for the gate is a separate question.

### 4.6 Generated limit-coverage suite (I-22 enforcement)

Generated from the parameter/meter registry in [13-parameters.md](13-parameters.md): for every rate limit, meter, and bound, one integration test drives a dispatch past it and asserts the specific error **or the specified boundary behaviour**. Registry keys without tests fail CI. This is the CI half of I-22's convention enforcement; the other half is the review checklist.

**Registry scope (normative; amended 2026-07-20, SQ-157).** "The registry" is the three *tabular* registries of [13](13-parameters.md) — §1 constitution keys, §2 kernel constants, §4 reconciled storage bounds. [13](13-parameters.md) §3 frozen protocol constants are deliberately **outside** the generated suite, on one operative test: no §3 value carries an independent dispatch limit of its own. Where a §3 value does carry a numeric bound, that bound is an alias of a §1/§2 row (`frn.window` is `dec.extension`) and is covered there. Should a §3 value ever acquire an independent dispatch limit, it is given a §1/§2 row — the extractor gains no special case. A corollary worth stating plainly: a normative constraint that lives only in §3 is **not** machine-checked by this suite, and if it needs to be, it needs a test of its own elsewhere.

**Enforcement unit (normative; amended 2026-07-20, SQ-160).** The unit of coverage is the individual **independent dispatch limit**, not the documentation row: a row declaring several independent limits materializes as one coverage key per limit, each separately bound to its own test. (It is not every numeric field — the hard-min/hard-max/max-Δ/cooldown tuple of a §1 key is one governed record, covered by the generated amendment-bounds suite, not four coverage keys.) `MinTrade`/`MaxTrade`, `prop.max_calls`/`max_bytes`/`max_weight`, the PB-LEDGER-FREEZE duration and one-renewal caps, the registry/attestor floors and the crank-batch bounds are therefore each covered in their own right. Non-numeric admissibility conditions sharing such a row — the I-4 drift-flag precondition of PB-LEDGER-FREEZE — are gates, not bounds, and carry no coverage key.

**`ledger.redeem_fee` is a new registry key and carries a coverage obligation (normative; added 2026-07-29, milestone E1).** [13](13-parameters.md) §1 gains `ledger.redeem_fee` (canonical key `ledger.rdm_fee`), so by the registry-scope rule above it MUST be classified in the coverage manifest and bound to a `// limit-coverage:` marked test, or CI fails. Applying the enforcement unit below to it gives exactly one coverage key and one marked test, not several:

- **The record's own hard-min/hard-max/max-Δ/cooldown tuple is one governed record**, covered by the generated per-key amendment-bounds suite — the same `param-bounds` treatment `mkt.fee` and `gate.v_min` already carry. It is not four keys, and the static `[0, 100]` bps ceiling is *not* the binding bound in any state where `mkt.fee < 100`.
- **The binding limit is the live cross-key coupling `ledger.redeem_fee ≤ mkt.fee`** ([08](08-treasury-and-economics.md) §10.6, [13](13-parameters.md) rule 7). Like `gate.v_min` ↔ `dec.v_min`, it binds at the **amendment boundary** against the live counterpart rather than at the consumer, so the marked test MUST drive an amendment of **either** key that would carry the pair outside the relation and assert the refusal — a test that only pushes `ledger.redeem_fee` upward leaves the `mkt.fee`-downward direction unproven, and that is the direction a revenue-motivated amendment would take (TH-65, [14](14-threat-model.md)). The same relation is asserted in `try-state` (§1).
- **The sub-`ledger.min_split` waiver is a specified boundary behaviour, not a bound**, and adds no key of its own: it is asserted alongside `ledger.min_split`'s existing key under the error-or-behaviour rule below, since the waived redemption succeeds rather than raising an error (I-32(b)).

**Error or behaviour (normative; amended 2026-07-20, SQ-156).** Several normative limits enforce *by design* without raising an error: the κ slew clamp and the observation-cadence no-op ([04 §7](04-markets-and-pricing.md)), the keeper-budget fail-soft zero-pay latch ([08 §6.3](08-treasury-and-economics.md)), FIFO ring eviction, bounded-progress batches that leave the remainder to the next crank, latch-once window extensions, and neutral settlement at `OracleSettleDeadline` ([07 §11](07-oracle-and-disputes.md)). For these the test asserts the **specified boundary behaviour** in place of a Module error; **exactly one** of the two — error or behaviour — is required per coverage key, never neither and never both. The key↔test binding is lexical, so what a key records is the *anchor* its test pins; for a behaviour-classified limit whose over-limit dispatch is nonetheless refused, that anchor may itself be an error variant, with the specified behaviour asserted alongside it in the same test body.

### 4.9 Economic simulation, contests, audits

Agent-based adversarial simulation (informed traders with planted ground truth, noise traders, arbitrage capital, scripted manipulators with [14](14-threat-model.md) budgets) across ≥ 10⁴ synthetic proposals: calibrates δ per class to a decidable-harm false-pass rate < 1 %, validates the measured-depth `AttackCost̂` mechanism of D-4 against **profitable** manipulation, and sizes POL. The proposal population's true-effect magnitude is modelled independently of δ (a proposal's welfare effect is a fact about the proposal, not the market's decision margin), so δ is a genuine calibration lever. The `3·InCapPrize ≤ AttackCost̂` step-9 certificate (SF = 3 kernel margin) and the [05](05-welfare-and-decision-engine.md) §5.6 `ManipFloor̂ ≥ 3·InCapPrize` Phase 3–4 sizing target are unchanged; the Phase-0 simulation additionally measures the *realized* attacker cost of each causal wrong-PASS flip and scores a flip that succeeds below the `3·InCapPrize` **budget** as a security failure **only when that realized cost is below the prize** — a profitable capture, the irreducible D-4 economic line that the SF = 3 margin conservatively guards. Causal decision-book displacement cost rises with δ, so δ-calibration closes profitable displacement captures (it moves the surviving near-boundary marginal exploit from ≈0.47× to ≈2.49× the prize); a flip whose realized cost instead holds **≥ the prize** — thin-market / gate-suppression griefing a deep-pocketed attacker sustains at a guaranteed loss — is a [14](14-threat-model.md) **TH-6** accepted residual (TM-18 is that row's superseded legacy label), recorded as a diagnostic rather than a gate failure. Public testnet contests with paid bounties for wrongful PASS, oracle corruption, or invariant breach — scope explicitly includes the frontend classes (tampered bundle, malicious provider, forged snapshot). ≥ 2 independent audit firms (scope A: ledger + constitution + guard; scope B: markets + decision + oracle) plus a mechanism-design review; scope-A re-audit before the final phase gate on any ledger change. Standing bug bounty from genesis.

**Reading of the < 1 % criterion (normative; amended 2026-07-20, SQ-269/SQ-273).** Two qualifiers on that threshold are load-bearing and neither may be dropped when the criterion is restated elsewhere ([09 §7.1](09-execution-upgrades-and-rollout.md) governs the phase gate).

1. **Per class, independently.** The rate is evaluated for **each** binding class — PARAM, TREASURY, CODE, META — and **every** class must hold strictly below 1 %; an aggregate or population-weighted rate is not the criterion. δ is calibrated per class, so a per-class target is what makes it a calibration lever at all, and a pooled rate would let a well-behaved class mask a mis-calibrated one. Each class therefore requires its own planted ground truth in the simulated proposal population.
2. **Decidable-harm, not raw.** The measured quantity is the **decidable-harm** false-pass rate — wrong PASSes among proposals whose true harm the decision rule was in a position to resolve — not the raw wrong-PASS rate over all proposals. The two differ materially and the distinction is the difference between a passable and an unpassable gate; a consumer field carrying this value is the decidable-harm rate regardless of any shorter name it is given.

**Realized-cost line (normative; ratified 2026-07-20, SQ-273).** The 1× *profitability* line stated above — a causal wrong-PASS flip is a security failure only when the attacker's realized cost falls **below the prize** — is the Phase-0 exit threshold. A flip whose realized cost holds at or above the prize but below `3·InCapPrize` is unprofitable griefing, recorded as a diagnostic and accepted as the [14](14-threat-model.md) TH-6 residual — whose own residual text names gate suppression alongside the deep-pocketed off-system-payoff attacker, so the reading covers the observed griefing mix and not merely the off-system case. The `3·InCapPrize ≤ AttackCost̂` step-9 certificate ([05 §5.6](05-welfare-and-decision-engine.md); D-4 states the same relation as `InCapPrize ≤ AttackCost̂/3`) is the **runtime** margin and is unchanged: it conservatively guards the 1× line the simulation validates directly. Raising the exit threshold to 3× is therefore not a tightening of the same measure but a different criterion, one the calibrated δ schedule alone cannot satisfy.

**The competing-venue leg, and why its two halves are gated differently (normative; added 2026-08-03, milestone N12).** Every rate above was measured on a chain with **no competing venue**, because Phase 0 has none: the hosted question service ([16](16-hosted-question-service.md), D-20) arms in Phase 4. The artifact therefore carries a separate `competing_venue` block, measured on a stratified sample against its own 0 % control and **never** entering `violations` — a Phase-4 condition cannot retro-invalidate a Phase-0 exit measured on a chain where the condition does not apply. Its arming rung is **anchored, not derived, and the difference is normative**: [16](16-hosted-question-service.md) §8.4's arming condition `Σ b_ext ≤ Σ pol.b(live)` bounds external **depth** at parity, and converting a depth bound into a **flow** bound requires a behavioural model. Proportional-to-depth allocation — the neutral one — is what puts the anchor at **one half**. That model errs in the **unsafe** direction: an external venue of equal depth but better fees, better returns or more interesting questions could take far more than half the flow, because depth parity does not imply flow parity. The ladder therefore **MUST** carry at least one rung above the arming rung, and the artifact reports the verdict there beside the arming verdict; where the two disagree, the arming decision depends on proportional allocation holding and that dependence is a published fact rather than a buried one. *(An earlier revision of this paragraph claimed the rung was derived outright and refused any rung above it as "a chain state §8.4 forbids" — wrong twice: a higher rung describes a different flow model on an admissible chain state, and refusing it suppressed the one probe of the anchor's optimistic direction. Corrected 2026-08-03 after adversarial review.)* Diversion thins **organic** formation on decision, gate and Baseline books and leaves attacker budgets untouched — an adversary targeting one proposal is not diverted by a venue elsewhere ([14](14-threat-model.md) TH-72) — so it thins the defense without thinning the attack.

**The leg has two halves and only one of them can be a threshold, which is the substantive part.** *Security*: per-class decidable-harm false-pass must hold < 1 % at the arming rung under the same reading as above; if it does not, the calibrated δ is under-sized for a chain running the service and [13](13-parameters.md) §1's δ rows MUST be raised before arming. *Liveness*: the decision-grade formation loss under the same diversion. **These MUST be read together and a clean security leg alone MUST NOT be reported as a clean result**, because diversion's first-order effect is that thin books stop being decision-grade at all — the proposal is rejected `NotDecisionGrade` and never reaches a wrong outcome. A false-pass-only criterion therefore reads *cleaner* the more decisions the diversion destroys, which is exactly backwards, and TH-72 names the real harm directly: proposals rejected for thin books, with no market signal that anything was attacked. No threshold is invented for the liveness half: [16](16-hosted-question-service.md) §8.4 states its falsifier and deliberately states no number, so the rise is measured here and the response — cutting `svc.max_live` — stays a values decision.

**Revenue and demand are an open obligation on this simulation (normative; added 2026-07-29, milestone E1).** [08](08-treasury-and-economics.md) §10 makes the protocol's self-funding arithmetic explicit and names this simulation as the falsifier of its central hypothesis — that uninformed flow of order `V*` exists at the [13](13-parameters.md) fee rates. **The simulation as it stands cannot test that hypothesis, and this paragraph records the gap as an obligation rather than leaving it to be rediscovered.** Its flow targets are `dec.v_min × formation_stratum` (`corr(volume, dec.v_min)` = 0.947, r² = 0.90) and **nothing in it responds to fee level, proposal salience or trader population**. Its fee output is therefore a restatement of the security parameter: a `mkt.fee` sensitivity sweep run against the present model would show revenue perfectly linear in the rate with **zero volume elasticity** — a property of the model, not of any market — and MUST NOT be presented, cited or published as a fee-sensitivity result. Five obligations follow, and the first is a gate on a claim rather than on a commit:

1. **A demand-side driver, before any self-funding claim.** Trading volume MUST be generated by a mechanism **not keyed off the security floor** — salience, information value, trader population, or fee-responsive participation — so that `V` and `H` can move independently of `dec.v_min`. Until that exists, no statement that the protocol is or becomes self-funding may rest on this simulation, and [08](08-treasury-and-economics.md) §10.2/§10.4's figures stand explicitly as a **structural consistency check, not a forecast**.
2. **Export the fee ledger.** `ExecutedBook.fees` is computed and then discarded, so **no fee figure appears in the committed artifact at all** — the one quantity [08](08-treasury-and-economics.md) §10 is accountable for is the one the evidence does not carry. Realized fee income MUST be recorded per book and aggregated into `bleavit.sim-calibration.v1`.
3. **Fix the lifetime-volume truncation.** `book.events.clear()` discards the pre-extension trade ledger, so an extended proposal's lifetime volume is measured from the extension onward. **51 % of proposals extend**, and the measured under-report is **2.5–3.3×**. Every volume-derived figure taken from the present artifact is low by that factor and MUST be treated as a floor until the truncation is repaired.
4. **One Baseline book per epoch, not per proposal.** The Baseline market is epoch-scoped ([04](04-markets-and-pricing.md) §8, [08](08-treasury-and-economics.md) §4.3); instantiating one per proposal inflates aggregate volume by **4.4 %** and mis-states the per-epoch Baseline fee base.
5. **Publish `τ`, the per-class realized fee income, and the informed/uninformed split**, alongside the existing decidable-harm rates. [08](08-treasury-and-economics.md) §10.6 states the who-pays hypothesis as a hypothesis — POL is a subsidy paid *to* traders, fees are collected *from* them — and these three series are what make it falsifiable. A Phase-0 artifact that omits them does not discharge that section's falsifier duty.

**Measured values [08](08-treasury-and-economics.md) §10 relies on, recorded here as the evidence side of that dependency.** Over the committed population, all-book turnover runs **5.8× min-book contest capital** (median; mean 7.29), of which **47.9 % is round-trip churn** that the [04](04-markets-and-pricing.md) §7a contest measure nets out by construction — giving **≈ 3.0 ex-churn**, the central `τ` of [08](08-treasury-and-economics.md) §10.4. Decision-grade books carry **1.5–1.8× `dec.v_min`** of held capital (median 1.76 among passing books). These are the structural relations the simulation *does* establish and they are legitimate as such; they are **not** measured demand, and obligations 1–5 above are what would make them so.

## 5. Cross-repo test artifacts (X-15)

The frontend's compatibility controls (§4.8) previously had no defined input feed. The publication contract below is normative; the exact schema and location constants of artifacts (1)–(4) are frozen in [02-integration-contract.md](02-integration-contract.md) §11 (the chain↔frontend runtime surface), while artifact (5) — the reference-model vector corpus — is schema-owned by [04-markets-and-pricing.md](04-markets-and-pricing.md) §5: 02 was finalized without a corpus row, deliberately, because the corpus is a test-time input consumed by suites, never by the running frontend.

**Per-release publication (backend duty).** For every tagged runtime release, backend CI MUST publish, as content-addressed release artifacts:

1. the reproducibly built **runtime wasm** with its hash, and the **SCALE metadata** with its metadata hash (the descriptor-generation inputs);
2. the **chain-spec artifacts** for every live environment;
3. the **Chopsticks configuration and Zombienet topology** files the backend's own §4.7 suites ran against;
4. **chainHead fixture transcripts** (deterministic JSON-RPC recordings) covering every storage item, event, and runtime-API call in the integration contract's critical surface;
5. the **reference-model JSON vector corpus** of §4.4 (LMSR V1–V6 + MPFR corpus + decision/ledger scenario vectors), as regenerated by that release's CI.

Artifacts are published to the backend repository's release feed and mirrored content-addressed (Arweave) so frontend release verification never depends on a mutable host.

**Paired recovery artifact (normative; B16 / contract v9).** In addition to artifacts (1)–(5), every primary runtime publication MUST carry its terminal-recovery runtime Wasm, SCALE metadata, build record and boot-extracted runtime identity. Assembly fails unless both builds come from the release commit, share one base profile and `spec_name`, bind their file bytes to booted `:code`, and the recovery `spec_version` is exactly primary + 1. The recovery profile MUST execute its zero-SDK-MBM and transition-repair suites before assembly. Because the recovery image becomes the live runtime when used, its metadata is a canonical-frontend descriptor input under [02 §11](02-integration-contract.md): descriptor generation, publication and drift CI MUST cover it before the primary is eligible. The Wasm/build identity remains an operator/consensus-safety input, and the new guard calls, internal storage and diagnostics remain outside the frontend ingest set. Any primary profile that registers an ordinary multi-block migration additionally needs mechanically bound, exhaustive cutpoint-repair evidence for each registered segment; absent that evidence, the build integrity gate requires zero registered MBMs. The first admitted segment, [03](03-conditional-ledger.md)'s `TotalEscrowed` backfill, proves exact-one primary registration, finite aggregate steps below the stall budget, zero recovery-profile SDK registrations, restart-safe recovery at every proposal/Baseline boundary and terminal unlock only with the exact mirror/version commit.

**Publication ordering and the mirror duty (normative; added 2026-07-20).** "Published" and "mirrored" above are two steps, not one, and their order is forced: CI publishes but cannot mirror, because CI holds no Arweave keys ([12 §1.4](12-release-and-operations.md)). The ordering is therefore (a) backend CI publishes the artifact set to the release feed as a **prerelease** whose notes state that it is not canonical and whose manifest records the mirror duty as outstanding; (b) an operator mirrors the complete set content-addressed and attaches **mirror evidence** — a mapping from every published content digest to its Arweave transaction id; (c) the release is promoted to canonical. **"Publishable" in the gating rule below is step (a)** — the gate a runtime release must clear to ship at all. Canonical status, which is what a frontend release may depend on under §4.8 and what [12 §1.4](12-release-and-operations.md) may repoint to, requires (c). A prerelease that never obtains mirror evidence never becomes canonical, so the mutable-host independence asserted above is preserved by (c) rather than by (a).

**Gating rule (binds both WBS rows).** Backend row **E15** and frontend row **FE-R1** implement the two sides of this contract; both are **release-gating**: a runtime release is not publishable until its artifact set (1)–(5) is published and the backend's own suites ran against exactly those artifacts; a frontend release is not publishable until §4.8's descriptor-drift, fixture, Chopsticks and Zombienet suites are green **against the published artifacts of every runtime version in its supported range**. A runtime change that breaks `FutarchyApi` or critical-surface compatibility MUST NOT merge without a coordinated frontend release (old P-10, accepted by D-2), and the D-14 descriptor lead time (`DescriptorLeadTime`, *normative value: [13](13-parameters.md)*) gives the frontend train the enforced window to consume a new artifact set before enactment.

**What "covering" means for artifact (4) (normative; added 2026-07-20).** A release-time fixture is recorded against a freshly built chain, which has not exercised the protocol; requiring it to contain an instance of every frozen event would make artifact (4) unproducible. Coverage of the critical surface is therefore defined per entry as (i) the entry is **present in this release's metadata** under its frozen name, and (ii) its **rendered layout agrees** with the layout [02 §11](02-integration-contract.md) freezes — the drift check the frontend's descriptor suites actually consume. Additionally, once per fixture, (iii) the `System.Events` blob of a **real executed block** MUST be retrievable and non-empty over **both** the `chainHead` and the legacy storage transports, so a fixture cannot certify a surface that only one transport can reach. Requirement (iii) is a single per-fixture transport-and-liveness proof and explicitly **not** per-variant evidence: a release fixture does not assert that any particular event variant was ever emitted. Demonstrating actual emission belongs to the scenario-driven §4.7 suites, whose execution is evidenced by the environment-run contract below.

**Environment run evidence (normative; added 2026-07-20).** "The backend's own suites ran against exactly those artifacts" is discharged by a machine-checkable artifact, never by a green commit-level CI run: commit CI proves the *source* was tested, not that the *packaged bytes* were. The release pipeline MUST re-execute the suites against the built artifacts and emit run evidence carrying, as frozen fields: the schema identifier; the suite kind; the **release runtime-wasm hash**; the **release commit**; the **tier** the run covers (below); the **named suites that ran, each with its result**; the **suites excluded, each with its reason** (below); and a **per-file digest inventory** of the environment definitions the run used. Assembly MUST validate that evidence against the packaged artifact set **byte-for-byte** — every inventoried file present and hash-equal, with no unpackaged extras — and MUST reject an **empty** inventory, which would otherwise let a placeholder environment directory satisfy the gate vacuously. It MUST also refuse evidence whose wasm hash or commit does not bind to the release under assembly. Producers MAY emit additional fields; consumers MUST NOT depend on them. A release whose evidence is absent or invalid is not publishable — including when the evidence is withheld because a suite's prerequisites are unwired, which is the intended fail-closed behavior and not a reason to relax the gate.

**Suite tiering (normative; added 2026-07-20).** §4.7's list includes drills whose real-time cost — multi-hour finality stalls, multi-day relay-block leads, multi-epoch soaks — makes per-tag execution physically impossible. The gating rule is therefore satisfied against a declared **release tier**: the subset of §4.7's suites that MUST run against the packaged artifacts at every tag, with the remainder assigned to a **phase-gate tier** proven against the [09](09-execution-upgrades-and-rollout.md) §7.1 rollout gates instead. This is a deliberate narrowing of the gating sentence above — §4.7 names the dead-man drill among the backend's own suites, and its real-time cost puts it in the phase-gate tier, so a tag's evidence does not cover it — and it is admissible only under all four of: (1) tier membership is declared in a checked-in manifest and **pinned by the environment validator**, so no suite changes tier silently; (2) a release-tier suite that does not run and pass **blocks evidence emission** — it never degrades to a pass, whatever the reason for the skip; (3) every excluded suite is **recorded inside the evidence** with its reason — a frozen field, validated at assembly, so the subset a release actually ran is auditable from the artifact alone rather than resting on a producer's goodwill; and (4) evidence is admissible for this gate only when stamped with the release tier. Tier membership is a claim about execution cost and never about importance: a suite sits in the phase-gate tier only because it cannot run per tag, and [09](09-execution-upgrades-and-rollout.md) §7.1 owns proving it.
