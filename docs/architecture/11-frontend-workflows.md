## 11.1 What is carried forward unchanged

The design review verified the following as correct; this document carries them forward deliberately, not by omission:

1. **The pre-sign refresh design (INV-FE-2).** Every submit path re-evaluates its full precondition set against a single freshly pinned finalized block B′ immediately before the wallet is invoked, structurally mirroring the backend's own dispatch-time revalidation (`execute()`'s checks in [09](09-execution-upgrades-and-rollout.md); `decide()`'s ordered checks in [05-welfare-and-decision-engine.md](05-welfare-and-decision-engine.md)). The frontend never predicts an outcome the runtime would not re-derive; the runtime is always the final arbiter (§11.4).
2. **The E-row discipline.** Every user-visible degradation state is specified as a row with six mandatory facets: **V** visible state · **L** loading behavior · **A** verified data available · **U** unavailable convenience data · **F** failure message · **R** recovery (§11.12).
3. **Signing-flow safety.** `Finalized` is the only success state; the confirm screen is decoded from the exact payload bytes (`prep.scaleHex`), never from form state; addresses render with identicon + checksummed SS58 (prefix 7777, *(normative value: [02](02-integration-contract.md))*); metadata-hash signing is the second display channel; dispatch outcomes are decoded from finalized events only (§11.3).

### 11.2a External (hosted) books in the canonical client (normative; added 2026-08-03, SQ-571)

The canonical client **serves external books**. `BookKind::External` rows in `Market.Markets` are ordinary trading surfaces on S3, and an account's holdings in them are ordinary rows on S4, read through `service_positions()` or the `ServiceLedger` prefix ([02](02-integration-contract.md) §3, §7.1 — admitted at contract v23).

This is not a new capability being granted; it is an existing one being made visible. `market.buy` is a `CallDomain::Public` call, `LedgerRoute::for_book` already routes such a trade into `ServiceLedger` with no caller-visible difference, and `quote()` already prices external books through the same physical `Markets` map ([16](16-hosted-question-service.md) §6.2/§7.1). A client that traded a hosted book but could not read the resulting position would take a user's money into a book and then not show it — which no reading of INV-FE-1's honesty obligation survives.

Five rules bound how they are served, and they exist because the two domains are genuinely different, not merely differently named:

1. **Domain is always visible, never inferred by the user.** Every external book and every service-domain position is labelled as such wherever it is rendered. `kernel::SERVICE_ID_BASE = 1 << 63` partitions every question, book, vault and position id ([16](16-hosted-question-service.md) §7.1), so the client decides domain by a single bit test on an id it already holds — it MUST NOT infer domain from a name, a client id, or a heuristic, and MUST NOT render a row whose domain it could not establish.
2. **No merged portfolio total.** [03](03-conditional-ledger.md)'s I-4 solvency invariant is stated against *the* sovereign account, singular, and holds **per instance** — which is precisely why the second instance exists rather than a domain tag inside the first ([16](16-hosted-question-service.md) §7.1). A single figure summing both domains would assert one backing pool where there are two, so the client MUST NOT present one. Per-domain totals, shown side by side, are the honest form.
3. **External activity is never presented as governance or protocol health.** No external book, position, volume or fee may be rendered as an input to a decision statistic, a gate, a welfare pillar, or NAV. Welfare's `H` is computed on primary/system usage and never by subtracting service traffic ([16](16-hosted-question-service.md) §8.5, [05](05-welfare-and-decision-engine.md)); external quota and its fail-closed state are **operational diagnostics**, and copy MUST NOT imply that trading a hosted book participates in governing Bleavit.
4. **The trading and redemption rituals do not relax.** §11.3–§11.4 apply unchanged: the pre-sign refresh re-reads that domain's own state at B′, and an FE-P2-conservative cross-check of `service_positions()` goes against the `ServiceLedger` prefix, never the primary one ([02](02-integration-contract.md) §7.4). A hosted book's VOID follows §11.6 exactly, including the honesty copy — a client's failure to fund is not the trader's penalty to absorb.
5. **A write goes to the instance that owns the row.** The two ledgers are two *pallets* in the runtime — `ConditionalLedger` and `ServiceLedger` — not one pallet with a domain argument, so a service-domain position is split, merged, transferred and redeemed through `ServiceLedger.*` and a primary one through `ledger.*`. Only `market.buy`/`sell` are domain-agnostic to the caller, because `LedgerRoute::for_book` selects the instance *inside* the market pallet ([16](16-hosted-question-service.md) §7.1); no ledger call has an equivalent. The client MUST derive the target instance from the same rule-1 bit test that labelled the row, and MUST NOT carry a default instance on the write path — a hosted redemption addressed to `ledger.*` does not silently misroute, it fails `UnknownVault` against a vault map that has never heard of the id, which is the correct outcome and a useless one. **The reachable service subset is smaller**, and a client that offers the full primary list on a hosted position offers buttons that cannot fire: a hosted question has two books and no gate or Baseline leg ([16](16-hosted-question-service.md) §7.6), so `split_gate`/`merge_gate`/`redeem_gate` and every `*_baseline` call are structurally absent there. §11.5's precondition rows are evaluated against the owning instance's own storage, per rule 4.

Under the §11.2 handoff-first default these surfaces sit in **Advanced** with the rest of S3/S4, and they are demoted, not removed: rule 1 of that default applies to them identically.

**Forecast trading is cut (D-8).** Books close at branch resolution and never reopen. No screen, route, precondition row, or copy in this document refers to post-resolution ("forecast") trading; the residue in FE §17.6/§14.1 is removed. S3 trades only while the owning proposal is in `Trading`/`Extended` (Baseline books: while the epoch trading window is open — see §11.5 row P-2).

FE-15 lives under an explicit **"Advanced"** navigation area: same trust rules, same precondition discipline, denser information, no simplified summaries. It is part of the canonical release, not a separate app.

**Navigation default: handoff-first (normative; added 2026-08-03).** The inventory above is the set of screens the release **contains**; it is not a statement about what the user meets first. The canonical release's default navigation presents **two primary surfaces** — *prepare a capsule for an external tool* (S21) and *review, confirm and sign* (§11.3–§11.4, plus S22 for an imported action) — and places the analytical depth of S2/S3/S4/S7/S8 and the whole FE-14/FE-15 set behind the **"Advanced"** area alongside it. The intent is that a user forms their understanding wherever they like, including in an external tool, and returns to the client for the one thing only the client can do: re-read the chain and construct the bytes.

Three constraints bound that default, and each is what keeps it a presentation choice rather than an architectural one:

1. **Every screen in the inventory remains present, reachable without an external tool, and complete.** INV-FE-4 ([15 §2](15-invariants-and-testing.md)) requires every protocol workflow to operate with zero optional infrastructure available, and the [15 §2.1](15-invariants-and-testing.md) reading that admits the handoff at all rests on the clause *"every INV-FE-4 workflow completes with none present."* A release that reached a workflow only through an external tool would falsify both. **Demoting a surface is permitted; removing one is not**, and the no-infrastructure certification run continues to execute with the handoff surfaces disabled ([15](15-invariants-and-testing.md) §4.8).
2. **§11.14.5's scope statement is unchanged.** The handoff is still convenience: no protocol workflow depends on it, every action expressible as an intent remains a strict subset of what the transaction screens do by hand, and disabling it breaks nothing. Being the *default* surface and being *load-bearing* are different properties, and only the first one moved.
3. **The confirm surface does not simplify.** §11.4 rule 3 and INV-FE-14 require expected/actual for every precondition row and a three-level payload review derived from `prep.scaleHex`. Progressive disclosure satisfies both — a plain-language summary in front, the decoded tree, the raw SCALE bytes and the precondition detail one deliberate step behind it, expert mode behind that — because the obligation is that everything is *inspectable before signing*, not that all of it occupy the first screen. **What MUST NOT be deferred behind a step is any fact that changes the meaning of the signature**: the net payout of a charged redemption (§11.5), the lock consequence of a conviction vote (§11.7.6), the VOID recovery decomposition (§11.6), the sudo-era banner (§11.10), and the origin disclosure on an imported action (§11.14.4) are all named "above the fold" or "non-dismissible" by their owning sections, and this paragraph grants no relief from any of them.

An external tool's own output — its prose, its charts, its explanations — is outside the client and therefore outside INV-FE-9; the client labels what the client renders. That is the accepted cost of this default, and the residual it enlarges is recorded in [14](14-threat-model.md) §3.9 (TH-74) rather than left implicit here.

## 11.3 Transaction construction and signing safety

Carried forward from FE §17.1–§17.3, §17.5, §17.7–§17.8 with the fee repair of D-12:

- **Signers.** Injected PJS-compatible extensions via `polkadot-api/pjs-signer`, whose exports are **pinned (FE-P1, 2026-08-03)**: `getInjectedExtensions(): string[]`, `connectInjectedExtension(name, dappName?): Promise<InjectedExtension>` and `getPolkadotSignerFromPjs(address, signPayload, signRaw): PolkadotSigner`. Raw-payload flow (QR/hex + metadata-hash mode) for air-gapped and hardware signers **[VERIFY whether a Ledger app blind-signs when a chain offers no digest — FE-P6's device half; the chain half is settled and the chain is the blocker (SQ-594, milestone B21)]**. Note that PAPI signs `CheckMetadataHash` as **mode 0 (Disabled)** on every in-app path and offers no option for mode 1 other than `customSignedExtensions` (FE-P1), so metadata-hash signing is a deliberate build rather than a flag. Multisig via `Multisig.as_multi` with approval state read from `Multisig.Multisigs`; proxies supported as call wrappers under the same precondition system, with the delegation itself read from **`Proxy.Proxies(real)`** ([02](02-integration-contract.md) §7.6, contract v27).
- **A wrapper splits identity, and the delegation is its own precondition (SQ-590).** `Proxy.proxy` executes the inner call as `real` and `Multisig.as_multi` as the derived multisig account, while the **signer** still pays the fee and owns the nonce — so every clause below carries the subject it is about, and resolving one account for both questions checks the wrong one. The proxy case adds a check no other row covers: *may this signer act for `real` at all?* Evaluating the table against `real` is correct and, on its own, **passes green for a delegation that does not exist** — the runtime then refuses with `NotProxy` after the user has signed. The client MUST therefore read `Proxy.Proxies(real)` and require a delegation naming **this signer** as `delegate`, whose **stored** `proxy_type` covers the call and whose `delay` is zero (a non-zero delay makes bare `proxy` unreachable — `Unannounced`). A caller-supplied proxy type satisfies nothing: the claim is the part that must come from the chain. An unrecognised `ProxyType` variant is **unproven, never permissive** (INV-FE-12), and an *unperformed* read is distinct from an *empty* one — empty means nobody may act for this account, unread means the client does not know, and collapsing them makes a missing check look like a passed one.
- **Lifecycle.** Draft → Prepared(at B) → Refreshing → {Blocked | AwaitingSignature(at B′)} → Broadcast → InBestBlock → **Finalized** (only success state) | Dropped | Retracted. Post-finalization the app decodes the extrinsic's events to distinguish inclusion from call success and renders dispatch errors with human text (e.g. `market.buy failed: MaxCostExceeded — you paid nothing`).
- **Mortality/nonce.** Era 64 blocks from B′ (256 for raw-external); nonce from finalized `System.Account(who).nonce` at B′ plus tracked in-flight increments; phase-boundary proximity warning when a relevant boundary is < 25 blocks away.
- **Fee currency selector (D-12, X-14 resolved).** Fees are payable in VIT or USDC via `pallet-asset-tx-payment`; the conversion binds to the constitution key **`fee.vit_usdc_rate`** (typed, bounded [0.1×, 10×] around its reference, PARAM-adjustable — *(normative value: [08](08-treasury-and-economics.md)/[13](13-parameters.md))*). The selector reads this key live (a `Constitution.Params` storage read, light-client verified), shows the estimate in both currencies, and recomputes on selection. USDC-only accounts are always viable: every precondition table below computes fee headroom in the *selected* fee asset. The rate key and its bounds MUST be displayed in expert mode.
- **Anti-substitution.** The confirm screen derives its human summary by decoding `prep.scaleHex` — the exact bytes to be signed — never from form state; the wallet's metadata-hash decode is the independent second channel.
- **Dry-run.** No general dry-run through the light client; the precondition system statically checks every failure mode the runtime would (per-call tables, §11.5–§11.9); expert mode allows dry-run via the quarantined RPC fallback labelled "unverified simulation", never gating success.

## 11.4 Pre-sign refresh (INV-FE-2)

```ts
export async function refreshAndGate<T>(prep: TxPreparation<T>): Promise<Gate> {
  const at = await client.getFinalizedBlock();                 // B' — single pin
  const rt = await api.runtimeVersionAt(at.hash);              // compat gate (doc 10)
  if (rt.spec_version !== prep.builtFor.specVersion) return blocked('FE-TX-007', rt);
  const results = await Promise.all(prep.preconditions.map(p => p.evaluateAt(at.hash)));
  const failed = results.filter(r => !r.ok);
  return failed.length ? blocked('FE-TX-004', failed /* diff view */)
                       : proceed({ at, results });
}
```

Rules (normative):

1. Every submit path passes through `refreshAndGate` — structurally (the tx machine has no bypass edge), not by convention.
2. Each precondition row is an **exact read at B′**: a storage key, a runtime-API call, or a **constants-API (metadata) read**. Values that the backend defines as kernel constants with *no storage representation* — per-trade min/max, `MinSplit`, `MinTransfer`, `MaxPositionsPerAccount`, and every §21-class tunable's kernel floor — MUST be read from the runtime **constants API** exposed per D-2/[02](02-integration-contract.md), never from storage and never hardcoded (X-11e, X-11h). Constants are re-read whenever the compat layer observes a new `spec_version` (they can only change via Wasm change).
3. Expected/actual values render in the confirm screen; expert mode shows raw keys and SCALE values (INV-FE-14).
4. Provider/local-index data never satisfies any precondition (INV-FE-3); every row reads chain state.
5. A precondition failure shows a diff (expected vs. actual at B′) and returns to Draft with form state preserved.

**P-13's bond is read, not recomputed and not floored (normative; contract v29, added 2026-08-07, SQ-620 superseding its own filing).** This row previously required the round bond *"recomputed and displayed"* from `max(flat_floor, bps × cohort_escrow)`. SQ-598 established that no client could do that — `StakeAtRisk(c, m)` sums escrow over every cohort whose frozen MetricSpec consumes the component ([07](07-oracle-and-disputes.md) §6.1) and no surface published it — and SQ-620 was filed to amend this row to that refusal, showing `orc.bond_floor` as a labelled lower bound. **Contract v29 supersedes both readings.** The chain now publishes the amount, so P-13 is neither recomputed nor floored: it is **read**, exactly as P-14's challenge side already reads `OracleRoundView.bond`. Three consequences bind.

1. **One implementation, not two.** The escrow clause this row used to carry is deleted and does not return. It cited `Epoch.Cohorts`, whose `CohortInfo { epoch, proposals, status }` has no escrow field at all — a clause reading a map that cannot answer it — and it sat beside a client module that had independently concluded the bond was uncomputable. A bonded, slashable action carried two answers to *"what will this hold?"*; it now carries one, and it comes from the chain.
2. **The figure is a quote and MUST be shown as one.** [07](07-oracle-and-disputes.md) §6.1 reads the cohort escrow when round 1 is created and freezes it there, so the amount is priced at `BondQuoteView.read_at` and fixes at submission. The client displays that, and MUST NOT present the quote as the settled amount.
3. **`None` blocks; the floor is never substituted.** `orc.bond_floor` is a lower bound on the bond, not the bond, and offering it as the amount understates what the user is about to commit — the under-custody direction. A client that cannot read the quote refuses the action with the reason stated, which is [10](10-frontend-architecture.md) §5.4's rule for an unreadable figure a signature depends on.

The identical rule binds the registry filing bond at row O-8 (§11.8.6), which reads `bond_quote(IncidentFiling { epoch })` or `bond_quote(MilestoneFiling { epoch })` for the instance being filed to.

**The redemption-fee rate is chain-read, never hardcoded (normative; contract v17, added 2026-07-29, milestone E1).** Wherever a net redemption payout is displayed, the frontend reads the rate from the frozen **`ConditionalLedger::RedemptionFee`** basis-points metadata constant and cross-checks it against raw `params(ledger.redeem_fee)` by the canonical floored `Perbill / 100,000` projection — **exactly the rule row P-1 already applies to `Market::Fee` ↔ `mkt.fee`** ([02](02-integration-contract.md) §4/§9 rule 4). Five rules bind:

1. **Scope — the charged set, and nothing else.** The deduction applies to `ledger.redeem_scalar`, `redeem_scalar_pair`, `redeem_gate`, `redeem_baseline` and `redeem_baseline_pair`. It MUST NOT be applied, shown, or implied for `redeem`, `redeem_void`, any `merge*` call, or any payout whose **gross** is below `MinSplit` `[C]` — all exempt under [03](03-conditional-ledger.md) §5.3a(1)/(3). Applying it to an exempt call misstates the par promise G-3 depends on; omitting it on a charged call overstates the payout. Rows P-6/P-7 carry the scalar and Baseline legs; **`redeem_gate` has no precondition row of its own in this table and needs one** — a pre-existing gap in the §11.5 inventory, not one E1 introduced (the call is in the S4 extrinsic set and in [03](03-conditional-ledger.md) §5.3, and its gross payout is `a` 1:1 on the winning side of the winning branch, 0 and reap-only on the losing side). Until that row is written, this rule is what binds the fee display for it, and the call MUST NOT be surfaced with a payout figure that omits the deduction.
- **Fee arithmetic MUST use the net-based waiver of [03](03-conditional-ledger.md) §5.3a(2), not a gross test.** `fee(g) = 0` exactly when `g − ceil(g · ledger.redeem_fee) < ledger.min_split`, else `ceil(g · ledger.redeem_fee)`. A gross test (`g < ledger.min_split`) disagrees with the chain across the whole boundary band: at the 30 bps default a gross of 10,000 has a provisional fee of 30, so the **runtime waives it and pays 10,000**, while a gross-based client would display a 30 fee and a 9,970 net. Confirmation screens and post-finalization reconciliation would then disagree with the chain on ordinary traffic, not on an edge case. **Pair calls use `fee_pair` (§5.3a(2a)), not `fee(a)`** — the sum of the fees the legs would pay, each leg applying its own waiver — so a client computing `fee(a)` on a pair overstates the fee (at `a` = 20,000, `s` = 0.70005: 60 displayed against 43 charged).
3. **Presentation.** `net` is the headline; `gross` and `fee` are itemized beside it; the rate is shown in basis points with its `ledger.redeem_fee` key in expert mode. The displayed `fee` is the protocol's, **not** the transaction fee of §11.3 — the two are separate deductions in separate assets and MUST NOT be summed into one line.
4. **The two fee rates are a coupled pair but separate keys.** `ledger.redeem_fee ≤ mkt.fee` holds live ([08](08-treasury-and-economics.md) §10.6), and the FE MAY surface the relation; it MUST NOT substitute `Market::Fee` for `ConditionalLedger::RedemptionFee` or derive either from the other.
5. **Unreadable ⇒ no figure, never a default.** If either the metadata constant or the raw parameter is unreadable, or the two disagree under the projection, the net-payout figure is disabled with an explanation and the transaction blocked — a redemption net payout is computed from chain-read values or not displayed at all ([10](10-frontend-architecture.md) §5.4). The **runtime's** own read fails open (a missing or malformed record waives the fee, [03](03-conditional-ledger.md) §5.3a(5)); the frontend MUST NOT mirror that and display a fee-free payout it cannot verify.

The completed redemption then emits the fee it charged: the ledger's `ScalarRedeemed` / `ScalarPairRedeemed` / `GateRedeemed` / `BaselineRedeemed` each carry a trailing `fee: Balance` beside the unchanged gross `amount`/`payout` ([02](02-integration-contract.md) §6, contract v17), and the post-finalization decode of §11.3 SHOULD reconcile the displayed estimate against it.

## 11.6 VOID redemption workflow (X-6, D-1)

The redeem screen (S4) handles the `VaultState::Voided` state end-to-end. On `VaultVoided` (event frozen in [02](02-integration-contract.md)) the position card for that vault switches to the VOID layout:

1. **Primary action — `merge`, and only `merge`, is the 100 % path.** It is offered as "Merge pairs → 100 % recovery" **only** when the user holds an **Accept+Reject branch-USDC** pair, which is the sole holding that redeems at par under VOID. The screen computes the maximal cross-branch pairable amount across their positions and pre-fills it. A user who holds no cross-branch pair MUST NOT see a 100 % headline (SQ-171).

1a. **Consolidation step — `merge_scalar` / `merge_gate` are NOT recovery actions.** A same-branch LONG+SHORT or YES+NO set pays **no USDC**: merging it climbs the set to one *same-branch* branch-USDC. That output is worth par only once paired with the opposite branch, and `floor(a/2)` otherwise. The UI MUST present these calls as value-neutral consolidation, label the resulting branch-USDC with its actual VOID value, and route the user to whichever of step 1 or step 2 their post-merge holdings actually reach. Presenting `merge_scalar` under a 100 %-recovery heading is exactly the overstatement this section forbids.
2. **Secondary action — `redeem_void(pid, kind, amount)`** for genuinely unpaired holdings, with the rates shown **honestly and prominently**: unpaired branch-USDC pays `floor(a/2)`; unpaired LONG or SHORT pays `floor(a/4)` *(normative values: [13](13-parameters.md))*. Copy (normative intent, exact wording localizable): *"This vault was voided. Cross-branch complete pairs (Accept **and** Reject) recover 100% by merging; a same-branch LONG+SHORT set alone does not — merging it yields one branch-USDC, worth 0.5 under VOID. An unpaired single-branch position redeems at 0.5 per branch-USDC (0.25 per LONG/SHORT) — the value of a voided binary claim."* No copy may describe the 0.5/0.25 rates as a penalty or confiscation — they are the neutral price of a voided binary claim. **Nor may any copy promise "par" or "full principal" to a wrapper buyer unless the displayed holdings are complete across both branches (SQ-171).** The screen MUST show the **pair-first D-1 neutral recovery of the user's actual package** and explain that any difference from the original debit is the premium or discount of their realized average execution price against the neutral prior, plus fees. Cross-branch complete-set holders do recover par; a buyer recovers `cost` only if their *realized average execution price* was 0.5, which a finite buy opening at that quote does not achieve. **The E1 redemption fee does not qualify this rule, and does not add a deduction to any figure on this screen (added 2026-07-29, milestone E1):** `redeem_void` and every `merge*` primitive are **exempt** ([03](03-conditional-ledger.md) §5.3a(1)) — VOID is protocol failure, and charging users for it would invert G-1 — so the par leg's promise stays literally true where it is permitted at all, and the `floor(a/2)` / `floor(a/4)` rates above are what the account receives, gross and net alike. The SQ-171 constraint is therefore unchanged in both directions: it still forbids the "par"/"full principal" copy for incomplete holdings, and it still permits it, unhedged, for complete cross-branch pairs.
3. **Mixed holdings**: the screen decomposes the user's balances into (max **cross-branch** pairs, at par) + (same-branch sets, consolidated by step 1a) + (residual unpaired amounts, at the step-2 rates) and offers the actions in one flow. The headline figure MUST be the **total recovery those actual holdings reach**, never the par value of the pairs alone.
4. Rounding is against the redeemer; residues follow the dust rule ([03](03-conditional-ledger.md)); the displayed payout is the exact floor computation.

Precondition rows:

| Tx (under `Voided`) | Preconditions re-read at B′ |
|---|---|
| `ledger.merge` / `merge_scalar` | vault state == `Voided` (or `Open`/`Resolved`); user holds ≥ amount of **both** sides of the pair; payout = amount USDC (par), displayed — fee-exempt, no fee line (§5.3a(1)) |
| `ledger.redeem_void(pid, kind, amount)` | vault state == `Voided`; user balance of `kind` ≥ amount; expected payout recomputed and displayed (`floor(a/2)` branch-USDC; `floor(a/4)` LONG/SHORT) — fee-exempt, so the displayed figure is both gross and net and MUST carry no fee line; **no winning-position-balance requirement** — that requirement applies only to P-5/P-6 under `Resolved`/`ScalarSettled` and is explicitly absent here |

There is no "winning branch" under VOID; any UI element that gates redemption on a winning position MUST NOT render for a `Voided` vault. See E-row E16 (§11.12).

### 11.7.4 Ratification status on proposal detail

For every proposal whose class requires values ratification (CODE/META per [06](06-governance-and-guardians.md)), the proposal detail screen (S2) MUST render a ratification panel:

- linked `ratify`-track referendum (or "none submitted yet — anyone may submit; after submission the proposer binds its exact index" with one-click G-6/G-9 flows; the artifact hash was committed at proposal submission);
- its live status and tally;
- the **execute-time deadline** (D-5, [06](06-governance-and-guardians.md)): *"must be Approved by the moment `execute()` is dispatched; execution window: maturity → grace_end"* with both block numbers and countdowns;

The panel MUST derive those lifecycle states from `pallet-referenda` (`ReferendumInfoFor`, calls and tallies above). `RatificationStatus::Passed { referendum }` supplies the guard's passed-record linkage after approval; it does not replace the referendum read.

### 11.7.5 OracleResolution ballot and the pre-cohort snapshot rule

Terminal (round-3) oracle disputes escalate to the hardened `oracle` track: 60% approval / 10% support / 7-day *(normative values: [13](13-parameters.md); D-18)*, only admissible call `oracle.adjudicate(component, epoch, spec_version, value, reporter_wrong)`. The tally uses a **pre-cohort conviction snapshot**: only VIT conviction-locked **before the subject cohort's creation block** counts; capital that entered after the cohort began is excluded ([06](06-governance-and-guardians.md)).

The ballot screen MUST:

1. show the dispute lineage: component, epoch, all round reports/challenges with bonds, and evidence links (§11.8.1 evidence rules);
2. display the snapshot block (cohort creation) and the **user's effective voting power at that snapshot** — reading the user's conviction-lock history from `ConvictionVoting.VotingFor`/`ClassLocksFor` as of the snapshot block **[VERIFY the snapshot mechanism's exact readable storage representation — whether the runtime stores a snapshot map or re-derives from lock timestamps; frozen in [02](02-integration-contract.md); the FE binds to whichever representation the contract freezes]**;
3. pre-sign, warn (and show effective power = 0) when the user's locks post-date the snapshot — the vote would be signable but weightless;
4. never present the ballot as a routine vote: copy states it is the stake-weighted backstop that makes earlier-round lying unprofitable ([07](07-oracle-and-disputes.md)).

### 11.8.3 Treasury: stream claims and `nav()`

| Tx | Preconditions re-read at B′ |
|---|---|
| `futarchy_treasury.claim_stream(stream_id)` | **`NavView.stream_claims_wired` true** ([02](02-integration-contract.md) §4) — an unwired runtime refuses every claim with `OutflowCustodyUnwired`, so this is checked first and blocks with a reason about the runtime rather than the stream; the stream appears in `FutarchyApi.treasury_streams(caller)` at B′ — its presence there **is** the exists-and-is-yours check, since the projection is per caller; `StreamView.cancelled` false; `StreamView.claimable_now > 0`, displayed as the amount ([02](02-integration-contract.md) §3/§4) |

**The claimable amount is read, not computed client-side (normative; contract v29, added 2026-08-07, SQ-601).** This row previously required *"linear vesting, computed client-side from stream fields at B′"* over *"stream storage per 02"* — and [02](02-integration-contract.md) freezes no `pallet-futarchy-treasury` storage at all, while its §7.6 closing rule requires every treasury consumer to bind `nav()` instead, which publishes only the `stream_remainders` aggregate. The console's central read was therefore unbuildable as written, and the tier shipped closed.

The resolution is a **published per-caller projection**, and it needs no exception to §7.6: that rule forbids binding **raw storage**, and a runtime-API projection is not raw storage — `nav()` is itself one. So §7.6 stands unchanged, and [11](11-frontend-workflows.md) §11.4 rule 2's *exact chain read* property holds for the row, which a stated exception would have given up. Three rules bind the display:

1. **`claimable_now` is the figure.** The client MUST NOT re-derive it from `total`, `claimed`, `start` and `duration`: the vesting division floors against the claimant ([08](08-treasury-and-economics.md) §1.4), and a client rounding the other way shows a payout the chain will not make.
2. **Zero has three meanings and the client MUST say which.** Cancelled, not yet started, and fully claimed are different states that all report nothing to claim; the other `StreamView` fields distinguish them, and a bare zero reads as a fault.
3. **The figure is a lower bound at inclusion, never an upper one.** Vesting is monotone and `claimed` moves only on a claim, so what a later claim pays is at least what was displayed. Cancellation is the one discontinuity and is caught by the B′ re-read.
4. **A claimable figure is not an offer to claim.** [08](08-treasury-and-economics.md) §1.4's A9 follow-up leaves `claim_stream`'s real-asset leg unwired in a runtime that has not bound custody, and such a runtime refuses **every** claim with `OutflowCustodyUnwired`. `NavView.stream_claims_wired` is the read that says so, and it is checked **before** the per-stream row: without it this section's own repair would open a control whose every use is refused after the signature — the failure it exists to prevent, arriving from the direction of the fix. The figure is still rendered when the leg is unwired, because a recipient is entitled to know what has vested; what is withheld is the control, with the reason naming the runtime rather than the stream.

**`nav()` view (rendered, at last).** The treasury screen renders every [02 §4](02-integration-contract.md) `NavView` field: the account decomposition, stream remainders, obligations, `total`, `spendable_nav`, `meter_utilization_bps`, and the Param/Treasury/Code/Meta `class_floors` (including continuous distance-to-floor). In-flight XCM and VIT holdings remain marked 0 with copy explaining the conservative rule. **Reserve-haircut flag**: when the reserve-health trigger R is set ([07](07-oracle-and-disputes.md)/[08](08-treasury-and-economics.md) — e.g. a frozen USDC sovereign account), `haircut_flag` is exactly 08 §1.2's `reserve_impaired` and `spendable_nav` is 0; the FE MUST replace the headline NAV with the haircut presentation and a persistent banner *"reserve health degraded — NAV shown with haircut; split inflows halted (PB-RESERVE)"*. The FE never renders full backing while the flag is set.

**`INSURANCE` after E1: a sized reserve that overflows, not a revenue meter (normative; added 2026-07-29, milestone E1).** `NavView.insurance` is rendered under the standing [08](08-treasury-and-economics.md) §1.2 constraint that the account fields are a **partial** view of treasury custody — the nine `ops.*` lines carry no field of their own — and MUST NOT be presented as an additive decomposition of `total`. Two further readings are now wrong and MUST NOT be offered:

- **A rising `INSURANCE` balance is no longer a signal of protocol income, and never was a complete one.** Protocol revenue routes **100 % to `MAIN`** — realized market fees, redemption fees and USDC transaction fees alike ([08](08-treasury-and-economics.md) §1.1/§9) — so income shows up in `main` and in `total`, not here. What reaches `INSURANCE` is slash proceeds and swept ledger residue, and only the residue is retained.
- **`INSURANCE` is bounded and self-balancing.** It has a derived target `T_ins` — the unreclaimed swept-residue liability it actually backs, plus `min_balance` — and any balance above that overflows to `MAIN` **automatically**, in the same transaction as the inflow that created it, with no governance act and no proposal slot ([08](08-treasury-and-economics.md) §1.2). A flat balance under continuing inflows is therefore the normal state and MUST NOT be rendered as stagnation, a stalled sweep, or a failure of the `sweep_insurance` path, which remains the only way to draw the account *below* `T_ins` and remains a TREASURY-class decided act.
- **The target is read from `NavView.insurance_target`, never derived (contract v29; SQ-602).** The two bullets above require `INSURANCE` classified against `T_ins`, and until v29 no surface published it — `insurance_target()` was a pallet-internal helper — so the only client that could classify was one fabricating the quantity it compares against, which is the INV-FE-1 defect. The field is now the exact figure [08](08-treasury-and-economics.md) §1.2's own overflow rule uses. Two readings remain wrong: `T_ins` is not a floor anything tops the account up to, and the gap between `insurance` and `insurance_target` is not a measured shortfall — §1.2's archived-claims decrement is unspecified in v1, so the counter is a deliberate over-estimate and the account is expected to sit below it.

The FE reads `NavView` and nothing else for this screen: cumulative fee income is a diagnostic on the monitoring-only `TelemetryApi` ([12](12-release-and-operations.md) §6.3), outside the [02](02-integration-contract.md) contract, and the canonical frontend does not consume it ([10](10-frontend-architecture.md) §5.5). Any income figure the treasury screen shows MUST be derived from the **ingest-set** events `RevenueSwept` and `RedemptionFeesSwept` ([02](02-integration-contract.md) §5/§6) within the committed history window, and labelled as the partial, window-bounded total it is — never as lifetime protocol revenue. `InsuranceSwept` is deliberately **not** in the ingest set ([02](02-integration-contract.md) §5's `pallet-futarchy-treasury` row admits only `NavHaircutFlagged`), so no income or reserve figure may depend on observing it.

### 11.8.4 Upgrade crank — `system.apply_authorized_upgrade`

Permissionless and load-bearing for liveness; the Advanced area makes it executable from the canonical frontend:

1. Read the authorized upgrade state: the authorized code hash from `System.AuthorizedUpgrade` (`frame_system`, **not** `cumulus-pallet-parachain-system`, which carries no such item), and `ExecutionGuard.PendingUpgrade { hash, authorized_at, applicable_at, target_spec_version }` — `authorized_at` is recorded when `execute()` dispatches `authorize_upgrade`, and the SafetyFilter denies `apply_authorized_upgrade` until `applicable_at = authorized_at + DescriptorLeadTime` ([09](09-execution-upgrades-and-rollout.md) §2.2; [02](02-integration-contract.md) names).
2. Fetch the matching Wasm from the **Arweave release artifact** published by the backend release train ([02](02-integration-contract.md) test/release artifact feed; [12](12-release-and-operations.md)) — via the same multi-gateway, hash-verified retrieval as app assets.
3. **Verify the artifact hash against the authorized hash BEFORE submission** — client-side, streaming BLAKE2b-256 over the downloaded bytes; a mismatch hard-blocks with `FE-UPG-001` and never reaches the wallet.
4. Precondition row: authorized hash present; artifact hash == authorized hash (step 3); **`now ≥ ExecutionGuard.PendingUpgrade.applicable_at`** (D-14) — read the stored field, do **not** recompute `authorized_at + DescriptorLeadTime` client-side, because [09](09-execution-upgrades-and-rollout.md) §2.2's SafetyFilter denies on `applicable_at` and a client that re-derived it from a separately-read registry value would refuse or admit on a number the filter is not using; fee headroom for a multi-MB extrinsic (displayed — it is large). **This is the sole home of the descriptor-lead-time precondition** (SQ-552, 2026-08-03): it gates *application*, never `execute`, whose success is what sets `authorized_at` in the first place.
5. Submit `system.apply_authorized_upgrade(code)`.

**Memory/streaming honesty.** Hashing streams in bounded chunks, but *submission* requires the full Wasm (typically 1.5–5 MB compressed) in memory as a call argument, and the signed extrinsic transits the light client's transaction pool path. This is architecturally heavier than any other FE extrinsic. **[VERIFY smoldot + PAPI behavior for multi-MB extrinsic submission — pool/gossip size limits, peer banning on oversized transactions, and mobile memory headroom; prototype FE-P10 (extends FE-P4). Fallback if it fails: the Advanced screen performs steps 1–3 (fetch + verify) and hands the verified blob + prebuilt call data to the expert RPC path or an operator CLI (`tools/` in [12](12-release-and-operations.md)) — verification stays in-browser even when submission cannot.]** The screen states which path is active.

### 11.8.5 Welfare snapshot crank

`welfare.record_snapshot(epoch, spec_version)`: precondition — epoch boundary passed and no snapshot yet recorded **for that `(epoch, spec_version)` pair** (staleness read at B′); otherwise "no-op — nothing to crank" (row P-15). The Advanced dashboard shows snapshot staleness prominently (an overdue snapshot > 4 days engages the dead-man rule — [05](05-welfare-and-decision-engine.md)).

**The call takes the version, and the staleness key is the pair (normative; contract-v29 batch, SQ-618).** This section named `welfare.snapshot(epoch)` and keyed *already taken* on the epoch alone. The runtime's call is `record_snapshot(epoch, spec_version)` and `Welfare.Snapshots` is keyed `(epoch, spec_version)` (§7.4), because an activation boundary keeps two admissible MetricSpec versions live for one measurement epoch and each needs its own record ([05](05-welfare-and-decision-engine.md) §4.6; I-16). The consequence is not a naming nit: a client keyed on the epoch alone reports *"already taken"* for a version that has no record and **refuses a lawful crank** — on precisely the crank whose overdue state engages the dead-man rule. The console MUST therefore render the version alongside the epoch, so an operator can tell a genuine no-op from a second version awaiting its own snapshot.

The consequence is the one SQ-580 named: a precondition with no declared read is **vacuously satisfied** by any checker that asks whether every declared read passed, so the row reported complete coverage of a check nothing performed, and a filer was walked to a bonded signature the runtime refuses. `CohortSchedule.specs` is `BoundedVec<(ProposalId, MetricSpecVersion)>` and answers it directly. **A client MUST NOT substitute the near miss**: `Cohorts[epoch].proposals` joined to each proposal's `metric_spec` is a computation over two maps where §11.4 rule 2 requires an exact read, and it reads each proposal's *current* spec rather than the version its cohort froze — which are the same value only until a MetricSpec activation boundary, exactly the case this clause exists for.

## 11.10 Sudo-era banner (X-9, D-13)

While the chain is in Phases 0–3, the app renders a persistent **"Bootstrap governance: sudo active"** banner:

- **Driver:** the `pallet-constitution` `PhaseFlags` bitset (D-17), read light-client-verified at every finalized head; the banner is pure chain state — no remote config, no release-baked assumption.
- **Placement:** the global app shell, above navigation, on **every** route (including FE-14/FE-15 and the funding flow), and repeated as a line item on every transaction confirm screen.
- **Dismissal: none.** The banner is non-dismissable and non-collapsible for the entire Phase 0–3 window; it disappears only when a finalized `PhaseFlags` read shows the **`sudo present` bit clear** (bit 4, [02](02-integration-contract.md) §7.3 — see the note below). It MUST NOT be gated behind settings, themes, or "compact mode".
**`PhaseFlags` is a bitset and admits no ordering (normative correction; 2026-08-05).** Both this section and §11.9.1 previously expressed their condition as a comparison against the number 4 — *"Phase ≥ 4"* and *"PhaseFlags < Phase 4"*. `Constitution.PhaseFlags` is a `u32` **bitset** ([02](02-integration-contract.md) §7.3) and is the **only** phase-related surface the contract freezes; there is no governance-phase integer for a client to read. So the comparison is not merely loose wording, it is unperformable on the surface that exists — and performing it anyway is worse than failing, because a bitset compares as a number without error. A real bootstrap value of `17` (shadow mode + sudo present) satisfies `17 ≥ 4`, which **hides this banner on a chain running sudo**; the same value fails `17 < 4`, which **skips §11.9.1's D-13 exposure caps entirely** during exactly the window they exist for. Both conditions are the single bit 4 (`sudo present`), and both sections now say so. The defect was found in the canonical client, where the banner had been implemented from this text (PLAN.md · Session log, 2026-08-05).

- **Copy (normative intent):** *"Bootstrap governance is active: a founding multisig holds sudo. On-chain state is finality-verified but not yet protected by full protocol governance."* — sudo-era state keeps its `verified-finalized` badge (it *is* valid finalized state) while the banner prevents it being presented as trust-equivalent to post-sudo state.
- The funding flow additionally surfaces the Phase-3 exposure caps (§11.9.1) as part of the same containment story.

## 11.14 External-tool handoff — share context, import an action (D-21)

Architecture and formats: [10](10-frontend-architecture.md) §13. This section owns the *workflow*.

```
export a capsule → analyse it anywhere → import a proposed action → admission checks
→ Draft → refreshAndGate at B′ → confirm → wallet signs → submit → finalize → receipt
```

### 11.14.1 Admission checks are not preconditions

The distinction is load-bearing and must not be collapsed. **Admission checks** are properties of a *file*: schema equality, digest, chain binding, expiry, closed-object shape, limit presence and internal consistency. **Preconditions** (§11.5) are re-reads of *chain state* at B′, and §11.4 rule 2 requires every row in that table to be an exact chain read. Putting a file-derived row into the precondition table would make that rule false.

Admission checks therefore run **before the transaction enters Draft**. A document that fails any of them never becomes a transaction at all, and the user sees a `FE-HANDOFF-*` refusal with its fixed copy and stated fix rather than a blocked confirm screen.

From Draft onward the imported action is indistinguishable from one the user assembled by hand: same screens, same `refreshAndGate`, same P-1 row, same confirm surface decoded from `prep.scaleHex`.

### 11.14.2 The action vocabulary is closed

Three actions, matching the trading workflows S3/S4 already offer: **prepare a PASS position**, **prepare a FAIL position**, **close a fraction of a held position**.

Three encoding choices, each earning itself:

- **The intent names an economic goal; the client computes the calls.** This is not a stylistic preference. Under D-3 the market wrapper splits internally, so a tool that emitted a call *sequence* would very plausibly emit a ledger split *and* a market buy and double-split the user's collateral. The correct call count is a function of chain semantics that changes between contract versions, so it is the client's to determine, always.
- **Size is expressed as collateral, never as instrument quantity.** Users budget in USDC, and the LMSR inversion from collateral to quantity is exactly the arithmetic an external tool gets wrong. Doing it client-side is also what makes the cost ceiling derivable and therefore clampable.
- **A close is expressed as a fraction, never an absolute amount.** An absolute amount taken from a stale capsule can exceed the current holding (a dispatch failure) or leave unredeemable dust. A fraction is stale-safe and clamps naturally against a freshly read balance. This is a security choice, not a convenience.

Governance votes and delegation, transfers to an arbitrary address, the Asset Hub funding legs, the operator surfaces of §11.8, and redemptions are **out of scope**, each for a stated reason: irreversible values-layer acts on possibly someone else's proposal; the classic send-to-the-attacker primitive that no analytical workflow needs; two-leg cross-chain flows that §11.9 gates separately; bonded adversarial operator actions that are not analysis-driven; and — for redemptions — that the client's own "you have redeemable positions" prompt does the job better, so admitting them would grow the vocabulary for no analytical gain.

### 11.14.3 Clamping: the client asserts authority over the tool

**A limit is never widened, only narrowed.** For a buy the encoded ceiling is the minimum of what the intent asked, what the client's own recomputed cost at B′ permits under the stated slippage, and the client's own policy cap; symmetrically a floor on proceeds is only raised. When the client's number is the binding one, **the difference is shown, not silently applied**.

A stated deadline is compared against B′, the chain clock, never the device clock. A stated maximum context age is honored only in the narrowing direction: a tool may make its own advice expire sooner, and cannot make it expire later — staleness needs no timer, because it is bounded structurally by `refreshAndGate`. The capsule's age is **displayed and diffed**, never trusted.

Every limit is re-expressed on the confirm screen as the value that will actually be encoded, and that screen is decoded from `prep.scaleHex` (INV-FE-14) — so even a clamping bug cannot make the display disagree with the bytes.

### 11.14.4 Required UX

- The **chain-read identity of the action's target** renders alongside the id at `verified-finalized` status. Id substitution is the sharpest attack this surface admits, and rendering what the id actually resolves to is what defeats it.
- Every imported value renders with **`external-proposal` status** ([10](10-frontend-architecture.md) §2.1) wherever it is shown — including the asked side of the asked-vs-encoded pair. INV-FE-9 admits no unlabeled rendering path, and a requested ceiling displayed beside a chain-derived one is exactly where an unlabeled number would be mistaken for a verified one.
- The origin disclosure is **fixed in-bundle copy and non-dismissible**. No format carries a tool-supplied label, because a label reading "Bleavit Official Assistant" inside the confirm flow would be a phishing primitive.
- Expert mode exposes the full clamp derivation — asked ceiling, chain-derived value at B′, encoded value — alongside the capsule's block height and age, in the same habit §11.4 rule 3 establishes for preconditions.
- Export requires **per-export consent** with the scope shown, and the **default scope excludes account-specific data** — positions, balances and addresses are opt-in per export, never included because the last export included them. **Pseudonymization MUST be offered** for the account-bearing scopes, and MUST be labelled for what it is: it replaces the address in the capsule and does nothing about the holdings themselves, which remain a fingerprint. What leaks is linkage rather than content: holdings on a public chain are already public, but a capsule pasted into a hosted service ties them to an identity in a third party's logs, and it cannot be un-sent.
- An imported document **writes nothing at all** — no setting, no default, no preference, and no record that it was ever seen ([10](10-frontend-architecture.md) §13.3). There is deliberately no replay memory: a re-import is simply an import, rebuilt and re-reviewed against current state.

### 11.14.5 Scope statement

This surface is convenience only. Every action expressible as an intent is a strict subset of what S3/S4 already do by hand; no protocol workflow depends on it; and it may be disabled entirely without affecting any INV-FE-4 workflow — which is why the no-infrastructure certification run executes with these surfaces disabled ([15](15-invariants-and-testing.md) §4.8). The external tool is IN scope as a recipient of exported files and a source of proposed actions; embedding a model, calling one over the network, or running any tool-protocol server, tunnel or sidecar is OUT of scope (INV-FE-6, INV-FE-13; D-21).
