# 13 — Parameters, Bounds and Constants (single reconciled table)

**Status: normative component specification. Supersedes the corresponding sections of BACKEND_PLAN.md/FRONTEND_PLAN.md** (BE §21 in full; every bound, constant or default restated anywhere else in either source).

**Boundary.** This document is the **single source of truth for every tunable parameter, kernel constant, storage bound and frozen protocol constant**. Other component documents reference these values and MUST NOT restate different ones (quoting for readability is permitted when marked *(normative value: §13)*). Chain-identity constants and the integration surface are jointly owned with [02](02-integration-contract.md) (D-17); where both documents state a value they are byte-identical by construction of the D-2 freeze.

Normative language: RFC 2119. Blocks at 6 s (14,400/day); USDC 6 decimals, VIT 12 decimals; `Fixed` = `FixedU64` (1e9 scale) at API boundaries.

**Reading rules (X-11e/X-11h — no hardcoding, anywhere):**

1. **K** = kernel constant: compile-time in `futarchy-primitives`, no storage representation, changeable only by a Wasm upgrade that the attestation regime surfaces ([09](09-execution-upgrades-and-rollout.md)). **Boundary of the primitives home:** every K-marked numeric value in this document — the LMSR domain bound and error-bound constants included, which `futarchy-fixed` imports and asserts rather than re-declares — lives in `futarchy-primitives::kernel`; sibling crates MUST import it, never re-declare it. Two carve-outs: per-pallet **storage-bound arguments** (§4) live with their owning pallets ([02 §7](02-integration-contract.md)), and pallet-internal implementation constants with no row in this document need no primitives home. Contract-surface **types** — every type named in 02 §§2–7, event-field enums such as `MarketKind` included — likewise live in `futarchy-primitives` (02 §2).
2. Everything not marked K lives in `pallet-constitution::Params` as a typed record `{ value, min, max, max_delta_per_decision, cooldown, last_change, class, kernel_bounded }`; min/max/max-delta/cooldown/class are genesis-fixed for kernel-bounded keys and META-amendable within compile-time meta-bounds otherwise.
3. **Every value in this document — K constants included — is machine-readable by clients** via the runtime **constants API** (metadata) or the named storage item, per the [02](02-integration-contract.md) contract. The frontend MUST read, never hardcode (this closes X-11h's backend side: there is no value the FE re-checks that the chain does not expose).
4. Every default is a **simulation hypothesis** unless marked frozen; Phase 0–3 calibration obligations are tagged *sim-gated*.
5. `ProposalClass::Emergency` is deleted (D-7): no row in this document carries an EMERGENCY value, and none may be added without reopening D-7.
6. **`ParamKey` encoding (canonical).** The on-chain `ParamKey` ([02](02-integration-contract.md) §2, `[u8; 16]`) is the row's dotted name, UTF-8-encoded and zero-padded to 16 bytes. Names longer than 16 bytes carry an explicit canonical key, written `key:` in their row — truncation is forbidden (the encoder rejects over-long names). **Per-class rows** (`dec.delta`, `dec.sigma`, `dec.v_min`, `gate.v_min`, `prop.bond`, `pol.b`, `exec.timelock` → base `exec.lock`, `trs.proposer_reward` → base `trs.reward`) materialize as four keys with the class suffixes `.param` / `.trs` / `.code` / `.meta`. `gate.v_min` is per-class because its default and both its bounds are expressed as multiples of `dec.v_min`(class) — a single key could not carry a class-derived value (added 2026-07-20, SQ-194).
7. **Record classes and the view projection.** `ParamRecord.class` uses the six-class set {PARAM, TREASURY, META, CONST, entrenched, META+values}; `ParamView.class: ProposalClass` ([02](02-integration-contract.md) §4) projects CONST and entrenched onto `Constitutional` and META+values onto `Meta`. Rows whose min or max is a kernel floor/ceiling are marked `kernel-bounded`: per rule 2 their **entire** governance-metadata tuple (min/max/max-Δ/cooldown/class) is genesis-fixed and `amend_registry` refuses them outright; all other rows are META-amendable within the compile-time meta-bounds (the amendment must keep `min ≤ value ≤ max`, preserve the value kind, and keep `cooldown ≤ 8` epochs). The kernel-bounded set is, normatively and exhaustively (per-row K/floor/ceiling markers plus the §1 safety rationale; conservative where a bound is cross-key-derived or marked "never lowered"/"down only"): `att.window`, `code.spacing`, `dec.delta.code`, `dec.delta.meta`, `dec.delta.param`, `dec.delta.trs`, `dec.sigma.code`, `dec.sigma.meta`, `dec.sigma.param`, `dec.sigma.trs`, `dec.window`, `epoch.horizon_k`, `epoch.length`, `exec.grace`, `exec.lock.code`, `exec.lock.meta`, `exec.lock.param`, `exec.lock.trs`, `gate.eps`, `gate.p_max`, `intake.slash_pct`, `iss.inflation`, `keeper.budget`, `ledger.archive`, `ledger.min_split`, `ledger.pos_dep`, `mkt.kappa`, `orc.bond_bps`, `orc.n_min`, `orc.window`, `pol.budget_epoch`, `res.fail_thr`, `res.probe_amount`, `res.probe_int`, `res.probe_to`, `res.recover_thr`, `sec.prize.code`, `sec.prize.meta`, `sec.prize.param`, `svc.max_live`, `trs.cap_180d`, `trs.cap_30d`, `trs.cap_proposal`, `welfare.thC_lo`, `welfare.thS_lo`, `wt.quorum`. Cross-key couplings that a static record cannot express (`dec.sigma ≤ δ/2`, `gate.eps ≤ p_max/2`, `welfare.wP + wA = 1`, the classless Baseline book grading at the `dec.v_min.trs` floor — [05](05-welfare-and-decision-engine.md) §5.2, SQ-232) bind at the consuming engine; the seeded static bounds are conservative over-approximations. **The `gate.v_min` coupling is the exception and binds earlier** (corrected 2026-07-20, SQ-194): `0.1 × dec.v_min(class)` is its *default*, not an invariant — the row admits the band `[×0.05, ×0.5]` — and that band, evaluated against the **live** `dec.v_min(class)`, is enforced **at the amendment boundary** jointly over the pair, so an amendment of either `dec.v_min.<class>` or `gate.v_min.<class>` that would carry the pair outside it is refused rather than left for a consumer to reconcile. The same relation is asserted in `try-state`. Two constraints therefore bind a `gate.v_min` amendment and the admissible set is their **intersection**: this live coupling band, which is the standing invariant, and the record's own `min`/`max`, which are ordinary META-amendable metadata seeded at genesis from the same multiples of the *then-current* `dec.v_min`. The seeded bounds coincide with the band at genesis but do not track later `dec.v_min` amendments, so the `×0.05` / `×0.5` columns of the §1 row state the coupling invariant, not a promise about the stored metadata. **`ledger.redeem_fee` ≤ `mkt.fee` is the second such coupling** (added 2026-07-29, milestone E1) and takes the identical shape: the relation is the standing invariant, it is enforced **jointly over the pair at the amendment boundary** — so an amendment of *either* key that would carry the pair outside it is refused rather than left for a consumer to reconcile — and it is asserted in `try-state`. It binds earlier than the consuming engine for the same reason `gate.v_min` does: the consumer is a payout deduction in audit-scope-A code that has no admissible way to fail closed on a bad rate without stranding a claimant, so the only safe place to refuse is before the value is stored. The row's own static `[0, 100]` bounds are ordinary META-amendable metadata; the live coupling is strictly tighter whenever `mkt.fee < 100` and is what actually binds. Derivation of the relation: [08](08-treasury-and-economics.md) §10.6.

**One asymmetry against the `gate.v_min` precedent is deliberate and is recorded rather than smoothed over.** `gate.v_min` and `dec.v_min` are both META; `ledger.redeem_fee` and `mkt.fee` are both **PARAM**, so this pair is jointly screened at a *lower* governance class than the pair it is modelled on. That is correct for what these two keys are — fee rates are the responsiveness case PARAM exists for, and both are ordinary-class in [08](08-treasury-and-economics.md) §10 — but it has a consequence a reader should not have to derive: a PARAM decision can move **either** side of the relation, so the screen MUST refuse a *lowering* of `mkt.fee` that would carry the pair out of band exactly as it refuses a *raising* of `ledger.redeem_fee`. Screening only the second key would leave the invariant breakable from the first, which is precisely the "left for a consumer to reconcile" failure rule 7 exists to prevent. Both directions are in scope, and the `try-state` assertion is the backstop for both.
8. **The `Unit` column is human/display notation, not `ParamView` encoding.** The §1 table's Default/Hard min/Hard max/Max Δ figures are written in the human unit printed in that column. By contrast, [02 §4](02-integration-contract.md) `ParamView.value/min/max` carry the raw inner scalar of the stored `ParamValue`: `Fixed` on the 1e9 grid, `Perbill` in parts per billion, `Percent` as integer percent, and integer/balance variants in their native scalar. In particular, converting raw `Perbill` to displayed basis points divides by **100,000**, floored; market-fee recomputation uses the frozen `Market::Fee` bps metadata constant and cross-checks it against that raw projection.

**`svc.fee_bps` shipped unset and was adopted at 1,000 bps on 2026-08-02 (normative; D-20).** It ships as a value **chosen, not derived**, and that is the one legitimate route for this key: R-2 permits a new key only when it is derived, and this one **cannot be derived from anything in this repository** — it is a market price for a service nobody has sold. R-2's escalation clause therefore applies and the value is the **user's**, recorded here with its authority rather than reverse-engineered into a false derivation. The error direction is safe in the direction R-2 cares about: **too low costs revenue, too high costs demand, and neither can produce a wrong decision or an unbacked claim**, which is precisely why no amount of analysis in this repository could have settled it. Until adoption the key was **absent from the registry entirely** (not present-and-zero), `ServiceParams::fee_rate()` returned `None`, and `question_service.register` refused with `ServiceRateUnset` — so the absence, not a `PhaseFlags` bit, was the arming gate, which is why the [02](02-integration-contract.md) §7.3-frozen bitset never widened. **Seeding the row is therefore the act that arms the hosted service.** Two mechanical consequences of adopting at the ceiling: the ×2 max-Δ can only be exercised **downward**, and raising the rate later requires a META `amend_registry` to lift the row max first — down being the reversible direction, this is a safe starting point rather than a trap.

**`svc.price_cap` shipped unset with its consumer defaulting to the *status quo* rather than to a refusal, and was adopted at 4× on 2026-08-04 (normative; N14, 2026-08-03).** It bounds the scarcity multiplier `M` of [16](16-hosted-question-service.md) §8.6, which re-prices a hosted slot under contention so admission allocates by value instead of by transaction latency. It shipped `[VERIFY]` because the value that would anchor it does not exist: the natural anchor is the measured cost of buying governance denial, and [14](14-threat-model.md) TH-72's attack-cost cell carries **no figure at all** (SQ-574) — an equalization against 08 §7's priced channels was attempted and refused, because queue-flooding blocks *admission* while depth-thinning starves an *already-trading* proposal, and the two are not commensurable.

**SQ-574 is still open, and adopting this row did not close it.** The value is a values-layer choice made without the anchor, not a derivation: 4× is the ceiling on how far contention or starvation may raise the tariff, so a fully-contended slot costs at most `4 × max(393 USDC, 10 % × declared_stake)`. Two mechanical properties make 4 a good pair with `svc.max_live` = 16 rather than an arbitrary pick. The per-admission step is `(4 − 1) / 16` = 0.1875, which on the 1e9 grid is `3e9 / 16` = 187,500,000 **exactly** — 16 divides 3e9, so taking every slot at once lands *on* the ceiling instead of short of it by the integer remainder note 1 describes. And 4 sits far enough above the `1` minimum that the step cannot truncate to zero, which is the silent failure a ceiling within `svc.max_live` grid units of 1 would produce. Both properties are asserted in the constitution's genesis test rather than left to inspection, so an amendment to either row that breaks the divisibility is visible.

Three things follow, and the third is the one that distinguishes this row from `svc.fee_bps` and `svc.client_bond`:

1. **Only this row is new.** The multiplier's decay is anchored to `svc.max_window` — `M` returns to 1 over one full question window, the timescale on which the whole slate turns over, so a price cannot outlive the demand that set it. Its per-admission step is `(svc.price_cap − 1) / svc.max_live`, so taking every slot at once reaches the ceiling — **up to integer division's remainder**, and never past it. It lands *exactly* on the ceiling only when `svc.max_live` divides `svc.price_cap − 1`; otherwise it stops short by under `svc.max_live` grid units, which is the cost of exact integer arithmetic and errs short rather than over. A ceiling set within `svc.max_live` grid units of 1 truncates the step to zero and the mechanism does nothing — the correct reading of a ceiling that close to the `1` minimum, which means *off*. **Additive, not geometric**, and the reason is a runtime constraint rather than an economic one: a fractional root is a transcendental, and runtime code admits no floating point and no transcendental outside the `futarchy-fixed` kernel. The additive step reaches the ceiling at full occupancy exactly as a geometric one would, in exact integer arithmetic; decay is linear toward 1 over `svc.max_window` for the same reason. Both are **derived from keys that already exist**; the mechanism adds no other row.
2. **Amendment direction.** Raising it sharpens rationing; lowering it relaxes toward the posted tariff. At the unset default the behavior *is* today's — a flat two-part tariff, first come first served.
3. **Its unset consumer must not fail closed, and this is deliberate.** `svc.client_bond` unset refuses admission because it prices registration abuse — a safety gate, where refusing is the safe direction. `svc.price_cap` gates an *allocation refinement*: `M = 1` reproduces the behavior the chain has today, while a refusal would close the service entirely and be strictly worse than the status quo it replaces. Fail-closed is a rule about the direction of error, not a reflex, and here the closed direction is the wrong one.
4. **It bounds *both* halves of `M`, and that is why no second row exists (N15, 2026-08-03).** [16](16-hosted-question-service.md) §8.7 raises the same multiplier when Bleavit's own decision books sit below their `dec.v_min` floor, and it reuses this ceiling rather than introducing one of its own. Two consequences bind. The halves combine by **`max`**, never by a product — a product would reach `svc.price_cap²` and this row's bounds would no longer say what the worst case is. And **one adopted row arms the whole mechanism**: while this row is unset, contention pricing and the starvation response are *both* inert, so there is no state in which one is live and the other is not.

**`svc.client_bond` shipped fail-closed and was adopted at 100,000 VIT on 2026-08-04 (normative; N4, 2026-08-01; D-20).** Its production consumer reads the live `Params` row only; no default or genesis fallback exists, so while the row was absent `client_registry.admit_client` returned `ClientBondUnset` before any hold or registry write. **Seeding this row is the act that opens the service to clients** — it was the only one of the three `[VERIFY]` `svc.*` rows that gated admission, since `svc.max_live` was already seeded at its provisional and `svc.price_cap`'s absence meant `M = 1` rather than a refusal.

Like `svc.fee_bps`, the value is **chosen, not derived**, and that is the legitimate route: registration-abuse calibration would need usage this repository has never had, so R-2's escalation clause applies and the authority is recorded here rather than a derivation reverse-engineered for it. The only in-system anchor is `att.bond` = 25,000 VIT, the sole other VIT-denominated bond, and the adopted value is **exactly 4× it** — treating a hosted client as a higher-risk counterparty than a seated attestor. **The stated cost is adoption:** at 4× the attestor bond the first cohort will be institutions rather than experiments, and both [16](16-hosted-question-service.md) §8.4's cannibalization falsifier and `svc.max_live`'s sizing evidence need real occupancy to settle, so both stay open longer than a lower bond would leave them. That is the direction that cannot create an unbacked claim, and the ×2 max-Δ with a 2-epoch cooldown makes it roughly six weeks per halving if the barrier proves too high.

The unit is native VIT because N4 deliberately follows the B19 native-hold custody precedent; calling the same hold “USDC” would require an unowned conversion rate and make the custody record disagree with the asset actually at risk. The bond is **held, not spent** — returned on clean exit — and it is not the anti-spam gate: admission is a per-client `ConstitutionalValues` act ([06](06-governance-and-guardians.md) §2.1) and the roster is hard-capped at `MaxClients` = 64, so the bond is the residual first loss behind a governance gate rather than the gate itself.

**On a live chain, existing amendment calls cannot create an absent registry row**, so a post-launch activation would require a runtime migration to seat it first, after which ordinary values amendments operate inside this row's bounds and cooldown. This adoption was pre-genesis, so the row was seeded directly into `genesis_params()` — the same route `svc.fee_bps` took on 2026-08-02.

**N9 correction — the bond does not fund egress (2026-08-02).** Report postage is client-selected USDC
`delivery_float` custody, not a new parameter. Its exact debit reuses the existing
`xcm.usdc_per_sec` and `xcm.usdc_per_mb` rate records on the fixed three-instruction push envelope,
rounded up per dimension. No `svc.delivery_*` key is necessary: the existing rate card already
prices the same two dimensions, while a new key would duplicate its job and violate R-2's
necessity test. Raising either existing rate increases postage and drains floats sooner; lowering it
reduces MAIN revenue, but neither direction can move `X` because I-36 separates the router and
counter. Both records already carry bounds, ×2 max-Δ and a one-epoch cooldown.

**`svc.fee_floor` is a kernel constant, not a key (§2), and it is anchored to fully-allocated cost.** Marginal cost is the keeper crank load: `2 · ceil(svc.max_window / mkt.obs_interval) · keeper.rebate` = `2 · 30,240 · 0.000255` = **15.42 USDC/question** at a full-epoch window. Fully-allocated recovery at [08](08-treasury-and-economics.md) §10.1's `C` = 109,281, 17.39 epochs/yr and 16 slots is 392.75 USDC, rounded against the service claimant to the frozen **393 USDC/question** (`SVC_FEE_FLOOR_USDC = 393_000_000` µUSDC). The floor is anchored to the **second** figure. Pricing a scarce slot at marginal cost prices it at approximately zero, and the slot is scarce by construction — `svc.max_live` is bounded by the §8.5 resource partition, not by demand.

**`svc.max_live` is the row whose unsafe direction has no measurement behind it.** It bounds worst-case external block-weight consumption, which reaches [05](05-welfare-and-decision-engine.md) §4.3's `H` through resource use rather than through data — the one channel no import lint can close. Its value must be set so worst-case external load stays inside the reserved external quota, and **there is no measurement in this repository to size that against**, so 16 ships conservative and `[VERIFY]`-tagged. TH-73 is the pressure on it; PT-10 is the proof that the partition holds; and 16 §8.4's `NotDecisionGrade` falsifier is the standing instruction to **cut** it if external occupancy correlates with Bleavit proposals failing their depth floor.

N7 does not introduce a second quota or reservation parameter. The runtime derives the external
two-dimensional `Weight` quota from the existing operational reserved block capacity and derives
the primary reservation from its complement; `svc.max_live` remains the only values-layer input to
the service occupancy bound. Until the required worst-case service-load evidence exists, an absent
or invalid `svc.max_live` reads as zero at the consumer, so service admission fails closed rather
than silently running above an unverified quota.

**`collator.comp_epoch`: the one row whose value is a market price, and where it comes from (normative record; added 2026-07-31, milestone E5, SQ-536).** Every other default in this section is derived from a kernel constant, another key, or this document set's own arithmetic. Collator compensation cannot be: it is what an operator will accept to run a node, which no amount of internal derivation reaches. Rule R-2 forbids inventing such a number, and the row's error direction is **unsafe in the low direction** — underpaid collators stop authoring and the chain stalls — so the seed was carried at D-15's 2,000 with no costing behind it until this milestone.

It is now anchored to **published, governance-approved evidence for the same role**: Polkadot OpenGov referendum **#1870** (passed and executed) funds **38** system-parachain collators at **$250/collator/month**, or **$307.24** fully loaded once the bounty's own fixed hosting, curator and coordinator lines are spread across the funded set. An epoch is **21.0 days, not a month**, so the rate in this row's units is **211.97 USDC/epoch** — making the superseded 2,000 seed **9.44×**, and the shipped 500 **2.36×**, a rate real operators demonstrably accepted.

The comparison is like-for-like on the axis that decides it: a Bleavit collator earns **nothing** from transaction fees or tips ([08](08-treasury-and-economics.md) §9 and D-15 burn collected VIT fees and route USDC to `MAIN`), so this line is its entire compensation — which is exactly why Polkadot's system parachains are treasury-funded rather than fee-funded. Where the analogy is imperfect it is imperfect in one known direction: a system-parachain operator already runs Polkadot infrastructure and so quotes a **marginal** cost, while a new chain's operators amortize nothing. **That gap is what the 2.36× margin exists to absorb, and it is the reason the seed is the registry minimum rather than the anchor itself.**

**Two properties bound the risk of seeding at the floor, and a third that an earlier revision of this note claimed does NOT (normative correction; 2026-07-31, raised by review of the same change).** (1) The **min is unchanged at 500** — the seed moved to the floor, the floor did not move to the seed — so all 20× of remaining headroom is in the safe direction. (2) Recovery is bounded and fast, at ×2 per amendment with a 1-epoch cooldown, so one amendment reaches 1,000 and two reach the superseded 2,000.

(3) **The `ops.collators` fail-soft path does *not* protect against this row being underpriced, and must not be cited as if it did.** [08](08-treasury-and-economics.md) §2.4's pending-accumulator behaviour catches a **funding** failure — the line or its custody pot cannot pay the pool the configured value implies — and in that case the claim survives for a later retry. It does nothing about a **pricing** failure: when the configured value is simply below what operators will accept, the pool is computed from that value, the payout **succeeds in full**, the accumulator is cleared, and no unpaid difference is preserved anywhere. Underpricing therefore does not degrade to "a delayed payment"; it degrades to collators leaving. The two failures are different and only the first is fail-soft.

**What actually protects the low direction is therefore the margin and the gate below, not the payout mechanism.** The margin is 2.36× a rate real operators accepted, and its known weakness is stated above: the anchored operators quote a *marginal* cost, because they already run Polkadot infrastructure. That weakness binds wherever this chain's collators do **not**.

**A second correction, same day and same shape as the first (normative; raised by review).** An earlier revision of this note scoped the gate below to the *permissionless* transition, on the reasoning that "the launch set is invulnerable, so the market rate does not bind while it is the whole set". That is also wrong, and wrong the same way — it leans on a mechanism that protects something else. **Invulnerability fixes a collator's *selection status*: it exempts the account from the candidate-selection and bond churn of `CollatorSelection`. It does not oblige anyone to keep authoring at a rate they will not accept**, and an invulnerable operator who stops running the node stops producing blocks exactly as a permissionless one does. Worse, the launch operators are the *most* likely to be standing up infrastructure specifically for this chain, which is precisely the case the marginal-cost anchor does not cover. Scoping the gate to Phase 4+ would therefore have let genesis ship at 500 with no evidence that the people actually authoring blocks accept it.

> **Gate (normative).** `collator.comp_epoch` MUST be re-verified against operator quotes obtained for **this** chain, and amended if they exceed it, **before production launch and before each subsequent enlargement of the collator set** — the invulnerable launch set included. Invulnerability is not an exemption: it governs selection, not willingness to author. The re-verification is a **launch blocker enforced mechanically**, not a best-effort check: `tools/release/surface-manifest.json` carries the `collator.rate_unverified` row in `release_blockers`, which fails a tagged release closed even when every artifact surface records. It is cleared by recording the quotes in PLAN.md's Verification log, exactly as the genesis anchor was recorded (V-61). The genesis seed of 500 stands as the *anchored default* the launch set is quoted against — it is a starting point supported by evidence for an adjacent role, not a substitute for a quote for this one.

**A detection gap is recorded rather than papered over:** no row of [12](12-release-and-operations.md) §6.3's alert tables covers collator-set attrition or a fall in the authoring set, so the reactive path in (2) currently depends on an operator noticing, not on an alarm. That is a monitoring obligation, filed as **SQ-537**, and it is the reason the gate above is a pre-launch check rather than a promise to react.

Consequences for the cost base, crossover and runway are in [08](08-treasury-and-economics.md) §10; the derivation and its margin are re-derived by the Phase-0 reference model and pinned by a genesis test, so this row and that arithmetic cannot drift apart silently.

**Existing-chain introduction of new rows (normative).** Adding a row to the genesis `Params` template is not an upgrade path: any runtime that first consumes a newly introduced key MUST carry a versioned constitution-state migration that inserts the complete bounded record on existing chains without overwriting a lawful value already present. This requirement applies to `ops.probe_rate` and `ops.probe_fee`; their first production runtime seeds both records by migration as well as by genesis, and its try-runtime checks prove the records are present and valid after upgrade.

Safety rationale (row-wise, carried forward): kernel floors/ceilings exist so no captured decision sequence can walk a defense to zero — δ cannot reach 0, windows cannot reach one block, κ cannot open flash manipulation, timelocks/grace cannot vanish, p_max cannot exceed 0.10, guardian scope cannot grow, the intake slash fraction cannot reach 0, and the Ask-scaling `2·InCapPrize` term of `dec.v_min` is kernel, not a key.

1. **Entrenched, kernel-scoped rows with no amendment path.** `grd.bond` — an `entrenched` row whose bound is scope-K and which carries neither a max-Δ nor a cooldown — is carried as a **kernel constant exposed through pallet metadata** rather than as a `Params` record: a record bearing governance metadata would misdescribe a value that cannot be governed. 2. **Rows that gate nothing and have no number yet.** A row carrying **no dispatch-path limit of its own** — a pure economic, operating-budget or diagnostic value that no extrinsic checks against — may remain unseeded while its default is still `[VERIFY]`- or *sim-gated* under rule 4; reading rule 2 binds it **from adoption onward**, at which point it is seeded like any other.    **Derivation is not an exemption.** Where a value is computable today and the implementation nonetheless derives it at its consuming engine while the §1 row still advertises an amendment path — a max-Δ, a cooldown, an amendable class — the missing record is a **defect**, not an exempt shape: the row promises a governance lever that derivation silently removes. (A row still awaiting its first number is the case above, not this one.)

**Unbounded sentinel (normative; amended 2026-07-20, SQ-196).** The "unbounded sentinels" of [09 §5.2](09-execution-upgrades-and-rollout.md) are the **maximum representable value of the key's `Balance` type**, which is also the seeded hard max of `phase3.tvl_cap` and `phase3.dep_cap` — so arming one is an ordinary amendment of the row to its own ceiling, requiring no distinguished value and no separate mechanism. (The phase at which each is installed is owned by [09](09-execution-upgrades-and-rollout.md), not by this row.) The two sentinels are **independent, and each disables only its own check**: `phase3.dep_cap` at the sentinel retires the per-account cumulative meter — which then neither reads nor writes that cumulative — while `phase3.tvl_cap` at the sentinel lifts only the global-issuance admission test. A bounded cap on either axis continues to reject inflows that breach it, so containment disappears entirely only when **both** sentinels are installed. Entries already recorded are **retained, never reaped**; they stay visible to `try-state` and bind again unchanged if a bounded cap is later restored.

It does **not** say that every consumer of a schedule-shaped parameter reads a frozen copy, and one does not: the **decision-critical crank classification** — which decides whether an observation draws on the metered `keeper.budget_epoch` (§5 item 4; [08](08-treasury-and-economics.md) §6.2) — recomputes `decide_at − dec.window` from the **live** registry on every crank. Raising `dec.window` therefore re-classifies cranks on books already trading, immediately and retroactively, without moving any accrual boundary. That is why §5's occupancy screen treats `dec.window` as live-consumed and composes against in-flight book counts rather than trusting this pin; the earlier revision of that paragraph read this sentence as covering the classification too, which it never did. Nothing here licenses adding a *new* live read of a pinned value: a consumer that needs the creation-time schedule MUST read the stored boundaries.

### 3.2 Markets and TWAP

## 5. Derived-value cross-checks (recomputed from 32/196/2,240 plus the 128-book service partition — normative derivations)

1. **Market state:** the active/POL envelope is 196 primary books. `BookKind::External` raises measured `MarketBook<AccountId>` `MaxEncodedLen` from 205 B to **208 B**; the primary retained partition is therefore 2,240 × 208 = **465,920 B = 455 KiB**. The independently enforced external partition adds at most 128 rows, so the shared physical ceiling is 2,368 × 208 = **492,544 B = 481 KiB**, still inside the existing **512 KiB** retained-map budget. This is why the external unsafe direction is bounded twice: raising either its row ceiling or its encoded payload can crowd primary state, while a lower ceiling only refuses service admission. The values are derived, not selected: two books per question × the existing `svc.max_live` hard maximum 64, with no cooldown/max-Δ because all four are compile-time CODE bounds rather than §1 tunables. This conservative archive envelope combines the independent worst-case 73-primary-book creation batch with the 14-day epoch floor, one-year `ledger.archive` ceiling and one extra boundary batch; it deliberately exceeds the tighter cross-coupled occupancy and gives a healthy keeper a whole creation boundary to reap each fixed-work eligible batch, while external cleanup applies its own backpressure instead of borrowing rows. Per-extrinsic touch bounds do not grow with the retained-map ceiling: `decide(pid)` reads ≤ 6 proposal books + 1 Baseline + O(10) params; `settle_cohort` ≤ 100 (market, total) items/call; `market.reap` reads/removes at most 28 protocol-position cells and never waits for claimant cleanup. `decide` additionally walks [07](07-oracle-and-disputes.md) §12's ProcessHold predicate over the oracle round map — ≤ `MAX_ROUNDS` = 128 rounds scanned, each costing a `RoundSchedules` and a `ComponentValues` read when it carries the proposal's frozen version. 02 §7.2's `16 × ≤4 × ≤2` decomposition suggests ≤ 64 can share one version, but its 4-settling-epoch factor holds only once [07](07-oracle-and-disputes.md) §11(1)'s retained rounds are actually reaped — which they were not before SQ-492 gave that retention a deadline, so successive epochs accumulated money-settled rounds on one long-lived version to the cap. The charged worst case is therefore all 128, which with SQ-492 in place is **conservative rather than exact** and is kept for that reason (SQ-494). That is a **kernel constant, not a map ceiling**, so the clause above still holds in the sense it was written for: no per-call touch bound scales with `Markets`, `Vaults` or any other growing map. The clause was silent about the round scan until SQ-494 measured it — the `decide` benchmark seeded no rounds at all, so the predicate ran against an empty map. PoV per production call remains bounded. The pinned figures are **dispatched** weights — the 50×20 generated function plus the A13 collator-compensation term each clock-syncing crank composes at its `#[pallet::weight]` attribute: `decide` **745,551 B** = 356,514 + 389,037, `settle_cohort(5)` **727,942 B** = 185,135 + 5 × 30,754 + 389,037, pinned as exact regression values in the runtime's `pov_budgets` suite. The normal class is measured against **7,864,320 B**, which is the primary reservation `pallet_welfare::primary_capacity()` returns: `MAXIMUM_BLOCK_WEIGHT`'s proof half is the relay's `MAX_POV_SIZE` = **10 MiB**, and the resource partition reserves a quarter of it for the external client domain. `decide`'s figure is 9.5 % of that budget, beside `settle_cohort(5)`'s 9.3 % and `settle_cohort(12)`'s 12.0 %; its local drift ceiling is **1 MiB** (`settle_cohort`'s **1.25 MiB**), still comfortably above the measurement, so both remain detectors rather than formalities. Until 2026-08-09 this clause measured the same proof figures against **3,932,160 B** and printed doubled shares (19.0 %, 18.5 %, 23.9 %). That divisor is a real limit of this runtime and the wrong one: it is 75 % of the 5 MiB `BlockLength`, so it bounds an extrinsic's **encoded length** rather than the proof its execution generates. The two resources are independent, are enforced by different code paths, and are not even scaled alike here — `BlockLength` scales the normal class by `NORMAL_DISPATCH_RATIO` while `BlockWeights` deliberately exposes it to the whole physical block so `CheckWeight` cannot pre-empt the partition extension (N7). Nothing was under-declared by the error, because the pinned figures and the drift ceilings were always measured against the runtime's own budget; what was wrong was the published share, in the unsafe direction of looking twice as full as it is. The collator-compensation term moved 48,000 → 389,037 B when it stopped being a hand-written estimate and became a benchmark: that 8× is the generator's **synthetic per-key envelope**, which charges each of the 120 payees' `ForeignAssets::Account` keys as an independent maximum-depth trie path and ignores their shared asset prefix — the benchmark's *recorded* proof was 17,874 B, ~22× smaller. The estimate is nonetheless what is declared, because the two directions of error are not symmetric: over-declaring PoV costs block capacity, while under-declaring it yields blocks that exceed their proof budget at execution, and a sparse benchmark trie under-represents production path depth. The resulting capacity cost is real — a crank reserves ~389 KB of proof for a payout that fires once per epoch — and its remedy is the post-dispatch refund §4.5 of [15](15-invariants-and-testing.md) already mandates for payload-executing extrinsics, tracked as its own PLAN row. The `try-runtime`-only market `try_state` is intentionally a full retained-map audit, measured for the primary partition at the saturated 2,240-book/4,480-account fixture with all 2,240 seed/rerun markers and all 196 active books/POL commitments carrying maximum checkpoint/window/owner auxiliaries (17,079,651 B estimated proof, 24,464 reads); it executes out of band against a snapshot and is not a normal-class block call. N7 MUST re-measure that fixture with both partitions populated when the service instance becomes live.
2. **Vaults:** ≤ 32 live + 4 cohorts × 5 settling = **≤ 52** × **160 B** (measured `VaultInfo` `MaxEncodedLen`, B5 2026-07-17; ~256 B stays the pinned ceiling) ≈ **8.1 KiB**, within the ≤ 13 KiB budget; per-branch supply fields (B-4) add two `Balance` words/vault. The budget is that occupancy at the pinned ceiling — 52 × 256 B = 13,312 B — which is why the item-6 screen measures a proposed `epoch.slots` against the **pinned** figure rather than the current measurement: an occupancy admitted only because today's struct happens to be small would be an envelope that the next field addition breaks.

6. **Parameter-coupling rule (normative):** a decision changing `epoch.slots`, `mkt.obs_interval`, `dec.window`, `epoch.length`, `ledger.archive`, `pol.budget_epoch`, any `pol.b.{param,trs,code,meta}`, `pol.b_gate` or `pol.b_baseline` MUST carry re-derivations of items 1–5 in its committed artifact. **The obligation is enforced at the parameter boundary, by value (normative; SQ-303 resolution, 2026-07-26, extended to the occupancy family by SQ-501).** `constitution.set_param` refuses a change whose derivations would not survive it. Both families are screened the same way — re-derive from the proposed parameter set, refuse exactly when the result exceeds the frozen figure the runtime compiles against — and they differ only in *which* figures: 08 §4.1's per-class NAV floors for one, items 1–4's occupancy envelopes for the other. For the **class-floor** keys — `pol.budget_epoch`, `pol.b_gate` and the four `pol.b.*` — the runtime re-derives [08](08-treasury-and-economics.md) §4.1's per-class floors from the *proposed* parameter set and refuses exactly when one would exceed the frozen literal the treasury enforces, rounding the derived floor **up** so the error direction is against the proposal. That is what makes §4.1's paired-**CODE** route usable rather than theoretical: a direction test refuses every raise and every cut unconditionally, so a CODE proposal that has correctly updated the literals still cannot carry its values change through, and the keys are frozen in fact rather than screened. Under a value test the same change simply stops being unsafe once the literals fit — no artifact schema, no pairing record, no verifier, none of which could have delivered the property anyway, since §4.1 states that no governance artifact can move a compile-time floor. For the **occupancy** keys — `epoch.slots`, `mkt.obs_interval`, `dec.window` and `epoch.length` — the same value test applies (normative; SQ-501 resolution, 2026-07-26): items 1–4's envelopes are frozen figures of this document, the runtime re-derives them from the *proposed* parameter set, and the change is refused exactly when one would exceed its frozen figure — see the occupancy rule below. An equal write is not a change and is never screened. `ledger.archive` can only move downward from its one-year K ceiling, so the compiled 2,240-row storage envelope remains safe; its artifact must nevertheless recompute expected retained occupancy. It is therefore **not** screened at the boundary — that safety argument is exactly a reason not to refuse it, and refusing it was an over-rejection the SQ-303 wiring removed. For the six **class-floor** keys — `pol.budget_epoch`, the four `pol.b.*` keys and `pol.b_gate` — the operative control meanwhile is the paired **CODE** proposal [08](08-treasury-and-economics.md) §4.1 requires, since a re-derivation carried only in an artifact cannot move compile-time floors. That substitute does **not** extend to `pol.b_baseline`, which moves no frozen literal (below): for it the artifact obligation is simply unenforced — and it is **not** screened against the §4.1 floors, which would refuse a key the same sentence says moves none of them (SQ-303). The **seven** POL keys are triggers, for two distinct reasons. Six of them — `pol.budget_epoch`, the four `pol.b.*` class keys and `pol.b_gate` — are triggers because [08](08-treasury-and-economics.md) §4.1's per-class NAV floors are **frozen constants derived from them**: lowering `pol.budget_epoch` or raising a `pol.b` raises the true floor above the frozen literal, so without re-derivation the loud §4.2 arming gate would pass a class below its real minimum-viable NAV. **`pol.b_baseline` is the seventh (SQ-305 resolution)**, on the narrower ground that item 5 above expressly carries the 17,329 USDC Baseline commitment among the values item 6 requires re-deriving. Its inclusion is *not* a claim that it moves the four class floors — [08](08-treasury-and-economics.md) §4.3 deliberately keeps the Baseline book outside the §4.1 floor arithmetic and outside `pol.budget_epoch` — but raising it does raise a real standing obligation against NAV on its own dedicated `POL_BASELINE` line, and item 6 promises re-derivation of item 5, not of §4.1 alone. Omitting it left a value that item 5 derives with no trigger obliging anyone to re-derive it; the omission was undocumented rather than reasoned. Books-per-proposal (6), `MaxLiveProposals` (32) and either market-cap constant are not keys — changing them is a CODE change that reopens this document.
**Occupancy admission rule (normative; SQ-501, 2026-07-26).** `constitution.set_param` screens the four occupancy keys **by value**, against the frozen figures items 1–4 publish above; the earlier unconditional refusal of every timing/capacity-key change is superseded, and with it the last direction test at this boundary. The refusal is `BudgetDerivationRequired`, raised exactly when the re-derivation at the proposed parameter set — the amended key at its proposed value, every other key at its live one — exceeds one of:

| # | Envelope re-derived | Frozen figure | Inputs |
|---|---|---|---|
| 1 | `MaxLiveMarkets + (ceil(ledger.archive / epoch.length) + 1)·(epoch.slots·6 + 1)` primary retained `Markets` rows, plus the fixed 128-row external partition; physical count × 208 B | **2,240 primary + 128 external = 2,368 rows / 512 KiB** | `epoch.length`, `epoch.slots`, `ledger.archive`; external term is CODE-fixed |
| 2 | `MaxLiveProposals + MaxSettlingCohorts·epoch.slots` vaults, and that count × the pinned 256 B | **52** vaults / **13 KiB** | `epoch.slots` |
| 3 | `market.reap` protocol-position cells (14 instruments × 2 protocol accounts) | **28** cells | none — no §1 key moves item 3 |
| 4 | `(epoch.slots·6 + 1)·ceil(dec.window / mkt.obs_interval)` and `(epoch.slots·6 + 1)·ceil(epoch.length·13/21 / mkt.obs_interval)` observations/epoch | **133,920** / **580,320** | all four |

Every division rounds **up**, so the error direction is against the proposal (R-7); an overflow, a zero `epoch.length`, a zero `mkt.obs_interval` or an unreadable registry row refuses rather than reading as "no envelope was breached" (G-1). Equal writes are not changes and are never screened, and the 13 §1 bounds, max-Δ and cooldown checks run **before** the screen, so an out-of-registry value still fails as an ordinary registry violation.

**In-flight state (normative; SQ-501 amendment, second revision).** The re-derivation above reads the proposed registry, and a registry is not the live chain. Whether a key's proposed value is already in force depends on how the *code* consumes it, so the screen composes the registry with what is actually in flight, and each key's classification is **audited against its consumer** rather than assumed:

| Key | Consumed | Evidence | Consequence for the screen |
|---|---|---|---|
| `epoch.slots` | **Pinned** | Read only at qualification to decide admissions; thereafter the cohort's book count is fixed state (the post-qualification `Proposals` working set, §4's `MaxLiveProposals`). No consumer scales an existing cohort's load off the registry value. | A reduction binds only cohorts that form later, so the screen takes the **larger** of the proposed value and the largest live cohort. |
| `epoch.length` | **Pinned** | Snapshotted per epoch into the epoch clock and staged next length, per proposal into its schedule (with `decide_at`), and per cohort into its creation-time length; try-state binds the three together. | As above: the screen takes the **larger** of the proposed value and the largest length in flight. |
| `mkt.obs_interval` | **Live** | Re-read on every observation, both for the crank cadence and for the coverage requirement at decision-grade evaluation. | The proposed value *is* the live value, and it applies to every book already trading. |
| `dec.window` | **Live** | The decision-critical crank classification computes `decide_at − dec.window` from the **live** registry on every crank, and that classification is what draws on the metered `keeper.budget_epoch`. The TWAP *accrual* boundaries are separately pinned when the window is registered at Seed, so §3.1's schedule-pinning holds for accrual and **not** for the metered classification item 4 sizes. | As above — and this is the correction: an earlier revision of this paragraph claimed `dec.window` was pinned, which the code does not implement. |
| `ledger.archive` | **Live** | Read at reap as `terminal + archive delay`. | Only an input to item 1, never a trigger; its one legal direction (down, from the K ceiling) shortens retention. |

Two consequences follow, and they are why the fix is a composition rather than a list of forbidden transitions. **First**, a *reduction* of a pinned key is credited by a registry-only screen before it has materialised: lowering `epoch.slots` 5 → 4 and then `mkt.obs_interval` 10 → 9 each pass such a screen (`25 × 4,800 = 120,000`) while a still-live five-slot cohort needs `31 × 4,800 = 148,800`. **Second**, that unmaterialised saving can be laundered through a key whose *safe* direction is the other one: from the same state, `mkt.obs_interval` 10 → 11 is genuinely safe and admitted, and it manufactures exactly enough registry headroom for `dec.window` 43,200 → 51,840 (its 20 % max-Δ) to read `25 × ceil(51,840/11) = 117,825` while the live cohort immediately incurs `31 × 4,713 = 146,103`. Any live-consumed key has that shape in whichever direction increases load, so enumerating transitions closes instances while composing against reality closes the class.

The screen therefore takes the **worst case over what is live**: the book count from the largest cohort in flight (bounded — the post-qualification working set is `MaxLiveProposals`-bounded and the cohort schedules are bounded by `MaxSettlingCohorts`), the epoch length from the longest in force, and the three live keys at their proposed values. An in-flight maximum that cannot be established — state unreadable, or a bound already exceeded — is a **refusal**, never a fallback to the registry value, which is the defect itself (G-1). With the book count taken from reality the value test is *exact* for the binding leg rather than merely conservative: every cohort shares one live `ceil(window / interval)`, so `books_max × ceil(window / interval)` is the true worst-case decision-critical load. No direction rule is needed for any key, and none is imposed.

Only **item 4** carries this exposure, and the other three are stated rather than guarded so that no reader mistakes their absence for an oversight. **Item 1** cannot be breached by any history of in-bounds values: its **2,240** is the same formula at each input's compiled bound, and an archive window spans at most `ceil(1 yr / 14 d) + 1 = 28` creation boundaries of at most `12·6 + 1 = 73` books each, so `196 + 28·73 = 2,240` dominates every reachable history — and `set_param` cannot move those bounds. **Item 2** depends on `epoch.slots` alone, so it admits no compensating route; the screen refuses every raise above 5, hence every historical slot count is ≤ 5 and vault occupancy is ≤ 52 permanently. **Item 3** has no 13 §1 input at all.

Three consequences are normative, and all three are subject to the in-flight rule below. **(a)** `ledger.archive` is an *input* to item 1's re-derivation but not a trigger, for the reason item 6 already gives; it is read live and never screened. **(b)** The genesis registry sits exactly on three of the four figures (52 vaults, 133,920 and 580,320 observations), so each key's admission boundary is its own default: raising `epoch.slots`, lowering `mkt.obs_interval`, raising `dec.window` or raising `epoch.length` is refused **at that registry**, and the opposite direction is ordinary business — subject in both directions to the in-flight composition below, which is what decides the verdict. **(c)** The refused direction reopens the same two ways the class floors do — a **CODE** change that moves the frozen figure (items 1–4 are figures of this document, so that change reopens it), or a compensating amendment of another input, since the test is on the derived value and not on the direction. Two worked cases, both landing exactly on the frozen figure: with `mkt.obs_interval` raised to 20, `dec.window` = 86,400 passes the screen at exactly 133,920, and `epoch.length` = 604,800 — its 13 §1 hard max — passes at exactly 580,320. (Passing the screen is not the same as reaching the value in one decision; the row's own max-Δ still applies, and `epoch.length` carries 10 %.) That second route is what a direction test could not express, and its absence is why these four rows were declaratory before SQ-501: no value of any of them was admissible, in either direction. Screening item 4's **full-window** figure deserves its own note, because [08](08-treasury-and-economics.md) §6.3 states that full-window coverage is deliberately *not* metered — out-of-window observation gaps degrade chart density, never decisions. It is screened anyway, and on the narrower ground that item 6 obliges its re-derivation: the figure sizes the funded `ops.keepers` continuity line, and a published normative figure that silently goes stale under a lawful amendment is exactly what this boundary exists to prevent. It is also, at the current registry, the only envelope `epoch.length` can breach: item 1's **2,240** is that same formula evaluated at each input's compiled bound (the archive ceiling, the 14-day epoch floor, the 12-slot registry maximum), so every in-range parameter set lands strictly under it and item 1 binds only if one of those bounds is later widened. Omitting the full-window figure would therefore leave `epoch.length` screened by nothing at all.

7. **Chain-served history budget:** `RecentCohortSummaries` max-encodes to **1 + 32 × 158 = 5,057 B** (the one-byte SCALE compact collection-length prefix plus 32 measured `CohortSummary` values, whose `MaxEncodedLen` includes the 12-proposal hard maximum) + 8 TWAP checkpoints × 196 active markets at the [04 §7](04-markets-and-pricing.md) spec shape (8 × (4 B `u32` block + 32 B two-limb cumulative) + 1 length byte = 289 B/market; terminal observation deletes that book's checkpoint and decision-window auxiliaries before releasing its active slot) = **5,057 + 56,644 = 61,701 B ≈ 60.3 KiB** of always-served light-client state, within the ≤ 70 KiB D-6 layer-1 budget stated in [02](02-integration-contract.md). The 2,240 retained-book bound does not multiply this history envelope because terminal rows carry no auxiliary series.
